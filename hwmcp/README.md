# hw-mcp — MCP-сервер контекста оборудования

`hw-mcp` — компонент ВКР «Разработка ИИ-агента для приложений граничного ИИ» (агент EdgeCtx).
Это MCP-сервер на Go, который работает на одноплатном компьютере рядом с агентом `edgectx`. Он даёт агенту
контекст оборудования: что подключено (L0), какие значения у датчиков и сколько им секунд (L1), что изменилось
(L2, уведомления), в каком состоянии плата (L3, `board_health`). Каждая команда исполнительному устройству
проходит детерминированный шлюз безопасности.

Контракт с остальными компонентами задан в `IMPLEMENTATION_SPEC.md` §4. Подробная мотивация описана в
`research/new_topic/THESIS_CONCEPT.md`, §7.2, §9 и §10. Отступления от спецификации записаны в `docs/DECISIONS.md`
с пометкой `[hw-mcp]`.

## Что делает

- **Инвентарь из sysfs без опроса шин.** IIO (`in_*_input`, иначе `(raw + offset) × scale` по ABI ядра), hwmon
  (`temp*/in*/curr*/power*/humidity*_input`), 1-Wire `w1_therm`, V4L2, USB, I²C-клиенты без драйвера, `gpiochip*`
  и EEPROM HAT. Значения переводятся в единицы SenML (Cel, %RH, Pa, V…). Чего ОС не знает (назначение линий GPIO,
  место установки), берётся из `declared.json`. Это порт прототипа `research/new_topic/GAP2_artifacts/sysfs_probe.py`
  с полным паритетом: на фикстуре результат совпадает с прототипом поле в поле.
- **Линии GPIO без libgpiod.** Символьное устройство `/dev/gpiochipN`: uAPI v2 (ядра ≥ 5.10) или v1
  (ядра 4.8+, в том числе 4.9 у Jetson Nano с JetPack 4.6) — версия определяется для каждого чипа сама.
  Чип в `declared.json` задаётся номером узла или меткой. Без платы линии эмулируются файлами, а sysfs
  симулятора можно сочетать с настоящими линиями (смешанный режим). Подробно — раздел «GPIO».
- **Живые датчики.** Пропавшее устройство, нечитаемый атрибут и «застрявшее» значение дают `null` с
  причиной (`absent`, `unreadable`, `not_a_number`, `stuck`), агент получает уведомление, `board_health`
  показывает, что недоступно сейчас. Вернувшееся устройство читается снова, в том числе под новым номером
  узла (`iio:deviceN`, `hwmonN`); на плате (`-root /`) чужое устройство под старым номером не читается.
  Журнал о сбоях одного свойства — не чаще раза в минуту. Подробно — раздел «Живые датчики».
- **Модель устройств** в духе W3C WoT TD 1.1 (минимально нужное). Устройство состоит из свойств (чтение и запись)
  и действий. Сгенерированные TD проходят официальную JSON Schema TD 1.1.
- **Инструменты MCP.** Каталог задаётся флагом `-catalog`:
  - `generic` — `list_devices`, `read_property`, `write_property`, `invoke_action`, `board_health`;
  - `explicit` — `read_<устройство>_<свойство>`, `set_<устройство>_<свойство>`, `<действие>_<устройство>`
    и `board_health`; инструменты генерируются из инвентаря.

  `board_health` отдаёт только то, что нужно модели: нагрузку, память, температуру SoC, троттлинг и uptime,
  с округлением, и сбои датчиков: `sensor_faults` — какие свойства сейчас без значения и почему
  (`{"kitchen_bme280.temperature": "absent"}`), `sensor_errors` — неудачных чтений с начала работы.
  Остальные счётчики hw-mcp и ресурсы процесса — в `hw://diag`. Описание инструмента («hw-mcp counters»)
  совпадает с каталогом `bench/simmcp` и меняется только вместе с ним.
- **Ресурсы MCP.** `hw://inventory`, `hw://inventory/text`, `hw://td`, `hw://probe`, `hw://diag` (счётчики
  hw-mcp и ресурсы процесса — для оператора и стенда, не для LLM) и `hw://state/<устройство>`.
  Подписчикам `hw://state/<устройство>` при изменении приходит `notifications/resources/updated` с новыми
  значениями в `_meta`. Изменение ищет фоновый сэмплер с периодом и порогом. Фронты входов GPIO на Linux
  приходят от ядра сразу, без ожидания следующего опроса.
- **Уведомления не тормозят оборудование.** Сэмплер, сторожевой таймер аренды и обработчик фронтов только
  ставят изменение в очередь (не блокируются), отправляет одна горутина-рассыльщик. Если клиент перестал
  читать (`edgectx` завис или остановлен), опрос и аренда продолжают работать, а очередь ограничена: числа
  сворачиваются в последнее значение, переходы логических значений (импульс PIR 0→1→0) сохраняются до 8 на
  устройство.
- **Шлюз приводов.** Это порт `research/new_topic/GAP3_artifacts/actuator_gate.py` с паритетом решений.
  Проверки идут в таком порядке: идемпотентность, реестр, схема и диапазон, TTL решения, свежесть состояния
  (неизвестное считается опасным), блокировки и clamp, частота, подтверждение. Есть пробная проверка без
  исполнения (`_meta edgectx/dry_run`) и аренда со сторожевым таймером: по истечении аренды привод уходит в
  безопасное состояние точно в срок. Двухфазная фиксация прототипа (`DryRun`/`Commit` с окном
  `commit_window_s`) портирована в пакет шлюза и сверена тестами паритета, но через MCP недоступна. Отказ
  возвращается структурно:
  `{"denied": true, "verdict": …, "reason": …, "detail": …}`.
- **Журнал (JSONL).** В него пишутся решения шлюза вместе со срезом состояния, по которому принято решение,
  а также срабатывания аренды, концы импульсов, уведомления, ошибки датчиков, `run_start` и `run_end`.
- **Транспорты.** stdio (как дочерний процесс `edgectx`) и streamable HTTP на официальном
  `github.com/modelcontextprotocol/go-sdk` v1.8.0. По умолчанию используется ревизия протокола 2025-11-25.
- **Время берётся только из часов.** Реальные часы — это секунды Unix, отсчитанные монотонно от старта процесса.
  Виртуальные часы (`-clock virtual`) двигает `POST /control/clock {"t": …}`. При продвижении все сроки (опрос,
  истечение аренды, конец импульса) выполняются по порядку, и каждое событие получает точное виртуальное время.
  В реальном режиме сэмплер и таймеры не опрашивают по тикеру, а спят до ближайшего срока: сэмплер — до
  срока опроса (следующий срок = предыдущий + период, фактический период равен заданному), таймеры — до
  конца ближайшей аренды или импульса. Без аренд и импульсов таймеры не просыпаются вовсе.

## Сборка и тесты

Нужен Go 1.27 (`brew install go`). Сборка идёт без cgo.

```bash
cd hwmcp
make build              # .build/hw-mcp (нативно)
make build-linux-arm64  # .build/hw-mcp-linux-arm64, статический (CGO_ENABLED=0): Raspberry Pi 5, Jetson Nano, ВМ
make test               # go test -race ./...
make vet                # go vet (darwin и linux/arm64) + gofmt
make bench              # бенчмарки шлюза, валидатора, опроса (hub, sysfs)
make vm-test            # тестовые бинарники linux/arm64 в Lima VM "sbc" (каталог проекта смонтирован в ВМ)
make vm-gpiosim         # GPIO uAPI v1/v2 и метки чипов на модуле ядра gpio-sim в ВМ (sudo в ВМ)
make vm-hotplug         # пропажа и возвращение устройства iio_dummy на настоящем sysfs ВМ (sudo в ВМ)
make golden             # пересоздать эталоны паритета из Python-прототипов (research/ только читается)
```

Числа бенчмарка, полученные при разработке (параллельно работают другие агенты), результатами не являются.
Задержку шлюза для ВКР нужно мерить по протоколу на целевой плате.

## Запуск

```bash
# на плате: настоящий /sys и /dev/gpiochipN (нужны права на /dev/gpiochip*), stdio
hw-mcp -root / -declared declared.json -trace /var/log/hw-mcp.jsonl

# на Mac/в ВМ: фикстура sysfs, линии GPIO эмулируются файлами <root>/dev/<chip>/line<N>
cp -a testdata/fixture_root /tmp/root
hw-mcp -root /tmp/root -declared configs/declared.lab.json -transport http -ready-file /tmp/hw.url
#   stderr: "hw-mcp: listening on http://127.0.0.1:PORT/mcp (catalog generic, clock real)"

# T0/тесты: виртуальные часы
hw-mcp -root /tmp/root -declared configs/declared.lab.json -transport http -clock virtual
curl -s -XPOST http://127.0.0.1:PORT/control/clock -d '{"t": 3600}'

# stdio + виртуальные часы: управление часами на отдельном адресе
hw-mcp -root /tmp/root -clock virtual -control-addr 127.0.0.1:0     # адрес печатается в stderr

# Jetson Nano (JetPack 4.6, ядро 4.9): auto должен выбрать v1 (на плате не проверено); -gpio-uapi v1 — явно
hw-mcp -root / -declared declared.json -gpio-uapi v1

# смешанный режим: sysfs — каталог симулятора, линии GPIO — настоящий /dev/gpiochipN (в declared.json —
# метка чипа, например чипа gpio-sim в ВМ)
hw-mcp -root /tmp/sim-root -declared declared.json -gpio-driver cdev

# посмотреть, что увидит LLM (линии GPIO при этом не трогаются)
hw-mcp -root testdata/fixture_root -declared configs/declared.lab.json -catalog explicit -print-tools
hw-mcp -root testdata/fixture_root -declared configs/declared.lab.json -print-text
hw-mcp -root / -print-inventory          # то же, что sysfs_probe.py --root /
```

Сервер HTTP по умолчанию слушает `127.0.0.1:0`, то есть свободный порт. Диапазона портов для hw-mcp
в спецификации (§10) нет, поэтому фактический URL печатается в stderr и пишется в `-ready-file`.
`GET /healthz` возвращает текущее время и режим часов.

Флаги (`hw-mcp -h` печатает тот же список):

| флаг | по умолчанию | смысл |
|---|---|---|
| `-root` | `/` | корень sysfs/procfs: `/` на плате, каталог фикстуры или симулятора для эмуляции |
| `-declared` | — | `declared.json`: назначение линий GPIO, места, пороги, периоды, политика шлюза |
| `-catalog` | `generic` | каталог инструментов: `generic` или `explicit` |
| `-transport` | `stdio` | транспорт MCP: `stdio` или `http` (streamable HTTP) |
| `-addr`, `-path` | `127.0.0.1:0`, `/mcp` | адрес и путь HTTP (порт 0 — свободный) |
| `-ready-file` | — | записать сюда URL после запуска HTTP |
| `-session-timeout` | `1h` | закрыть HTTP-сессию, у которой столько нет ни запросов, ни открытого потока SSE (0 — не закрывать) |
| `-clock`, `-clock-start` | `real`, `0` | часы `real` или `virtual` и начальное виртуальное время |
| `-control-addr` | — | отдельный HTTP для `/control/*` (stdio + виртуальные часы) |
| `-sample-period` | `1s` | общий период фонового опроса |
| `-cache-ttl` | `0` | `read_property` перечитывает значения старше (0 — два периода опроса свойства) |
| `-rescan-period` | `10s` | пока устройство IIO/hwmon пропало, искать его заново: первый раз через этот период, дальше с удвоением до 5 мин (0 — не искать: на плате вернувшееся устройство тогда не читается до перезапуска) |
| `-gpio-driver` | `auto` | `auto` (cdev при `-root /`, иначе files), `cdev` (`/dev/gpiochipN`), `files` (эмуляция) |
| `-gpio-uapi` | `auto` | версия uAPI для cdev: `auto` (v2, при ENOTTY/EINVAL — v1), `v1`, `v2` |
| `-gpio-dir` | — | files: каталог эмуляции (по умолчанию `<root>/dev`); cdev: каталог узлов (по умолчанию `/dev`) |
| `-gpio-edges` | `true` | события фронтов входов (только cdev; линия без прерывания открывается без них и опрашивается) |
| `-protocol` | `2025-11-25` | ревизии MCP через запятую (пусто — все, что знает SDK) |
| `-board-health` | `true` | инструмент `board_health` |
| `-trace`, `-run-id` | — | журнал JSONL и идентификатор прогона в нём |
| `-log-level` | `warn` | уровень журнала в stderr: `debug`, `info`, `warn`, `error` |
| `-print-inventory`, `-print-tools`, `-print-td`, `-print-text` | — | напечатать инвентарь, каталог, TD или проекцию L0 и выйти |
| `-version` | — | версия |

Флага `-watchdog-tick` больше нет: таймеры спят до срока. Лимита памяти в hw-mcp нет: его задают снаружи —
переменной `GOMEMLIMIT` рантайма Go и (или) `memory.max` cgroup (`systemd-run -p MemoryMax=…`).

**Брошенные HTTP-сессии.** `SessionTimeout` в SDK считает активностью только POST: агент, который часами
лишь слушает уведомления в потоке SSE (ночью LLM не будят), потерял бы сессию. Поэтому hw-mcp считает
сессию брошенной, когда у неё дольше `-session-timeout` нет ни одного запроса в работе, в том числе
открытого потока GET: клиент завершился без DELETE, и его соединения оборвались. Сессия закрывается вместе с
подписками; счётчики — `http_sessions` в `hw://diag` и `run_end`. Учитываются только живые сессии SDK:
запрос с неизвестным или закрытым `Mcp-Session-Id` (ответ 404) записи не заводит. Клиент без потока SSE, молчащий дольше
часа, получит 404 и по спецификации MCP (streamable HTTP) должен открыть новую сессию. Значение 1 ч —
допущение: дольше периода heartbeat аналогов (30 мин).

Остановка: по SIGINT/SIGTERM (или концу stdio-сессии) приводы с `safe_state` сразу переводятся в него, это
не зависит от транспорта. Потом закрывается транспорт; его ждут не дольше 3 с, поэтому клиент, который не
читает stdout, не задерживает выход процесса.

## Для `edgectx` (MCP host)

1. **Каталог.** `tools/list` возвращает инструменты в детерминированном порядке по имени. Результат инструмента —
   одно текстовое содержимое с каноническим JSON: ключи отсортированы, без отступов, UTF-8 без `\u`.
   `structuredContent` не дублируется, чтобы не удваивать трафик.
2. **L0 в стабильный префикс.** Прочитайте ресурс `hw://inventory/text`, по строке на устройство:
   ```
   kitchen_bme280: humidity [%RH], pressure [Pa], temperature [Cel]
   pir_hall: state [/]
   relay_fan @kitchen: state [/, rw]; actions: pulse(seconds:number)
   ```
   Полная модель лежит в `hw://inventory`, TD 1.1 — в `hw://td`.
3. **L1/L2.** Подпишитесь на `hw://state/<устройство>` (`resources/subscribe`). Уведомление
   `notifications/resources/updated` несёт в `_meta` изменившиеся свойства (`"hw/changed"`), устройство
   (`"device"`) и их новые значения (`"state": {"temperature": 25.0}`), поэтому читать ресурс после
   уведомления не нужно, и быстрые переходы (PIR 1→0) не теряются между уведомлением и чтением. Если клиент
   отстаёт, несколько изменений устройства сворачиваются в одно уведомление с последними значениями.
   Полный снимок с единицами и возрастом даёт `resources/read` того же URI:
   `{"device":…, "now":…, "properties":{"temperature":{"value":22.51,"unit":"Cel","ts":…,"age_s":0.4}}}`.
4. **Сведения оркестратора** передаются в `_meta` запроса `tools/call`, а не в `arguments`. Их задаёт хост,
   LLM их подделать не может:

   | ключ `_meta` | тип | смысл |
   |---|---|---|
   | `edgectx/cmd_id` | string | ключ идемпотентности: повтор после обрыва связи не переключит привод второй раз |
   | `edgectx/issued_at` | number | момент решения LLM по часам hw-mcp (реальные — секунды Unix; виртуальные — `t` дня) |
   | `edgectx/ttl_s` | number | TTL решения (по умолчанию `default_ttl_s` политики, 10 с) |
   | `edgectx/confirmed` | bool | пользователь подтвердил команду (для `requires_confirmation`) |
   | `edgectx/dry_run` | bool | только проверить шлюзом, не исполнять |

   Без `cmd_id` hw-mcp выдаёт свой ключ, и повтор считается новой командой. Без `issued_at` берётся момент
   получения, и TTL ничего не отсекает.
5. **Ответы на команды.**
   - Принятая команда:
     `{"ok":true,"verdict":"allow"|"clamp","executed":true,"device":…,"property":…,"value":…,"cmd_id":…}`.
     При clamp добавляются `requested` и `applied_args`, для импульса — `off_in_s`, для аренды — `lease_expires_in_s`.
   - Отказ: `isError: true` и `{"denied":true,"verdict":"reject"|"confirm","reason":…,"detail":…}`.
     Причины — как в прототипе: `unknown_device`, `unknown_tool`, `invalid_args`, `stale_command`, `stale_state`,
     `interlock`, `rate_limit`, `needs_confirm`, плюс `no_active_lease`.
   - Повтор `cmd_id` — это не ошибка: `{"ok":true,"verdict":"duplicate","executed":false,…}`.
   - Сбой записи в линию после допуска: `isError: true`, `{"ok":false,"error":"actuation_failed",…}`.

## declared.json

Базовый формат совпадает с прототипом (`locations`, `gpio`, `serial`). Расширения:

```json
{
  "gpio": [{"id": "relay_fan", "chip": "gpiochip0", "line": 27, "direction": "output", "quantity": "switch",
            "location": "kitchen", "requires_confirmation": false,
            "active_low": false, "property": "state", "debounce_ms": 0}],
  "names": {"iio:bme280@i2c-1/0x76": "bme280"},
  "thresholds": {"kitchen_bme280.temperature": 0.2},
  "sample_periods": {"kitchen_bme280": 5, "kitchen_bme280.temperature": 1},
  "stuck_after_s": {"boiler_pipe_ds18b20": 3600},
  "gate": {
    "default_ttl_s": 10, "max_state_age_s": 5, "commit_window_s": 5, "idem_capacity": 4096, "idem_max_age_s": 600,
    "devices": {"relay_fan": {"min_interval_s": 2, "max_per_min": 10, "requires_confirm": ["set_state"],
                              "lease_s": 600, "safe_state": {"state": false}}},
    "interlocks": [
      {"name": "overheat_keeps_fan_on", "device": "relay_fan", "tool": "*",
       "needs": ["kitchen_bme280.temperature"],
       "deny": [{"if": {"all": [{"arg": "value", "eq": false},
                                {"state": "kitchen_bme280.temperature", "ge": 35}]},
                 "reason": "перегрев на кухне: вентилятор нельзя выключать"}],
       "clamp": null}
    ]
  }
}
```

- **Имена устройств для агента** строятся детерминированно. Объявленные устройства получают свой `id`,
  обнаруженные — `names[<id sysfs>]`, иначе `slug("<место>_<драйвер>")`: `kitchen_bme280`,
  `boiler_pipe_ds18b20`, `board_cpu_thermal`. При совпадении добавляется суффикс `_2`.
- **Инструменты шлюза.** Запись свойства `P` — это инструмент `set_P` с аргументом `{"value": …}`.
  Действие `pulse {"seconds"}` (0 < seconds ≤ 3600) есть у логических выходов. Действие `renew_lease`
  получают устройства с `lease_s`.
- **Ключи состояния** в блокировках имеют вид `<устройство>.<свойство>`. Опечатка в ключе — ошибка запуска.
- **Условия.** Сравнения: `{"arg"|"state": …, "eq"|"ne"|"lt"|"le"|"gt"|"ge": значение}`. Комбинации:
  `{"all": […]}`, `{"any": […]}`, `{"not": {…}}`. Правила `deny` проверяются по порядку, срабатывает первое.
  Отсутствующий аргумент делает сравнение ложным. Условие, которое нельзя вычислить (например, сравнение
  не-числа), даёт отказ.
- **Clamp.** Вместо отказа можно ограничить аргумент: `{"pct": {"set": 30}}` или `{"pct": {"max": 30}}`.
- **`requires_confirmation: true`** у линии означает подтверждение для `set_<свойство>` и `pulse`.
- **Безопасное значение.** Выход при старте переводится в `safe_state` (если `safe_state` не задан — в `false`).
  При завершении (SIGINT/SIGTERM, конец stdio) устройства с `safe_state` возвращаются в него.
- **Период опроса** должен быть меньше `max_state_age_s`, иначе любая команда с блокировкой видела бы
  устаревшее состояние. hw-mcp проверяет это при старте.
- **`sample_periods`** — положительные периоды в секундах по имени обнаруженного устройства или
  `<устройство>.<свойство>`; настройка свойства имеет приоритет. Неизвестный ключ останавливает запуск.
  Без настройки действуют общий период и ограничения медленных драйверов. Это позволяет выбрать
  частоту чтения после получения реальных датчиков, сохраняя общий MCP-контракт агента.
- **`chip`** — имя узла `gpiochipN` или метка чипа (label; её показывает `gpiodetect` из libgpiod). Номер узла может
  измениться после перезагрузки или с другим набором драйверов, метка — нет. Существующий узел `gpiochipN`
  берётся как есть; иначе метка ищется перебором `/dev/gpiochip*` и должна быть ровно у одного чипа:
  если её нет или она у нескольких чипов, запуск останавливается с перечнем найденных чипов и меток.
  В эмуляции файлами метка — просто имя каталога `<gpio-dir>/<метка>/line<N>`.
- **`stuck_after_s`** — окна «застревания» в секундах по устройству или `<устройство>.<свойство>`
  (свойство важнее устройства): число, не менявшееся дольше окна, становится `null` с причиной `stuck`.
  Одиночные сбои чтения (меньше 3 подряд) окно не прерывают и «застрявшее» значение не возвращают,
  перерыв (3 сбоя подряд) — прерывает. Только для опрашиваемых числовых свойств (ключ устройства — для
  устройства, у которого такие есть), окно длиннее периода опроса; иначе — ошибка запуска. По умолчанию
  не проверяется: показания стабильного помещения законно стоят часами, а фикстура неизменна.
  Окно — параметр эксперимента (допущение), его выбирают под конкретный датчик.
- **Периоды медленных драйверов.** DHT11 опрашивается раз в 2 с (драйвер ядра всё равно кэширует измерение
  на 2 с), DS18B20 (1-Wire) — раз в 10 с (каждое чтение — преобразование 750 мс). Если от такого датчика
  зависит блокировка, он опрашивается с общим периодом `-sample-period`. Действующие периоды пишутся в
  запись `ready` журнала и видны в `hw://diag`.
- **Идемпотентность.** Ключ `cmd_id` помнится не дольше `idem_max_age_s` (по умолчанию в hw-mcp 600 с) и не
  больше `idem_capacity` ключей. Ключи, которые hw-mcp выдал сам (команда без `cmd_id`), не запоминаются.

Пороги уведомлений по умолчанию (единицы SenML): температура 0.2, влажность 1.0, давление 50, освещённость 10,
напряжение и ток 0.01, мощность 0.05, ускорение 0.1. Изменение должно строго превышать порог. Логические
значения сообщаются при любом изменении. Сравнение идёт с последним сообщённым значением, поэтому медленный
дрейф со временем тоже даёт уведомление. Первый отсчёт задаёт базу и уведомления не порождает.

Дрожание и сбои датчиков не порождают уведомлений:

- изменение не больше одного наблюдённого шага квантования датчика (минимальная ненулевая разница соседних
  отсчётов; у DHT11 это 1 °C и 1 %RH) сообщается, только если продержалось 3 отсчёта подряд;
- одиночный сбой чтения оставляет последнее хорошее значение (его возраст растёт, и шлюз со временем увидит
  `stale_state`); значение становится `null` и сообщается только после 3 неудачных чтений подряд;
- повторная запись того же значения в выход (например, «выключить» уже выключенное реле) не уведомляет.

Пороги и эти правила — параметры эксперимента: их фиксируют до прогонов.

## GPIO

Драйвер линий выбирает `-gpio-driver`:

| драйвер | когда | линии | фронты входов |
|---|---|---|---|
| `cdev` | плата (`auto` при `-root /`) или смешанный режим | `/dev/gpiochipN`, ioctl ядра | события ядра |
| `files` | фикстура, симулятор (`auto` при `-root` ≠ `/`) | файлы `<gpio-dir>/<чип>/line<N>` («0»/«1») | нет, только опрос |

Символьное устройство GPIO — готовый интерфейс ядра Linux (`include/uapi/linux/gpio.h`); hw-mcp вызывает
его ioctl напрямую через `golang.org/x/sys/unix`, без cgo и libgpiod. Структуры повторяют заголовок ядра, их
размеры и номера ioctl сверяет тест `TestUAPIStructSizes` (значения из `linux/gpio.h` ядра 6.8).

- **uAPI v2** — ядра ≥ 5.10 (docs.kernel.org/userspace-api/gpio/chardev.html: «First added in 5.10»):
  `GPIO_V2_GET_LINE_IOCTL`, `GPIO_V2_LINE_GET/SET_VALUES_IOCTL`, фронты с подавлением дребезга ядром.
- **uAPI v1** — ядра 4.8+ (…/chardev_v1.html: «First added in 4.8»; в новых ядрах — при
  `CONFIG_GPIO_CDEV_V1=y`). Нужен для ядра 4.9 Jetson Nano (JetPack 4.6). Выход и вход без фронтов —
  `GPIO_GET_LINEHANDLE_IOCTL`, вход с фронтами — `GPIO_GET_LINEEVENT_IOCTL` (по его дескриптору читается и
  уровень), значения — `GPIOHANDLE_GET/SET_LINE_VALUES_IOCTL`, сведения о чипе — `GPIO_GET_CHIPINFO_IOCTL`.
  Подавления дребезга в v1 нет, его делает hw-mcp: после фронта ждёт `debounce_ms` без событий и сообщает
  установившийся уровень, если он изменился (так же ведёт себя debounce ядра в v2).
- **`-gpio-uapi auto`** — для каждого чипа один раз пробуется `GPIO_V2_GET_LINEINFO_IOCTL` (только чтение
  сведений линии 0); `EINVAL` (так `gpio_ioctl` ядра 4.9 отвечает на неизвестную команду) или `ENOTTY` —
  значит v1. Что выбрано, видно в журнале: `ready.gpio_chips` (`{"<чип>": {"node": "gpiochip1", "uapi": "v1"}}`).
- **Метка чипа** вместо `gpiochipN` в `declared.json` — см. ключ `chip` выше.
- **Смешанный режим** (`-gpio-driver cdev` при `-root <каталог>`): датчики sysfs — из каталога фикстуры или
  симулятора, линии — настоящий `/dev/gpiochipN`. Так в ВМ проверяются приводы и фронты на модуле ядра
  `gpio-sim` при эмулированных датчиках.
- **Линия без прерывания** (расширитель GPIO на I²C без вывода INT): запрос фронтов ядро отвергает
  (`ENXIO` в v2, `ENODEV` в v1), и hw-mcp открывает вход без фронтов — он только опрашивается
  (`line_error` с `"fallback": "poll"`).

Без `debounce_ms` направление фронта ядро определяет по уровню, прочитанному уже в обработчике прерывания
(`lineevent_irq_thread` в v1, `edge_irq_thread` в v2), поэтому импульс короче задержки обработчика может
прийти двумя одинаковыми событиями. hw-mcp сообщает только смену значения, и такой импульс теряется (до
опроса он почти наверняка не доживёт). С `debounce_ms` о смене сообщается установившийся уровень.

## Живые датчики

Датчики на плате пропадают и появляются (отошёл разъём, перезагрузили драйвер, переподключили USB-адаптер),
атрибут временно не читается (DHT11 при сбое обмена, NACK на шине I²C), показание может «застрять».

| что произошло | `error` | когда значение становится `null` |
|---|---|---|
| атрибута или устройства нет (`ENOENT`, `ENODEV`) | `absent` | после 3 неудачных чтений подряд |
| атрибут есть, но не читается (`EIO`, `ETIMEDOUT`, `EACCES`…) | `unreadable` | то же |
| прочитано не число | `not_a_number` | то же |
| число не менялось дольше `stuck_after_s` | `stuck` | сразу по окну (если окно задано) |
| линия GPIO не открылась при старте | текст ошибки драйвера | сразу; линия не опрашивается и заново не запрашивается |
| линия GPIO не читается | текст ошибки драйвера | после 3 неудачных чтений подряд |

- Пока неудачных чтений подряд меньше трёх, остаётся последнее хорошее значение; его возраст растёт, и шлюз
  сочтёт его устаревшим (`stale_state`). Переход в `null` и обратно сообщается сразу
  (`notifications/resources/updated`, в `_meta.state` — `null`).
- Причина видна в `read_property` и `hw://state/<устройство>` (`"error": …`), текущие сбои — в
  `board_health.sensor_faults`, число неудачных чтений — в `board_health.sensor_errors`, история по
  свойствам (`read_errors`, `outages`, длительность текущего перерыва) — в `hw://diag` (`sensors`).
- **Возвращение устройства.** Номера `iio:deviceN` и `hwmonN` ядро выделяет заново: вернувшееся устройство
  может получить другой номер, а его прежний номер — другое устройство. На плате (`-root /`) hw-mcp держит
  дескрипторы атрибутов: они привязаны к узлу sysfs конкретного устройства, и после его пропажи чтение даёт
  `ENODEV`, даже если номер уже занят другим. Тогда hw-mcp не читает старый путь, а, пока хоть одно
  устройство IIO или hwmon отсутствует, перечитывает инвентарь только этих источников: первый раз через
  `-rescan-period` (10 с) после пропажи, дальше с удвоением периода до 5 мин (допущение: снятое насовсем
  устройство не ищется каждые 10 с всё время работы, вернувшееся находится не позже чем через 5 мин);
  когда пропавших не остаётся, период сбрасывается. Привязка — к устройству с тем же id инвентаря, тем же
  родителем на шине и тем же каналом (журнал `sensor_rebound`, один раз на перерыв). Родитель нужен hwmon:
  его id — только имя драйвера, и два
  одинаковых чипа (два `lm75` на I²C) различает лишь родитель (`1-0048`, `1-0049`). Повторная
  инвентаризация не читает значений — только имена, родителей и списки атрибутов: чтение значения запускает
  измерение на шине (I²C у BME280 и ADS1015, обмен с DHT11). 1-Wire адресуется серийным номером: его путь не
  меняется, и читатель привязывается заново сразу. Пока всё на месте, повторной инвентаризации нет.
- На фикстуре и в симуляторе (`-root` ≠ `/`) атрибуты читаются по пути (файлы там заменяют через rename),
  поэтому пропажа видна как отсутствие файла, а возвращение по тому же пути — со следующим опросом; подмену
  устройства под тем же номером в этом режиме hw-mcp не отличает.
- Журнал без спама: запись о сбое свойства (`sample_error`) — не чаще раза в 60 с на свойство (допущение).
  Перерыв, начавшийся внутри этого окна, записывается по окончании окна, если ещё длится (`down_s` —
  сколько он уже длится): датчик, который «мигнул» и пропал насовсем, в журнале не выглядит работающим.
  Возвращение (`sample_recovered`) пишется парой к записанному сбою; счётчики (`outages`, `recoveries`,
  `quiet_faults`) полные. То же правило — для предупреждений в stderr.
- Модель устройств при этом не меняется: устройства, которых не было при старте, не добавляются, пропавшие
  не удаляются из каталога. Инвентарь — стабильный префикс промпта агента, и его смена стоила бы токенов и
  кэша, поэтому `list_changed` не посылается (контракт IMPLEMENTATION_SPEC §4 его не предусматривает).
  Новое устройство подключается перезапуском hw-mcp.

## Экономность

- Сэмплер спит до ближайшего срока опроса, таймеры — до конца аренды или импульса. Сроки, совпадающие с
  точностью 1 мс, выполняются в одно пробуждение: иначе сроки периодов 0,1 и 0,3 с из-за округления float64
  расходятся, и за 3 с было бы 39 пробуждений вместо 30 (`TestCloseDeadlinesShareOneWakeup`). Повторная
  инвентаризация планируется, только пока есть пропавшее устройство, её период растёт до 5 мин
  (`TestReboundIsJournaledOncePerOutage`), и она не читает значений датчиков
  (`TestProbeRenumberedReadsNoValues`); не открывшаяся линия GPIO не опрашивается.
- Опрос неизменных значений не выделяет память (`TestSamplingDoesNotAllocate`, Linux): пути атрибутов
  готовятся один раз с завершающим NUL и уходят в `openat` без копии, округление до 6 знаков — в буфере на
  стеке, неизменное число повторно не упаковывается в `any`. Изменившееся число — одна упаковка (8 Б), а
  уведомление о нём строит свои карты. До правки шаг опроса восьми датчиков фикстуры давал 12 выделений
  (760 Б) на Mac.
- На плате (`-root /`, в `ready` — `sysfs_keep_open`) атрибуты открыты постоянно: чтение — один `pread`
  вместо `openat` + `pread` + `close`, отсутствие необязательных атрибутов запоминается.
- `make bench`, `BenchmarkStepSample` в ВМ sbc: шаг опроса 8 датчиков фикстуры — 12,2–12,3 мкс с открытием
  атрибутов и 2,7 мкс с удержанием дескрипторов, 0 выделений
  (`experiments/results/hwmcp_vmchecks_20261014_a/bench_stepsample_vm.log`). Ориентир, не результат: ВМ,
  параллельно работали другие агенты.
- Лимит памяти в коде не задаётся: `GOMEMLIMIT` и `memory.max` cgroup — снаружи (см. «Запуск»).

## Журнал

Одна строка — одна запись канонического JSON. Обязательные поля: `ts_wall` (секунды Unix), `ts_clock`
(часы hw-mcp), `type`, `run_id`.

| type | содержимое |
|---|---|
| `run_start` | хеш конфигурации, версия, корень, каталог, транспорт, часы, ревизии MCP, периоды опроса и повторной инвентаризации, тайм-аут HTTP-сессий, политика шлюза (как в declared.json), устройства |
| `ready` | действующие `max_state_age_s`, `default_ttl_s`, `commit_window_s`, устройства шлюза, число инструментов, драйвер GPIO (`gpio_backend`, у cdev — `gpio_chips`: чип из declared.json → узел и uAPI), `sysfs_keep_open`, периоды опроса по ключам (`sample_periods`: период, источник `default`/`driver`/`declared`/`interlock`, окно `stuck_after_s`) |
| `output_init` | выход и его начальное (безопасное) значение |
| `gate` | `cmd_id`, устройство, инструмент шлюза, `origin` (инструмент MCP), `args`, `issued_at`, `ttl_s`, `confirmed`, `dry_run`, `verdict`, `reason`, `detail`, `final_args`, `state` (`{ключ: {"v":…, "age_s":…}}` — срез, по которому проверялись блокировки), `executed`, `applied`, `error`, `check_ns`, `lease_until`, `pulse_until` |
| `lease_renew`, `lease_expired`, `pulse_end`, `shutdown_safe_state` | таймеры и безопасное состояние |
| `notify` | `uri`, устройство, изменившиеся свойства |
| `sample_error` | свойство стало `null` (после 3 неудачных чтений подряд или по окну `stuck_after_s`) или сменилась причина: `error`, `consecutive` (неудачных чтений подряд; у `stuck` — 0), `outages`, `down_s` (сколько длится перерыв; больше 0, если запись отложена); не чаще раза в 60 с на свойство, перерыв внутри окна — по его окончании, если ещё длится |
| `sample_recovered` | значение вернулось после записанного `sample_error`: `down_s` — длительность перерыва |
| `sensor_rebound` | пропавшее устройство найдено повторной инвентаризацией, читатель привязан к пути `path`; один раз на перерыв |
| `line_error` | запрос линии GPIO при старте не удался: `error`; с `"fallback": "poll"` — линия открыта без фронтов и опрашивается, иначе она недоступна |
| `run_end` | счётчики: опросы, сбои и одиночные сбои (`sample_glitches`), перерывы и возвраты (`outages`, `recoveries`), отложенные или пропущенные ограничением записи о сбоях (`quiet_faults`), повторные инвентаризации и привязки читателей заново (`rescans`, `rebound`), уведомления и подавленные правилами квантования, фронты, отброшенные устаревшие отсчёты (`superseded`), пробуждения таймеров и сэмплера, решения по вердиктам, события безопасного состояния; `notify_dispatch` — очередь рассылки (`enqueued`, `coalesced`, `sent`, `queued`); `http_sessions` — отслеживаемые и закрытые брошенные сессии |

По записям `gate` и политике из `run_start` монитор (класс `actuator_safety`) может независимо перепроверить
каждое решение.

силу эталонов: 12 малых мутаций политики демонстрационного стенда (граница `ge`→`gt`, TTL +0,0001 с, возраст

## Что проверено и чем

Всё ниже — проверки работоспособности; числа, снятые на Mac или в ВМ, — ориентир, не результат.

- **Тесты пакетов:** `make vet` (gofmt, go vet для darwin и linux/arm64), `make test` (`go test -race ./...`
  на Mac), `make vm-test` — те же тесты бинарниками linux/arm64 в ВМ Lima `sbc` (Ubuntu 24.04 arm64, ядро 6.8),
  в том числе нулевые выделения при опросе.
- **GPIO на настоящем ядре — `make vm-gpiosim`** (`tools/vm_gpiosim_check.sh`). Скрипт создаёт в ВМ чипы
  модуля ядра `gpio-sim` (готовый модуль: Documentation/admin-guide/gpio/gpio-sim.rst; в ядре с 5.17, в 4.9
  его нет) с уникальными метками `hwmcp-chk-<pid>` и удаляет их при выходе (trap). Входы двигаются записью
  `pull-up`/`pull-down` в `sim_gpio<K>/pull`, уровень выхода читается из `sim_gpio<K>/value`. Для uAPI v1 и v2:
  чтение входа (и `active_low`), события фронтов, подавление дребезга (v2 — ядро, v1 — hw-mcp), запись выхода
  с проверкой уровня, начальное значение, отказ на занятую линию, сведения о линии; разрешение чипа по метке
  и отказ при метке у двух чипов; `auto` выбирает v2 на ядре 6.8. Затем hw-mcp целиком в смешанном режиме
  (sysfs — копия фикстуры, линии — чип gpio-sim по метке, stdio): чтение входа, уведомление по фронту при
  периоде опроса 60 с, запись выхода, `safe_state` при выходе, `ready.gpio_chips`.
- **Известный дефект ядра стенда.** В ядре 6.8 снятие чипа gpio-sim, пока линию держит запрос (в журнале
  ВМ 09.10.2026 — `gpiomon` другого компонента с запросом событий uAPI v1), даёт обращение к освобождённой
  памяти (`lineevent_release` → `gpiod_free`, затем Oops), и ядро ВМ приходится перезагружать. hw-mcp
  этого не вызывает, но его проверка снимает чипы, поэтому уборка в `vm_gpiosim_check.sh` идёт в порядке:
  завершить группу процессов теста (тест и запущенный им hw-mcp) и дождаться выхода → убедиться по
  `/sys/kernel/debug/gpio`, что линии чипа никем не запрошены (иначе чип остаётся, проверка не проходит) →
  снять чип → проверить `/proc/sys/kernel/tainted`. На ядре с ненулевым `tainted` проверка не начинается.
  Обрыв проверки сигналом TERM, пока hw-mcp держит запрос событий v1, проверен отдельно: группа завершена,
  чипы сняты, `tainted` остался 0 (`vm_gpiosim_abort.log`).
- **Горячее отключение на настоящем sysfs — `make vm-hotplug`** (`tools/vm_hotplug_check.sh`). Устройства
  модуля ядра `iio_dummy` (готовый модуль) создаются и удаляются через configfs с именами `hwmcp-hp-<pid>-*`.
  hw-mcp с `-root /`: устройство пропадает, его номер `iio:device0` тут же занимает другое с теми же
  значениями — hw-mcp сообщает `null` (`absent`), а не чужие значения; устройство возвращается как
  `iio:device1` и находится повторной инвентаризацией (`sensor_rebound`, `sample_recovered`). Удаление
  устройства при открытых дескрипторах его атрибутов — штатный для sysfs случай (чтение затем даёт `ENODEV`,
  это и проверяется); `tainted` до и после — 0.
- **Настоящий sysfs ВМ и PL061 — `tools/vm_smoke.sh`.** Статический бинарник с `/dev/gpiochip0`
  (`configs/declared.vm.json`: вход на линии 0 с событиями фронтов, выход на линии 1), сеанс JSON-RPC по stdio:
  запись, отказ по частоте, чтение входа, `board_health`, `list_devices`; в конце печатается журнал. Модель
  PL061 в QEMU не возвращает уровень выхода (даже debugfs ядра показывает «out lo» после установки 1), поэтому
  уровень выхода проверяется на gpio-sim.
- **Последний прогон** — 14.10.2026, ВМ `sbc`, ядро 6.8.0-146 (после перезагрузки ВМ; 09.10 было 6.8.0-106):
  `make vm-test`, `vm-gpiosim`, проверка обрыва, `vm-hotplug`, `vm_smoke.sh` прошли, `tainted` до и после — 0.
  Логи — `experiments/results/hwmcp_vmchecks_20261014_a/`.
- **Живые датчики на фикстуре:** тесты `internal/hub` (пропажа и возвращение, перенумерация, два одинаковых
  hwmon, «мигающий» датчик, ограничение журнала и отложенная запись затяжного сбоя, одна запись
  `sensor_rebound` на перерыв, рост периода повторной инвентаризации до 5 мин и его сброс, `stuck_after_s` и
  одиночные сбои до и после «застревания», не открывшаяся линия, линия без прерывания
  на поддельном драйвере) и `internal/server` (то же глазами клиента MCP: уведомление с `null`,
  `read_property`, `board_health`). Нечитаемый атрибут эмулируется каталогом на его месте (`EISDIR`).
- **Брошенные HTTP-сессии:** `internal/server` через httptest и клиент go-sdk — слушающий поток SSE клиент
  сессию сохраняет, клиент без потока и «упавший» клиент (соединения оборваны без DELETE) её теряют, запросы с
  неизвестным идентификатором сессии учёта не заводят.
- **Совместимость с агентом:** `bench/tests/test_hwmcp_edgectx.py` (настоящие edgectx и hw-mcp) проходит.
- **Симулятор датчиков `bench/sysfsim`:** `bench/tests/test_sysfsim_hwmcp.py` (бэкенд `files`, весь сценарий
  `dense`: значения `hw://state` равны журналу истины, отказы видны как `null`, реле по `write_property`) и
  `bench/sysfsim/vm_check.sh` в ВМ (бэкенд `gpiosim`, `-gpio-driver cdev`; 15.10.2026, ядро 6.8.0-146, код 0,
  `experiments/results/sysfsim_vmcheck_20261015_b/`). Связка «симулятор + hw-mcp (чип по метке, stdio) +
  edgectx» под лимитами `board.sh run` (64 МиБ, CPU 25 %, сеть 3g) —
  `experiments/results/minboard_smoke_20261014_a/`; журнал hw-mcp принят монитором (`n_unsafe` 0).

## Не проверено на настоящей плате

- **Jetson Nano, JetPack 4.6, ядро 4.9.** uAPI v1 проверен только на ядре 6.8 (`CONFIG_GPIO_CDEV_V1=y`,
  gpio-sim); что ядро 4.9 отвечает `EINVAL` на ioctl v2 и что раскладка структур v1 у него та же, выведено из
  документации и исходного кода ядра; выбор v1 по `EINVAL`/`ENOTTY` проверяет только модульный тест
  `TestUAPIByProbe`. На плате: `TestCdevOnRealChip` на свободных неподключённых линиях (меняет их уровни!):

  ```bash
  GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go test -c -o .build/gpio.test ./internal/gpio
  sudo HWMCP_GPIO_TEST_CHIP=<gpiochipN или метка> HWMCP_GPIO_TEST_IN=<линия> HWMCP_GPIO_TEST_OUT=<линия> \
      HWMCP_GPIO_TEST_UAPI=auto ./.build/gpio.test -test.v -test.run CdevOnRealChip
  ```

  Подавление дребезга в v1 (в hw-mcp) и задержка событий фронтов на реальных линиях Tegra не измерялись.
- **DS18B20 на ядре 4.9 не будет обнаружен.** hw-mcp (как и прототип) находит термометр 1-Wire по атрибуту
  `temperature` драйвера `w1_therm`, а он появился в ядре 5.8 (`drivers/w1/slaves/w1_therm.c`: в v5.7 его
  нет, в v5.8 есть). В v4.9 у драйвера есть только `w1_slave` (две строки: `crc=… YES` и `t=<м°C>`) и нет
  интерфейса hwmon, через который температуру увидела бы инвентаризация hwmon. На Jetson Nano с JetPack 4.6
  нужен разбор `w1_slave` — не сделан.
- **Линия без прерывания.** Откат к опросу проверен только на поддельном драйвере в тестах (у `gpio-sim`
  прерывание есть всегда); настоящий расширитель GPIO без вывода INT не проверялся.
- **Настоящие датчики.** Пропажа устройства на ядре проверена только на `iio_dummy`; DHT11 (`EIO`), шина I²C
  (`EREMOTEIO`), 1-Wire и hwmon с настоящим железом не проверялись. Перенумерация hwmon не проверялась на ядре.
- **Подмена устройства под тем же путём** в режиме фикстуры и симулятора (`-root` ≠ `/`) не отличается от
  смены значения (см. «Живые датчики»). Замена файлов, удаление файлов и каталогов, мусор в атрибутах и
  неизменные значения поддержаны; на симуляторе `bench/sysfsim` из них проверены замена файлов, исчезновение
  устройства и нечитаемый атрибут.

## Ограничения

- Записывать можно только выходы GPIO. IIO `out_*` (ЦАП) и hwmon `pwm*` (вентилятор Pi 5) не подключены:
  у `pwm*` есть автоматика ядра, и ручное управление ей мешает.
- Модель устройств строится при старте: устройства, появившиеся позже, не добавляются, `list_changed` не
  посылается (см. «Живые датчики»). События ядра (uevent) не слушаются: вернувшееся устройство IIO/hwmon
  находит периодическая повторная инвентаризация.
- Горячее отключение чипа GPIO (например, USB-адаптера) не обрабатывается: линия, не открывшаяся при старте
  или пропавшая, заново не запрашивается.
- 1-Wire: только атрибут `temperature` (`w1_therm`, ядра 5.8+); на старых ядрах, где есть лишь `w1_slave`,
  DS18B20 не обнаруживается (см. «Не проверено на настоящей плате»).
- V4L2 и USB видны только в инвентаре (уровень B): кадры с камеры отдаёт отдельный `cam-mcp`.
- `board_health` не знает о мощности PMIC Pi 5 (`vcgencmd pmic_read_adc`). Троттлинг читается из
  `get_throttled` прошивки, если этот файл есть.
- Эмуляция линий файлами не порождает фронтов: входы на фикстуре только опрашиваются.
- DS18B20 при чтении блокирует опрос примерно на 750 мс (`conv_time`). Опрос идёт без блокировок шлюза,
  а быстрые датчики читаются и сообщаются раньше медленных, но следующий опрос ждёт конца этого чтения.
