# edgectx — ИИ-агент одноплатного компьютера

`edgectx` — агент ВКР «Разработка ИИ-агента для приложений граничного ИИ». Он работает на
одноплатном компьютере, получает сведения об оборудовании через MCP-серверы, ведёт два контекста
(пользователя и оборудования) и сам решает, **когда** и **с какой справкой** обращаться к внешней
LLM (OpenAI-совместимый Chat Completions; в разработке — только локальный `mock-llm`).

Контракт с остальными компонентами — `../IMPLEMENTATION_SPEC.md` (§0, §3, §5.1, §6); отступления и
уточнения — `../docs/DECISIONS.md` (строки с пометкой `[edgectx]`).

- Go ≥ 1.27, модуль `github.com/local/edgectx`, **статический бинарник** (`CGO_ENABLED=0`; SQLite —
  `modernc.org/sqlite` на чистом Go), собирается под `linux/arm64` (Raspberry Pi 5, Jetson Nano с
  ядром 4.9 / glibc 2.27, Lima VM `sbc`).
- MCP — официальный SDK `github.com/modelcontextprotocol/go-sdk` v1.8.0, ревизия протокола
  **2025-11-25**, транспорты stdio и streamable HTTP.
- Всё время — только из `Clock` (реальные или виртуальные часы): рабочий день проигрывается за секунды.
- Рассчитан на минимальную плату и плохую связь: обрыв связи с LLM не теряет пробуждений и не
  порождает шквала запросов, упавший MCP-сервер переподключается, память ограничена во времени,
  запись на SD-карту экономная (разделы «Плохая сеть…», «Падение MCP-сервера», «Память и SD-карта»).

> Числа времени, полученные при разработке (в том числе в тестах), — **не результаты** экспериментов.

## Быстрый старт

```sh
cd agent
make test            # юнит- и интеграционные тесты (go test ./...)
make test-race       # то же с детектором гонок
make build-mac       # bin/edgectx-darwin-arm64
make check-static    # bin/edgectx-linux-arm64 + проверка `file … statically linked`

./bin/edgectx-darwin-arm64 -config configs/example.yaml -check-config
./bin/edgectx-darwin-arm64 -config configs/example.yaml -trace run/trace.jsonl -listen 127.0.0.1:18080
```

Предел памяти рантайма Go задаётся снаружи переменной `GOMEMLIMIT` (например `GOMEMLIMIT=24MiB`
вместе с `MemoryMax` cgroup); в коде он не дублируется, фактическое значение пишется в `run_start`.

Флаги: `-config` (YAML; без него — умолчания), `-trace` (JSONL; относительно текущего каталога),
`-listen` (`:0` — свободный порт; фактический адрес печатается в stderr строкой
`edgectx: listening on http://…`), `-run-id`, `-check-config`, `-version`. Остановка — `SIGINT`/`SIGTERM`
(по PID) или `POST /v1/shutdown`: текущие ходы дорабатывают, отложенное до связи с LLM получает
исход `shutdown`, пишется `run_end`, stdio-серверы завершаются. Если MCP-сервер из конфигурации не
подключился при старте, агент завершается с кодом 1 (прогон без сервера тихо исказил бы метрики);
сервер, упавший позже, переподключается.

Пример ручного прогона на виртуальных часах (нужны запущенные `mock-llm` и `sim-mcp`):

```sh
curl -s -XPOST localhost:18080/v1/event -d '{"device":"door1","property":"open","value":true}'
curl -s -XPOST localhost:18080/v1/clock/advance -d '{"to_t": 27000}'      # 07:30
curl -s -XPOST localhost:18080/v1/user -d '{"id":"u1","text":"включи свет"}'
curl -s localhost:18080/v1/metrics | head
```

|---|---|
| `internal/clock` | `Clock` (Now, Epoch, AfterFunc). `Real` — настенные часы; `Virtual` — дискретно-событийные: таймеры срабатывают по порядку при `AdvanceTo`, после каждого вызывается `settle` (ожидание затишья агента). Обращение к LLM занимает ноль виртуального времени. |
| `internal/activity` | Счётчик незавершённой работы (задания, события MCP, действия правил, проба связи) — по нему виртуальные часы ждут затишья. |
| `internal/backoff` | Экспоненциальная пауза с «равным» джиттером и детерминированное псевдослучайное число из зерна (`run_id`): паузы повторов LLM, проб и переподключений воспроизводимы. |
| `internal/breaker` | Предохранитель внешней LLM: счёт временных сбоев подряд, размыкание после `failures`, растущая пауза до пробы, полуоткрытое состояние после удачной пробы (счётчик обнуляет только ответ модели). Таймер пробы и блокировку держит агент. |
| `internal/gate` | Событийный гейт: дебаунс (значение должно продержаться `debounce_s`; значения, сменяющиеся чаще, подтверждаются не реже раза в 2·`debounce_s` — иначе датчик, меняющийся каждую секунду опроса, не дошёл бы до порога, пока меняется), правила (по фронту, `for_s`, окно времени суток, cooldown, `once`), эхо собственных команд, сигналы `change` / `threshold` (порог + гистерезис) / `delta` / `episode` («конец эпизода» после `gap_s` тишины) / `ignore`, cooldown по ключу, коалесценция в окне W (досрочно — при `coalesce_max` событиях). Каждый вход получает ровно один исход. |
| `internal/sched` | Очередь ходов с приоритетами «пользователь > безопасность > фон», 1–2 исполнителя, суточные лимиты вызовов и входных токенов (сутки — по `Clock`), режимы normal → degraded (фон отклоняется) → exhausted (обслуживается только пользователь). |
| `internal/userctx` | SQLite: факты профиля (ADD/UPDATE/DELETE), история ходов, сводка, правила; политики истории `full` / `window` / `mask` / `summary_system`; экспорт `MEMORY.md`; кэш страниц, журнал и синхронизация — из конфигурации. |
| `internal/hwctx` | L0 — разбор инвентаря и текстовая проекция (строка на устройство); L1 — состояние с округлением до точности датчика, режимы `snapshot_head` (снимок в префиксе, не чаще `snapshot_period_s`), `delta_tail` (изменения с последнего ответа модели — в хвосте), `pull`; показания упавшего сервера помечаются «нет связи» до свежего показания каждого устройства; L2 — кольцевой журнал событий (`recent_events`). |
| `internal/prompt` | Сборка сообщений в порядке сегментов, учёт размера сегментов в символах и оценке токенов. |
| `internal/canon` | Каноническая сериализация JSON: ключи отсортированы, без пробелов, UTF-8 без `\u`, кратчайшие числа; округление до шага. |
| `internal/llm` | Chat Completions с tools: одно keep-alive соединение (HTTP/2 для TLS, кэш TLS-сессий), без потока, каноническое тело, полный `usage`; раздельные таймауты соединения и попытки; повтор после сетевой ошибки до ответа, 429 и 5xx с паузой и `Retry-After`; классы ошибок и признак «запрос мог быть оплачен»; проба связи `GET /models`. |
| `internal/mcphost` | MCP host: подключение, каталог инструментов (имена приводятся к `^[a-zA-Z0-9_-]{1,64}$`, конфликты — префикс `сервер__`), вызовы, чтение ресурсов, подписка; события серверов (уведомления, смена каталога, падение/восстановление) — одной ограниченной очередью вне горутины протокола, доставка — после `run_start`; переподключение упавшего сервера (короткие сессии паузу не сбрасывают) и повтор восстановления подписки и состояния, если оно не удалось; JSON-результаты сжимаются в канонический вид; структурный отказ `{"denied": true, "reason": …}`. |
| `internal/trace` | Писатель трассы JSONL (§6) с буферизацией и сбросом по таймеру, на `run_start`/`run_end` и при закрытии. |
| `internal/config` | YAML, умолчания, строгая проверка (неизвестный ключ — ошибка), SHA-256 конфигурации. |
| `internal/channel` | HTTP-канал. |
| `internal/agent` | Ядро: входы → гейт/heartbeat → планировщик → ход (до `max_steps`) → ответ/уведомление → трасса; встроенные инструменты. |
| `internal/fakemcp` | Фейковые MCP-серверы для тестов (в бинарник не входят): «комната» (с переключателем «датчики не отвечают») и «камера» (сводка детектора, состояние шаблоном `cam://state/{device}`). |
| `cmd/edgectx` | Команда. |

### Ход агента

1. **Вход.** Реплика пользователя (`/v1/user`), изменение состояния (уведомление
   `notifications/resources/updated` или `/v1/event`), ситуация (`/v1/event` с `kind: situation`),
   тик heartbeat. Каждое изменённое свойство — отдельный вход `sensor`.
2. **Решение.** Реплика пользователя будит LLM всегда. События идут через гейт; heartbeat — по
   политике: `heartbeat` (только тики каждые `heartbeat_min`, события LLM не будят), `gate` (только
   гейт), `hybrid` (гейт + тик после `heartbeat_min` тишины LLM: таймер сбрасывается каждым
   пробуждением). Локальные правила исполняются в любой политике (если `rules_enabled`).
3. **Планировщик** допускает или отклоняет ход по приоритету и бюджету. Пока модель недоступна
   (предохранитель разомкнут), допущенный ход не начинается, а откладывается (раздел «Плохая сеть…»).
4. **Промпт** (каждый шаг хода):

   | Сегмент | Сообщение | Содержимое |
   |---|---|---|
   | `prefix` | `system` + `tools` | системный промпт, схемы инструментов (MCP + встроенные, по имени), инвентарь L0; в `snapshot_head` — снимок L1 |
   | `profile` | `system` | факты профиля (обновляются только при консолидации через `profile_consolidate_s`) |
   | `history` | `system` + диалог | сводка (`summary_system`) и ходы по политике истории |
   | `state` | `user` «Время: …» | время, дельта L1 (`delta_tail`), разбудившие события / сработавшее правило; у хода `deferred` — всё отложенное без связи с моделью |
   | `turn` | `user` + ассистент/`tool` | реплика или задача фонового хода и сообщения текущего хода |

5. **LLM → инструменты** до `max_steps`: инструменты MCP-серверов и встроенные (`notify_user`,
   `create_rule`, `delete_rule`, `update_profile`, `recent_events`, по желанию `agent_status`).
6. **Итог.** Ответ пользователю (`user_reply`); у фонового хода непустой ответ, не начинающийся с
   `noop_reply` (`NO_ACTION`), — уведомление (`notify`). Ход сохраняется в историю (у фонового — с
   описанием события вместо текста задачи). При `summary_system` и превышении порога оплаченных
   токенов старые ходы сжимаются в сводку отдельным запросом (`purpose: summary`).

Полный архив ходов остаётся в SQLite. В оперативном кеше `window` и `mask` с заданным
`window_turns` держат только это окно, `summary_system` — ходы после последней сводки (при
успешной консолидации старые ходы освобождаются). Это действует и при перезапуске.
`full`, `mask` без окна и `summary_system` без консолидации по-прежнему растут с историей;
это следует учитывать при сравнении памяти. Метрики `history_turns` и `history_cached_turns`
показывают размер архива и оперативного кеша соответственно.

**Правила-договорённости.** LLM создаёт правило один раз (`create_rule`: `device.property op value`,
`for_s`, окно `after..before`, действие `notify` / `tool` / `wake`), дальше его исполняет гейт без LLM.
Пока условие правила истинно (в его окне), события этого свойства принадлежат правилу и LLM не будят
(`rule_handled`). Правила хранятся в SQLite и переживают перезапуск; заранее заданные — в файле
`rules_path` (YAML/JSON).

**Эхо собственных команд.** После успешного вызова инструмента-«записи» (`write_*`, `set_*`, …)
изменения этого устройства в течение `self_echo_s` помечаются `self` и не будят LLM (`self_caused`);
правила их видят.

**Дельта L1 только после ответа.** В `delta_tail` изменения состояния считаются показанными модели,
только когда она ответила на первый запрос хода. Если запрос не удался, следующий ход снова получит
те же изменения (раньше они терялись).

## Плохая сеть и обрывы связи с LLM

Связь платы с внешней LLM может пропадать на секунды и на часы. Решения ниже — инженерная практика
устойчивых клиентов, а не собственное изобретение: экспоненциальная пауза с джиттером (M. Brooker,
«Exponential Backoff And Jitter», AWS Architecture Blog, 2015), предохранитель с полуоткрытым
состоянием (circuit breaker: M. Nygard, «Release It!», 2007; M. Fowler, «CircuitBreaker», 2014),
заголовок `Retry-After` (RFC 9110 §10.2.3). Умолчания повторов взяты из официального клиента OpenAI для
Python (`openai-python`, `_constants.py`: 2 повтора, первая пауза 0,5 с, предел 8 с; проверено 09.10.2026).

1. **Таймауты раздельные.** `connect_timeout_s` (10 с) — установление TCP-соединения и, отдельно,
   TLS-рукопожатие; `timeout_s` (60 с) — попытка запроса целиком, до конца ответа. 10 с на соединение —
   **допущение** для медленного канала: при начальном RTO 1 с (RFC 6298 §2) успевают исходный SYN и
   три его повтора (через 1, 3 и 7 с); у `openai-python` — 5 с.
2. **Повтор внутри обращения** (`retries`, 2) — только если ответа нет или он говорит «повторите»:
   сетевая ошибка до ответа (DNS, TCP, TLS, обрыв), `429`, `5xx`. Пауза `retry_backoff_ms`·2^(n−1), не больше
   `retry_backoff_max_ms`, с «равным» джиттером (пауза в [½, 1] от этого значения), не короче
   `Retry-After` / `retry-after-ms`. Не повторяются: таймаут попытки и ответ, оборванный на середине
   (запрос мог быть уже обработан и оплачен — такой сбой помечен в `llm_response` как `maybe_billed: true`),
   `4xx`, непригодный ответ. `Retry-After` длиннее предела паузы клиент не ждёт: обращение завершается
   ошибкой, ожидание берёт на себя предохранитель. Паузы внутри обращения идут по настенным часам (это
   свойство сети); джиттер берётся из хеша (`run_id`, номер обращения, попытка), поэтому при одном
   `run_id` паузы воспроизводятся, в том числе на виртуальных часах. Риск двойной оплаты остаётся у
   обрыва соединения после отправки запроса, но до начала ответа: такой сбой неотличим от сетевого и
   повторяется.
3. **Предохранитель** (`llm.breaker`). Временный сбой обращения (`network`, `timeout`, `http_429`,
   `http_5xx`) после всех повторов увеличивает счётчик; после `failures` (1) сбоев подряд модель
   считается недоступной (`llm_unavailable`). Одно обращение уже включает до `retries + 1` попыток,
   поэтому умолчание — 1: на мёртвой сети каждая лишняя попытка держала бы единственный слот LLM по
   `connect_timeout_s`. Связь проверяет **проба без токенов** `GET {base_url}/{probe_path}` (`models`) по
   таймеру **часов агента** (в T0 — виртуальных, детерминированно): пауза `probe_s`·2^(k−1) (k — сбоев
   подряд, включая неудачные пробы и сорвавшиеся пробные ходы), не больше `probe_max_s`, с тем же
   джиттером и не короче `Retry-After`. Провайдер достижим при любом HTTP-ответе пробы, кроме 429 и 5xx
   (401/404 тоже значат, что сервер отвечает; ошибку запроса покажет ход). Тело пробы читается не больше
   256 КиБ и отбрасывается; байты пробы учитываются (`llm.probe_bytes`): `/models` у агрегаторов бывает
   большим — тогда `probe_path` стоит сменить на более короткий ресурс провайдера.
   Удачная проба лишь **полуоткрывает** предохранитель: `/models` агрегатора — статический каталог и
   отвечает, даже когда сама модель недоступна (5xx от её провайдера). Поэтому проба допускает
   **пробный ход**, но счётчик сбоев не обнуляет. Замыкает предохранитель и обнуляет счётчик только ответ
   модели (`llm_available`); сбой пробного хода снова размыкает его с паузой больше прежней. При живом
   `/models` и мёртвой модели за час уходит не больше 4 + 3600/(`probe_max_s`/2) ≈ 28 пробных ходов (в
   тесте с умолчаниями — 18), а не ход каждые 15–30 с. Каждое обращение, и неудачное, учитывается в
   суточном лимите `budget.daily_calls`.
4. **Что происходит, пока модели нет.** Локальные правила, гейт, журнал L2, контекст оборудования и
   MCP работают как обычно — безопасность локальна. Ходы не начинаются: пробуждения (гейт, правило,
   heartbeat, реплика) откладываются, каждое — запись `deferred`. Очередь хранит отдельные пробуждения,
   не больше `sched.deferred_max` (32): пробный ход, сорвавшийся снова, возвращает в неё свои части по
   одной, так что предел действует, сколько бы ни длился обрыв. Ход, сорвавшийся из-за недоступности
   модели на **первом** обращении (он ещё ничего не сделал), тоже откладывается (`deferred` с
   `retry: true`) — если запрос заведомо не оплачен. После таймаута попытки или оборванного ответа ход
   не повторяется (вопрос пользователя получает ошибку, `ok: false`): иначе одно и то же обращение могло
   бы быть оплачено дважды, а медленная, но живая модель оплачивалась бы на каждом пробном ходе. Ход,
   сорвавшийся позже, после вызовов инструментов, не повторяется (иначе повторились бы команды
   приводам). Новая плановая проверка не копится, если одна уже ждёт (`heartbeat_pending`). При
   переполнении вытесняется худшее по приоритету и самое старое пробуждение, если новое лучше, иначе
   отклоняется новое (`deferred_full`), как в очереди планировщика. Если сбой был, а предохранитель ещё
   замкнут (`failures` > 1), проба тоже заведена: отложенное не ждёт следующего события.
5. **Восстановление — одним ходом.** После удачной пробы всё отложенное сливается в **один** пробный
   ход с причиной `deferred` (запись `wake` с `coalesced` — идентификаторами слитых пробуждений) и
   наивысшим приоритетом из слитых: без шквала запросов после обрыва. В хвосте промпта — список
   отложенного по времени («Пока связи с моделью не было, произошло: …»; не больше `deferred_max`
   пробуждений), дельта L1 с последнего ответа модели (показания не теряются), сообщения пользователя.
6. **Вопрос пользователя без связи.** Канал `/v1/user` синхронный: ответ приходит, когда ход закончен,
   а при таймауте ожидания (504) ход дорабатывает и ответ остаётся только в трассе. Отложенный вопрос —
   тот же случай, известный заранее, поэтому агент **сразу** отвечает `202` с `deferred: true`,
   фактическими `latency_ms` и `llm_calls` и текстом «Нет связи с языковой моделью. Вопрос сохранён и будет
   обработан после восстановления связи» (ответ не обещается: канала доставки поздних ответов нет).
   Держать HTTP-запрос открытым часами бессмысленно, а повторять попытку на каждый вопрос — значит
   занимать слот LLM таймаутом на мёртвой сети. Вопрос ждёт в очереди отложенного с приоритетом
   пользователя, ответ модели после восстановления пишется как `user_reply` с `deferred: true` (на каждый
   отложенный вопрос — свой, текст общий: модель отвечает одним сообщением). Если обрыв ещё не
   обнаружен, первый вопрос ждёт неудачного обращения (`llm_calls: 1`) и тоже получает `202`, а после
   таймаута попытки — ответ с ошибкой (п. 4). Если связь так и не вернулась (остановка, вытеснение) или
   сорвавшийся ход вопроса не поместился в полную очередь отложенного, — `user_reply` с `ok: false` (у
   каждой реплики ровно один `user_reply`).

Предохранитель, таймер пробы и очередь отложенного меняются под одной блокировкой: пробуждение не
застревает в очереди, если связь восстановилась, пока его откладывали.

## Падение MCP-сервера и несколько серверов

Конец MCP-сессии — процесс stdio завершился, HTTP-сессия оборвана — означает падение сервера
(`mcp_down`). Host переподключается сам: заново запускает процесс stdio или соединяется по HTTP,
повторяет `initialize` и чтение каталога; паузы `reconnect_s`·2^(n−1) до `reconnect_max_s`, с
джиттером, по **настенным** часам — это свойство транспорта, а не логики агента (как паузы повторов
LLM). Сессия, оборвавшаяся быстрее `reconnect_max_s`, паузу не сбрасывает: сервер, который проходит
инициализацию и сразу падает (например, на первом чтении sysfs), переподключается всё реже, а не
каждую секунду с полной ресинхронизацией. После подключения (`mcp_up`) агент перечитывает инвентарь,
восстанавливает подписку и читает состояние заново: то, что изменилось без связи, приходит входами
`sensor` с прежним значением в `old` и проходит через гейт. Если подписка или чтение не удались (датчик
не ответил, сервер занят), host пишет `error` с `where: mcp_resync` и повторяет восстановление с той же
растущей паузой, пока оно не удастся или сессия не оборвётся; `mcp_up` пишется один раз. Для HTTP
повторы SDK по потоку SSE выключены (`MaxRetries < 0`): серверы стенда не хранят события для
возобновления потока, так что повторы лишь откладывали бы обнаружение падения. При штатной остановке
HTTP-сервер может держать поток SSE до своего таймаута остановки — тогда падение обнаруживается с этой
задержкой (в ВМ — около 3 с).

Пока сервер недоступен: его инструменты остаются в каталоге (стабильный префикс промпта не меняется),
вызовы сразу возвращают ошибку «сервер недоступен (переподключение)»; инвентарь — последний
прочитанный; показания его устройств помечаются «нет связи» в снимке и дельте L1 (переход в это
состояние и обратно — тоже изменение дельты) и не считаются известными для правил. Пометка снимается
с каждого устройства отдельно — только свежим показанием (чтение после переподключения или
уведомление), поэтому устройство, которое не удалось перечитать, модель не получит со старым значением
как свежее.

Агент работает с несколькими серверами одновременно (например hw-mcp и сервер камеры с тем же
контрактом ресурсов `…/state/<device>`): инвентари объединяются (у устройства запоминается сервер),
шаблоны ресурсов состояния раскрываются только по устройствам своего сервера, совпавшие имена
инструментов получают префикс `сервер__`, уведомления всех серверов идут одной очередью.

## Память и SD-карта

Всё, что копится во времени, ограничено:

| Что | Предел |
|---|---|
| очередь ходов планировщика | `sched.queue_max` (64), вытеснение худшего |
| отложенные до связи с LLM | `sched.deferred_max` (32) пробуждений, в том числе вернувшихся из сорвавшегося пробного хода; хвост промпта слитого хода — не больше `deferred_max` × `coalesce_max` событий |
| очередь событий MCP-серверов | 1024 уведомления; лишние отбрасываются и сообщаются одной записью `error` (`mcp_queue_full`, сколько отброшено) на всплеск |
| окно коалесценции гейта | `policy.gate.coalesce_max` (32) событий, затем окно закрывается досрочно |
| журнал событий L2 | 5000 событий (≈0,1–0,2 КБ каждое), кольцо без копирования и выделений памяти на событие |
| кеш истории в RAM | `window_turns` для `window` и `mask` с окном; для `summary_system` — ходы после сводки; `full` и `mask` без окна растут (полный архив — в SQLite) |
| кэш страниц SQLite | `userctx.cache_kib` (256 КиБ вместо 2000 КиБ по умолчанию SQLite) |
| буфер трассы | 64 КиБ |
| тело ответа LLM / пробы | 8 МиБ / 256 КиБ |
| сообщения хода, результат инструмента в промпте | `max_steps`, `max_tool_result_chars` |

Карты гейта и состояния растут только с числом пар «устройство.свойство» (инвентарь и входы
`/v1/event`), факты профиля — с числом добавлений моделью (`update_profile`, предела нет); архив ходов
растёт в SQLite на диске, а не в RAM. Лимит памяти рантайма Go — переменная `GOMEMLIMIT` снаружи,
в `run_start.runtime` — фактические `gomemlimit` (байт; 9223372036854775807 — предела нет), `gogc`
(−1 — сборка выключена), `gomaxprocs` и версия Go.

**SQLite на SD-карте.** Умолчание — `journal_mode: wal`, `synchronous: normal`: фиксация пишет только в
журнал WAL без `fsync`, `fsync` — на контрольной точке. При сбое питания база остаётся согласованной,
теряются лишь последние фиксации (документация SQLite: «Write-Ahead Logging», «PRAGMA synchronous»);
для контекста агента (история, правила, профиль) это допустимо, а число синхронных записей на флеш
падает с двух-трёх `fsync` на каждую фиксацию до двух на контрольную точку (по умолчанию SQLite — раз
в ≈1000 страниц журнала). Вне WAL (`delete`, `truncate`, `persist`) разрешён только
`synchronous: full`: с `normal` сбой питания может испортить базу.

**Трасса** буферизована: сброс не позже чем через `trace_flush_s` (2 с) после первой несброшенной записи,
сразу после `run_start` и `run_end` и при закрытии. Таймер сброса заводится только при непустом
буфере — простаивающий агент не просыпается ради трассы. `fsync` трасса не вызывает (на флеш данные
выносит writeback ядра), поэтому выигрыш — меньше системных вызовов и пробуждений, а не меньше
записей на карту; при SIGKILL или OOM теряется не больше `trace_flush_s` хвоста. `trace_flush_s: 0` —
сброс после каждой записи, как раньше.

трассы; предел цепочки дебаунса 2·`debounce_s` (константа `debounceChainMax`) — дребезг контакта длится
доли миллисекунды (герконы Standex-Meder — ≤ 0,5 мс, `bench/sysfsim/README.md`), а значения, сменяющие друг
друга секундами, — уже изменение, а не дребезг.

## HTTP-канал

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /v1/user` | `{"id": "u17", "text": "…"}` (`id` необязателен) | после окончания хода: `{input_id, wake_id, text, latency_ms, llm_calls, tool_calls, ok, error?}`; 202 `{…, deferred: true, ok: false}` с фактическими `latency_ms` и `llm_calls` — модель недоступна, вопрос отложен (ответ — `user_reply` в трассе после восстановления); 504 по таймауту ожидания (ход дорабатывает) |
| `POST /v1/event` | `{"id"?, "kind": "sensor", "device", "property", "value"}` или `{"kind": "situation", "id"?, "name", "text"}`; допускается массив | `{input_ids: […]}` — гейт уже обработал событие; повтор известного значения — вход с исходом `no_change` |
| `POST /v1/clock/advance` | `{"to_t": 27000, "min_inputs"?: {"sensor": 120}, "timeout_ms"?: 5000}` | `{now_t, timers_fired, inputs, idle, waited_ms, missing_inputs?}`; 409 для реальных часов, 400 — назад |
| `GET /v1/metrics` | — | счётчики: входы, пробуждения, подавления, LLM (запросы, токены, байты, `errors_<класс>`, `unavailable`, `probes`, `probe_bytes`), `llm_link{state: closed\|open\|half_open, failures, deferred}`, `deferred{wakes, turns}`, `mcp{updates, down, up}`, инструменты, правила, бюджет, планировщик, гейт, память процесса |
| `GET /v1/health` | — | `{ok, run_id, clock, now_t, idle, active, queued, inputs, servers[{…, down}], …}` |
| `POST /v1/shutdown` | — | 202; корректная остановка |

`/v1/clock/advance` сначала дожидается затишья (обработаны все входы, пришедшие раньше), затем по
порядку исполняет таймеры (heartbeat, дебаунс, окно коалесценции, конец эпизода, `for_s` правил,
консолидация профиля), дожидаясь окончания вызванных ходов после каждого. `min_inputs` нужен
реплееру: уведомления `sim-mcp` идут отдельным потоком SSE, и до продвижения часов агент должен
принять их все (счётчик `sensor` не включает производные входы «конец эпизода»).

## Трасса (JSONL, спецификация §6)

Строка — канонический JSON одной записи. Обязательные поля: `ts_wall` (Unix-время, с, точность
мкс), `ts_clock` (с от эпохи часов — та же шкала, что `t` файла дня), `type`, `run_id`; плюс `seq`
(порядковый номер записи).

| `type` | Поля |
|---|---|
| `run_start` | `config_hash`, `policy{wake, heartbeat_min, history, window_turns, hwctx, catalog, gate{…}, …}`, `clock`, `start_t`, `model`, `base_url`, `budget`, `sched`, `servers[]`, `n_tools`, `n_devices`, `n_rules`, `version`, `protocol`, `breaker{failures, probe_s, probe_max_s, probe_path}`, `runtime{gomemlimit, gogc, gomaxprocs, go}` |

Инварианты (проверяются в `tests/tracecheck_test.go`): `run_start` первая — даже если правило истинно с
самого старта или сервер прислал уведомление до него (правила взводятся, а события MCP доставляются
только после `run_start`), `run_end` последняя;
`seq` подряд; `ts_clock` не убывает; у каждого `llm_request` ровно один `llm_response`, у
каждого `tool_call` — один `tool_result`; у допущенного пробуждения есть запрос к LLM, у
отклонённого — нет; **каждый вход получает ровно один исход** — запись `suppress` или участие в одном
допущенном пробуждении; у реплики пользователя — один `user_reply`.

Причины `suppress`: гейт — `debounce`, `no_change`, `rule_handled`, `self_caused`,
`policy_heartbeat`, `ignored`, `below_threshold`, `threshold_hold`, `threshold_clear`, `not_numeric`,
`baseline`, `below_delta`, `episode`, `cooldown`; планировщик — `budget_degraded`,
`budget_exhausted`, `queue_full`, `shutdown`; heartbeat — `heartbeat_pending` (в том числе когда
плановая проверка уже ждёт связи с моделью); очередь отложенного — `deferred_full`.

Отложенное пробуждение (`deferred`) исхода входам не даёт: вход получает его в слитом ходе `deferred`
(участие в допущенном `wake`) или при сбросе очереди (`suppress` с `deferred_full`/`shutdown`). Вход хода,
сорвавшегося и отложенного повторно (`retry: true`), уже получил исход в первом `wake` и в `input_ids`
слитого хода не повторяется.

## Интерфейсы для других компонентов

- **mock-llm.** `POST {base_url}/chat/completions`, тело — канонический JSON
  (`model`, `messages`, `tools`, `tool_choice: auto`, `stream: false`, поля `llm.extra`). При
  `llm.trace_headers: true` в запросе есть `X-Edgectx-Run-Id`, `X-Edgectx-Req-Id`, `X-Edgectx-Wake-Id`,
  `X-Edgectx-Wake-Reason` (`user|gate|heartbeat|rule|deferred`), `X-Edgectx-Input-Ids` (через запятую —
  совпадают с `id` из `/v1/user` и `/v1/event`), `X-Edgectx-Purpose` (`turn|summary`),
  `X-Edgectx-Step`, `X-Edgectx-Clock-T`. Oracle «ничего не делать» — ответ `NO_ACTION`;
  уведомление — непустой текст или вызов `notify_user`. Проба связи — `GET {base_url}/models`
  (`llm.breaker.probe_path`).
- **sim-mcp / hw-mcp / сервер камеры.** Агент вызывает `tools/list`, `resources/list`, `resources/templates/list`;
  инвентарь — ресурс `inventory_uri` (по умолчанию первый ресурс `…inventory`), иначе инструмент
  `list_devices`. Понимаются массив устройств или `{"devices": […|{id: …}]}` со свойствами в
  `properties` / `channels` / `props` (поля `name`, `unit`, `type`, `writable`/`rw`/`readOnly`,
  `min`/`max`/`range`, `precision`, `value`), `location`, `actions`. Подписка — на ресурсы,
  подходящие под `subscribe` (по умолчанию все, кроме инвентаря; шаблоны вида `hw://state/{device}`
  раскрываются по ID устройств этого сервера). Состояние: `{"device", "properties": {p: v | {"value": v}}}`,
  `{"property", "value"}`, плоский объект или SenML. **Рекомендация:** класть новое состояние в
  `_meta.state` уведомления `resources/updated` — тогда агенту не нужно читать ресурс, и быстрые
  изменения (PIR 1→0) не теряются. Отказ шлюза — `{"denied": true, "reason": …}` в
  `structuredContent` или JSON-тексте. После перезапуска сервер переподключается без участия
  оператора; ресурсы состояния после переподключения агент читает заново.
- **Реплеер.** Порядок для события дня с временем `t`: `POST /v1/clock/advance {to_t: t}` →
  `POST sim-mcp /control/clock {t}` → следующий шаг с `min_inputs: {"sensor": N}` (N — сколько
  изменений опубликовал sim-mcp), реплики — `POST /v1/user {id, text}` с ожиданием ответа (`202` с
  `deferred: true` — модель недоступна, вопрос отложен), в конце — `advance` до конца окна и
  `POST /v1/shutdown`. Конфигурация прогона задаёт `clock.start_t` = начало окна.
- **monitor.** Формат трассы — таблица выше. Трасса без обрыва связи с LLM и падений MCP-серверов
  содержит только прежние типы записей. При обрыве и падении появляются дополнительные типы
  `llm_unavailable`, `llm_probe`, `llm_available`, `deferred`, `mcp_down`, `mcp_up`, причина
  пробуждения `deferred` (входы любого вида) и поле `maybe_billed` в `llm_response`; монитор
  (`monitor/trace_check.py`) их проверяет: поля, ссылки `deferred` на входы, исход каждого входа.

(modernc), ядро Linux с cgroup v2 и `tc netem` (ими моделируются плохая сеть и лимиты в ВМ).

устаревших показаний, переподключение и его учёт в контексте, ограничения памяти, трасса.

## Ограничения

- Оценка токенов в `llm_request` — эвристика «символов на токен» (3,4 для кириллицы, 4,3 для
  остального, по данным GAP4), до калибровки по `usage.prompt_tokens` (решение 6 концепции).
- Поздние ответы (после `202` или `504`) пишутся только в трассу: push-канала к пользователю нет.
- Отложенный повтор хода — только если ход сорвался на первом обращении к модели и запрос заведомо
  не оплачен; ход после таймаута попытки или оборванного ответа и ход, успевший вызвать инструменты,
  при сбое модели не повторяются (иначе возможны двойная оплата и повтор команд приводам), но их
  пробуждения получили исход и есть в трассе. `_meta edgectx/cmd_id` (идемпотентность команд hw-mcp)
  агент пока не передаёт.
- При `max_in_flight: 2` полуоткрытый предохранитель пропускает и второй ход одновременно с пробным;
  сбой обоих увеличивает счётчик на два.
- Счётчики трафика по классам (nftables), PSS/CPU — вне агента (`sysmon`); `/v1/metrics` даёт только
  размеры тел запросов к LLM и проб и память Go-рантайма.
- Веб-чат и VK-канал не реализованы (спецификация: опционально).
- При двух запросах в полёте (`max_in_flight: 2`) ходы делят историю и дельту состояния; порядок
  записи ходов в историю — порядок завершения.
- Неудачные подписка или чтение состояния при старте не повторяются (запись `error` с `where: start`);
  повтор с паузой есть только при восстановлении после переподключения (`mcp_resync`).
- Очередь событий MCP-серверов ограничена 1024 уведомлениями. Переполнение явно пишет
  `errors.mcp_queue_full`; такой прогон не подтверждает обработку полного входного потока.

Сквозной локальный тест `python -m unittest bench.tests.test_hwmcp_edgectx -v` (из корня проекта)
собирает настоящие EdgeCtx и hw-mcp во временный каталог, меняет копию sysfs-фикстуры и
проверяет обнаружение, подписку, обновление контекста, подавление незначимого показания и
пробуждение LLM значимым. Модель — `bench/mockllm`; это проверка интеграции, не замер качества
модели или производительности на плате.
