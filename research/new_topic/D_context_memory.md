# D. Контекст и память долгоживущего агента: одноплатник + внешняя LLM

*Заметка для новой темы ВКР «Разработка ИИ-агента для приложений граничного искусственного интеллекта» (согласована 06.10.2026). Направление 09.03.01 ИВТ.*
*Постановка после встречи с руководителем: агент-оркестратор работает на одноплатнике, рассуждает внешняя LLM (RouterAI, GPT «mini» разных версий), состояние оборудования агент получает через MCP-серверы, а инструменты — это датчики и исполнительные устройства. Оценивать надо работу системы во времени (несколько часов в день), а не надёжность.*
*Связанные заметки: `research/literature/G3_gap.md` (сжатие промпта и отбор инструментов, подробно), `_DIGEST.md` (MemGPT, MemoryOS, ClawVM, AIOS), R1 («Don't Break the Cache»), R7 (методика).*

## 0. Главное (коротко)

1. **Для нашей постановки контекст делится на четыре слоя, и у каждого своя скорость изменения:**
   - (1) статический префикс: system prompt и схемы MCP-инструментов;
   - (2) контекст пользователя: профиль, предпочтения, долговременные факты;
   - (3) контекст оборудования: реестр подключённых устройств и их текущее состояние;
   - (4) рабочая история текущего хода и сессии.

   Управлять контекстом — значит решать для каждого слоя три вопроса: где он хранится (на одноплатнике или в промпте), когда попадает в промпт и в каком месте промпта стоит. Место важно из-за префиксного кэша провайдера.
2. **Стоимость агента во времени определяют три механизма:**
   - рост истории: без компактизации суммарный вход растёт как O(n²) по числу вызовов;
   - доля входа, попавшая в кэш провайдера: чтение кэша стоит 0,1× у gpt-5-mini и 0,5× у gpt-4o-mini;
   - время жизни кэша относительно пауз между запросами пользователя.

   Третье в литературе почти не обсуждается, а для режима «несколько часов в день» оно главное. У «mini»-моделей до GPT-5.6 доступен только in_memory-кэш на ~5–10 минут бездействия: 24h-retention в документации OpenAI для них не указан. Значит, при редких запросах кэш работает только внутри одного хода агента.
3. **Системы памяти (MemGPT, Mem0, Zep, A-MEM, LightMem) экономят токены на чтении, но тратят их на запись.** По таблице LightMem на LongMemEval-S построение памяти у Mem0 и A-MEM обходится в 1,15–1,6 млн токенов против 35 тыс. у LightMem. Для мини-моделей полный контекст часто точнее: у Mem0 на LoCoMo full-context даёт 72,9% против 66,9%. Ответ на вопрос «нужна ли память» зависит от длины истории и тарифа, и его надо мерить, а не принимать по маркетинговым цифрам.
4. **Сложная суммаризация не всегда лучше простых эвристик.** Маскирование старых наблюдений вдвое снижает стоимость и не уступает LLM-суммаризации (Complexity Trap). Суммаризация ломает префиксный кэш и удлиняет траектории на 13–15%. Инкрементальные дописывания (ACE) дают 91,8% входа из кэша. Для одноплатника с внешней LLM это аргумент за детерминированные, дешёвые и кэш-дружественные политики на устройстве.
5. **Состояние оборудования нельзя класть снимком в начало промпта.** Каждое изменение датчика инвалидирует весь последующий кэш. По моему расчёту, при снимке в голове промпта стоимость суток примерно вдвое выше, чем при снимке в хвосте. Индустриальная практика (Home Assistant, MCP Resources, ros-mcp-server) — запрос по требованию: инструмент `GetLiveContext` / `resources/read` с `ttlMs`. Журнал событий хранится на устройстве (ReMEmbR: подписи, время и координаты в векторной БД), а в промпт попадает только реестр устройств, который меняется редко.
6. **Примеры руководителя.** PicoClaw (Go, <10 МБ ОЗУ по README, MIT, ~30 тыс. звёзд) и NanoClaw (TypeScript, контейнеры, Claude Agent SDK, ~31 тыс. звёзд) — облегчённые наследники OpenClaw. Память у всех трёх файловая: `MEMORY.md` плюс ежедневные заметки. PicoClaw суммаризирует историю при >20 сообщениях или >75% окна. Сводку, `MEMORY.md` и заметки за 3 дня он кладёт **в system prompt перед историей**. Поэтому каждая запись в память в течение дня меняет префикс и инвалидирует кэш всей последующей истории. Редкая суммаризация сама по себе обходится дёшево (§9.3). Научный разбор отказов памяти в этом семействе — ClawVM (EuroMLSys'26). Отсюда ниша ВКР: **измеренная политика контекста и памяти для Claw-подобного агента на одноплатнике** с метриками «токены, рубли, задержка и ресурсы за сутки работы».

## 2. Группа A. Архитектуры памяти агентов

### [A1] MemGPT и Letta — `packer2023memgpt` — [V-pre] / [V-doc]
- **Библ.:** Packer C., Wooders S., Lin K., Fang V., Patil S. G., Stoica I., Gonzalez J. E. MemGPT: Towards LLMs as Operating Systems. arXiv:2310.08560, 2023 (v2, 12.02.2024). Рецензируемого venue нет (Crossref его не находит). Проект: https://github.com/letta-ai/letta (Apache-2.0, ~25 тыс. звёзд, последний push 10.09.2026).
- **Что это.** «Виртуальная память» для LLM по аналогии с иерархией памяти ОС.
  - Основной контекст: system instructions (только чтение), working context (фиксированный блок с ключевыми фактами и предпочтениями пользователя) и FIFO-очередь сообщений с рекурсивной сводкой в начале.
  - Внешний контекст: recall storage (все сообщения) и archival storage (произвольные тексты).

  Данные между уровнями переносит сама LLM вызовами функций. Флаг `request_heartbeat` позволяет выстраивать вызовы в цепочку.
- **Числа из статьи.**
  - Порог «memory pressure» — 70% окна: в очередь вставляется системное предупреждение, чтобы модель успела сохранить важное.
  - При 100% окна вытесняется около 50% сообщений, а сводка пересчитывается рекурсивно.
  - Deep Memory Retrieval (MSC):

    | Модель | Без MemGPT | С MemGPT |
    |---|---:|---:|
    | GPT-3.5 Turbo | 38,7% | 66,9% |
    | GPT-4 | 32,1% | 92,5% |
    | GPT-4 Turbo | 35,3% | 93,4% |
- **Польза для ВКР.** Каноническая точка отсчёта и готовые пороги для baseline: «предупреждение на 70%, сброс на 100%». Минус для одноплатника и внешней LLM: модель сама управляет памятью, а значит, каждый перенос — дополнительный оплачиваемый вызов LLM. Рабочий блок в начале промпта меняется и при каждом изменении инвалидирует кэш. Важная для ВКР граница: где политика памяти исполняется — в LLM (MemGPT) или детерминированно на устройстве (PicoClaw, ClawVM).

### [A2] Generative Agents — `park2023generative` — [V]
- **Библ.:** Park J. S., O'Brien J. C., Cai C. J., Morris M. R., Liang P., Bernstein M. S. Generative Agents: Interactive Simulacra of Human Behavior // Proc. ACM UIST 2023. DOI 10.1145/3586183.3606763. arXiv:2304.03442.
- **Что это.** Поток памяти (memory stream): полный журнал наблюдений на естественном языке, извлечение по сумме трёх оценок и периодические рефлексии.
- **Числа (из HTML статьи).**
  - Recency — экспоненциальное затухание с коэффициентом 0,995 за игровой час с момента последнего извлечения.
  - Importance — оценка LLM по шкале 1–10.
  - Relevance — косинусная близость эмбеддингов.
  - Все три оценки нормируются min-max, веса α = 1.
  - Рефлексия запускается, когда сумма важности последних событий превышает 150; на практике это 2–3 раза за игровой день.
  - Симуляция 25 агентов на 2 игровых дня обошлась, по словам авторов, в «тысячи долларов» токенов и заняла несколько дней.
- **Польза для ВКР.** Формула извлечения «свежесть + важность + релевантность» напрямую переносится на **журнал событий оборудования**: событие датчика получает время, важность (по правилу или по порогу, без LLM) и эмбеддинг. Признание стоимости — честная мотивация темы «работа во времени»: без бюджета токенов долгоживущий агент дорог. Для одноплатника оценку важности стоит делать правилом, а не вызовом LLM на каждое событие.

### [A3] Reflexion — `shinn2023reflexion` — [V]
- **Библ.:** Shinn N., Cassano F., Berman E., Gopinath A., Narasimhan K., Yao S. Reflexion: Language Agents with Verbal Reinforcement Learning // NeurIPS 2023. arXiv:2303.11366.
- **Что это.** После попытки агент записывает вербальный вывод (self-reflection) в эпизодическую память и учитывает его в следующих попытках. Веса модели не меняются.
- **Числа.**
  - Память ограничена максимумом Ω сохранённых выводов, «обычно 1–3», чтобы уложиться в контекст (PDF, §3).
  - HumanEval pass@1 — 91% против 80% у GPT-4.
  - Прирост +22% на AlfWorld (134 окружения), +20% на HotPotQA, +11% на HumanEval.
- **Польза для ВКР.** Пример **жёсткого бюджета памяти**: хранится не история, а 1–3 вывода. Для агента с датчиками это «уроки» вида «датчик X врёт после перезагрузки», которые лежат в процедурной памяти и стоят константу токенов.

### [A4] CoALA — `sumers2024coala` — [V]
- **Библ.:** Sumers T. R., Yao S., Narasimhan K., Griffiths T. L. Cognitive Architectures for Language Agents // TMLR, 2024. arXiv:2309.02427 (v3 — camera-ready TMLR).
- **Что это.** Каркас описания языковых агентов. Рабочая память плюс три вида долговременной: эпизодическая, семантическая и процедурная. Действия делятся на внутренние (извлечение, рассуждение, обучение) и внешние (grounding).
- **Польза для ВКР.** Даёт терминологию главы 1 и раскладку наших слоёв.
  - Контекст оборудования: реестр — семантическая память, журнал событий — эпизодическая, текущее состояние — внешнее действие grounding (чтение датчика).
  - Контекст пользователя: профиль — семантическая память, история диалогов — эпизодическая.
  - System prompt и навыки — процедурная память.

### [A5] A-MEM — `xu2025amem` — [V]
- **Библ.:** Xu W., Liang Z., Mei K., Gao H., Tan J., Zhang Y. A-MEM: Agentic Memory for LLM Agents // NeurIPS 2025. arXiv:2502.12110 (v11). Код: https://github.com/WujiangXu/A-mem-sys (MIT, ~400 звёзд).
- **Что это.** Память в стиле Zettelkasten. Каждая запись — заметка с атрибутами (контекст, ключевые слова, теги). Связи между заметками строит LLM, и новые записи могут обновлять старые («эволюция памяти»).
- **Числа (из HTML).**
  - Около 1 200 токенов на операцию памяти против ~16 900 у LoCoMo-baseline и MemGPT (−85…93%).
  - Меньше 0,0003 $ на операцию.
  - Время операции: 5,4 с с GPT-4o-mini и 1,1 с с локальной Llama 3.2 1B на GPU.
  - Поиск при 1M записей — 3,70 мкс (по таблице масштабирования).
  - Проверено на Qwen2.5 1.5B/3B и Llama 3.2 1B/3B через Ollama.
  - LoCoMo, GPT-4o-mini: F1 в категории temporal 45,85 против 18,41 у baseline.
- **Польза для ВКР.** Одна из немногих работ, где память проверена на **малых локальных моделях**. Это аргумент, что операции записи в память (классификацию и выделение ключевых слов) можно отдать маленькой локальной модели или правилам на устройстве, а не внешней LLM. Оговорка: в независимом сравнении Mem0 (A6) у A-Mem J = 48,38% на LoCoMo. Результаты систем памяти сильно зависят от того, кто их меряет.

### [A6] Mem0 — `chhikara2025mem0` — [V]
- **Библ.:** Chhikara P., Khant D., Aryan S., Singh T., Yadav D. Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory // ECAI 2025, Frontiers in Artificial Intelligence and Applications. DOI 10.3233/FAIA251160. arXiv:2504.19413. Код: https://github.com/mem0ai/mem0 (Apache-2.0, ~66,7 тыс. звёзд).
- **Что это.** Двухфазный конвейер.
  - Извлечение: LLM получает пару сообщений и контекст и выделяет факты.
  - Обновление: для каждого факта LLM-резолвер выбирает операцию над похожими записями — ADD, UPDATE, DELETE или NOOP.

  Есть вариант Mem0g с графовой памятью. Все операции в статье выполняет GPT-4o-mini.
- **Числа (LoCoMo, таблица в HTML).**

  | Метод | J (LLM-судья) | Токенов контекста на запрос | Полная задержка p50 / p95, с |
  |---|---:|---:|---:|
  | Full-context | **72,90%** | 26 031 | 9,87 / 17,12 |
  | Mem0g | 68,44% | 3 616 | 1,09 / 2,59 |
  | Mem0 | 66,88% | 1 764 | 0,71 / 1,44 |
  | Zep | 65,99% | 3 911 | 1,29 / 2,93 |
  | лучший RAG | 60,97% | — | — |
  | OpenAI Memory | 52,90% | 4 437 | 0,47 / 0,89 |
  | A-Mem | 48,38% | 2 520 | 1,41 / 4,37 |

  Объём хранимой памяти на беседу: Mem0 ~7k, Mem0g ~14k, Zep >600k токенов. Аннотация: «на 91% ниже p95» и «более 90% экономии токенов» против full-context.
- **Польза для ВКР.**
  - (1) Модель **контекста пользователя**: факты-предпочтения с операциями ADD/UPDATE/DELETE естественно ложатся в профиль на устройстве (SQLite).
  - (2) Честный ориентир: при коротких историях (~26k токенов) full-context **точнее** всех систем памяти. Память окупается по стоимости и задержке, а не по точности.
  - (3) Цена записи: на каждую пару сообщений — минимум один вызов LLM на извлечение плюс вызовы на обновление. Для внешнего API это постоянная статья расходов, и её надо считать отдельно (см. A8).

### [A7] Zep / Graphiti — `rasmussen2025zep` — [V-pre]
- **Библ.:** Rasmussen P., Paliychuk P., Beauvais T., Ryan J., Chalef D. Zep: A Temporal Knowledge Graph Architecture for Agent Memory. arXiv:2501.13956, 2025. Код движка: https://github.com/getzep/graphiti (Apache-2.0, ~31,5 тыс. звёзд).
- **Что это.** Битемпоральный граф знаний. У рёбер четыре метки времени: когда факт записан и когда признан недействительным (время транзакции), с какого и по какой момент факт был истинен (время события). Три подграфа: эпизоды (сырые данные), сущности и связи, сообщества.
- **Числа (таблица 2, HTML).**

  | Модель | Метод | Точность | Задержка | Токенов контекста |
  |---|---|---:|---:|---:|
  | gpt-4o-mini | full-context | 55,4% | 31,3 с | 115k |
  | gpt-4o-mini | Zep | 63,8% | 3,20 с | 1,6k |
  | gpt-4o | full-context | 60,2% | 28,9 с | 115k |
  | gpt-4o | Zep | 71,2% | 2,58 с | 1,6k |

  DMR: 94,8% против 93,4% у MemGPT; полный диалог даёт 94,4%. На knowledge-update и single-session-assistant Zep хуже full-context (−3,4% и −9,1%).
- **Польза для ВКР.** Битемпоральная модель — готовая схема для **журнала состояния оборудования**: «датчик T1 показывал 24 °C с 10:00 до 10:20» плюс отдельная отметка, когда агент это узнал. Это прямой ответ на вопрос «что агент знал в момент решения», полезный для анализа трасс. Сам Zep с графовой БД для одноплатника тяжёл. Кроме того, Mem0 и Zep — вендорские бенчмарки с взаимно противоречивыми выводами (A6 против A7), поэтому их цифры надо перепроверять.

### [A8] LightMem — `fang2026lightmem` — [V]; Sleep-time Compute — `lin2025sleeptime` — [V-pre]
- **Библ.:**
  - Fang J., Deng X., Xu H., Jiang Z., Tang Y., Xu Z., Deng S., Yao Y., et al. LightMem: Lightweight and Efficient Memory-Augmented Generation // ICLR 2026. arXiv:2510.18866. Код: https://github.com/zjunlp/LightMem.
  - Lin K., Snell C., Wang Y., Packer C., Wooders S., Stoica I., Gonzalez J. E. Sleep-time Compute: Beyond Inference Scaling at Test-time. arXiv:2504.13171, 2025 (группа Letta и UC Berkeley).
- **Что это.** Три стадии по модели Аткинсона–Шиффрина.
  - Сенсорная память: предсжатие входа с помощью LLMLingua-2 (буфер 512 токенов) и группировка по темам.
  - Кратковременная память: тематическая консолидация.
  - Долговременная память: «мягкие» обновления онлайн плюс **офлайн-реорганизация во время простоя** (sleep-time update).

  Sleep-time Compute обобщает идею: модель заранее «думает» над контекстом до прихода вопроса, и это сокращает test-time вычисления примерно в 5 раз. Если делить предвычисления между связанными запросами, стоимость на запрос падает в 2,5 раза.
- **Числа (LongMemEval-S, GPT-4o-mini, таблица HTML).**

  | Метод | Точность | Токенов на построение памяти, всего | Вызовов API |
  |---|---:|---:|---:|
  | FullText | 56,80% | — | — |
  | A-MEM | 62,60% | 1 605,81 тыс. | 986,55 |
  | Mem0 | 53,61% | 1 152,62 тыс. | 811,57 |
  | MemoryOS | 44,80% | 2 991,75 тыс. | — |
  | LightMem (r = 0,6, th = 256) | **67,78%** | **35,11 тыс.** | **30,47** |

  Аннотация: точность до +7,7% / +29,3% (LongMemEval / LoCoMo), токенов до 38× / 20,9× меньше, вызовов API до 30× / 55,5× меньше. Только по онлайн-части — до 106× / 117× по токенам.
- **Польза для ВКР — высокая.**
  - (1) Доказывает, что **цена записи в память** у популярных систем — миллионы токенов, то есть главная статья расходов. Для режима «часы в день» это ключевой фактор.
  - (2) «Сон» прямо ложится на суточный цикл одноплатника: ночью устройство простаивает, и консолидацию памяти можно делать по дешёвому Batch/Flex-тарифу (у OpenAI это ~50% от Standard, E2) или локально.
  - (3) Предсжатие LLMLingua-2 — кандидат на исполнение на устройстве, но цена компрессора на одноплатнике не измерена (см. G3, CORE).

## 3. Группа B. Бенчмарки памяти и деградации длинного контекста

### [B1] LoCoMo — `maharana2024locomo` — [V]
- **Библ.:** Maharana A., Lee D.-H., Tulyakov S., Bansal M., Barbieri F., Fang Y. Evaluating Very Long-Term Conversational Memory of LLM Agents // Proc. ACL 2024 (Long). DOI 10.18653/v1/2024.acl-long.747. arXiv:2402.17753. Данные: https://github.com/snap-research/locomo (лицензия в API не определена — NOASSERTION, проверить).
- **Факты.**
  - Беседы в среднем по 300 ходов и ~9k токенов, до 35 сессий; сгенерированы агентами по персонам и графам событий, проверены людьми.
  - Задачи: QA (single-hop, multi-hop, temporal, open-domain, adversarial), суммаризация событий, мультимодальный диалог.
  - Публичный релиз — **10 бесед** (`locomo10.json`), отобранных из исходных 50.
- **Польза.** Стандартный бенчмарк, на котором меряются Mem0, A-MEM, MemoryOS и LightMem. Для ВКР он подходит как **контрольный** набор по памяти пользователя. Минус: беседы короткие (~26k токенов полного контекста, по данным Mem0), так что full-context их ещё «вытягивает».

### [B2] LongMemEval — `wu2025longmemeval` — [V]
- **Библ.:** Wu D., Wang H., Yu W., Zhang Y., Chang K.-W., Yu D. LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory // ICLR 2025. arXiv:2410.10813. Код и данные: https://github.com/xiaowu0162/LongMemEval (MIT, ~1,1 тыс. звёзд).
- **Факты.**
  - 500 вопросов, пять способностей: извлечение информации, многосессионное рассуждение, временное рассуждение, обновление знаний, отказ от ответа.
  - Конфигурации: S — около 115k токенов на задачу, M — 500 сессий, около 1,5M токенов.
  - GPT-4o: 0,870 при oracle-контексте против 0,606 на S (−30,3%). Llama 3.1 8B: 0,710 → 0,454.
  - Коммерческие ChatGPT и Coze теряют 37% и 64% на упрощённой версии (97 вопросов, 3–6 сессий).
  - Рекомендации по устройству памяти: разбивка на раунды, расширение ключей фактами (+9,4% recall@k, +5,4% точности), явные метки времени в ключах (+6,8…11,3% recall на временных вопросах), чтение в формате Chain-of-Note с JSON (до +10 п.п.).
- **Польза.** Даёт декомпозицию «индексация → извлечение → чтение» как структуру главы о памяти. Вопросы **knowledge update** и **temporal reasoning** — ровно то, что нужно для состояния оборудования («какая температура была до проветривания?»). Конфигурацию S (115k) стоит урезать до подмножества, чтобы прогоны через API были дешёвыми.

### [B3] PrefEval — `zhao2025prefeval` — [V]
- **Библ.:** Zhao S., Hong M., Liu Y., Hazarika D., Lin K. Do LLMs Recognize Your Preferences? Evaluating Personalized Preference Following in LLMs // ICLR 2025 (oral). arXiv:2502.09597. Данные: https://prefeval.github.io/.
- **Факты.**
  - 3 000 пар «предпочтение – запрос» по 20 темам; предпочтения бывают явные и неявные; контекст до 100k токенов; 10 моделей.
  - В zero-shot точность следования предпочтениям падает **ниже 10% уже на 10 ходах (~3k токенов)** у большинства моделей.
  - RAG и продвинутые промпты помогают, но деградация с длиной сохраняется.
- **Польза.** Обосновывает **явный профиль пользователя**: короткий блок предпочтений вместо надежды на то, что модель «вспомнит» реплику из истории. Блок кладётся в стабильную часть промпта и меняется редко. Подмножество PrefEval пригодно для теста «помнит ли агент, что пользователь просил не включать свет после 23:00».

### [B4] Lost in the Middle — `liu2024lost` — [V]; Context Rot — `hong2025contextrot` — [V-doc]
- **Библ.:**
  - Liu N. F., Lin K., Hewitt J., Paranjape A., Bevilacqua M., Petroni F., Liang P. Lost in the Middle: How Language Models Use Long Contexts // TACL. 2024. Vol. 12. DOI 10.1162/tacl_a_00638. arXiv:2307.03172.
  - Hong K., Troynikov A., Huber J. Context Rot: How Increasing Input Tokens Impacts LLM Performance. Chroma Technical Report, 14.07.2025. https://www.trychroma.com/research/context-rot; код: https://github.com/chroma-core/context-rot (MIT).
- **Факты.**
  - Lost in the Middle: зависимость от позиции имеет U-образную форму. В multi-document QA с 20–30 документами, когда нужный документ стоит в середине, GPT-3.5-Turbo отвечает хуже, чем вообще без документов (closed-book 56,1%).
  - Context Rot: 18 моделей (в том числе Claude 4, GPT-4.1, Gemini 2.5, Qwen3). Качество падает с ростом длины входа даже на простых задачах. Сильнее падает при низкой семантической близости вопроса и «иголки», на дистракторах и, неожиданно, на связном «стоге» по сравнению с перемешанным. На LongMemEval сфокусированный промпт (~300 токенов) заметно лучше полного (~113k).
- **Польза.** Длинный контекст стоит денег и вдобавок ухудшает ответ. Это аргумент за компактизацию и состояние по запросу даже там, где кэш делает токены дешёвыми. Позиционный эффект — аргумент ставить свежий снимок оборудования и текущий запрос в **конец** промпта. Это совпадает с требованием кэша (E1, E2).

## 4. Группа C. Сжатие и компактизация истории

*Методы сжатия промпта (LLMLingua, LongLLMLingua, LLMLingua-2) подробно разобраны в G3 [A1–A3]. Главное там: проверены на прозе, а не на JSON; компрессор LLMLingua — 7B LM; LLMLingua сжимает до 20× (EMNLP 2023, arXiv:2310.05736). Здесь — сжатие **истории агента**.*

### [C1] ACON — `kang2026acon` — [V]
- **Библ.:** Kang M., Chen W.-N., Han D., Inan H. A., Wutschitz L., Chen Y., Sim R., Rajmohan S. ACON: Optimizing Context Compression for Long-horizon LLM Agents // ICML 2026. arXiv:2510.00615 (v3). Код: https://github.com/microsoft/acon (MIT).
- **Что это.** Сжатие истории и наблюдений по инструкции-«guideline». Инструкция оптимизируется в пространстве естественного языка по разбору провалов (оптимизатор — o3), затем компрессор дистиллируется в малую модель.
- **Числа (HTML).**
  - Пороги: история сжимается при >4096 токенах (2048 для 8-objective QA), наблюдение — при >1024 (512 / 400). Последняя пара «действие – наблюдение» сохраняется без изменений.
  - AppWorld (gpt-4.1): пик 9,93k → 7,33k токенов (−26%) при точности 56,0% → 56,5%. По аннотации пик снижается на 26–54% в зависимости от задачи.
  - Дистиллированный Qwen3-14B снижает стоимость сжатия на 99,1% (до 0,0004 $).
  - Цена задержки: медиана на задачу 73,24 с без сжатия, 87,68 с со сжатием истории и 101,92 с со сжатием наблюдений. API-стоимость при этом 0,331 → 0,285 / 0,272 $.
  - Малые LM как агенты — до +46%.
- **Польза.** Количественно показывает **компромисс «дешевле, но медленнее»**: каждый вызов компрессора — лишний сетевой круг. Для одноплатника с внешней LLM это прямо входит в метрику «задержка ответа пользователю». Пороги 4096 и 1024 — готовые значения для baseline.

### [C2] ACE — `zhang2026ace` — [V]
- **Библ.:** Zhang Q., Hu C., Upasani S., Ma B., Hong F., Kamanuru V., Rainton J., Wu C., et al. Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models // ICLR 2026. arXiv:2510.04618 (v3).
- **Что это.** Контекст как растущий «playbook» из пронумерованных пунктов со счётчиками helpful/harmful. Обновляется инкрементальными дельтами (Generator → Reflector → Curator), без полной перезаписи. Дубликаты удаляются по эмбеддингам (grow-and-refine).
- **Числа (HTML).**
  - **Коллапс контекста** при итеративной перезаписи (Dynamic Cheatsheet, AppWorld): на шаге 60 контекст 18 282 токена и точность 66,7%; на шаге 61 он схлопнулся до 122 токенов, точность 57,1% — хуже baseline 63,7%.
  - +10,6% на агентных задачах, +8,6% на финансовых.
  - Против GEPA (офлайн, AppWorld): задержка адаптации −82,3%, rollouts −75,1%. Против DC (онлайн, FiNER): −91,5% задержки и −83,6% стоимости.
  - **Кэш:** с OpenAI API (GPT-5.1) 91,8% входных токенов ACE обслуживаются из кэша. Это снижает счёт за вход на 82,6% относительно «сырых» токенов (§4.7).
- **Польза — высокая.**
  - (1) Риск, который нужно учесть: **суммаризация-перезапись может уничтожить контекст** за один шаг.
  - (2) Ключевой для стоимости вывод: **append-only контекст дружественен префиксному кэшу**. «Длиннее, но кэшируемо» бывает дешевле, чем «короче, но каждый раз новое».

  Для профиля пользователя и «уроков» оборудования это аргумент за инкрементальные пункты с идентификаторами вместо регулярной перезаписи сводки.

### [C3] The Complexity Trap — `lindenbauer2025complexity` — [V]
- **Библ.:** Lindenbauer T., Slinko I., Felder L., Bogomolov E., Zharov Y. The Complexity Trap: Simple Observation Masking Is as Efficient as LLM Summarization for Agent Context Management // 4th DL4C Workshop @ NeurIPS 2025. arXiv:2508.21433 (v3). Код: https://github.com/JetBrains-Research/the-complexity-trap.
- **Что это.** Систематическое сравнение на SWE-agent и SWE-bench Verified: пять конфигураций моделей, лимит 250 ходов, плюс проверка на OpenHands. Стратегии: сырой агент, маскирование наблюдений (окно M = 10 последних ходов без изменений), LLM-суммаризация (21 ход за раз, хвост 10 ходов) и гибрид.
- **Числа (HTML).**
  - Маскирование **вдвое снижает стоимость** относительно сырого агента и не уступает суммаризации по solve rate. С Qwen3-Coder 480B оно на 52% дешевле и даёт +2,6% solve rate.
  - Гибрид ещё на 7% дешевле маскирования и на 11% дешевле суммаризации.
  - Суммаризация удлиняет траектории на 13–15% («trajectory elongation»).
  - Вызовы суммаризатора — до 7,2% стоимости. Каждый такой вызов обрабатывает уникальную последовательность, поэтому кэш переиспользуется только для его system prompt.
- **Польза — высокая.** Главный аргумент за **детерминированные политики на устройстве**: маскирование не требует вызова LLM, ничего не стоит и не нагружает одноплатник. Ещё одна находка — побочный эффект суммаризации на длину траектории. В ВКР его надо мерить в токенах **за сутки**, а не на шаг.

### [C4] AgentDiet — `xiao2026agentdiet` — [V]
- **Библ.:** Xiao Y.-A., Gao P., Peng C., Xiong Y. Reducing Cost of LLM Agents with Trajectory Reduction // FSE 2026. DOI 10.1145/3797084. arXiv:2509.23586.
- **Факты.** Анализ траекторий показывает, что в них много бесполезной, избыточной и устаревшей («expired») информации. AgentDiet удаляет её во время исполнения: входные токены −39,9…59,7%, полная стоимость −21,1…35,9% при той же эффективности (две LLM, два бенчмарка).
- **Польза.** Термин «устаревшая информация» прямо подходит к **показаниям датчиков**: старый снимок состояния после нового — мусор, и его можно удалить без LLM. Это рецензируемый (FSE) источник для тезиса «агентные траектории расточительны».

### [C5] Anthropic. Effective context engineering for AI agents — [V-doc]
- **Библ.:** Rajasekaran P., Dixon E., Ryan C., Hadfield J. Effective context engineering for AI agents. Anthropic Engineering Blog, 29.09.2025. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **Факты.** Определение context engineering: отбор и поддержание оптимального набора токенов при инференсе. Понятия «context rot» и «attention budget». Три техники для длинных задач:
  - **компактизация** — «самая лёгкая» форма: очистка старых результатов инструментов;
  - **структурированные внешние заметки** (NOTES.md, CLAUDE.md);
  - **субагенты**, которые возвращают сжатую сводку на 1 000–2 000 токенов.

  Подход just-in-time: в контексте лежат лёгкие идентификаторы (пути, запросы), а данные подгружаются инструментами по мере надобности.
- **Польза.** Индустриальная формулировка той же схемы, что у OpenClaw и PicoClaw: файловая память, компактизация, подгрузка по требованию. Цитировать только как свидетельство практики. Для оборудования just-in-time означает: в промпте держать идентификаторы устройств, а состояние читать инструментом.

## 5. Группа D. Отбор инструментов (кратко, подробно в G3)

### [D1] RAG-MCP — `gan2025ragmcp`; ScaleMCP — `lumer2025scalemcp`; Toolshed — `lumer2024toolshed` — [V-pre]
- **Библ.:**
  - Gan T., Sun Q. RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation. arXiv:2505.03275, 2025.
  - Lumer E., Gulati A., Subbiah V. K., Basavaraju P. H., Burke J. A. ScaleMCP: Dynamic and Auto-Synchronizing Model Context Protocol Tools for LLM Agents. arXiv:2505.06416, 2025.
  - Lumer E., Subbiah V. K., Burke J. A., Basavaraju P. H., Huber A. Toolshed: Scale Tool-Equipped Agents with Advanced RAG-Tool Fusion and Tool Knowledge Bases. arXiv:2410.14594, 2024.
- **Факты.**
  - RAG-MCP: точность выбора 13,62% → 43,13%, промпт 2 133,84 → 1 084 токенов (−49,2% по таблице при «более 50%» в аннотации); 20 прогонов на baseline. Подробно — G3 [C1].
  - ScaleMCP: агент сам добавляет инструменты в «память» через MCP-retriever, хранилище синхронизируется с MCP-серверами (CRUD), источник истины — сервер. Оценка на 5 000 финансовых MCP-серверов.
  - Toolshed: +46/56/47% Recall@5 (абс.) на ToolE single-tool, ToolE multi-tool и Seal-Tools.
- **Польза.** У одноплатника с датчиками инструментов немного (единицы–десятки), и отбор здесь второстепенен. Но **конфликт с кэшем** реален: смена набора инструментов инвалидирует кэш (E2 прямо называет `tools`). PicoClaw уже использует «скрытую библиотеку» с поиском инструментов, где найденные инструменты разблокируются на следующий ход (G1). Вывод для ВКР: держать каталог стабильным в префиксе и не делать динамический отбор без необходимости. Если отбор нужен — делать его «отложенной загрузкой» в хвост, как Anthropic Tool Search (G3 [D5]).

## 6. Группа E. Кэширование промптов и цены (ядро метрики «стоимость во времени»)

### [E1] Don't Break the Cache — `lumer2026dontbreak` — [V-pre]
- **Библ.:** Lumer E., Nizar F., Jangiti A., Frank K., Gulati A., Phadate M., Subbiah V. K. Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks. arXiv:2601.06007 (v2, 31.01.2026).
- **Факты.**
  - Три провайдера (OpenAI, Anthropic, Google) и три стратегии: кэш всего контекста, только system prompt, кэш без динамических результатов инструментов.
  - DeepResearch Bench, более 500 сессий, system prompt 10 000 токенов.
  - Кэширование снижает стоимость API на **41–80%** и TTFT на **13–31%**.

## 7. Группа F. Контекст оборудования

### [F1] MCP Resources, спецификация 2026-07-28 — [V-doc]
- **Источник:** Model Context Protocol Specification, ревизия 2026-07-28, раздел Server / Resources. https://modelcontextprotocol.io/specification/latest/server/resources
- **Факты.**
  - Ресурсы «application-driven»: что включать в контекст, решает хост, а не модель (в отличие от model-controlled инструментов).
  - Методы `resources/list`, `resources/read`, `resources/templates/list` (URI-шаблоны RFC 6570).
  - Подписка через `subscriptions/listen` с фильтром `resourceSubscriptions` и уведомлениями `notifications/resources/updated`; `notifications/resources/list_changed` при изменении набора ресурсов.
  - Ответы содержат `ttlMs` и `cacheScope` (утилита caching).
  - Аннотации: `audience`, `priority` (0..1) и `lastModified` (ISO 8601).
- **Польза.** Готовая модель для слоя оборудования. Датчик — ресурс `sensor://room1/temp` с `ttlMs` (свежесть). Камера — ресурс с бинарным содержимым или подписью. Список устройств — `resources/list` с `list_changed` (горячее подключение). Хост-оркестратор на одноплатнике сам решает, когда читать ресурс и класть его в промпт, — в этом и состоит **политика контекста оборудования**, которую ВКР может предложить и измерить. `priority` и `lastModified` — готовые входы для формулы отбора в стиле Generative Agents (A2).

### [F2] Home Assistant MCP Server и `GetLiveContext` — [V-doc]
- **Источник:** Home Assistant. Model Context Protocol Server integration. https://www.home-assistant.io/integrations/mcp_server/ (снято 06.10.2026).
- **Факты.**
  - Интеграция появилась в Home Assistant 2025.2; транспорт Streamable HTTP (stateless).
  - LLM получает только сущности, которые пользователь явно открыл (exposed entities).
  - Текущее состояние дома выдаёт инструмент `GetLiveContext`. Тот же снимок доступен как read-only MCP-ресурс `homeassistant://assist/context-snapshot` (для отладки и объяснений).
  - Sampling и уведомления **не поддерживаются**.
  - По трекеру issues (home-assistant/core #182006): с 2026.9 имена инструментов получили пространства имён, и встроенный промпт ссылался на старое имя `GetLiveContext`. Это пример хрупкости связки «промпт ↔ имена инструментов».
- **Польза.** Крупнейшая открытая платформа умного дома выбрала **состояние по запросу (pull)**, а не снимок в промпте и не push-уведомления. Это промышленный baseline для ВКР. Сравнение «pull через инструмент» против «снимок в хвосте промпта» против «подписка + журнал» — естественный эксперимент.

### [F3] SAGE — `rivkin2023sage` — [V-pre]
- **Библ.:** Rivkin D., Hogan F., Feriani A., Konar A., Sigal A., Liu S., Dudek G. SAGE: Smart home Agent with Grounded Execution. arXiv:2311.00772 (v2, 2024). Samsung AI Center Montreal.
- **Факты.** LLM управляет последовательностью дискретных действий: получить информацию, спросить пользователя, изменить состояние устройства. Решения строятся деревом промптов. В набор действий входят:
  - управление предпочтениями пользователя;
  - чтение API устройства без кода под конкретное устройство;
  - **постоянный мониторинг состояния** («напомни выбросить молоко, когда открою холодильник»);
  - ссылки на устройства по фото комнаты.

  Бенчмарк из 50 задач: 75% успеха против 30% у LLM-baseline.
- **Польза.** Близкий прототип нашей постановки с обоими слоями: пользователь (предпочтения) и оборудование (состояние, мониторинг). Мониторинг — пример задачи, где нужен **триггер на устройстве**, а не опрос через LLM: условие проверяется локально, LLM вызывается только при срабатывании. Похожая работа — Sasha (King E. et al., IMWUT 2024, DOI 10.1145/3643505): неточно заданные цели в умном доме.

### [F4] ReMEmbR — `anwar2025remembr` — [V]; ros-mcp-server, ROSA — [V-doc]
- **Библ.:** Anwar A., Welsh J., Biswas J., Pouya S., Chang Y. ReMEmbR: Building and Reasoning Over Long-Horizon Spatio-Temporal Memory for Robot Navigation // IEEE ICRA 2025. DOI 10.1109/ICRA55743.2025.11127706. arXiv:2409.13682. Код: https://github.com/NVIDIA-AI-IOT/remembr.
- **Факты.**
  - Фаза построения памяти: каждые t секунд VILA делает подпись к видео (в экспериментах VILA1.5-13b, 6 кадров на 3 с, то есть 2 FPS). Эмбеддинг подписи, позиция и время сохраняются в векторную БД.
  - Фаза запроса: LLM-агент делает до 3 шагов извлечения по тексту, времени и позиции.
  - Мотивация: роботы работают «часами», а прежние подходы держат 1–2 минуты видео.
  - Развёртывание: робот Nova Carter. Построение памяти идёт на Jetson Orin 32GB (квантованная VILA-3b, Whisper, Nav2, векторный поиск — всё на борту), LLM — GPT-4o через API. Это ровно схема «граничное устройство + внешняя LLM».
  - Бенчмарк NaVQA: пространственные, временные и описательные вопросы.
- **Связанные проекты.**
  - robotmcp/ros-mcp-server (Apache-2.0, ~1,5 тыс. звёзд): мост MCP ↔ ROS через rosbridge. Публикация и подписка на топики, сервисы и actions, обнаружение типов сообщений.
  - NASA JPL ROSA (Royce R. et al., IEEE Aerospace Conf. 2025, arXiv:2410.06472; https://github.com/nasa-jpl/rosa, Apache-2.0): агент для ROS1/ROS2 на естественном языке.
- **Польза — высокая.** Образец **журнала событий оборудования** для камер: сырые кадры на устройстве не хранятся, хранятся подписи с временем и позицией. LLM получает только отобранное. Для ВКР с камерой на одноплатнике это базовая архитектура слоя «эпизодическая память оборудования». Важно, что вычислительно тяжёлая подпись видео там делается на Jetson, а не на Raspberry Pi-классе. Для одноплатника нужна либо очень лёгкая модель, либо триггер (детектор движения) и отправка кадра во внешнюю VLM по событию.

## 9. Рост токенов и стоимости во времени: что известно и мой расчёт

### 9.1. Что известно из источников
- Рост контекста в агентных траекториях признают все работы группы C: ACON называет его «unbounded context growth», AgentDiet — «ever-growing trajectories», Complexity Trap — «iterative context expansion». Количественно:
  - маскирование и суммаризация снижают стоимость SWE-агента более чем на 50% (C3);
  - удаление мусора даёт −21…36% стоимости (C4);
  - кэш даёт −41…80% стоимости API (E1);
  - append-only контекст ACE даёт 91,8% входа из кэша (C2).
- **Чего нет в литературе:** измерений в режиме **«агент работает часами, запросы приходят редко, кэш успевает истечь»**. Все найденные измерения сделаны на непрерывных сессиях — SWE-bench, AppWorld, DeepResearch Bench. Работ о суточном профиле стоимости встроенного или IoT-агента с внешней LLM я не нашёл.

### 9.2. Простая модель (расчёт)
Пусть каждый вызов LLM получает статический префикс S и историю, которая растёт на Δ токенов за вызов. Тогда вход i-го вызова ≈ S + iΔ, а суммарный вход за n вызовов ≈ nS + Δn²/2, то есть **квадратичный рост**. Стоимость входа ≈ p_in · Σ · [(1 − c) + c·d], где c — доля кэш-попаданий, d — множитель цены кэша (0,1 у gpt-5-mini, 0,5 у gpt-4o-mini). Кэш снижает константу, но не порядок роста. Компактизация ограничивает историю и делает рост линейным.

### 9.3. Численная иллюстрация (расчёт, `D_artifacts/cost_model.py`)
**Сценарий:**
- 8 часов работы, 40 запросов в сутки, пауза 12 мин;
- 3 вызова LLM на запрос (2 инструмента + ответ);
- S = 4 000 токенов (system + схемы MCP);
- профиль 300 токенов, снимок оборудования 600, реплика 60, выход 150 на вызов, результат инструмента 300.

Чувствительность:
- **200 запросов в сутки, кэш ≥30 мин:** полная история — 69,5 млн токенов (рост квадратичный), 2,52 $ (278 руб.) даже при 96% кэша. Сводка или окно — 5,7–7,8 млн, 0,53–0,55 $ (59–60 руб.). Разница — в 4,7 раза.
- **10 запросов в сутки:** все стратегии дают около 0,04 $ (около 4,2–4,6 руб.). Управление историей не важно, доминирует статический префикс.
- **gpt-4o-mini (кэш 0,5×):** полная история со снимком в хвосте — 0,27 $ против 0,13 $ у окна со сбросом блоком. При неглубокой скидке компактизация выигрывает больше.

**Выводы расчёта** (проверить экспериментально):
- (1) На стоимость сильнее всего влияют **место динамических данных в промпте** и **соотношение TTL кэша и пауз**, а не изощрённость сжатия.
- (2) При малой нагрузке оптимизировать историю бессмысленно, при большой — обязательно.
- (3) Абсолютные суммы малы (рубли и десятки рублей в сутки). Значит, в ВКР стоимость надо показывать вместе с задержкой и ресурсами одноплатника, а не одну.
- (4) Модель не учитывает вызовы записи в память (A6, A8) и деградацию точности (B2–B4). Их надо добавить в эксперимент.

## 10. Представление состояния оборудования: варианты

| Вариант | Как | Свежесть | Токены | Влияние на кэш | Нагрузка на одноплатник | Источники |
|---|---|---|---|---|---|---|
| **Снимок в промпте** («цифровой двойник» целиком) | весь двойник сериализуется в каждый вызов | на момент вызова | O(число устройств) на **каждый** вызов | в начале — ломает весь кэш при любом изменении; в хвосте — теряются только его токены | мала | наивная реализация; позиционный эффект — B4; правило кэша — E1, E2; расчёт §9.3 |
| **Запрос по требованию** (pull) | инструмент `get_state(device)` / `resources/read` с `ttlMs` | точная | только запрошенное, но +1 вызов LLM на чтение | не ломает префикс; результат уходит в хвост | мала | HA `GetLiveContext`, MCP Resources, SAGE, ros-mcp-server |
| **Журнал событий** (event log) | события с временем и важностью — в SQLite или векторную БД на устройстве; в контекст — top-k или сводка | историческая | ограничены k | извлечённое — в хвост | средняя (эмбеддинги, поиск) | Generative Agents (оценка), ReMEmbR, Zep (битемпоральность), LongMemEval (метки времени) |
| **Подписка и триггеры** (push) | `notifications/resources/updated`, топики ROS; условие проверяется на устройстве, LLM будится по событию | реактивная | 0 при отсутствии событий | не участвует, пока не сработало | мала–средняя | MCP subscriptions, SAGE (мониторинг), ROS 2 |
| **Реестр устройств** | список: что подключено, типы, возможности, единицы измерения | меняется редко (`list_changed`) | константа | кладётся в стабильный префикс | мала | MCP `resources/list` / `tools/list`, CoALA (семантическая память) |

**Рекомендуемая гибридная схема** (гипотеза для ВКР):
1. **Реестр устройств** лежит в кэшируемом префиксе рядом со схемами инструментов и пересобирается только по `list_changed`.
2. **Текущее состояние** читается по требованию через инструмент или ресурс. Опционально в хвост добавляется сжатая «дельта с прошлого хода» — только изменившиеся значения (идея «expired information» из AgentDiet).
3. **События** пишутся в журнал на устройстве: время, значение, важность по правилу. Эмбеддинги — только для текстовых описаний, например подписей камеры. В контекст попадает top-k с весами в духе Generative Agents.
4. **Мониторинг** — локальные триггеры; LLM вызывается только при срабатывании. Это прямо снижает токены за сутки.

## 11. Контекст пользователя: что брать
- **Профиль и предпочтения** — явный короткий блок фактов с операциями ADD/UPDATE/DELETE (A6). Обновлять инкрементально, пунктами с идентификаторами (A6, C2), а не перезаписью сводки (риск коллапса, C2). Место — стабильная часть промпта после схем; блок меняется редко, поэтому кэш почти не страдает. Обоснование необходимости — PrefEval (B3): без явного профиля предпочтения теряются за ~10 ходов.
- **История диалогов** — файловая или SQLite-память на устройстве (`MEMORY.md` и ежедневные заметки, как в Claw-семействе) плюс поиск по требованию (`memory_search`). Перед компактизацией — «flush» важного (OpenClaw), с валидацией (ClawVM).
- **Консолидация** — в простое («сон», A8), по дешёвому Batch-тарифу или локально.

## 12. Выводы
1. Литература по памяти агентов (MemGPT → Generative Agents → Mem0/Zep/A-MEM → LightMem) оптимизирует **точность ответа о прошлом** и токены **на запрос**. Стоимость **записи** и суточный профиль затрат почти не рассматриваются. Единственная работа с явным учётом записи — LightMem: у Mem0 и A-MEM миллионы токенов на построение памяти.
2. На коротких историях full-context точнее систем памяти (Mem0 на LoCoMo: 72,9% против 66,9%). Память нужна ради стоимости и задержки, и выигрыш появляется только после некоторой длины истории.
3. Простые детерминированные политики — маскирование наблюдений и удаление устаревшего — не хуже LLM-суммаризации и дешевле её (C3, C4). Суммаризация ломает кэш и удлиняет траектории. Для одноплатника с внешней LLM это аргумент за политики, которые исполняются **на устройстве без вызова LLM**.
4. Префиксный кэш провайдера — главный рычаг стоимости (−41…80%, E1; 91,8% входа из кэша, C2). Но он чувствителен к месту динамических данных и к TTL. У mini-моделей OpenAI до GPT-5.6 доступен только ~5–10-минутный in_memory-кэш. У GPT-5.6+ запись не менее 30 минут, но платная (1,25×).
5. RouterAI тарифицирует чтение кэша (`input_cache_read`) в рублях с теми же пропорциями скидок, что OpenAI. Это делает кэш-осознанную политику измеримой и в рублях — если `usage.cached_tokens` действительно возвращается (проверить с ключом).
6. Для оборудования промышленная практика (Home Assistant, MCP, ROS-MCP) — состояние по запросу. Научные работы с долговременной памятью оборудования (ReMEmbR) строят журнал событий на устройстве с подписями, временем и позицией. Систематического сравнения «снимок / pull / журнал / push» по токенам, свежести и ресурсам я не нашёл.
7. Claw-агенты из примеров руководителя управляют контекстом эвристически и кэш-неосознанно: PicoClaw держит изменяемую память в system prompt перед историей и оценивает токены как 2,5 символа на токен. ClawVM формализует корректность, но не стоимость во времени.

## 13. Открытые проблемы
1. **Кэш при разреженной нагрузке.** Как политика контекста должна учитывать TTL кэша провайдера при паузах между запросами, сравнимых с TTL? Варианты: «прогрев» кэша дешёвым запросом против потери кэша; группировка событий; выбор модели с 30-минутным TTL и платной записью. Не измерено.
2. **Цена записи в память в суточном режиме.** Сколько токенов и рублей в сутки уходит на извлечение фактов (Mem0-подобная запись) по сравнению с экономией на чтении, при каком числе запросов в день память окупается.
3. **Сравнение представлений состояния оборудования** (снимок / pull / журнал / push) по токенам, свежести, задержке ответа и нагрузке на одноплатник. Систематических работ нет.
4. **Компактизация без LLM на устройстве** (маскирование, удаление устаревших показаний, окна с блочным сбросом) против LLM-суммаризации — на агенте с датчиками, а не на SWE-задачах. Оценка эффекта на точность: knowledge-update и temporal вопросы.
5. **Оценка токенов на устройстве.** PicoClaw использует эвристику ~2,5 символа на токен. Ошибка такой оценки для русского текста и JSON (MCP) по сравнению с реальным токенизатором o200k не измерена. Ошибка ведёт к лишним аварийным сжатиям или переполнению.
6. **Вендорские бенчмарки памяти противоречат друг другу** (Mem0 против Zep против LightMem). Нужна независимая перепроверка в одной обвязке с фиксированной моделью.
7. **RouterAI как посредник.** Сохраняется ли маршрутизация к одному кэшу (`prompt_cache_key`), возвращаются ли `cached_tokens`, какие добавочные задержки и трафик дают российский шлюз и сеть одноплатника.
8. **Корректность при компактизации** (ClawVM) в сочетании со стоимостью: какие «страницы» — профиль, реестр устройств, последний снимок — должны быть неприкосновенны под бюджетом токенов.

## 14. Следствия для постановки, архитектуры и экспериментов ВКР

**Постановка (уточнение темы).** «Разработка ИИ-агента для приложений граничного ИИ» конкретизируется так: оркестратор на одноплатнике (Go или Python) с внешней LLM через OpenAI-совместимый API (RouterAI) и MCP-доступом к датчикам и приводам. Вклад — **подсистема управления контекстом и памятью** с явными слоями «пользователь» и «оборудование» и политиками, которые минимизируют суточную стоимость и задержку при заданном качестве. Метрика — не надёжность, а интегральные показатели за сутки работы:
- токены вход / кэш / выход;
- рубли по тарифу RouterAI;
- p50/p95 задержки ответа пользователю;
- число вызовов LLM;
- трафик;
- CPU, ОЗУ и энергия одноплатника;
- точность на контрольных вопросах.

**Архитектура (минимум для реализации):**
- Сборщик промпта с фиксированным порядком сегментов: `[system + схемы MCP + реестр устройств] → [профиль пользователя] → [история / сводка] → [дельта состояния + извлечённые события] → [текущий ход]`. Всё, что меняется часто, — в хвосте.
- Хранилище на устройстве: SQLite (профиль-факты, журнал событий, сессии), опционально `sqlite-vec` или FAISS для поиска. Файловая память в стиле Claw (`MEMORY.md`) — для совместимости и baseline.
- Политики (подключаемые): полная история; скользящее окно; окно со сбросом блоком; маскирование результатов инструментов; удаление устаревших показаний; LLM-суммаризация (как PicoClaw: >20 сообщений или >75% окна); retrieval-память (Mem0-подобная). Отдельно — офлайн-консолидация в простое.
- MCP-слой оборудования: `resources/read` с `ttlMs` для состояния, `list_changed` для реестра, подписки для триггеров. Симуляция датчиков — MCP-сервер-эмулятор или ROS 2/Gazebo через ros-mcp-server.
- Учёт: логировать `usage.prompt_tokens`, `cached_tokens` и `completion_tokens` в трассу. Существующий `monitor/check_trace.py` уже проверяет трассы, а харнесс уже пишет `prompt_tokens / reused_tokens` для llama-server. Это расширяется до полей облачного API.

**Эксперименты:**
1. **Факторный эксперимент «политика × нагрузка × TTL × модель»:**
   - политики — 6–7 из списка выше;
   - нагрузка — 10 / 40 / 200 запросов в сутки (синтетическая трасса «день умного дома» с датчиками и камерой);
   - модели — gpt-5-mini (кэш 0,1×, ~10 мин), gpt-4o-mini (0,5×), модель класса GPT-5.6+/6-luna (30 мин, запись 1,25×).

   Отклик — метрики выше. Предварительно прогнать модель стоимости `cost_model.py`, затем сверить её с реальными `cached_tokens` (валидация модели — отдельный результат).
2. **Сравнение представлений состояния оборудования** (снимок в голове / снимок в хвосте / pull / журнал + top-k / push + триггер): токены, свежесть (доля ответов с устаревшим значением), задержка, CPU одноплатника.
3. **Качество памяти:** подмножества LongMemEval-S (вопросы knowledge-update и temporal), LoCoMo-10 и PrefEval плюс собственные контрольные вопросы об оборудовании («когда последний раз открывалась дверь?»). Статистика — парный bootstrap, McNemar и TOST из `harness/stats.py`: эквивалентность дешёвой политики дорогой.
4. **Накладные расходы на устройстве:** ОЗУ и CPU оркестратора (ориентир PicoClaw — 10–20 МБ), стоимость поиска и эмбеддингов, ошибка эвристической оценки токенов против токенизатора.

**Baselines:** политика PicoClaw (открытый Go-код, MIT), Home Assistant-подобный pull (`GetLiveContext`), MemGPT-пороги (70% / 100%), маскирование (M = 10, C3), пороги ACON (4096 / 1024).

**Что сделать сразу:**
- (а) получить ключ RouterAI и проверить `usage.cached_tokens` и повторяемость кэша при паузах 1, 5, 10, 15 и 30 минут. Это дешёвый пилот, он стоит копейки;
- (б) зафиксировать даты цен: тарифы меняются, например у моделей GPT-5.6+ запись кэша уже тарифицируется отдельно (1,25×).
