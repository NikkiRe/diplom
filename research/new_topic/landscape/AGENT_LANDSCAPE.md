**Дата проверки: 2026-10-06.** Звёзды, версии, даты и загрузки указаны на эту дату.

**На чём основано.** Это сводка заметок `L1_frameworks.md`, `L2_personal_edge_agents.md`, `L3_robotics_iot_agents.md`, `L4_jetson_nano.md` и заметок уровнем выше: `A_claw_analogs.md`, `B_mcp_hardware.md`, `C_llm_agents_robotics_iot.md`, `D_context_memory.md`, `E_time_cost_metrics.md`, `F_practical_stack.md`, `G_edge_ai_onboard.md`, `GAP1.md`, `GAP3.md`, `GAP4.md`. **Что перепроверено сегодня.** Метаданные 42 репозиториев через GitHub API. PyPI JSON для 12 пакетов. npm (`openclaw`, `@modelcontextprotocol/sdk`). arXiv API для 8 ключевых статей. ## 0. Коротко

1. **«Агентов для этой сферы» много, и они делятся на семь классов** (§2):
   - универсальные фреймворки (LangChain/LangGraph, OpenAI Agents SDK, Strands и др.);
   - личные агенты на своём железе: семейство OpenClaw и его лёгкие клоны NanoClaw, PicoClaw, nanobot, ZeroClaw;
   - голосовые агенты и умный дом: Home Assistant, xiaozhi-esp32;
   - ROS-агенты и MCP-мосты к роботам: ROSA, RAI, ros-mcp-server, OM1;
   - экосистема NVIDIA Jetson;
   - промышленные edge-агенты: AWS, Microsoft, Siemens;
   - научные системы от SayCan до ROSClaw.
2. **Постановка руководителя совпадает с основным путём области.** Тонкий оркестратор на устройстве, рассуждение во внешней LLM, контекст пользователя в файлах, оборудование через MCP. Так устроены почти все личные агенты 2026 года и большинство ROS-агентов. Значит, сам класс «агент на одноплатнике + внешняя LLM + MCP» **новизной не является**. Это надо честно сказать в главе 1 (§6.4).
3. **Названные руководителем аналоги существуют.**
   - **NanoClaw**: `nanocoai/nanoclaw`, TypeScript, ★30,9 тыс. Изоляция агентов в контейнерах, внутри — Claude Agent SDK.
   - **PicoClaw**: `sipeed/picoclaw`, Go, ★30,0 тыс. Один статический бинарник, есть инструменты I2C/SPI/serial и MCP-клиент.

   Оба — облегчённые потомки **OpenClaw** (★391,5 тыс., 15,6 млн загрузок npm в месяц).
4. **Что реально используется массово** (§4):
   - **Home Assistant с LLM-агентами разговора и MCP-сервером** — десятки тысяч реальных установок. По открытой аналитике HA: MCP Server настроен в 25 826 установках, агенты на Gemini — в 34 840, на OpenAI — в 24 517, на Ollama — в 12 576. Значительная часть HA OS работает на Raspberry Pi.
   - **OpenClaw** и его клоны: личные ассистенты на Mac mini, VPS, Pi.
   - **xiaozhi-esp32** — массовые голосовые устройства на ESP32, где сам микроконтроллер служит MCP-сервером.
   - **Универсальные фреймворки** — миллионы загрузок в месяц. Но популярные edge-агенты их не используют, а пишут свой тонкий цикл на SDK провайдера.
   - Робототехнические LLM-агенты пока на уровне исследований и пилотов: ROSA — 232 загрузки PyPI в месяц, ros-mcp-server — 1 464.
5. **Ресурсы.** Про RAM почти все цифры в README — маркетинг. Независимых измерений мало, и все они «на задачу», а не «за часы»:
   - ZeroClaw ≈ 20 МБ, PicoClaw ≈ 31 МБ, smolagents ≈ 90 МБ, nanobot ≈ 130 МБ пикового RSS на Raspberry Pi 4 2 ГБ с облачной моделью [Н, Zenodo 2026];
   - OpenClaw — медиана пика 2 926,6 МиБ против 136,1 МиБ у NanoBot [Н, arXiv:2608.27886].
6. **На слабом железе с внешней LLM доминируют не RAM и не CPU, а токены, деньги и задержки** (§5.2):
   - один запрос OpenClaw — ~28–30 тыс. входных токенов;
   - пустой heartbeat раз в 30 минут — до ~1,3 млн токенов в сутки. Это 7–107 ₽/сут в зависимости от mini-модели, без кэша, потому что in_memory-кэш mini-моделей живёт ~5–10 минут;
   - ход LLM — 1,3–2,3 с (замер ROSClaw на Claude, GPT-5.2, Gemini и Llama 4; для GPT mini через RouterAI не измерялось).

   Вторая проблема — **устанавливаемость**: Node ≥ 22, Python ≥ 3.10, колёса под manylinux_2_28.
7. **Jetson Nano на 1 ГБ не существует.** Бывают Jetson Nano 4 ГБ (Developer Kit A02/B01 и модуль с eMMC) и Jetson Nano 2GB Developer Kit.
   - Программный потолок обеих — **JetPack 4.6.6 / L4T R32.7.6**: Ubuntu 18.04, ядро 4.9, glibc 2.27, Python 3.6, CUDA 10.2.
   - **Нативно не запустится ничего на Node.js ≥ 18** (официальные glibc-сборки требуют glibc ≥ 2.28): OpenClaw, NanoClaw, NemoClaw, Mastra, ROSClaw от Tongji. Обходы не проверены: неофициальные musl-сборки Node 22/26 (нужен musl-рантайм) и Bun (glibc ≥ 2.17). Не запустятся и бинарники под glibc ≥ 2.34 (OM1, ZeroClaw-gnu).
   - **ROS 2:** свежего ROS 2 в apt для 18.04 нет. Есть EOL Dashing/Eloquent из apt, Humble — сборкой из исходников или образом `dustynv/ros:*-l4t-r32.7.1` (тот же Ubuntu 18.04), ROS 1 Melodic — нативно.
   - **Запустятся (ожидаемо, не проверено на плате):** статические Go/Rust-musl/Zig-бинарники — PicoClaw, ZeroClaw-musl, NullClaw (линковка проверена анализом бинарников); Edge Agents — если собрать движок самому. Python 3.12 через `uv` с официальным MCP SDK, OpenAI Agents SDK, MAF, LangGraph. **nanobot 0.3.5 — только со сборкой `tiktoken` из исходников.**
   - Разумная роль Nano — **«оборудование + лёгкий MCP-сервер» и, при желании, сам агент как статический бинарник или Python-процесс** (§7).
8. **Baseline для замеров** (§6.2):
   - PicoClaw v0.3.1 — лёгкий, Go;
   - nanobot 0.3.5 — Python, есть независимые замеры (на Nano — только со сборкой `tiktoken ≥ 0.12` из исходников);
   - OpenClaw 2026.9.8 — тяжёлая точка отсчёта, только Mac и Pi 5;
   - по желанию ZeroClaw v0.8.5 (musl);
   - внутренний baseline — «наивный режим» собственного агента: полный снимок в промпте, heartbeat, без кэша.

   Инструменты (не конкуренты): ros-mcp-server для сценария с Gazebo, MCP Server Home Assistant.
9. **Честный пробел, который закрывает ВКР** (§6.4). Нужно не «ещё один claw-агент», а:
   - (а) **измеренный суточный эксплуатационный профиль** тонкого агента на реальном одноплатнике: ₽/сут с учётом кэша провайдера, вызовы и токены в час, RSS-тренд, Вт·ч/сут, задержка реакции. Сюда же — зависимость профиля от политики контекста и событийности;
   - (б) **структурированный контекст оборудования как MCP-ресурс**, включающий «здоровье» платы и бюджет самого агента. В проверенных проектах такого не найдено, но поиск не исчерпывающий;
   - (в) работоспособность на «наихудшей» платформе (Nano, JetPack 4.6) с переносом на Pi 5.
10. **Что уточнить на кафедре:** точную модель платы и объём RAM (`cat /proc/device-tree/model`, `free -h`), версию L4T, наличие датчика мощности INA3221 (на 2 ГБ его нет), sudo и сеть до RouterAI. И у руководителя: обязателен ли именно оригинальный Nano, или допустимы Raspberry Pi 5 / Orin Nano (§7.4).

## 1. Как читать эту заметку (короткий словарь)

| Термин | Что значит здесь |
|---|---|
| **Агент** | Программа, которая в цикле отправляет LLM контекст и список инструментов, получает вызов инструмента, исполняет его и возвращает результат модели. Цикл повторяется, пока задача не решена |
| **Оркестратор / харнесс (harness)** | Та часть агента, что работает на устройстве: цикл, сборка промпта, память, планировщик, политика безопасности. Сама LLM — снаружи |
| **MCP** (Model Context Protocol) | Открытый протокол между агентом (клиентом) и сервером инструментов или ресурсов. Текущая ревизия спецификации — **2026-07-28**. Транспорты: stdio и Streamable HTTP; HTTP+SSE переведён в Deprecated [V, changelog спецификации; GAP1 §8.10] |
| **Claw-семейство** | OpenClaw (ноябрь 2025) и десятки клонов 2026 года с общим паттерном: шлюз, мессенджер, внешняя LLM, файлы памяти `MEMORY.md`/`USER.md`, heartbeat/cron, skills, MCP |
| **Heartbeat** | Периодический «пробуждающий» вызов LLM (по умолчанию раз в 30 минут), чтобы агент сам проверил задачи. Главный источник фоновой стоимости |
| **RSS** | Объём физической памяти, занятый процессом. «Пиковый RSS» — максимум за прогон |
| **glibc / manylinux_2_XX** | Системная библиотека C и её версия. Бинарник или Python-колесо, собранное под glibc 2.28+, не запустится на Jetson Nano (glibc 2.27) |
| **JetPack / L4T** | Программный стек NVIDIA для Jetson. Для оригинального Nano последний — JetPack 4.6.6 (Jetson Linux R32.7.6) |

### 2.2. Две оси, по которым всё раскладывается

**Ось 1 — где работает LLM.**
- (а) **Внешняя LLM, на борту — тонкий оркестратор.** Сюда относятся почти все К2, К3, К4 и ВКР.
- (б) **LLM на борту.** Это только платы класса Orin/Thor с 8 ГБ+, ПК с GPU и промышленные IPC: OpenClaw на Orin Nano, llama_ros, Siemens on-prem.

Руководитель выбрал вариант (а). Он обоснован числами (§5.2): на оригинальном Nano модель ~1B даёт 4–7 ток/с, на Pi 5 модели до 1,5B — 5–15 ток/с.

**Ось 2 — топология MCP** (L3 §0.4):
- (а) **устройство или робот — MCP-сервер, агент — внешний клиент**: xiaozhi-esp32, ESP-Claw `mcp_server_point`, ros-mcp-server, HA MCP Server, DimOS, node-hosted MCP в OpenClaw;
- (б) **агент на борту — MCP-клиент внешних сервисов**, а железо подключено собственными плагинами: OM1, PicoClaw (I2C/SPI — встроенные инструменты, не MCP), ZeroClaw (трейт `Peripheral`).

Для ВКР естественна топология (а) в варианте «одноплатник = оборудование + MCP-сервер(ы) + тонкий агент-клиент». Для Nano это ещё и способ вынести тяжёлое на Mac (§7.3).

  - «да» — ожидается нативный запуск (статический бинарник или Python 3.12 через `uv`, колёса manylinux_2_17);

### 4.4. Наблюдения, важные для выбора основы агента

1. **Популярные edge-агенты общих фреймворков не используют.** nanobot, PicoClaw и ForestHub Edge Agents построены прямо на SDK провайдеров (`openai`, `openai-go`, `anthropic`) и официальном MCP SDK [V, `pyproject.toml`/`go.mod`, L1 §6]. Исследование 11 харнессов: «No agent runtime imports a general-purpose agentic framework» [arXiv:2609.00006].
2. **Общие фреймворки «на железе» встречаются в робототехнике:** LangChain в ROSA, LangGraph в RAI и gpt-home, Strands в вендорской physical-AI-линии AWS. Массовых эталонных развёртываний общих фреймворков на одноплатниках нет (L1 §6).
3. **MCP-клиент есть у всех основных фреймворков и почти у всех claw-агентов** [V, по исходникам]. Поэтому выбор основы от MCP не зависит. Ограничивают установка и вес (§5.2).
4. **Звёзды и коммиты — плохая мера зрелости.** У OpenClaw ≈ 17,3 тыс., у Hermes Agent ≈ 13,5 тыс. коммитов за 30 дней (Search API, с 2026-09-06) — это артефакт автоматизации. Проекты «nano/pico» за 8 месяцев выросли до 45–290 тыс. строк кода [М, `wc -l`, L2 §6.2].

### 5.2. Общие проблемы на слабом железе

**1. Оперативная память.**
- Порядок величин для оркестратора с внешней LLM:
  - Go и Rust — 20–31 МБ;
  - Python — 90–136 МБ;
  - Node-шлюз OpenClaw — ~2,9 ГиБ в медиане пика [Н].
- Сервер MCP по нерецензированному бенчмарку (B [S3]): Rust ~11 МБ, Go ~24 МБ, Python (FastMCP, 4 воркера) ~259 МБ, Node ~395 МБ.
- **Рост во времени не измерен никем на плате.** Есть сигналы:
  - ZeroClaw — 100 МБ → 2,5 ГБ при многих MCP-инструментах (отчёт пользователя);
  - Node на Pi 5 вырос на +117 МБ (Oliveira).
- На Jetson память **общая для CPU и GPU**: на Nano 4 ГБ доступно ~3,9 ГБ. Локальное зрение и агент делят один пул.

**2. Рантаймы и установка — главный барьер для старых плат.**
- Официальные сборки Node.js 18–26 для linux-arm64 требуют **glibc ≥ 2.28 и ядро ≥ 4.18**. Будущая 27-я требует glibc ≥ 2.34 и ядро ≥ 5.14 [V, `BUILDING.md`]. Готовой glibc-сборки Node ≥ 18 под glibc 2.27 для aarch64 нет (`nodejs/unofficial-builds` делает glibc-217 только для x64). Оговорки, не проверенные на плате:
  - те же unofficial-builds публикуют `linux-arm64-musl` для Node 22 и 26 — это не glibc-сборка, нужен musl-рантайм (Alpine-контейнер или musl-загрузчик с libstdc++), ядро остаётся 4.9;
  - glibc-бинарники Bun требуют glibc ≥ 2.17 и ядро ≥ 3.10 (по документации Bun); Letta Code допускает `bun ≥ 1.3.2`, NanoClaw использует Bun внутри контейнера;
  - EOL Node 16 (arm64: glibc ≥ 2.17, ядро ≥ 4.5) на Nano запускается, но современным агентам его мало. `@modelcontextprotocol/sdk` 1.32.1 требует Node ≥ 18.
- Официальный MCP SDK (`mcp` 2.3.0), `fastmcp`, `openai` и почти все фреймворки требуют **Python ≥ 3.10** [V, PyPI]; исключение — `agno` (≥ 3.9). Python 3.10 сам стал EOL 2026-10-01, поэтому цель — 3.12. `uv` ставится standalone-установщиком: через `pip` системного Python 3.6 его не поставить (`uv` требует Python ≥ 3.8).
- Нативные колёса в 2025–2026 годах массово перешли на **manylinux_2_28** для aarch64: `tiktoken` ≥ 0.12 (с 2025-10-06), `pyarrow` ≥ 21, `onnxruntime` ≥ 1.29 (без sdist), `av` ≥ 15, `livekit`. У `hf-xet` колёса для aarch64 изначально только manylinux_2_28. `numpy` 2.5.3 выпускает manylinux_2_27 и на Nano ставится. Фреймворк ломается на старом glibc, если такой пакет у него обязателен: **nanobot 0.3.5** (`tiktoken` в ядре), PydanticAI ≥ 1.39 с extra `[openai]`, LiveKit Agents (`livekit==1.1.20`, ResolutionImpossible). У LangGraph + `langchain-openai` `tiktoken` откатывается до 0.11.0, у smolagents `huggingface-hub` — до 0.31.4 (L1 §4; `pip --dry-run` при фактчекинге).
- **Набор инструкций.** Cortex-A57 в Nano — это ARMv8.0-A, без LSE и dotprod. Бинарники, собранные под armv8.2-a, падают с SIGILL.
- **CUDA 10.2** на Nano: современный Ollama с GPU и NanoLLM не работают. Ollama для GPU с compute capability 5.0–6.2 требует драйвер ≥ 570, а у L4T R32 он намного старше; мейнтейнер Ollama называл JetPack 5 самой старой поддерживаемой версией (issue #4140).

**3. Трафик и сеть.**
- Сам MCP дешёвый: медиана 12,4 мс для stdio и 23,7 мс для HTTP [B, D2]; сотни байт на вызов.
- Дорого то, что MCP добавляет **в токены**: число входных токенов растёт в 3,25–236,5 раза, средняя точность падает на 9,5 % [B, D1 MCPGauge].
- Задержка облачного API нестационарна: у одного и того же запроса она меняется до 69 раз в зависимости от момента отправки [E, Bian et al.].
- На Wi-Fi при многочасовой работе поток обрывается. В ревизии 2026-07-28 возобновление SSE-потока убрано, поэтому оборванный запрос клиент отправляет заново (GAP1 §8.10).

**4. Токены и стоимость — доминирующая статья «во времени».**
- Типичный запрос OpenClaw — **~28–30 тыс. входных и ~500 выходных токенов**: стоимость определяется префиксом [arXiv:2607.02518].
- Heartbeat OpenClaw без изоляции — ~100 тыс. токенов за запуск, с `isolatedSession` — 2–5 тыс. [З, документация OpenClaw].
- Баг #61690: пустой `HEARTBEAT.md` стоил «$20+/неделю».
- Расчёт для heartbeat раз в 30 минут: 27 000 токенов × 48 тиков = 1,296 млн токенов в сутки. In_memory-кэш mini-моделей живёт ~5–10 минут, поэтому при паузе 30 минут попаданий нет. Отсюда **без кэша** (GAP1 §8.1, цены RouterAI на 2026-10-06):

  | Модель | ₽ в сутки |
  |---|---:|
  | gpt-5-nano | 7,2 |
  | gpt-6-luna | 14,3 |
  | gpt-4o-mini | 21,5 |
  | gpt-5-mini | 35,8 |
  | gpt-5.4-mini | 107,3 |

  В расчёте учтён только вход; выход (~500 токенов на запрос) добавит сверху. Пересчёт по `F_artifacts/routerai_models_2026-10-06.json` сходится [V].

  У luna-моделей запись в кэш платная и дороже обычного входа (у gpt-6-luna `input_cache_write` 1,38·10⁻⁵ против `prompt` 1,10·10⁻⁵ ₽/токен). Поэтому при периоде ≥ 30 минут кэш их **удорожает**.
- Русский язык добавляет токены: команды — ×1,36 против английских. Целый ход агента дорожает на +21 %, если всё на русском, и на +3 %, если системный промпт и инструменты на английском (GAP4).

**5. Контекст во времени.**
- Без компактизации суммарный вход растёт как O(n²) по числу вызовов (D).
- Файлы памяти в начале промпта при каждой записи инвалидируют кэш всей последующей истории. Так устроен PicoClaw (D §0.6).
- Снимок состояния оборудования в начале промпта примерно **вдвое** дороже за сутки, чем в конце или по запросу [М, D §0.5].
- Суммаризация ломает кэш префикса. Простое маскирование старых наблюдений не уступает ей по качеству и вдвое дешевле (D, Complexity Trap).
- Долгая работа деградирует:
  - AgentRM: «амнезия» от неограниченного роста памяти;
  - Octopus: за 11 ч агент «отремонтировал» систему, отключив 3 сустава.

**6. Локальная LLM на слабой плате — только аварийный режим.**
- Jetson Nano: 1B-модели — 4–7 ток/с генерации.
- Prefill агентского промпта на 1 500 токенов: **на GPU ≈ 13–65 с**, на CPU ≈ 200 с. Нижняя граница — по llama-bench pp512 (115,75 ток/с), который автор источника считает завышенным. Верхняя — по реальным промптам (23,3 ± 9,6 ток/с); длинные промпты обрабатываются быстрее, так что истина, вероятно, между ними. Шаг агента — от ~20 с до минуты и больше [М по данным kreier/llama.cpp-jetson, L4 §3.6].
- Pi 5: до 1,5B — 5–15 ток/с, 3B — 2–5 ток/с [arXiv:2511.07425].
- В Zenodo-бенчмарке ни один агент не выполнил задачу на локальной модели.

**7. Измерения.**
- Заявленные цифры RAM получены на `--help`/`status` под macOS и «нормированы на 0,8 ГГц» без описания процедуры (A §5).
- INA3221 на Nano 4 ГБ (I2C 0x40, каналы VDD_IN / VDD_GPU / VDD_CPU, в tegrastats — POM_5V_IN / POM_5V_GPU / POM_5V_CPU) видит только модуль, без несущей платы. Итог — POM_5V_IN, а не сумма трёх каналов. Встроенные датчики Jetson занижают мощность до 50 %; после калибровки ошибка ±3 % (Shalavi 2023, arXiv:2306.13107). **На Nano 2 ГБ этого датчика нет** [V, L4T R32.7.5 Power Management].
- Для «Вт·ч в сутки» нужен внешний ваттметр.

**8. Безопасность команд приводам** (инженерная, не инфобез; GAP3).
- LLM не может быть частью функции безопасности.
- Проверки (диапазоны, блокировки, подтверждение, read-only) должны выполняться на устройстве, до исполнения команды.

### 5.3. Приёмы экономии, уже реализованные у аналогов (кандидаты в абляции)

| Приём | Где | Что даёт |
|---|---|---|
| Script gates: дешёвый скрипт решает, будить ли LLM | NanoClaw | меньше вызовов в час |
| LLM один раз компилирует правило, дальше без LLM | WireClaw `rule_create`, ESP-Claw (Lua), ZeroClaw SOP | вызовы только на создание правила |
| Событийные триггеры вместо опроса | ZeroClaw SOP (MQTT/периферия), PicoClaw USB-hotplug, AWS-образец (ONNX-фильтр → облачный агент) | LLM — «обработчик исключений» |
| Изоляция или облегчение контекста heartbeat, окна активности | OpenClaw `isolatedSession`, `lightContext`, `activeHours` | в 20–50 раз меньше фоновых токенов [М, A §6] |
| Маршрутизация лёгкая/тяжёлая модель | PicoClaw (rule-based), OpenClaw (отдельная модель для heartbeat) | дешёвая модель для рутины |
| Отложенная загрузка схем MCP, поиск инструментов BM25 | PicoClaw `mcp add --deferred`, ha-mcp | короче префикс |
| Жёсткие лимиты вызовов | zclaw: 100/ч и 1000/сут; PicoClaw `rpm` | потолок расходов |

### 6.3. Что берём у аналогов (со ссылкой на источник)

- **Цикл и память:** тонкий цикл на `openai` + `mcp` (или Go SDK), как у nanobot и PicoClaw. Файлы `USER.md`/`MEMORY.md`, но с кэш-дружественной раскладкой: стабильное — в начале промпта, изменчивое — в конце.
- **Оборудование:**
  - устройство как MCP-сервер (xiaozhi `AddTool`, ESP-Claw `mcp_server_point`, HA MCP Server);
  - декларативное описание платы (ESP-Claw `board_peripherals.yaml`, ZeroClaw VID/PID);
  - снимок состояния по запросу (HA `GetLiveContext`);
  - скрытые от модели привилегированные инструменты (`AddUserOnlyTool`);
  - тяжёлые данные сводятся на сервере в компактное описание (ros2_mcp: PointCloud2 → PNG; детектор → текст).
- **Безопасность:** read-only-режим, в котором регистрируются только явно проверенные инструменты (fail closed), и классификация инструментов по опасности (ros2_mcp); `confirm` на запись (PicoClaw); лизинги и E-Stop (ROSClaw); проверка до исполнения (ROSClaw `before_tool_call`).
- **Экономия:** script gates (NanoClaw), компиляция правил (WireClaw), событийные триггеры, лимиты (zclaw), минимальный профиль инструментов.
- **Транспорт MCP:** только stdio (на плате) и Streamable HTTP (удалённо). SSE не использовать: он Deprecated. Учесть разброс ревизий: PicoClaw v0.3.1 (go-sdk v1.6.1) говорит на 2025-11-25, а не на 2026-07-28; HA-клиент при ошибке откатывается на SSE. Собственный сервер должен договариваться о версии.
- **Метрики:** совместимость с OpenTelemetry GenAI; учёт энергии в формате, близком к OpenJarvis (у них монитор Jetson не сделан).

### 6.4. Позиционирование: какой пробел закрывает агент (честно)

**Что новизной НЕ является** (и об этом лучше сказать в ВКР самим):
- «ИИ-агент на одноплатнике с внешней LLM». Класс массово существует: 10+ проектов с ★ > 5 тыс., официальные решения NVIDIA (NemoClaw) и Espressif (ESP-Claw).
- «MCP для доступа к оборудованию». Это стандарт де-факто 2025–2026 годов: ros-mcp-server, xiaozhi-esp32, HA MCP Server (25 826 установок), ESP-Claw, DimOS, Isaac Sim 6.0. Появляется и отдельный стандарт MHS.
- Количество каналов, функций и «умность». Здесь OpenClaw и Hermes недосягаемы, и цели соревноваться нет.
- Минимальная RAM. Rust- и Go-агенты уже дают ~20–31 МБ. Собственный агент может оказаться не легче PicoClaw, и это нормально.

**Что новизной является** (узкая, защитимая формулировка, согласованная с GAP1 §8.9):
1. **Измеренный суточный эксплуатационный профиль** тонкого агента на реальном одноплатнике с внешней LLM и MCP-доступом к оборудованию. В профиль входят:
   - ₽/сут с учётом кэша провайдера;
   - вызовы LLM и токены в час;
   - RSS-тренд (тест Манна–Кендалла, оценка наклона Сена);
   - Вт·ч/сут;
   - p50/p95 задержки реакции.

   Плюс сравнение с B0–B3 при одинаковой нагрузке и протокол ускоренного воспроизведения «дня» без смещения стоимости (GAP1 §6).

   Почему это пробел: в литературе такого нет. Salman et al. — Docker/WSL2 без токенов. Zenodo — короткие задачи. OM1 — только задержки. OpenJarvis — без Jetson.
2. **Контекст оборудования как структурированный MCP-ресурс.** Реестр устройств с единицами, диапазонами и стоимостью опроса, текущее состояние и **«здоровье» платы и бюджет самого агента** (CPU/RAM/температура/питание + токены и ₽ за окно). Агент учитывает их сам: реже будит LLM, переходит на дешёвую модель. Плюс измерение того, сколько стоит каждая политика подачи этого контекста.

   Почему это пробел: в проверенных проектах есть отдельные куски (NullClaw `hardware_memory`, HA `context-snapshot`, ESP-Claw YAML), но единого ресурса не найдено. **Поиск не исчерпывающий.**
3. **Работоспособность на «наихудшей» платформе** (оригинальный Nano, JetPack 4.6, glibc 2.27) с переносом на Pi 5 без изменений. Прецедент один — EdgeSentinel, и замеров во времени у него нет. Это инженерный, а не научный вклад. Его ценность зависит от ответа руководителя, обязателен ли Nano (§7.4).

**Риски позиционирования:**
- (а) область меняется за недели: версии надо фиксировать, а обзор обновить перед сдачей;
- (б) MHS и будущие ревизии MCP могут стандартизовать «контекст оборудования». Тогда вклад п. 2 смещается к измерению стоимости политик;
- (в) почти все сравнительные цифры конкурентов — заявления. Корректно сравнивать только с тем, что измерено самим на одной плате.

**Возможная формулировка для главы 1:**

> Существующие решения либо ориентированы на функциональность и не измеряют свою эксплуатационную стоимость (OpenClaw, PicoClaw, nanobot), либо предоставляют доступ к оборудованию без агента и метрик (ros-mcp-server, MCP-сервер Home Assistant), либо измеряют задержки без учёта токенов, стоимости и ресурсов хоста (OM1). Независимые измерения агентов этого класса на одноплатниках ограничены отдельными задачами и не охватывают многочасовую работу. Поэтому актуальна разработка агента с MCP-доступом к оборудованию и встроенным учётом ресурсов и стоимости, а также методики оценки его работы во времени.

### 7.3. Практическая схема для Nano

1. **Nano = оборудование + MCP-сервер(ы):**
   - датчики (I2C/GPIO), камера CSI/USB с детектором jetson-inference, телеметрия (tegrastats, INA3221, `nvpmodel`, jtop через `/run/jtop.sock`);
   - сервер — статический Go-бинарник на MCP Go SDK или Python 3.12 через `uv`;
   - транспорт — stdio (агент на плате) или Streamable HTTP (агент на Mac).
2. **Агент** — на Nano как статический бинарник или Python 3.12 через `uv`. Для отладки — на Mac.
3. **LLM** — внешняя, через RouterAI. Локальная 1B — только аварийный режим.
4. **Симулятор** (Gazebo Harmonic + ROS 2 Jazzy) — в ВМ на Mac. На Nano при необходимости — только rosbridge: проще всего под Melodic, есть и `ros-dashing-rosbridge-server`. Совместимость rosbridge-протокола Melodic/Dashing с ros-mcp-server и Jazzy на Mac не проверена.
5. **Энергия.** На 4 ГБ — INA3221 для разложения на CPU/GPU плюс внешний ваттметр 5 В для «всей платы». На 2 ГБ — только внешний ваттметр.

Решение, которое работает на Nano, переносится на Pi 5 и Orin почти без изменений. Обратное неверно. Поэтому Nano — честный «наихудший случай» (L4 §9).

### 7.4. Что уточнить на кафедре

Команды (только чтение):

```bash
cat /proc/device-tree/model        # Developer Kit или 2GB Developer Kit
free -h                            # ~3.9Gi → 4 ГБ; на 2 ГБ ожидается ~1.9Gi [НП: первичного вывода не найдено]
cat /etc/nv_tegra_release          # R32, REVISION 7.x
dpkg-query --show nvidia-l4t-core  # 32.7.6-... = JetPack 4.6.6
uname -r; ldd --version | head -1; python3 --version   # 4.9.x / 2.27 / 3.6.9
docker --version                   # ≥ 20.10.10 нужен для образов с glibc ≥ 2.34 (clone3 в seccomp); в bionic-updates docker.io 20.10.21 — достаточно
ls /sys/bus/i2c/drivers/ina3221x/  # есть ли датчик мощности
sudo nvpmodel -q; df -h /          # режим питания; объём microSD
ls /dev/video*                     # камеры
```

Физически: ревизия платы (два разъёма CSI — B01), блок питания (DC 5 В⎓4 А или micro-USB), вентилятор, объём microSD (рекомендовано от 32 ГБ, лучше 64 ГБ+), какая камера, есть ли Wi-Fi.

2. Можно ли запускать агент в контейнере, или нужен нативный запуск на L4T 18.04?
3. Есть ли sudo, можно ли перепрошить плату на 4.6.6, можно ли работать удалённо по SSH или забрать плату?

5. Есть ли на кафедре USB- или DC-ваттметр с логированием?

### 7.5. Эмуляция на MacBook до доступа к плате

- **Userland Nano:** `docker run --platform linux/arm64 --cpus=4 --memory=3.5g nvcr.io/nvidia/l4t-base:r32.7.1` (для 2 ГБ — `--memory=1.5g`). Тег r32.7.1 — последний `l4t-base` для r32, тега r32.7.6 в реестре нет. Воспроизводит glibc 2.27, Python 3.6.9 и apt-пакеты. **Не воспроизводит** ядро 4.9, CUDA (в образе она частичная), датчики, частоту и полосу памяти (L4 §6).
- **Проверка устанавливаемости Python-стека без эмуляции:** `pip install --dry-run --only-binary=:all: --python-version 3.12 --platform manylinux_2_17_aarch64 … --platform manylinux_2_27_aarch64 <пакеты>`. Так при фактчекинге найдена проблема nanobot 0.3.5.
- **Набор инструкций:** QEMU TCG с `-cpu cortex-a57` — дымовой тест бинарников на SIGILL.
- **Pi 5:** `debian:bookworm` arm64 или Lima с Ubuntu 24.04.
- **Задержки CPU** с Mac не переносятся: нужна калибровка коэффициентов на плате. Энергию в эмуляции не мерить.

Все команды — рекомендации, в этой работе они не запускались.
