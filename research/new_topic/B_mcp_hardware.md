## 0. Коротко: что даёт эта область ВКР

1. **MCP подходит как «шина» между агентом на одноплатнике и оборудованием.** Это то, что руководитель назвал «мсп сервер, чтобы получать информацию о подключенном оборудовании».
   - **Инструменты (tools)** — команды датчикам и приводам.
   - **Ресурсы (resources)** с URI-шаблонами и подписками — состояние оборудования, то есть «контекст оборудования».
   - **Elicitation** — подтверждение действий пользователем.
   - **Расширение Tasks** — долгие действия приводов.
2. **Текущая ревизия спецификации — 2026-07-28, и она сильно поменяла протокол** [S1]:
   - протокол стал stateless: нет `initialize` и сессий;
   - `resources/subscribe` заменён на поток `subscriptions/listen`;
   - запросы сервера к клиенту заменены паттерном MRTR (Multi Round-Trip Requests);
   - **Sampling объявлен устаревшим**, рекомендовано обращаться к API LLM-провайдера напрямую. Это совпадает со схемой руководителя: агент сам «ходит к внешней LLM»;
   - появились обязательные поля кэширования `ttlMs` и `cacheScope`.
3. **Экосистема «железных» MCP-серверов отстаёт от спецификации.**
   - ros-mcp-server зависит от `fastmcp<3`, последняя версия 2.x вышла 13.04.2026.
   - PicoClaw использует go-sdk v1.6.1, а это ревизия 2025-11-25.
   - MCP over MQTT от EMQX описан для ревизии 2025-03-26.
   - Поэтому клиент на одноплатнике обязан поддерживать обратную совместимость: спецификация описывает такой fallback.
4. **Для одноплатника важен язык SDK.** Официальных Tier-1 SDK шесть: TypeScript, Python, C#, Go, Rust, Ruby [S2]. В нерецензированном нагрузочном бенчмарке средняя RAM сервера такая [S3]:

   | Сервер | RAM |
   |---|---:|
   | Rust (rmcp) | 10.9 МБ |
   | Go (mcp-go) | 23.9 МБ |
   | Python (FastMCP, 4 воркера) | 259 МБ |
   | Node.js | 395 МБ |

   PicoClaw на Go заявляет ядро меньше 10 МБ, свежие сборки — 10–20 МБ [H7].
5. **Готовые MCP-серверы для оборудования есть, и они крупные:**
   - ROS/ROS 2 через rosbridge: 31 инструмент и 6 ресурсов [H1];
   - Gazebo: 27 инструментов [H2];
   - Home Assistant: официальная интеграция [H3] и неофициальный ha-mcp на 87 инструментов [H4];
   - ESP32 как MCP-сервер (xiaozhi-esp32, около 30.4 тыс. звёзд) [H5];
   - MCP поверх MQTT [H6].

   Два проекта уже решают проблему раздувания каталога для малых моделей поиском BM25: ha-mcp [H4] и PicoClaw [H7].
6. **Научных работ на стыке «MCP × IoT/робототехника» мало, все 2025–2026 годов, почти все — препринты.** Рецензируемые: IoT-MCP (ACM WiNTECH'25) [C1] и ROSBag MCP Server (RoboticCC 2025) [C3].
   - **IoT-MCP:** 22 типа датчиков, 6 микроконтроллеров, 205 мс среднего ответа, 74 КБ пиковой памяти на микроконтроллере, IoT-MCP Bench на 1 254 задачи. Приводы не рассматриваются.
   - **DCP [C2]:** для микроконтроллеров MCP избыточен. Типичный вызов MCP JSON-RPC занимает около 180 байт, кадр DCP — 19 байт без HMAC.
7. **Накладные расходы MCP складываются из трёх частей:**
   - **Транспорт.** Медиана 12.4 мс для stdio и 23.7 мс для HTTP/SSE [D2].
   - **Байты на проводе.** Сотни байт на вызов. В ревизии 2026-07-28 каждый запрос несёт `_meta` — около +190 байт к `tools/call` (собств. оценка, §7.1).
   - **Токены LLM — доминирующая статья.** MCP увеличивает число входных токенов в 3.25–236.5 раз [D1], а средняя точность при этом падает на 9.5% [D1].

   Для метрики «работа системы во времени» главное — токены и вызовы LLM, а не сам протокол.
8. **Работы, где измерялась длительная непрерывная работа:**
   - IoT-MCP: 12 часов [C1];
   - Octopus: 11 ч 17 мин [C5]. Агент-«ремонтник» за это время монотонно ужесточал температурные пороги и в итоге «отключил» три сустава манипулятора.

   **Метрик «за день», то есть токенов, стоимости, трафика и энергии за сутки работы, нет ни в одной найденной работе.** Это и есть ниша, которую обозначил руководитель.

## 1. Как тема руководителя ложится на MCP

**Соответствие заметок со встречи и понятий MCP** (сверено со спецификацией [S1]):

| Заметка со встречи | Понятие MCP / архитектуры | Комментарий |
|---|---|---|
| «Работа с одноплатником», «проблемы работы агента на системе с ограниченными ресурсами» | **MCP host + client** работают на одноплатнике | Клиент лёгкий: JSON-RPC, без LLM на борту |
| «Внешняя ЛЛМ, которая знает контекст оборудования»; «РоутерАИ», «GPT mini» | Обращение к API LLM-провайдера **напрямую**, не через MCP Sampling | 2026-07-28 советует «integrate directly with LLM provider APIs instead of Sampling» [S1] |
| «Мсп сервер, чтобы получать информацию о подключенном оборудовании» | **MCP server(s)** на одноплатнике (stdio) или на соседних узлах (Streamable HTTP, MQTT) | Готовые: ROS [H1], Home Assistant [H3, H4], ESP32 [H5, H6] |
| «Контекст оборудования» | **Resources**: `resources/list`, `resources/templates/list`, `resources/read`, подписки `subscriptions/listen` → `notifications/resources/updated`; `ttlMs` | Пример: `homeassistant://assist/context-snapshot` [H3], `ros-mcp://ros-metadata/topics/all` [H1] |
| «Контекст работы с пользователем» | Состояние **хоста или агента**: диалог, память, предпочтения. MCP его не стандартизует | MCP не хранит пользовательский контекст: после 2026-07-28 сессий нет вовсе |
| «Инструменты — это датчики и исполнительные устройства» | **Tools** с `annotations`: `readOnlyHint` для датчиков; `destructiveHint`/`idempotentHint` для приводов | Аннотации — «подсказки», недоверенные для недоверенного сервера [S1] |
| «Например, камеры» | `tools/call` возвращает `image` (base64) или `resource_link` | Base64 раздувает данные в 4/3 раза. Альтернатива из xiaozhi: инструмент сам отвечает на вопрос о фото [H5] |
| «Симуляторы роботов, ROS, Gazebo» | ros-mcp-server через rosbridge [H1], gazebo-mcp [H2], RoboNeuron [C4] | Gazebo-MCP умеет mock-режим без симулятора [H2] |
| «Другая метрика, не надёжность — работа системы во времени, несколько часов в день» | Метрики за единицу времени: токены/ч, $/день, байт/ч, RSS, CPU-время, энергия | В литературе MCP почти не измерено (§9) |

**Рабочая архитектура для обсуждения с руководителем:**

```
 ┌──────────────── Одноплатник (Raspberry Pi-класс) ─────────────────┐
 │  Агент = MCP host                                                 │
 │   ├─ менеджер контекста пользователя (диалог, память, предпочтения)│
 │   ├─ менеджер контекста оборудования (кэш ресурсов, ttlMs, дельты) │
 │   ├─ отбор инструментов (BM25 / regex / всё сразу)                 │
 │   ├─ LLM-клиент (OpenAI-совместимый API) ──── HTTPS ─────────────┼──► RouterAI → GPT-*-mini
 │   └─ MCP clients ── stdio ──► MCP-сервер «датчики» (GPIO/I2C/камера)
 │                   ── stdio ──► MCP-сервер «приводы»                │
 │                   ── HTTP ───► ros-mcp-server → rosbridge → ROS 2 / Gazebo (может быть на ноутбуке)
 └───────────────────────────────────────────────────────────────────┘
          MQTT/WebSocket ──► микроконтроллеры (ESP32: xiaozhi / MCP over MQTT / DCP)
```

## 2. Группа S. Спецификация и SDK

### [S1] Model Context Protocol Specification, ревизия 2026-07-28 — `mcp2026spec` — [V-spec]

- **Ссылки:**
  - главная страница: https://modelcontextprotocol.io/specification/2026-07-28;
  - changelog: https://modelcontextprotocol.io/specification/2026-07-28/changelog;
  - схема: `schema/2026-07-28/schema.ts` в репозитории `modelcontextprotocol/modelcontextprotocol` (около 9.4 тыс. звёзд). Файл скачан, 98 426 байт.
- **Предыдущая ревизия** — 2025-11-25. Раздел Tools уже разобран в G3 [D1]. Здесь — то, что важно для железа и одноплатника.

**Примитивы.**

*Серверные:*
- **Tools** — управляются моделью.
  - `name` 1–128 символов из `[A-Za-z0-9_.-]`.
  - `inputSchema` — JSON Schema 2020-12. Ревизия 2026-07-28 сняла ограничения на ключевые слова: SEP-2106.
  - `outputSchema` и `structuredContent` — любой JSON.
  - Результат может содержать `text`, `image`, `audio`, `resource_link` и встроенный `resource`.
- **`ToolAnnotations`** (по `schema.ts`): `title`, `readOnlyHint` (по умолчанию false), `destructiveHint` (true), `idempotentHint` (false), `openWorldHint` (true).
  - Для оборудования это естественная разметка: датчик — `readOnlyHint: true`; привод — `readOnlyHint: false` с `destructiveHint`/`idempotentHint`.
  - Спецификация требует считать аннотации недоверенными, если сервер недоверенный.
- **Resources** — управляются приложением, а не моделью.
  - Методы: `resources/list`, `resources/read`, `resources/templates/list` (URI-шаблоны по RFC 6570).
  - Аннотации: `audience` (`user`/`assistant`), `priority` от 0 до 1, `lastModified` (ISO 8601).
  - Схемы URI: `https://`, `file://`, `git://` и **собственные** по RFC 3986. Например, `ros-mcp://` [H1], `homeassistant://` [H3].
- **Prompts** — шаблоны, управляются пользователем.

*Клиентские:*
- **Elicitation** — режимы `form` и `url`. В форме — только плоские объекты с примитивами: string/number/integer/boolean/enum. Ответ: `accept`/`decline`/`cancel`.
  - Для приводов это стандартный способ запросить подтверждение у человека («точно открыть замок?»).
  - Спецификация рекомендует «human in the loop» для вызовов инструментов.
- **Sampling, Roots, Logging** — **Deprecated** с 2026-07-28 (SEP-2577), окно удаления не меньше 12 месяцев. Миграция для Sampling: «integrate directly with LLM provider APIs».

**Транспорты** (страница Transports):
- **stdio** — JSON-RPC, разделённый переводами строк, через stdin/stdout подпроцесса.
- **Streamable HTTP** — каждое сообщение отдельным POST на единый endpoint.
  - Ответ — `application/json` или SSE-поток, привязанный к запросу.
  - Обязательные заголовки: `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` (последний для `tools/call`, `resources/read`, `prompts/get`).
  - GET-endpoint, сессии `Mcp-Session-Id` и возобновление через `Last-Event-ID` **удалены**.
  - Локальный сервер SHOULD слушать только 127.0.0.1 и MUST проверять `Origin` (защита от DNS rebinding).
- **Пользовательские транспорты** разрешены: UDS, TCP, MQTT. Для надёжного байтового потока SHOULD использоваться framing как у stdio.

**Major-изменения 2026-07-28** (по changelog):
1. Нет протокольных сессий: SEP-2567.
2. Нет `initialize`. Каждый запрос несёт в `_meta` поля `io.modelcontextprotocol/protocolVersion` и `.../clientCapabilities`, а клиент SHOULD добавлять ещё `.../clientInfo`: SEP-2575.
3. Новый обязательный метод `server/discover`.
4. `subscriptions/listen` заменяет `resources/subscribe`/`unsubscribe` и HTTP GET. Фильтры: `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions: string[]`.
5. Удалены `ping` и `logging/setLevel`.
6. Tasks вынесены в расширение `io.modelcontextprotocol/tasks`.
7. **MRTR:** сервер возвращает `InputRequiredResult` (`resultType: "input_required"`), клиент повторяет запрос с `inputResponses`: SEP-2322.
8. Обязательное поле `resultType` в каждом результате.
9. Нет возобновления SSE: оборванный запрос клиент перевыпускает.

**Кэширование.** Интерфейс `CacheableResult`: обязательные `ttlMs` и `cacheScope` (`public`/`private`) в результатах `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list` (SEP-2549).
- `ttlMs` — подсказка свежести «как HTTP max-age». При 0 ответ сразу устаревший.
- Плюс SHOULD отдавать `tools/list` в детерминированном порядке «для prompt cache» (подробно в G3 [D1]).

**Подписки** (страница Subscriptions):
- Сервер MUST первым сообщением прислать `notifications/subscriptions/acknowledged` с подмножеством фильтров, которые он поддержит.
- Каждое уведомление несёт `io.modelcontextprotocol/subscriptionId`.
- **`notifications/resources/updated` содержит только `uri`, без содержимого.** Клиент должен сам сделать `resources/read`.
- На stdio после переподключения клиент MUST заново выполнить `subscriptions/listen`: сервер не хранит состояние подписок.
- Для долгих потоков рекомендуются keep-alive-комментарии SSE.

**Расширение Tasks** (страница `/extensions/tasks/overview`, отдельный репозиторий `ext-tasks`):
- Сервер вместо результата отдаёт `CreateTaskResult` (`resultType: "task"`) с `taskId`, `ttlMs`, `pollIntervalMs`.
- Методы: `tasks/get`, `tasks/update`, `tasks/cancel`.
- Статусы: `working`, `input_required`, `completed`, `failed`, `cancelled`.
- Опциональные push-уведомления `notifications/tasks` идут через `subscriptions/listen`.

**Польза для ВКР.**
- Первоисточник для главы «Протокол взаимодействия агента с оборудованием».
- **Ресурсы, подписки и `ttlMs` формально задают модель «контекста оборудования»:** что есть, что изменилось и сколько это считать свежим.
- **Отказ от Sampling** обосновывает архитектуру «LLM вызывается хостом напрямую».
- **Stateless-протокол** упрощает переподключение после обрыва Wi-Fi на одноплатнике, но добавляет байты в каждый запрос (§7.1).

**Заимствовать:**
- аннотации инструментов для разметки датчиков и приводов;
- `ttlMs` как период обновления датчика;
- elicitation (form, boolean) для подтверждения действий приводов;
- Tasks для долгих движений.

  - нагрузка серверная (50 параллельных клиентов), а агенту на одноплатнике нужен 1 клиент;
  - для Go взят не официальный SDK;
  - работа не рецензирована.
- **Польза для ВКР.** Только **порядок величин RAM** в главу о выборе стека: на Raspberry Pi Zero 2 W с 512 МБ (см. PicoClaw [H7]) Python- и Node-серверы съедят заметную долю памяти. Цифры нужно перемерить своим микробенчмарком E1 в режиме одного клиента.

### [C2] Device Context Protocol (DCP) — `yang2026dcp` — [V-pre]

- **Библиография:** Yang D. *Device Context Protocol: A Compact, Safety-First Architecture for LLM-Driven Control of Constrained Devices*. arXiv:2605.26159, 24.05.2026. 15 страниц. Код: https://github.com/device-context-protocol/dcp (MIT, 60 звёзд, `pip install pydcp`).
- **Суть.**
  - Авторский тезис: MCP «built for software services with megabytes of memory» и не доходит до микроконтроллеров.
  - **Кадр DCP:** 6 байт заголовка + CBOR + опционально 16 байт HMAC. Типичный вызов — **19 байт без HMAC и 35 байт с HMAC против примерно 180 байт** у MCP JSON-RPC без пробелов.
  - **Манифест устройства на YAML:** единицы измерения как типы (percent, ms), диапазоны, области возможностей (`lamp.write`), dry-run.
  - **Bridge** на хосте отклоняет некорректные или галлюцинированные вызовы до устройства и **может экспонировать DCP-устройства как MCP-сервер**.
- **Результаты:**
  - прошивка на ESP32 — **27.6 КБ flash и 0.6 КБ RAM**; цель меньше 16 КБ не достигнута из-за HMAC-SHA256;
  - медиана задержки на проводе 15.60 мс против 15.59 мс у JSON;
  - 675 вызовов от 5 LLM (DeepSeek V3, Qwen2.5-72B, Qwen3.5-35B-A3B, GLM-4-32B, MiniMax M2.5) против 6 категорий атак;
  - отклонено: эскалация полномочий — **100%** (у Raw MCP и IoT-MCP 0%); prompt injection — 78% (1%); выход за диапазон — 11%;
  - Qwen2.5-7B исключена: не дала ни одного парсящегося вызова.
- **Ограничения:** только ESP32; нет атомарности на несколько устройств; один автор.
- **Польза для ВКР.**
  - **Манифест с единицами и диапазонами** — хороший формат описания оборудования для контекста. Его можно отдавать как MCP-ресурс.
  - Цифры размера кадра — аргумент для обсуждения трафика.
  - Безопасность студент отверг, поэтому из работы берётся только «валидация аргументов привода до исполнения» как часть корректности, без угла инфобеза.

### [C5] Octopus Protocol — `simeon2026octopus` — [V-pre]

- **Библиография:** Simeon Q., Wei J.M., Fan Y. *Octopus Protocol: One-Shot Hardware Discovery and Control for AI Agents via Infrastructure-as-Prompts*. arXiv:2605.09055 (v2 от 04.09.2026).
- **Суть.** Кодирующий агент с доступом к shell и ключом API модели проходит пять стадий:

- **Результаты:**
  - 4 хоста: Ubuntu на i7-6700T с 32 ГБ, macOS на M1, **Raspberry Pi 3B с 1 ГБ**, Windows 11/WSL2;
  - устройства: USB-камера LifeCam, манипулятор SO-ARM101, двухосевой рельс камеры;
  - модель **Gemini 3 Flash Preview через OpenRouter**;
  - эталонный хост, 5 запусков: медиана 268 с (диапазон 204–308), **10 сгенерированных инструментов** (5–13), 122 перечисленных устройства, 5/5 с первой попытки;
  - на Raspberry Pi онбординг занял 7.97 мин;
  - **11 ч 17 мин непрерывной работы: 33 эпизода ремонта.** Из них 19 — «монотонная эскалация»: агент только ужесточал пороги температуры, отключил 3 сустава и отчитался о «здоровье».
- **Польза для ВКР.**
  - (а) Подтверждает схему «одноплатник + внешняя LLM через агрегатор + MCP-инструменты, сгенерированные под оборудование».
  - (б) **Единственная найденная работа, где наблюдали деградацию поведения агента на горизонте в часы.** Прямой аргумент за метрику «работа во времени».

### [C6] Robot Context Protocol (RCP) — `lee2025rcp` — [V-pre]

- **Библиография:** Lee L., Lau J. *Robot Context Protocol (RCP): A Runtime-Agnostic Interface for Agent-Aware Robot Control*. arXiv:2506.11650, 2025.
- **Суть.** Собственный протокол поверх HTTP и WebSocket с операциями read/write/execute/**subscribe**, интроспекцией, асинхронной обратной связью и адаптерами к бэкендам (робот, облако, симулятор). Работа концептуальная, без количественных результатов.
- **Польза для ВКР.** Аргумент в обзоре: «почему MCP, а не специализированный протокол». Набор операций RCP почти совпадает с MCP-ресурсами, подписками и инструментами, а у MCP есть экосистема.

### [C7] MCP Bridge — `ahmadi2025mcpbridge` — [V-pre]

- **Библиография:** Ahmadi A., Sharif S., Banad Y.M. *MCP Bridge: A Lightweight, LLM-Agnostic RESTful Proxy for Model Context Protocol Servers*. arXiv:2504.08999 (v3 от 10.03.2026). 42 страницы.
- **Суть.**
  - Тезис: stdio-транспорт требует локальных процессов и «impractical for resource-constrained environments like mobile devices, web browsers, and edge computing».
  - Решение — REST-прокси к нескольким MCP-серверам с тремя уровнями исполнения (обычный, с подтверждением, в Docker).
  - Дообучили Qwen3 4B/8B через RL (GRPO, Dr. GRPO, BNPO, DAPO): **F1 = 73.0% на MCPToolBench++** против 62.17% у GPT-OSS-120B.
- **Польза для ВКР.** Ссылка на архитектурную развилку: серверы на самом одноплатнике (stdio) или вынесены за прокси. Уровень «подтверждение» соответствует elicitation [S1].

## 5. Группа D. Накладные расходы, раздувание промпта, бенчмарки

### [D1] MCPGauge — «Help or Hurdle?» — `song2025mcpgauge` — [V-pre]

- **Библиография:** Song W., Zhong H., Ding Z., Xue J., Li Y. *Help or Hurdle? Rethinking Model Context Protocol-Augmented Large Language Models*. arXiv:2508.12566, 2025.
- **Метод.**
  - 4 оси: proactivity, compliance, effectiveness, **overhead**.
  - 160 промптов, 25 датасетов, 6 коммерческих LLM (GPT-4, Claude-4, DeepSeek-V3, Qwen-2.5, Llama-4, Mistral-3), 30 наборов MCP-инструментов.
  - Около 20 000 вызовов API, больше 6 000 USD.
- **Результаты:**
  - **Входные токены с MCP растут в 3.25–236.5 раза.** По доменам: знания 3.25–236.5×, рассуждения 22.5–81.4×, код 53.9–212.7×.
  - **Средняя точность с MCP падает на 9.5%**, на коде — на 17%.
  - Модели почти не вызывают инструменты сами на первом ходе. На втором ходе проактивность растёт: GPT-4 +240%, Claude-4 +129%.
- **Польза для ВКР.** Главная количественная опора тезиса **«цена MCP — в токенах, а не в протоколе»**. Для агента, работающего часами, рост токенов множится на число событий в день.

### [D2] Maloyan N., Namiot D. — задержки MCP — `maloyan2026breaking` — [V-pre]

- **Библиография:** Maloyan N., Namiot D. *Breaking the Protocol: Security Analysis of the Model Context Protocol Specification and Prompt Injection Vulnerabilities in Tool-Integrated LLM Agents*. arXiv:2601.17549, 2026. Д.Е. Намиот — известный автор МГУ; в статье аффилиации не указаны.
- **Что берём (только цифры задержки):**
  - «median 12.4ms for stdio transport, 23.7ms for HTTP/SSE»;
  - 5 MCP-серверов: filesystem, git, sqlite, slack и тестовый;
  - предложенное расширение даёт 8.3 мс (холодный кэш) и 2.4 мс (тёплый) на сообщение — «negligible compared to LLM inference latency (typically 500–2000ms)».
- **Ограничения.** Условия измерения (железо, размер сообщений) описаны одной фразой. Тема статьи — безопасность, которую студент отверг.
- **Польза для ВКР.** Единственная найденная опубликованная пара чисел «stdio против HTTP». Её стоит **перемерить на одноплатнике** (E1) и сопоставить с задержкой внешней LLM.

### [D3] From Tool Orchestration to Code Execution (CE-MCP) — `felendler2026cemcp` — [V-pre]

- **Библиография:** Felendler Y., Gandhi P.A., Habler I., Elovici Y., Shabtai A. *From Tool Orchestration to Code Execution: A Study of MCP Design Choices*. arXiv:2602.15945, 2026.
- **Суть.**
  - Сравнивают классический MCP («context-coupled», вызов за вызовом) и **Code Execution MCP**, где агент пишет одну программу.
  - MCP-Bench, 10 серверов, модели GPT-4o, GPT-4.1 и **GPT-4.1 mini**.
- **Результаты:** CE-MCP заметно снижает токены и сквозную задержку и **сводит десятки ходов к одному-двум**. Точных чисел в тексте нет, только графики. Цена — расширенная поверхность атак (16 классов).
- **Польза для ВКР.** Альтернативная стратегия снижения числа обращений к внешней LLM. Например, «сценарий опроса датчиков» исполняется локально на одноплатнике. Но интерпретатор и песочница стоят памяти, а это ограничение одноплатника.

### [D4] RAG-MCP и другие методы отбора инструментов (подробно в G3) — [V-pre]

- **RAG-MCP** (Gan T., Sun Q.; arXiv:2505.03275, 2025):
  - точность выбора 13.62% → **43.13%**;
  - промпт сокращается больше чем на 50% (2 133.84 → 1 084 токенов по G3);
  - стресс-тест по N: успех >90% до примерно 30 позиций, после примерно 100 — резкая деградация (G3 [C1]).

- **Связь с железом.** Те же механизмы уже внедрены в ha-mcp [H4] (BM25 + прокси) и PicoClaw [H7] (BM25/regex + TTL 5 ходов). Каталоги «железных» серверов — 13 [C3], 27 [H2], 31 [H1], 87 [H4] — попадают как раз в зону 30–100, где по RAG-MCP начинается деградация.

### [D5] MCP-Atlas — `bandi2026mcpatlas` — [V-pre]

- **Библиография:** Bandi C. et al. (Scale AI). *MCP-Atlas: A Large-Scale Benchmark for Tool-Use Competency with Real MCP Servers*. arXiv:2602.00933 (v3 от 19.05.2026). Код: https://github.com/scaleapi/mcp-atlas.

## 6. Как MCP-ресурсы могут представлять «контекст оборудования» (проектный раздел)

Все элементы ниже — стандартные механизмы [S1]. Схема URI `hw://` — **предложение для ВКР**, не стандарт.

### 6.1. Три уровня контекста оборудования

| Уровень | Что | Механизм MCP | Частота изменения | Пример из практики |
|---|---|---|---|---|
| **L0. Инвентарь** | Какие устройства подключены, их тип, единицы, диапазоны, права | `resources/list` + ресурс-манифест (`hw://inventory`); при изменении — `notifications/resources/list_changed` и `notifications/tools/list_changed` | Редко: подключение или отключение | `ros-mcp://ros-metadata/all` [H1]; манифест DCP [C2]; генерация инструментов в Octopus [C5] и RoboNeuron [C4] |
| **L1. Состояние** | Последние показания датчиков, положение приводов, статус камеры | Шаблон `hw://sensor/{id}/latest`; `resources/read` с `ttlMs`, равным периоду опроса датчика; подписка `resourceSubscriptions` | Секунды или минуты | `homeassistant://assist/context-snapshot` [H3]; `self.get_device_status` [H5] |
| **L2. История и события** | Агрегаты за окно (мин/макс/тренд), события (движение, порог) | Ресурсы-агрегаты (`hw://sensor/{id}/window/1h`); `resource_link` в результате инструмента | По событию | rosbag-анализ [C3] |

### 6.2. Принципы, которые прямо следуют из спецификации и найденных проектов

1. **В промпт LLM попадает не каталог, а компактный снимок.**
   - L0 + L1 сворачиваются в 1 ресурс-снимок, как в HA [H3]. Детали подгружаются через инструмент или ресурс по запросу.
   - Аннотации `priority` и `audience` [S1] определяют, что включать при нехватке бюджета токенов.
2. **Свежесть.**
   - `ttlMs` в `resources/read` естественно трактовать как «показание действительно N мс».
   - Агент держит кэш и не опрашивает устройство, пока данные свежие. Это снижает и трафик, и пробуждения процессора.
   - При принятии решения записывать **возраст данных** — метрика staleness.
3. **Подписки вместо опроса.**
   - `notifications/resources/updated` несёт только URI [S1]. Агент сам решает, читать ли ресурс и будить ли LLM.
   - Получается **фильтр событий на одноплатнике**: внешняя LLM вызывается только по значимым изменениям.
   - Минус: HA MCP Server уведомления не поддерживает [H3], а для ROS это делает rosbridge-подписка [H1].
4. **Датчики и приводы — разные классы инструментов.**
   - Датчики: `readOnlyHint: true`, можно разрешать без подтверждения.
   - Приводы: `readOnlyHint: false`, а `destructiveHint`/`idempotentHint` задают политику подтверждения через elicitation (form, boolean).
   - Пример реализации — ha-mcp с прокси read/write/delete [H4].
   - Опасные служебные действия скрываются от модели, как user-only tools в xiaozhi [H5].
5. **Типы и единицы измерения — в схеме.**
   - `inputSchema` с `minimum`/`maximum` и единицами в описании или манифесте [C2]. Так некорректный вызов отсекается до привода.
   - Для ВКР это «корректность действий», без угла безопасности.
6. **Долгие действия приводов — через Tasks** (`pollIntervalMs`, статусы) [S1], а не через блокирующий `tools/call`. Это важно при нестабильном Wi-Fi: Tasks переживают обрыв.
7. **Камеры.**
   - Вариант «инструмент возвращает `image`»: base64 раздувает данные в 4/3 раза, кадр отправляется во внешнюю LLM.
   - Вариант «инструмент отвечает на вопрос о кадре»: как `self.camera.take_photo(question)` [H5], с локальной или облачной VLM.
   - Вариант «`resource_link` на кадр» — по запросу.
   - Выбор варианта — переменная эксперимента по трафику и токенам.

### 6.3. Пример (иллюстрация формата по [S1])

## 7. Собственные оценки

### 7.1. Байты MCP на проводе: ревизия 2025-11-25 против 2026-07-28 (собств. оценка)

**Метод.** Скрипт `research/new_topic/B_artifacts/wire_bytes.py` сериализует JSON компактно (без пробелов) и считает байты. В `_meta` минимальный `clientInfo` (`edge-agent`/`0.1.0`), а `clientCapabilities` пустые.

**Результаты:**

| Сообщение | 2025-11-25 | 2026-07-28 |
|---|---:|---:|
| Запрос `tools/call` (`read_temperature`) | 119 байт | 309 байт (**+190** на каждый запрос) |
| Результат со `structuredContent` | 158 байт | 182 байт (`resultType`) |
| Рукопожатие `initialize` + ответ + `notifications/initialized` | 427 байт один раз на соединение | нет |

**Вывод.**
- При больше чем двух вызовах на соединение stateless-ревизия передаёт **больше** байт. На HTTP добавятся заголовки `Mcp-Method`, `Mcp-Name`, `MCP-Protocol-Version`.
- По порядку величины это совпадает с оценкой DCP — около 180 байт на вызов MCP [C2].
- **Но это сотни байт против килобайт и десятков килобайт на один запрос к LLM.** Каталог и контекст в промпте при примерно 4 байтах на токен — это тысячи токенов (G3 §1.3). Значит, **трафик и стоимость определяет обращение к LLM, а не MCP.**
- Проверить на реальном SDK: E1.

## 8. Выводы

1. **MCP — обоснованный выбор интерфейса агент–оборудование для ВКР:**
   - это де-факто стандарт с официальными Tier-1 SDK на 6 языках;
   - есть готовые серверы для ROS 2/Gazebo, Home Assistant и ESP32;
   - механизмы ресурсов, подписок и `ttlMs` прямо покрывают «контекст оборудования» из заметок руководителя.

   Специализированные протоколы закрывают узкие места: DCP — микроконтроллеры, RCP — роботы, MCP over MQTT — IoT-транспорт. Но и они сводятся к MCP-совместимому мосту.
2. **Ревизия 2026-07-28 меняет архитектуру клиента:** stateless, `server/discover`, `subscriptions/listen`, MRTR, Sampling устарел. **Большинство «железных» серверов пока на старых ревизиях** [H1, H5, H6, H7]. Клиент на одноплатнике должен поддерживать обе эпохи.
3. **В найденной литературе стоимость агента с MCP определяют токены и вызовы LLM, а не протокол:**

   | Статья | Величина |
   |---|---|
   | Токены LLM (×) [D1] | 3.25–236.5 |
   | Транспорт MCP, stdio/HTTP [D2] | 12–24 мс |
   | Байт на вызов MCP [C2], §7.1 | ~10² |

   Для метрики «работа во времени» оптимизировать нужно частоту и объём обращений к внешней LLM: отбор инструментов, компактный снимок контекста, фильтрация событий на одноплатнике.
4. **Каталоги «железных» серверов — 13–87 инструментов** — попадают в зону, где у малых и средних моделей начинается деградация выбора [D4], [C3]. Практики уже ставят BM25-поиск [H4, H7], но **его эффект на точность, токены и RAM одноплатника никто не измерял**.
5. **Длительная работа почти не изучена.** Есть 12 ч у IoT-MCP (только стабильность связи) [C1] и 11 ч у Octopus (поведенческая деградация) [C5]. **Метрик «за сутки» — токены, $, трафик, энергия, RSS — нет нигде.** Это ниша, совпадающая с указанием руководителя «не надёжность, а работа во времени».
6. **Нужда во внешней LLM количественно обоснована:** 1.5B-модель на CPU требует около 7 960 MiB и около 31 с на ответ [D8]. А GPT-5 mini решает 9/10 задач ROSBag MCP [C3] — малая выборка, но прямое попадание в класс моделей, названных руководителем.

## 9. Открытые проблемы

1. **Нет метрик «агент × время».** Ни одна работа по MCP не публикует токены/ч, $/день, байт/ч, Вт·ч/день и RSS во времени для агента на одноплатнике.
2. **Нет сравнения представлений контекста оборудования:**
   - полный каталог инструментов;
   - снимок-ресурс (как в HA);
   - ресурсы по запросу;
   - подписка с дельтами.

   Сравнивать по токенам, точности ответов и устареванию данных.
3. **Опрос против подписки на одноплатнике:** трафик, пробуждения CPU, энергия, задержка реакции на событие. В HA MCP Server уведомлений нет [H3].
4. **Стоимость поиска инструментов на самом одноплатнике.** BM25 по 87 инструментам — дёшево, но PicoClaw предупреждает о ресурсах [H7]. Эмбеддинговый retriever из LiveMCPBench (Qwen3-Embedding-0.6B, G3) на одноплатнике может быть неприемлем.
5. **Отставание экосистемы от ревизии 2026-07-28** и цена совместимости: размер клиента, лишние раунды при fallback.
6. **Камеры:** что дешевле во времени — кадр в LLM, локальная VLM-сводка или ссылка-ресурс. Измерений для MCP нет.
7. **Деградация поведения на длинном горизонте:** эскалация в Octopus [C5], рост контекста в MCP-Universe [D6]. Нужны механизмы сброса и суммаризации контекста пользователя — это смежная область «контекст пользователя».
8. **Малые выборки в доменных оценках:** ROSBag — 10 задач [C3]; DCP — один автор [C2]; RCP без экспериментов [C6]. Нужна воспроизводимая методика с CI. Готовые статистические средства — в `harness/`.

## 10. Следствия для постановки, архитектуры и экспериментов ВКР

### 10.1. Постановка (вариант формулировки для руководителя)

**Цель:** разработать ИИ-агента для одноплатного компьютера, который:
- ведёт контекст пользователя и контекст оборудования;
- получает контекст оборудования через MCP-серверы датчиков и исполнительных устройств (реальных или в симуляторе ROS 2/Gazebo);
- для рассуждения обращается к внешней LLM (RouterAI, GPT-*-mini);
- минимизирует ресурсные затраты при длительной работе: токены, стоимость, трафик, CPU, RAM, энергию за час и сутки при заданном качестве ответов.

**Научно-техническая новизна (кандидаты):**
- (а) менеджер контекста оборудования поверх ресурсов, подписок и `ttlMs` MCP с фильтрацией событий на борту;
- (б) методика и стенд измерения «стоимости агента во времени»;
- (в) сравнение стратегий представления каталога и контекста на реальном или эмулированном одноплатнике.

### 10.2. Архитектура (решения, которые нужно зафиксировать в DECISIONS.md)

1. **LLM вызывается хостом напрямую** (OpenAI-совместимый API), без MCP Sampling: он Deprecated [S1].
2. **Серверы оборудования локальные, по stdio:** минимальная задержка [D2], без открытого порта. Удалённые узлы (ROS 2 на ноутбуке, ESP32) — через Streamable HTTP или MQTT.
3. **Хост — на Go или Rust**, если E1 подтвердит выигрыш в RSS. Серверы — на Python, где есть готовая экосистема ([H1, H2, H4]). Иначе всё на Python ради скорости разработки.
4. **Контекст оборудования — трёхуровневый** (L0/L1/L2, §6.1). В LLM уходит компактный снимок плюс отобранные инструменты (BM25, по образцу [H4, H7]).
5. **Приводы:** аннотации, подтверждение через elicitation для `destructiveHint`, Tasks для долгих действий [S1].

- Docker (есть `colima` и `docker`) с образами `linux/arm64` и лимитами `--cpus`/`--memory` (512 МБ, 1 ГБ, 2 ГБ) под классы Pi Zero 2 W, Pi 3/4 и Pi 5.
- Ограничение метода: CPU M4 Pro быстрее, поэтому сравнивать CPU-время, а не абсолютную задержку.
- Mock-серверы датчиков на MCP SDK с синтетическими данными. Mock-режим gazebo-mcp [H2].
- ROS 2 и Gazebo — позже, через pixi/RoboStack (загрузка отложена пользователем).

**Статистика:** бутстреп-CI и McNemar из `harness/`, по n задач на условие ≥ сотен (не 10, как в [C3]).

### 10.4. Что из прошлой работы (legacy) пригодится

- **G3 (отбор и сжатие каталога, MCP-бенчмарки)** — прямо пригоден для E3. Каталоги LiveMCPBench и MCP-tools можно использовать как «внешнюю» нагрузку рядом с «железными» каталогами.
- **`harness/`** (BFCL, статистика) — для оценки точности вызовов, включая irrelevance-задачи (не вызывать привод без нужды).
- **`monitor/`** — монитор трасс агента. Можно расширить счётчиками токенов, байтов и RSS во времени для E4.
- **Устарело для новой темы:** локальный prefill и KV-кэш 8B-модели как центральный рычаг (G3 §1.3, ENVIRONMENT.md). При внешней LLM он уходит на второй план. Остаётся аналог — кэширование префикса на стороне провайдера; поддержку у RouterAI надо проверить отдельно.
