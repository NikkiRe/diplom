# C. LLM-агенты для робототехники, IoT и умного дома: что сделано и что из этого берём для ВКР

Тема ВКР (согласована 06.10.2026): «Разработка ИИ-агента для приложений граничного искусственного интеллекта».
Область этой заметки: научные работы и открытые проекты, где LLM управляет физическим миром (роботы, IoT, умный дом, датчики и исполнительные устройства). Нас интересует, как устроена архитектура (где работает LLM, где исполнение, как передаётся контекст оборудования и пользователя), как это оценивали (метрики, сценарии, симуляторы) и что из этого переносится на одноплатник с датчиками и внешней LLM.

Дата составления: 2026-10-06. Каждый источник проверен по первоисточнику: метаданные arXiv API, DOI через Crossref, площадки через OpenAlex и страницы PMLR, проекты через GitHub API и README. Числа проверены поиском по HTML-версии статьи на arXiv. При каждом числе указано, откуда оно взято. Звёзды на GitHub указаны на 2026-10-06.
Пересечений с уже сделанным обзором (research/literature/_DIGEST.md, R1–R9, G3–G7) почти нет: там нет ни одной работы по робототехнике, IoT или умному дому. Единственное пересечение — обзор edge–cloud коллаборации SLM/LLM (Li et al., ACM CSUR 2026, arXiv:2507.16731). Он уже разобран в R6_adaptive_routing, и здесь на него только ссылаюсь.

## 0. Коротко

1. Во всех работах 2022–2026 годов повторяется одна схема. LLM служит планировщиком высокого уровня и сама ничего не исполняет: она выбирает и параметризует вызовы из **ограниченной библиотеки навыков или функций**, которую описали заранее. Эти навыки в SayCan, «high-level function library» в ChatGPT for Robotics, Python-подобное описание API в ProgPrompt, JSON-библиотека атомарных действий в ROS-LLM, tools в ROSA, Assist API в Home Assistant. С 2025 года эту роль стандартно играют **MCP-серверы** (ROS MCP Server, IoT-MCP, Home Assistant MCP Server, MCP в PicoClaw). Значит, схема из заметок со встречи («ходить к LLM за рассуждением, MCP-сервер даёт информацию о подключённом оборудовании, инструменты = датчики и исполнительные устройства») — это не экзотика, а основной путь области. Открытым остаётся другой вопрос: как такая система ведёт себя **во времени и под ресурсными ограничениями одноплатника**.
2. Почти все работы используют **облачную LLM** (GPT-3/3.5/4/4o/4.1, PaLM, Claude, DeepSeek через API). Локально на слабом железе запускают только малые модели под узкие подзадачи. Число параметров, которое выдерживает одноплатник, ограничено: на Raspberry Pi 5 модели до 1.5B дают 5–15 ток/с, модели 3B — 2–5 ток/с (arXiv:2511.07425). Для 70B даже при 4-битной квантизации нужно 43 ГБ памяти (ROSA). Это прямо подтверждает слова руководителя: «локальные тупые LLM, нужна нормальная оперативка, можно запускать внешнюю».
3. **Ресурсы во времени почти никто не измеряет.** Стандартная метрика — success rate на наборе эпизодов. Ресурсные числа встречаются эпизодически и снимаются «на запрос»:
   - стоимость команды $0.02–0.03 и задержка от 1 до 30–45 с (Sasha);
   - $0.10 на 100 примеров для GPT-4o-mini и 7.45 с на задачу (IoT-LLM);
   - 205 мс, 74 КБ и 12-часовой прогон, но без токенов и энергии (IoT-MCP);
   - лаг 2–3 с при межконтинентальном вызове (ROS-LLM);
   - время эпизода от 8 до 135 с (SimuHome);
   - энергия облачного вызова против бортовой LLM в зависимости от уровня сигнала (Metareasoning, ACM TECS 2026).

   Работы, где снят **суточный или многочасовой профиль** агента на одноплатнике (токены, стоимость, трафик, CPU/RAM, энергия, рост контекста), я не нашёл. Это и есть ниша, на которую указал руководитель: «другая метрика, не надёжность — работа системы во времени, несколько часов в день, считать это всё».
4. Самые слабые места LLM-агентов в физическом мире по современным бенчмаркам:
   - **временные задачи и расписания**: в SimuHome (ICLR 2026) GPT-4.1-mini проходит лишь 10–40 % feasible-эпизодов на планирование по времени;
   - **проверка состояния после действия**;
   - **недопустимые или противоречивые команды**: в HomeBench (ACL 2025) GPT-4o проходит 0 % «invalid multi-device»;
   - **безопасность вызова актуаторов**: Device Context Protocol отклоняет 100 % попыток эскалации полномочий, тогда как «сырой» MCP и IoT-MCP — 0–1 %.

   Каждая из этих проблем годится как требование к архитектуре агента в ВКР.
5. Подходящие среды для экспериментов без железа:
   - для «одноплатника с датчиками» лучше всего подходит **эмуляция среды за MCP-серверами** с тиковой моделью и ускорением времени, по образцу SimuHome (Matter, тик 0.1 с). Так прогон «рабочего дня» укладывается в минуты;
   - **Gazebo Harmonic + ROS 2 Jazzy** (официальная пара по REP-2000, Ubuntu 24.04 arm64 — Tier 1) нужен, только если в постановке появится мобильная платформа или манипулятор. Тогда к агенту подключается готовый ros-mcp-server.

## 1. Интерпретация постановки (сверено с литературой)

Заметки со встречи с литературой сходятся так:

| Фраза из заметок | Что это в терминах литературы | Ближайшие аналоги |
|---|---|---|
| «Работа с одноплатником», «вопрос в одноплатнике» | Хост агента — ресурсно-ограниченное edge-устройство. LLM на нём не крутится | PicoClaw (<10–20 МБ RAM, Go), Home Assistant на SBC, IoT-MCP (MCP-серверы на edge) |
| «Внешняя LLM, которая знает контекст оборудования» | Облачная LLM + grounding: описание доступных навыков/устройств/состояний передаётся в промпт или через инструменты | SayCan (affordances), ProgPrompt (API+объекты в промпте), Sasha/SAGE (JSON-описание дома), ROSA (интроспекция ROS) |
| «Контекст работы с пользователем» | Память предпочтений, история диалога, уточнение недоопределённых целей | Sasha (clarifying), SAGE (user profiler + long-term memory), TidyBot (суммаризация предпочтений) |
| «МСП сервер, чтобы получать информацию о подключенном оборудовании» | MCP: Tools / Resources / Prompts. Спецификация актуальной редакции — 2026-07-28 | ROS MCP Server, IoT-MCP, HA MCP Server, DCP |
| «Инструменты — датчики и исполнительные устройства» | Tool calling к sensor/actuator API, замыкание обратной связи | Inner Monologue (success detection), IoT-MCP (22 типа датчиков), PicoClaw (i2c/spi tools) |
| «Другая метрика, не надёжность; работа во времени; несколько часов в день» | Ресурсный профиль за длительную эксплуатацию: токены/стоимость, задержки, трафик, CPU/RAM, энергия; зависимость от стратегии ведения контекста | Фрагментарно: Sasha, IoT-LLM, IoT-MCP (12 ч), Metareasoning (энергия vs сигнал). Целостной методики нет |
| «RouterAI, GPT mini разных версий» | Сравнение малых коммерческих моделей по качеству и стоимости | SimuHome (GPT-4.1 / mini / nano), IoT-LLM (GPT-4o-mini), HA (gpt-4o-mini по умолчанию) |
| «ROS, Gazebo» | Симуляция роботов для проверки агента без железа | ROSA (TurtleSim, IsaacSim), ROS-LLM, ros-mcp-server (Isaac Sim), RAI |

Уточнение интерпретации. В литературе «агент на edge» бывает двух видов. В первом LLM работает на борту (LLMind 2.0 — Qwen3-0.6B; Metareasoning — LLaMa2-7B на Jetson Orin Nano). Во втором на борту только оркестратор, а LLM внешняя (ROS-LLM, ROSA в API-режиме, IoT-MCP, Home Assistant + OpenAI, PicoClaw). Руководитель сузил тему до **второго варианта**. Тогда главный вычислительный и экономический ресурс — это токены и сеть, а не FLOPs на борту. А ресурсы одноплатника (RAM/CPU/энергия) уходят на сам оркестратор, MCP-серверы, локальную предобработку (например, детекцию на камере) и хранение контекста.

## 3. Источники (25 основных)

### 3.1. Основополагающие работы: LLM как планировщик для робота

#### [1] SayCan: Do As I Can, Not As I Say: Grounding Language in Robotic Affordances (2022)
- **Запись:** Ahn M., Brohan A., Brown N., et al. (всего 45 авторов). Do As I Can, Not As I Say: Grounding Language in Robotic Affordances. *Proceedings of the 6th Conference on Robot Learning (CoRL 2022)*, PMLR 205, pp. 287–318, 2023. arXiv:2204.01691.
- **Ссылки:** https://arxiv.org/abs/2204.01691 ; https://proceedings.mlr.press/v205/ichter23a.html ; https://say-can.github.io/
- **Что это:** LLM (PaLM, FLAN) оценивает, насколько каждый навык из заранее заданной библиотеки полезен для инструкции. Value-функция навыка оценивает, выполним ли он в текущем состоянии. Выбирается навык с максимальным произведением этих оценок: робот служит LLM «руками и глазами», а LLM поставляет семантику задачи.
- **Ключевые факты:** 101 инструкция на естественном языке, две кухонные сцены, мобильный манипулятор. PaLM-SayCan выбирает правильную последовательность навыков в 84 % случаев (planning) и успешно её исполняет в 74 % (execution). Это на 14 и 13 п.п. лучше, чем FLAN-SayCan [сайт проекта; arXiv v2]. Есть открытая версия на симулированном столе [комментарий v2 на arXiv].
- **Польза для ВКР:** даёт первичное обоснование grounding: LLM без знания о возможностях конкретного устройства предлагает невыполнимые действия. Для нас «affordance» — это то, что MCP-сервер оборудования объявляет как доступные инструменты, и их текущая применимость (датчик подключён, актуатор свободен). Схема «значимость × выполнимость» переносится на фильтрацию инструментов перед вызовом LLM, а заодно экономит токены.
- **Проверено:** arXiv API, страница PMLR (pp. 287–318), числа — на сайте проекта.

#### [2] Inner Monologue: Embodied Reasoning through Planning with Language Models (2022)
- **Запись:** Huang W., Xia F., Xiao T., Chan H., Liang J., Florence P., et al. Inner Monologue: Embodied Reasoning through Planning with Language Models. *CoRL 2022*, PMLR 205, pp. 1769–1782, 2023. arXiv:2207.05608.
- **Ссылки:** https://arxiv.org/abs/2207.05608 ; https://innermonologue.github.io
- **Что это:** замкнутый цикл, в котором LLM-планировщик после каждого шага получает текстовую обратную связь: детектор успеха, описание сцены (пассивное), ответы человека (активное).
- **Ключевые факты** [Таблица 4 и результаты, arXiv HTML]:
  - Модели: InstructGPT-1.3B в симулированном и реальном tabletop, PaLM-540B на кухне.
  - Реальная кухня с помехами: SayCan 30.8 %, Inner Monologue с обратной связью Success 48.7 %, Object+Success 60.4 %.
  - Симулированный tabletop, pick-and-place: CLIPort 24 %, Inner Monologue (Object+Scene) 94 %.
  - Реальный tabletop: без детектора успеха 20 %, Object+Success в среднем 90 %.
- **Польза для ВКР:** обосновывает обязательную **проверку результата действия по показаниям датчиков** (state verification), которой нет в открытом цикле. Заодно показывает, что даже модель на 1.3B параметров справляется с планированием, если цикл замкнут. Для нашего агента: после команды актуатору читаем датчик и передаём в LLM короткое текстовое подтверждение. Это отдельная статья расхода токенов, её надо мерить во времени.
- **Проверено:** arXiv API, PMLR (pp. 1769–1782), числа и размеры моделей — по HTML.

#### [3] Code as Policies: Language Model Programs for Embodied Control (2023)
- **Запись:** Liang J., Huang W., Xia F., Xu P., Hausman K., Ichter B., Florence P., Zeng A. Code as Policies: Language Model Programs for Embodied Control. *IEEE ICRA 2023*. DOI: 10.1109/ICRA48891.2023.10160591. arXiv:2209.07753.
- **Ссылки:** https://arxiv.org/abs/2209.07753 ; https://code-as-policies.github.io
- **Что это:** LLM, обученная на коде (Codex `code-davinci-002`, temperature 0), по few-shot примерам пишет Python-программы политик. Эти программы вызывают API восприятия и примитивов управления, а неопределённые функции LLM дописывает рекурсивно (hierarchical code-gen).
- **Ключевые факты** [arXiv HTML]:
  - HumanEval: 39.8 %.
  - Собственный бенчмарк RoboCodeGen: 37 задач.
  - Задачи на пространственное рассуждение (Таблица IV): обычный NL — 35 %, CoT — 58 %, код (LMP) — 98 %.
  - Обобщение на невиданные атрибуты и инструкции (UA UI Long-Horizon, по 50 испытаний на задачу): CLIPort 0 %, NL-планировщик 64 %, CaP 80 %.
- **Польза для ВКР:** код как промежуточное представление точнее свободного текста и, что важно для нас, **кэшируется и переиспользуется** без повторного вызова LLM. Это рычаг снижения токенов за сутки работы (см. LLMind [15]). Минус для одноплатника: генерируемый код надо где-то безопасно исполнять (песочница, ограничения), а это стоит RAM/CPU.
- **Проверено:** arXiv API, OpenAlex (ICRA 2023, DOI), числа — в HTML.

#### [4] ProgPrompt: Generating Situated Robot Task Plans using Large Language Models (2023)
- **Запись:** Singh I., Blukis V., Mousavian A., Goyal A., Xu D., Tremblay J., Fox D., Thomason J., Garg A. ProgPrompt: Generating Situated Robot Task Plans using Large Language Models. *IEEE ICRA 2023*, DOI: 10.1109/ICRA48891.2023.10161317. Расширенная версия: *Autonomous Robots* 47(8):999–1012, 2023, DOI: 10.1007/s10514-023-10135-3. arXiv:2209.11302.
- **Ссылки:** https://arxiv.org/abs/2209.11302 ; https://progprompt.github.io
- **Что это:** промпт строится как программа. В нём импорты доступных действий (API), список объектов окружения и примеры программ-планов с комментариями и assert-проверками предусловий. LLM дописывает новую функцию-план.
- **Ключевые факты** [Таблица I и III, arXiv HTML]:
  - Датасет: 70 бытовых задач в VirtualHome.
  - Метрики: SR — доля выполнений, где достигнуты все целевые условия; Exec — доля исполнимых действий плана; GCR — полнота целевых условий.
  - GPT-3, полная конфигурация: SR 0.34±0.08, Exec 0.84, GCR 0.65.
  - Codex: SR 0.40±0.11, Exec 0.90, GCR 0.72.
  - Базовая линия Huang et al. и LangPrompt на том же GPT-3: SR 0.00.
  - На дополнительных сценах средний SR 0.48.
  - Есть демонстрация на физическом манипуляторе.
- **Польза для ВКР:** даёт образец **формата передачи контекста оборудования**: «API + объекты + примеры» в программном виде. Этот формат можно сравнить с MCP-описанием tools по качеству и по длине в токенах. Метрики SR/Exec/GCR годятся для наших сценариев, где есть целевое состояние устройств.
- **Проверено:** arXiv API, OpenAlex (ICRA + AuRo), Crossref (AuRo 47(8):999–1012), числа — в HTML.

#### [5] ChatGPT for Robotics: Design Principles and Model Abilities (2024)
- **Запись:** Vemprala S. H., Bonatti R., Bucker A., Kapoor A. ChatGPT for Robotics: Design Principles and Model Abilities. *IEEE Access*, vol. 12, pp. 55682–55696, 2024. DOI: 10.1109/ACCESS.2024.3387941. arXiv:2306.17582 (Microsoft).
- **Ссылки:** https://arxiv.org/abs/2306.17582 ; https://github.com/microsoft/PromptCraft-Robotics (MIT, ≈2.1k звёзд)
- **Что это:** экспериментальное исследование ChatGPT в робототехнике. Ключевой приём — **высокоуровневая библиотека функций**: вместо генерации кода под конкретную платформу LLM вызывает простые функции, которые на бэкенде связаны с API реальной платформы. Авторы описывают принципы проектирования промптов и диалога с человеком в контуре.
- **Ключевые факты** [arXiv HTML, оглавление и разделы]: сценарии — реальный дрон, AirSim (инспекция, обход препятствий), манипуляция (сборка логотипа из кубиков), навигация в Habitat с текстовым описанием сцены (полярные координаты объектов) на каждом шаге. Оценка в основном качественная, на примерах.
- **Польза для ВКР:** это прямой предок идеи «MCP-сервер оборудования как библиотека функций». Работа даёт аргумент за **узкий высокоуровневый интерфейс** вместо сырых вызовов (I2C-регистры, топики ROS). Это и надёжнее, и короче по токенам. Пример с Habitat показывает «телеметрию в виде короткого текста», то есть то, как стоит отдавать показания датчиков LLM.
- **Проверено:** arXiv API, Crossref (IEEE Access 12:55682–55696), GitHub API.

#### [6] TidyBot: Personalized Robot Assistance with Large Language Models (2023)
- **Запись:** Wu J., Antonova R., Kan A., Lepert M., Zeng A., Song S., Bohg J., Rusinkiewicz S., Funkhouser T. TidyBot: Personalized Robot Assistance with Large Language Models. *Autonomous Robots* (спецвыпуск «LLMs in Robotics»), 2023; также *IEEE/RSJ IROS 2023*. arXiv:2305.05658.
- **Ссылки:** https://arxiv.org/abs/2305.05658 ; https://tidybot.cs.princeton.edu
- **Что это:** LLM по нескольким примерам («куда этот пользователь кладёт вещи») суммаризует **обобщённые предпочтения пользователя** и применяет их к новым объектам.

#### [18] LLMind и LLMind 2.0 (2025)
- **Запись (1):** Cui H., Du Y., Yang Q., Shao Y., Liew S. C. LLMind: Orchestrating AI and IoT with LLM for Complex Task Execution. *IEEE Communications Magazine* 63(4):214–220, 2025. DOI: 10.1109/MCOM.002.2400106. arXiv:2312.09007.

- **Что это:**
  - LLMind — центральный координатор. - **Ключевые факты:**
  - LLMind 1: количественных метрик нет (по разбору HTML).

Агенты устройств в эксперименте запущены на **GTX 1060** как «представителе» вычислительных возможностей IoT. - **Польза для ВКР:** накопление опыта (кэш скриптов и планов) — **ключевой механизм снижения токенов и задержки «во времени»**: повторяющиеся ежедневные запросы перестают ходить в LLM. Его эффект в работе не измерен, и это измеримая гипотеза для нас. LLMind 2.0 показывает граничный вариант, когда на устройстве работает микромодель для узкой подзадачи. При этом «edge» там на деле GTX 1060, а не одноплатник, и это стоит отмечать при сравнении.

Польза: предупреждение для главы об ограничениях: успех в эмуляции ≠ успех на железе, поэтому финальная часть ВКР нужна хотя бы на одном реальном датчике или актуаторе.
- **SMH-Bench** (arXiv:2606.01912, 2026, препринт): 1 100 задач, 7 категорий и 22 подкатегории; дома до 135 устройств на исполняемом симуляторе HomeEnv. Слабые места моделей: планирование автоматизаций, неоднозначность, персонализация, рост сложности дома [аннотация].
- **When IoT Meet LLMs: Applications and Challenges.** Kok I., Demirci O., Ozdemir S. *IEEE BigData 2024*, arXiv:2411.17722. Обзор интеграции LLM с IoT в парадигмах edge/fog/cloud [аннотация]. Польза: обзорная ссылка для главы 1 по IoT.
- **A Survey of Foundation Models for IoT: Taxonomy and Criteria-Based Analysis.** Wei H. et al. arXiv:2506.12263, принят в CCF TPCI. Работы сгруппированы по целям: эффективность, контекстная осведомлённость, безопасность, приватность [аннотация].
- **VirtualHome** (Puig et al., CVPR 2018 Oral, arXiv:1806.07011) и **AI2-THOR** (Kolve et al., arXiv:1712.05474) — бытовые симуляторы, на которых оценивали ProgPrompt и EAI. Для одноплатника с датчиками они избыточны (Unity3D, визуальные сцены); их уместно упомянуть в обзоре симуляторов.
- **ROS 2 / Gazebo (REP-2000):** https://www.ros.org/reps/rep-2000.html (источник: github.com/ros-infrastructure/rep). **Jazzy Jalisco** (LTS, май 2024 – май 2029) — Tier 1 на Ubuntu 24.04 amd64 и **arm64**, macOS — Tier 3; парная версия Gazebo — **Harmonic**. Kilted Kaiju (май 2025 – ноябрь 2026) идёт в паре с Gazebo Ionic. Вывод: для ВКР брать Jazzy + Harmonic. На Mac запускать в Docker или ВМ с Ubuntu 24.04 arm64, так как нативный macOS — Tier 3.
- **Спецификация MCP** (текущая редакция 2026-07-28): https://modelcontextprotocol.io/specification/latest. JSON-RPC 2.0, stateless-запросы. Возможности сервера — Resources, Prompts, Tools; клиента — Elicitation. Есть расширение **Tasks** для долгих асинхронных операций, что естественно подходит для актуаторов с длительным исполнением. В принципах безопасности — явное согласие пользователя на вызов инструментов. Подробный разбор MCP, вероятно, в соседней области обзора.

## 6. Что применимо к одноплатнику с датчиками

1. **Интерфейс оборудования — узкий и высокоуровневый, через MCP** ([5], [9], [10], [19], [23]). Сырые I2C/SPI-инструменты (как в PicoClaw) удобны для отладки, но дороги по токенам и опасны. Основной вариант — семантические инструменты: `get_temperature(room)`, `set_relay(id, on)`, `camera.describe()`. Сырые лучше оставить как режим эксперта с подтверждением.
2. **Контекст оборудования — по запросу, а не дампом** ([11] фильтрация устройств, [9]/[10] интроспекция, [15] exposed entities). Это главная переменная эксперимента: полный снимок состояния в каждом промпте, сводка с изменениями или только инструменты для запроса (`GetLiveContext`).
3. **Телеметрия — агрегированная** ([16]: 10 с ЭКГ ≈ 5 100 токенов; [17]: предобработка даёт до +108 % относительного прироста у GPT-4o-mini на HAR-3cls). Одноплатник считает признаки и события, детектор на камере отдаёт текст.
4. **Замкнутый цикл с проверкой состояния** ([2], [14]): после действия читаем датчик. Это стоит токенов, но без этого падает успех.
5. **Кэш планов и скриптов** ([3], [18]): повторяющиеся команды исполняются без LLM. Ожидается, что доля попаданий в кэш растёт по ходу дня и недели, — это измеримо.
6. **Расписания и триггеры исполняются локально кодом** ([12] персистентные команды, [14] планирование по времени): LLM вызывается один раз, чтобы создать правило, а не на каждой проверке условия.
7. **Валидация команд актуаторам на хосте** ([9] blacklist и e-stop, [20] DCP, [23] confirm). Ресурсно почти бесплатна.
8. **Fallback при потере сети** ([21]): правила, кэш, при желании микромодель ≤0.6–1.5B ([18], [22]) для классификации интентов или «безопасного режима».
9. **Платформа:** Raspberry Pi 5 (8 ГБ) — разумная цель: Ubuntu 24.04 arm64 — Tier 1 для ROS 2 Jazzy ([REP-2000]), мощность около 10 Вт под LLM-нагрузкой ([22]). Агенту без локальной LLM хватит и меньшего (PicoClaw — на Pi Zero 2 W и LicheeRV-Nano). До покупки можно эмулировать в Docker arm64 на M4 Pro с ограничениями `--cpus` и `--memory`. Цифры энергии в эмуляции получить нельзя, их снимаем на железе USB-ваттметром.

## 7. Выводы

1. Схема «внешняя LLM + тонкий агент на edge + MCP-серверы оборудования + контекст пользователя» хорошо обоснована литературой. Её элементы появились в 2022–2024 годах (function library, grounding, обратная связь, память предпочтений), а с 2025 года стандартизованы через MCP. Это **инженерно реализуемая постановка с готовыми базовыми линиями**: ROSGPT-подобная трансляция, Home Assistant + gpt-4o-mini, PicoClaw.
2. Научная новизна ВКР — **не в самом агенте, а в методике и результатах оценки его работы во времени на ограниченном хосте**. Ни одна работа из 25 не даёт многочасового профиля «токены / стоимость / трафик / задержки / CPU / RAM / энергия» и его зависимости от стратегии контекста, кэша и модели.
3. Самые дорогие по токенам решения в литературе: передача полного состояния дома или сырых рядов датчиков в промпт и повторный вызов LLM на одинаковые запросы. Им противостоят фильтрация, агрегация, интроспекция по запросу, кэш планов и локальные триггеры. Это **естественные факторы эксперимента**.
4. «Mini»-модели — рабочий вариант для простых запросов и управления: GPT-4.1-mini 96 % на запросах состояния в SimuHome, GPT-4o-mini с предобработкой в IoT-LLM. На временных и неявных задачах они сильно проседают, а nano-версии почти неработоспособны. Значит, нужен **сравнительный эксперимент по качеству и стоимости по классам сценариев**. RouterAI с централизованной оплатой факультета для этого подходит.
5. Симулятор робота (Gazebo/ROS 2) не обязателен для ядра работы. Для «одноплатника с датчиками» адекватнее и дешевле **эмулированная среда за MCP-серверами** с тиковой моделью и ускорением времени. Gazebo через ros-mcp-server — опциональное расширение на актуатор-робота.

## 8. Открытые проблемы

- Нет **методики и метрик длительной эксплуатации** LLM-агента на edge-хосте: что считать (токены, $, трафик, Вт·ч, p95-задержка, RAM), на каком профиле нагрузки (сценарий «день»), как нормировать (на команду, на час, на сутки).
- **Рост контекста во времени**: история диалога, память пользователя, журнал состояний. Неясно, как ограничивать его при фиксированном окне модели (≥8192 по ROSA) и бюджете токенов и как часто пересуммаризировать (TidyBot, SAGE).
- **Временные задачи** (расписания, «когда X — сделай Y») остаются худшей категорией даже у сильных моделей (SimuHome).
- **Невалидные и мультиустройственные команды** (HomeBench: 0 % у GPT-4o на IM).
- **Безопасность актуаторов** при недоверенной LLM и prompt injection: даже DCP отсекает только 78 % инъекций.
- **Связь как ресурс**: энергия и задержка облачного вызова зависят от сигнала (Metareasoning). Политика fallback для одноплатника не стандартизована.
- **Sim-to-real**: успех в симуляции не переносится автоматически (SimVerity).
- **Несравнимость бенчмарков**: у каждой работы свой набор, и нет общего бенчмарка «одноплатник + датчики + MCP + пользователь».
- **Зависимость успеха от конвенций tool calling** конкретной модели (IoT-MCP: Claude 99–100 % против заметно более низких значений у DeepSeek V3 и GPT-4.1).

## 9. Следствия для ВКР

### 9.1. Постановка
Объект — LLM-агент для приложений граничного ИИ на одноплатном компьютере. Предмет — архитектура агента с внешней LLM и MCP-доступом к оборудованию, а также её ресурсные характеристики при длительной эксплуатации. Цель — разработать агента и методику оценки, которая показывает, как архитектурные решения (стратегия передачи контекста оборудования и пользователя, кэш планов, локальные триггеры, выбор модели) влияют на ресурсный профиль системы за N часов работы при сохранении качества.
Возможная формулировка гипотезы: при заданном сценарии суток агрегирование телеметрии на edge, контекст по запросу и кэш планов вместе снижают число токенов и стоимость в разы. Success rate при этом не должен статистически значимо падать относительно наивного агента («полный дамп + без кэша»). Проверка — тест эквивалентности TOST, он уже есть в harness/.

### 9.2. Архитектура (компоненты с обоснованием из литературы)
1. **Ядро агента** — ReAct-цикл с tool calling (ROSA, SimuHome), OpenAI-совместимый клиент к RouterAI.
2. **MCP-серверы оборудования:**
   - `sensors`: агрегированные показания и события — [16], [17];
   - `camera`: локальная детекция, наружу отдаётся текст — LLMind;
   - `actuators`: валидация диапазонов и полномочий, dry-run, подтверждение — [20], [23], [9];
   - опционально `ros` через ros-mcp-server [10].
3. **Менеджер контекста:**
   - оборудование: инвентарь, текущее состояние, лента изменений; отдаётся по запросу или сводкой;
   - пользователь: профиль предпочтений с суммаризацией (TidyBot, SAGE) и история диалога с усечением.
4. **Планировщик времени и триггеры**: локальное исполнение правил, которые создала LLM (SAGE persistent commands, SimuHome scheduling).
5. **Кэш планов и скриптов** с семантическим поиском (LLMind experience accumulation).
6. **Fallback** при недоступности LLM: правила и кэш (Metareasoning).
7. **Монитор ресурсов**: токены, $, трафик, задержки по компонентам (как декомпозиция в IoT-MCP), CPU/RAM процесса, энергия на железе. Использовать имеющийся `monitor/`.

### 9.3. Эксперименты
1. **Среда без железа (сейчас):** эмулятор дома или лаборатории с тиковой моделью (по образцу SimuHome: тик 0.1 с, ускорение времени, детерминизм) за MCP-серверами. Хост агента — Docker arm64 на M4 Pro с ограничениями `--cpus` и `--memory` под Pi 5 или Pi Zero 2 W. Сеть деградируется через `tc netem` (задержка, потери, обрыв).
2. **Нагрузка «сутки»:** поток пользовательских запросов по классам (состояние, явное управление, неявное намерение, расписания, невыполнимые и мультиустройственные — по HomeBench и SimuHome) и события среды. Длительность: несколько виртуальных часов или суток при ускорении. Токены и деньги при этом реальные: вызовы идут в RouterAI.
3. **Факторы:**
   - стратегия контекста: полный дамп / сводка / по запросу;
   - уровень агрегации телеметрии;
   - кэш вкл/выкл;
   - локальные триггеры против опроса через LLM;
   - модель: GPT-4.1-mini / nano, GPT-4o-mini, GPT-5-mini — проверить фактическую доступность в RouterAI;
   - качество сети.
4. **Метрики:**
   - качество: SR по состоянию (как в SimuHome) и по типам ошибок (как в EAI);
   - ресурсы: токены вход/выход, $/сутки, число вызовов LLM, доля попаданий в кэш, трафик, p50/p95 задержки end-to-end и по компонентам, пиковая и средняя RAM, CPU-время хоста, рост размера контекста и памяти за прогон, на железе — Вт·ч/сутки.
5. **Базовые линии:**
   - наивный агент (полный дамп, без кэша);
   - ROSGPT-подобная трансляция «текст → JSON» без цикла;
   - готовый агент (PicoClaw или Home Assistant + gpt-4o-mini) на той же нагрузке, если позволит время.
6. **Статистика:** бутстреп-интервалы и TOST из `harness/`. Корректность tool calling у mini-моделей отдельно проверяется на стенде BFCL (`harness/`) — это прямо закрывает проблему «зависимость от конвенций tool calling» [19].
7. **Железо (после покупки):** Raspberry Pi 5 (8 ГБ) + 2–3 датчика (например, AHT20/BME280 по I2C, PIR) + реле или сервопривод + опционально USB-камера. Повторить подмножество прогонов, снять энергию USB-ваттметром, сравнить с эмуляцией — это отдельный подраздел об ограничениях, по SimVerity.
8. **Опционально:** ROS 2 Jazzy + Gazebo Harmonic в Docker, TurtleBot3 через ros-mcp-server — как демонстрация переносимости агента на «исполнительное устройство-робот».
