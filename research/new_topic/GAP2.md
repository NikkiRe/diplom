# GAP2. Контекст оборудования на уровне ОС и стандарты описания устройств

**Тема ВКР (согласована 06.10.2026):** «Разработка ИИ-агента для приложений граничного искусственного интеллекта».
**Пробел, который закрывает заметка.** Фраза руководителя «мсп сервер, чтобы получать информацию о подключённом оборудовании» требует ответа на вопрос, *как MCP-сервер на Linux узнаёт, что подключено*. В заметках A–G этого слоя не было (0 упоминаний IIO, libgpiod, device tree, udev, V4L2). Не было и стандартов описания возможностей устройств (0 упоминаний WoT, SenML, LwM2M). Вместо них B и D предлагали самодельные `hw://` и манифест в стиле DCP, хотя сама работа DCP (разобрана в B [C2] и C [20]) называет направление «MCP + W3C WoT как слой описания».

## 0. Главное

1. **Linux узнаёт оборудование двумя принципиально разными путями.** USB и PCI перечисляются аппаратно: устройство само сообщает VID:PID и классы. I2C, SPI, GPIO, UART не перечисляются: документация ядра прямо говорит, что для I2C программа должна заранее знать, что и по какому адресу подключено [K4]. На Raspberry Pi это знание задаётся **device tree overlay** в `config.txt` (`dtoverlay=i2c-sensor,bme280`, `dtoverlay=w1-gpio`, `dtoverlay=dht11`) [P1, P2]. Только после этого драйвер ядра поднимает устройство в стандартной подсистеме. Отсюда главный инженерный вывод: **MCP-сервер не должен «искать» датчики на шине — он должен читать то, что ядро уже описало.**

2. **Ядро уже даёт машиночитаемое описание каналов с единицами.** Подсистема IIO публикует `/sys/bus/iio/devices/iio:deviceN/` с файлами вида `in_temp_input`, `in_humidityrelative_raw`, `in_pressure_scale`. Для каждого типа канала ABI фиксирует единицу: температура — милли-°C, влажность — милли-%, давление — кПа, напряжение — мВ, ускорение — м/с². Правило пересчёта: значение = (raw + offset) × scale [K1]. hwmon делает то же для `temp*_input` (милли-°C), `in*_input` (мВ), `power*_input` (мкВт) [K2]; 1-Wire `w1_therm` отдаёт `temperature` в 1/1000 °C [K7]. Это готовый вход для **механической** генерации описания устройства, без LLM.

3. **Оверлей `i2c-sensor` в ядре Raspberry Pi (ветка rpi-6.18.y) знает 64 модели датчиков** (BME280, AHT20, SHT3x, BH1750, MPU6050, INA238, SCD4x и др.) [P2, собств. подсчёт по README оверлеев]. В стандартном ядре Pi модули `BMP280` (покрывает BME280), `DHT11`, `W1_SLAVE_THERM`, `SENSORS_IIO_HWMON` включены [P3]. Для типового хоббийного набора «датчики → IIO/hwmon/w1» путь через ядро уже существует.

4. **Sysfs GPIO официально устарел, но в ядре Pi ещё включён.** Документация ядра называет интерфейс устаревшим и обещает удалить его; новые разработки должны идти через символьное устройство `/dev/gpiochipN` [K5]. В Kconfig опция `GPIO_SYSFS` спрятана за `EXPERT`, а ABI v1 символьного устройства помечен как устаревший [K6]. При этом в `bcm2711_defconfig`/`bcm2712_defconfig` Raspberry Pi стоит `CONFIG_GPIO_SYSFS=y` [P3]. Вывод для ВКР: работать через **libgpiod v2** (v2.0 от 02.03.2023, текущая 2.3.1 от 03.07.2026 [K8]); там есть события фронтов с метками времени и `gpionotify` для изменений линий — источник событий вместо опроса.

5. **Опрос шины I2C опасен, и это не теория.** Страница man `i2cdetect` предупреждает, что программа «can confuse your I2C bus, cause data loss and worse» [K9]. PicoClaw выдаёт LLM инструмент `i2c` с действием `scan`: он перебирает адреса 0x08–0x77 той же гибридной стратегией, что `i2cdetect` (SMBus Quick Write и Read Byte), и подтверждения `confirm` для этого не требует — оно нужно только для записи [R7, V-code]. Для ВКР: **инструмент сканирования шины не выдавать модели**; инвентарь строить по sysfs.

6. **«Семантическая наблюдаемость» (термин Octopus [L5]) — удобная ось для классификации.** Я ввожу три уровня (**собственная классификация** на основе таблицы Octopus):
   - **A** — ОС знает тип, каналы и единицы (IIO, hwmon, w1_therm с драйвером);
   - **B** — ОС знает идентичность, но не возможности (USB VID:PID, имя V4L2-узла, HAT EEPROM);
   - **C** — ОС знает только транспорт (адрес I2C без драйвера, линия GPIO, `/dev/ttyUSB0`).

   Для C нужен человеческий «профиль» (как Layer 2 в Octopus). Это прямо определяет, какая часть контекста оборудования генерируется автоматически, а какая пишется руками.

7. **Стандарт описания уже есть: W3C WoT Thing Description 1.1** (Рекомендация W3C от 05.12.2023) [S1]. TD описывает свойства, действия и события, типы данных, `unit`, `minimum`/`maximum`, `readOnly`, а в `forms` — как до них дотянуться. Есть официальная JSON Schema (версия 1.1-12-March-2025) [S1s], WoT Discovery (Рекомендация от 05.12.2023: `/.well-known/wot`, DNS-SD `_wot._tcp`, каталог TD с API `/things`) [S2]. У node-wot есть привязки `file://` и `modbus+tcp://` [R2] — то есть **TD может буквально указывать на файл sysfs**. TD 2.0 пока только First Public Working Draft (04.11.2025) без гарантии обратной совместимости [S3].

8. **Связка LLM + MCP + WoT существует, но молодая.** Работа, где MCP-шлюз стоит поверх WoT Things, найдена одна — Web-of-Drones (по полю comments arXiv принята на IEEE WoWMoM 2026): 4 универсальных инструмента (`list_web_things`, `read/write_web_thing_property`, `call_web_thing_action`), каталог TD Zion, 6 LLM [L1]. Ещё есть LLM-MaGe (ICWE 2025): LLM переводит запрос и набор TD в PDDL для планировщика [L4]. Открытые мосты TD→MCP — `macc-n/wot-mcp` (10★), `thingctx` (15★), `thingwire` (1★) [R3–R5]; оценок ни у одного нет. **Поправка к подсказке задания:** AgentOptics [L2] — это 64 MCP-инструмента для 8 оптических устройств, но **WoT в статье не упоминается ни разу** (проверено по полному тексту: 0 вхождений «Web of Things», «Thing Description», «W3C»). DCP [L3] относит её к «линии MCP + WoT» только в смысле «протокол не меняется, безопасность — в рантайме».

9. **Собственное измерение (GAP2_artifacts, синтетический набор: 7 устройств, 10 свойств; токенизатор o200k_base, как у GPT-4o/4.1/5 mini и nano):**
   - полный TD в промпте стоит **1 027 токенов**, «агентский» вид TD без `forms`/`@context`/`security` — **253** (в 4,1 раза меньше), текстовая строка на устройство — **86**;
   - MCP «инструмент на свойство» — **469** токенов на каждый вызов LLM, 4 универсальных инструмента + ответ `list_devices` — **327**; при 140 устройствах — 9 782 против 2 861 (в 3,4 раза);
   - снимок состояния в SenML — **248** токенов против **121** у компактного JSON и **110** у текста: стандарт для провода и журнала, но не для промпта.

   Переводя в деньги (F: 480 вызовов в сутки, gpt-5-mini 27,60 ₽ за 1 млн входных токенов без кэша): каталог «инструмент на свойство» стоит 6,21 ₽/сутки при 7 устройствах и 129,59 ₽/сутки при 140 (**расчёт**).

10. **Шины сильно различаются по стоимости чтения, и это прямо метрика «работы во времени».** DS18B20 при 12 битах блокирует чтение на 750 мс (95/190/375 мс при 9/10/11 битах), а мастер 1-Wire по умолчанию ищет новые устройства раз в 10 с [K7, V-code]. I2C на Pi по умолчанию работает на 100 кГц [P2]. В IoT-MCP заметно дольше отвечали датчики на I2C (MPU6050), а 30–75 % времени ответа съедал сервер соединений [L6]. Значит, чтение датчиков надо вынести с критического пути LLM: фоновый сэмплер плюс кэш с `ttlMs` не меньше времени преобразования.

11. **До покупки платы эмулировать можно не всё, и это зависит от дистрибутива ВМ** [K10, V-code]:
    - Debian 13 trixie (ядро 6.12.111): из четырёх модулей эмуляции есть только `VIDEO_VIVID` (виртуальная камера); `GPIO_SIM`, `I2C_STUB`, `IIO_SIMPLE_DUMMY` не включены;
    - Debian experimental (7.3-rc6): добавляется `GPIO_SIM`;
    - Fedora (kernel-ark, ветка os-build): включены `GPIO_SIM`, `I2C_STUB` и `VIDEO_VIVID`, нет только `IIO_SIMPLE_DUMMY`;
    - в ядре Raspberry Pi нет `GPIO_SIM` и `I2C_STUB` [P3].

    План из A «i2c-stub в ВМ colima» на ядре Debian stable не сработает. Для Linux-ВМ на M4 лучше Fedora aarch64; перед планированием всё равно проверить `modinfo gpio-sim i2c-stub vivid`. Без ВМ, прямо на Mac, — HAL с подменяемым корнем sysfs (`sysfs_probe.py --root`). Для записи и воспроизведения реальной платы — umockdev [R6].

12. **Рекомендация для архитектуры:** вместо самодельного `hw://` взять внутреннюю модель **TD 1.1** (генерируется из sysfs и профилей), а в LLM отдавать её **проекции**: компактный инвентарь, MCP-инструменты (explicit или generic — это переменная эксперимента), снимок состояния текстом или компактным JSON. SenML оставить для журнала и обмена с узлами. Подробно — §7–8.

## 2. Слой ОС: как Linux узнаёт, что подключено

### 2.1. Перечисляемые и объявляемые шины

- **USB/PCI** перечисляются аппаратно. В sysfs для каждого USB-устройства есть `idVendor`, `idProduct`, `manufacturer`, `product` [K3]. Корневые хабы имеют VID 1d6b (Linux Foundation). Но VID:PID — это уровень B: по нему видно *кто*, а не *что умеет*. Octopus показывает это на примере: `/dev/ttyACM0` с VID:PID не отличает манипулятор от платы датчиков или контроллера 3D-принтера [L5].
- **I2C** не перечисляется. Документация ядра даёт четыре способа объявить устройство: статически (device tree, ACPI, board info), явно из драйвера, пробингом через `detect()` и из userspace записью в `/sys/bus/i2c/devices/i2c-N/new_device`. Пробинг ядро советует по возможности не использовать и включает его только для шин, которые явно на это согласились [K4].
- **1-Wire** — промежуточный случай: мастер периодически ищет ведомых сам, ID ведомого начинается с кода семейства (`28-…` — DS18B20) [K7]. То есть тип датчика виден, но надо, чтобы оверлей `w1-gpio` поднял мастер на нужном GPIO (по умолчанию GPIO4) [P2].
- **GPIO/UART** — только транспорт: линия или tty ничего не говорят о том, что к ним подключено.

### 2.2. Device tree и оверлеи на Raspberry Pi [P1, P2]

- Ядро и прошивка Pi описывают оборудование деревом устройств. Оверлеи описывают *необязательное* внешнее оборудование и принимают параметры. Задаются строками `dtoverlay=` и `dtparam=` в `/boot/firmware/config.txt`. Пустая `dtoverlay=` в начале запрещает загрузку оверлея HAT [P1].
- **Готовые оверлеи для датчиков** (README оверлеев, ветка rpi-6.18.y; всего описано 411 оверлеев):
  - `i2c-sensor` — 64 модели, параметр `addr` (например BME280: 0x76–0x77, по умолчанию 0x76; MPU6050: 0x68/0x69);
  - `dht11` — DHT11/DHT21/DHT22 (AM230x), параметр `gpiopin`, по умолчанию 4;
  - `w1-gpio` и `w1-gpio-pullup` (+ варианты `-pi5`), `gpiopin` по умолчанию 4.
- **Загрузка во время работы**: утилита `dtoverlay` (`-l` — список активных, `-h <overlay>` — справка) применяет оверлей на лету. Документация предупреждает, что не все подсистемы ядра реагируют на добавление устройств во время работы. I2C, SPI и звук работают, остальные — не обязательно [P1].
- **Стабильный путь к живому дереву** — симлинка `/proc/device-tree`; прямой путь `/sys/firmware/devicetree/base` ядро использовать запрещает [K3b].
- **HAT+ EEPROM.** При загрузке прошивка опрашивает пины ID_SD/ID_SC и ищет EEPROM по адресам 0x50–0x53. В EEPROM обязательны UUID продукта, строки производителя и продукта и рекомендуется имя оверлея. Оверлей прошивка загружает сама, пропуская его имя через `overlay_map` [P4]. Файл `hat_map` позволяет подменить оверлей для старых HAT без перепрошивки EEPROM [P1]. Спецификация HAT+: первая редакция 08.12.2023, последняя 05.12.2024 [P4]. Что прошивка кладёт строки EEPROM в `/proc/device-tree/hat/{vendor,product,uuid,…}`, подтверждают форум и документация RevPi, но не официальный документ — **[не первоисточник]**.

**Следствие для ВКР.** «Подключение нового датчика» на Pi — это строка в `config.txt` (или `dtoverlay` на лету) плюс, возможно, профиль. Это декларативный и воспроизводимый шаг, его можно описать в методике эксперимента.

### 2.3. IIO: датчики с единицами в ABI [K1]

- Каталог устройства: `/sys/bus/iio/devices/iio:deviceX/`, атрибут `name` — обычно номер детали (`bme280`).
- **Каналы и единицы** (ABI `sysfs-bus-iio`, ядро 7.3-rc6; в файле 870 записей `What:`):

| Тип IIO | Атрибуты | Единица после scale/offset | SenML (RFC 8428) |
|---|---|---|---|
| `temp` | `in_temp_raw`, `in_temp_input`, `in_tempY_*` | милли-°C | `Cel` ×10⁻³ |
| `humidityrelative` | `in_humidityrelative_*` | милли-% | `%RH` ×10⁻³ |
| `pressure` | `in_pressure_*` | кПа | `Pa` ×10³ |
| `illuminance` | `in_illuminance_*` | лк | `lx` |
| `voltage` | `in_voltageY_raw` | мВ | `V` ×10⁻³ |
| `current` | `in_currentY_raw` | мА | `A` ×10⁻³ |
| `power` | `in_powerY_*_raw` | мВт | `W` ×10⁻³ |
| `accel` | `in_accel_{x,y,z}_raw` | м/с² | `m/s2` |

- **Пересчёт**: offset прибавляется к raw *до* умножения на scale. Если offset всегда 0 или неизвестен, файла нет. scale/offset бывают на канал (`in_voltage0_scale`) и на тип (`in_voltage_scale`) [K1]. Если есть `*_input`, это уже обработанное значение.
- **Тонкость для конвертера**: во вторичных единицах SenML (RFC 8798) порядок обратный — значение × scale + offset [S5]. При генерации описаний порядок легко перепутать; в `test_gap2.py` есть тесты на формулу IIO и на scale «на канал» и «на тип».
- **Что реально отдают драйверы** [V-code]:
  - `bmp280-core.c`: у BME280 для давления, температуры и влажности одновременно `PROCESSED` (оставлен для совместимости ABI), `RAW`, `SCALE` и `OVERSAMPLING_RATIO`;
  - `dht11.c`: только `PROCESSED` для температуры и влажности; совместимая строка DT — `dht11`.
- **Буферы и триггеры**: `/dev/iio:deviceX` для потокового чтения, программные триггеры (hrtimer) через configfs `/config/iio/triggers/hrtimer/<имя>` [K1, K1b]. Это путь для частых измерений без опроса sysfs.
- **libiio** (Analog Devices, 640★, LGPL-2.1) работает с локальными и удалёнными IIO-устройствами (сетевой бэкенд) [R1]. Утилита `iio_info` печатает дерево каналов.

### 2.4. hwmon [K2]

- `/sys/class/hwmon/hwmonX/name` — единственный обязательный атрибут; у I2C-устройств создаётся автоматически.
- Единицы: `tempY_input` — милли-°C, `inY_input` — мВ, `currY_input` — мА, `powerY_input` — мкВт, `humidityY_input` — милли-%, `fanY_input` — об/мин.
- Документация советует идти через libsensors, а не читать sysfs напрямую: иначе программа сама должна делать пересчёт, метки и скрытие входов. Для агента это означает: либо libsensors, либо явная таблица единиц, как в артефакте.
- Температуру SoC на Pi ядро отдаёт через тепловую зону (`/sys/class/thermal`, ABI `sysfs-class-thermal`); имя hwmon-устройства `cpu_thermal` в фикстуре — моё допущение, проверить на плате. Это бесплатная метрика «работы во времени» (троттлинг).

### 2.5. GPIO: символьное устройство и libgpiod v2

- **Статус sysfs** [K5, K6]: интерфейс `/sys/class/gpio` объявлен устаревшим, ABI перенесён в `obsolete/`, новые разработки — только через символьное устройство, интерфейс удалят. В Kconfig `GPIO_SYSFS` доступен только при `EXPERT`, а глобальная нумерация вынесена в `GPIO_SYSFS_LEGACY`. ABI v1 символьного устройства (`GPIO_CDEV_V1`) помечен как устаревший.
- **Символьное устройство** [K5b]: `/dev/gpiochipN`; ioctl `GPIO_GET_CHIPINFO_IOCTL` (имя, метка, число линий), `GPIO_V2_GET_LINEINFO_IOCTL` (имя линии, потребитель, флаги: вход/выход, используется, active-low, подтяжки), `GPIO_V2_GET_LINE_IOCTL` (запрос линий), `GPIO_V2_GET_LINEINFO_WATCH_IOCTL` (наблюдение за изменениями). События фронтов приходят с метками времени. uAPI v2 появился в Linux 5.10.
- **libgpiod** [K8]: библиотека на C, биндинги и утилиты `gpiodetect`, `gpioinfo`, `gpioget`, `gpioset`, `gpiomon`, `gpionotify`; есть D-Bus-интерфейс. Релизы: 2.0 — 02.03.2023, 2.1 — 03.11.2023, 2.2 — 22.10.2024, 2.3 — 16.06.2026, 2.3.1 — 03.07.2026 (листинг kernel.org). Зеркало на GitHub: 445★.
- **Для инвентаря**: имена линий берутся из `gpio-line-names` в DT, но «что подключено к GPIO17» ОС не знает никогда — это уровень C, нужен профиль.
- **Для событий**: PIR на GPIO — это событие фронта (`gpiomon` или чтение событий из запроса линий в libgpiod), а не опрос. Это прямо снижает пробуждения процессора и вызовы LLM.

### 2.6. Горячее подключение: uevent → udev → агент

- Ядро шлёт uevent через netlink; `systemd-udevd` их принимает, применяет правила (`SUBSYSTEM`, `KERNEL`, `ATTR{}`, `ACTION` = add/remove/change/bind/unbind) и выставляет `SYMLINK`, `TAG`, `ENV`, `RUN`. Правила лежат в `/usr/lib/udev/rules.d`, `/etc/udev/rules.d` и др. `RUN` предназначен только для очень коротких задач; долгие процессы убиваются после обработки события (man udev(7), systemd 262~devel) [K11].
- **pyudev** (177★, LGPL-2.1): `Context().list_devices(subsystem='iio'|'video4linux'|'tty'|'usb')`, `Monitor.from_netlink(context)` + `filter_by(...)` (фильтр ставится на стороне ядра), `MonitorObserver` для асинхронной обработки [R8]. Источник по умолчанию — `udev` (устройство уже настроено). Источник `kernel` пакет прямо не рекомендует: устройство может быть ещё не готово [R8, V-code].
- **Отображение на MCP 2026-07-28** (термины из B [S1]): событие `add`/`remove` → пересобрать инвентарь → `notifications/resources/list_changed` и `notifications/tools/list_changed` для клиентов, подписанных через `subscriptions/listen` с фильтрами `resourcesListChanged`/`toolsListChanged`. Изменение каталога ломает префиксный кэш LLM (G3, п. 1б), поэтому hotplug — событие с измеримой ценой.
- В PicoClaw уже есть сервис событий USB hotplug на шине сообщений агента (A).

### 2.7. Камеры: V4L2 против libcamera

- **V4L2** [K12]: `VIDIOC_QUERYCAP` возвращает `driver`, `card`, `bus_info`, `capabilities` (всё физическое устройство) и `device_caps` (конкретный открытый узел; при флаге `V4L2_CAP_DEVICE_CAPS`). Решать, что узел — это захват видео (`V4L2_CAP_VIDEO_CAPTURE`), а не метаданные (`V4L2_CAP_META_CAPTURE`), надо по `device_caps`. В sysfs у `/sys/class/video4linux/videoN` есть только `name`, `index` и `dev_debug` (v4l2-dev.c) [V-code]. Одна UVC-камера даёт несколько узлов.
- **На Raspberry Pi с CSI-камерой** `/dev/videoN` — это не камеры. `video0`/`video1` — приёмники Unicam, `video10`/`11` — кодек, `video12`–`16` — ISP, `video19` — HEVC [P5]. Наивный перебор `/dev/video*` даст около десяти «камер». Правильный путь:
  - `rpicam-hello --list-cameras` перечисляет камеры и режимы сенсора [P5];
  - в Python `Picamera2.global_camera_info()` возвращает `Model`, `Location`, `Rotation`, `Id`, `Num`, а USB-камеры ставит в конец списка [R9, V-code];
  - `camera_auto_detect=1` в `config.txt` (по умолчанию в Raspberry Pi OS) сам грузит оверлеи распознанных CSI-камер [P1].
- **Для агента**: камера — уровень B (модель известна, «что видно» — нет). Решение «кадр в LLM или ответ на вопрос о кадре» уже вынесено в B §6.2 п. 7 как переменная эксперимента.

### 2.8. Риски опроса шин

- `i2cdetect` [K9]: по умолчанию для каждого адреса выбирается «наиболее безопасная» команда (SMBus Quick Write или Receive Byte). Флаг `-q` (только Quick Write) не рекомендуется: известна порча EEPROM AT24RF08. Флаг `-r` (только Receive Byte) может заблокировать SMBus на микросхемах только для записи, например на тактовых генераторах по адресу 0x69.
- **PicoClaw** [R7, V-code]: `pkg/tools/hardware/i2c_linux.go`, действие `scan` перебирает 0x08–0x77 стратегией `MODE_AUTO` от `i2cdetect`. Адреса, занятые драйвером ядра, отмечаются как `busy` по `EBUSY` из `I2C_SLAVE`. Подтверждение `confirm` в схеме инструмента требуется только для записи.
- **Альтернатива без риска**: устройства, уже заявленные в DT, видны в `/sys/bus/i2c/devices/N-00AA/name` без единой транзакции на шине. Именно так работает `sysfs_probe.py`.
- **Права**: доступ к `/dev/i2c-*`, `/dev/gpiochip*`, `/dev/video*` обычно дают через группы (`i2c`, `gpio`, `video`; состав групп проверить на образе ОС). ZeroClaw ставит в systemd-юнит `SupplementaryGroups=gpio spi i2c` (A). Минимальные права MCP-серверу — часть корректности, а не безопасность ради безопасности.

### 2.9. Задержки и стоимость чтения: что важно для метрик «во времени»

| Источник | Что известно | Пометка |
|---|---|---|
| DS18B20 (1-Wire, `w1_therm`) | Чтение `temperature`/`w1_slave` запускает преобразование и блокируется: 95/190/375/750 мс при 9/10/11/12 битах; MAX31850 — 100 мс. `therm_bulk_read` запускает преобразование сразу на всей шине | [K7, V-code] |
| Поиск на шине 1-Wire | Раз в `timeout` секунд, по умолчанию 10 с (`w1_timeout = 10` в `w1.c`), пока `w1_master_search` > 0 или = −1 | [K7, V-code] |
| I2C на Pi | `i2c_arm_baudrate` по умолчанию 100 000 | [P2] |
| I2C, грубая оценка | Чтение 8 байт с указанием регистра ≈ (1 + 1 + 1 + 8) байт × 9 бит ≈ 99 тактов ≈ 1 мс при 100 кГц, без времени измерения самого датчика | **расчёт** |
| IoT-MCP (ESP32 + MCP) | Средний ответ 205 мс; заметно дольше датчики на I2C (MPU6050); сервер соединений — 30–75 % времени ответа | [L6] |

**Вывод.** Вызов инструмента «прочитать датчик» может стоить от микросекунд (`*_input` hwmon) до 750 мс (DS18B20) и сотен миллисекунд сети. В инвентарь надо класть **подсказку стоимости чтения** (в `sysfs_probe.py` — заметка `blocking read: conversion 750 ms`), а `ttlMs` ресурса делать не меньше этого времени. Тогда LLM не ждёт шину, а агент не будит её чаще, чем она успевает измерить.

## 4. Стандарты описания возможностей устройств

### [S1] W3C Web of Things (WoT) Thing Description 1.1 — [V-doc]

- **Статус:** W3C Recommendation, 05.12.2023. Редакторы: S. Kaebisch, M. McCool, E. Korkan. https://www.w3.org/TR/wot-thing-description11/
- **Модель:** Thing с обязательными `@context` (`https://www.w3.org/2022/wot/td/v1.1`), `title`, `security`, `securityDefinitions` (это `required` в официальной схеме [S1s]). Взаимодействия:
  - `properties` (PropertyAffordance, флаг `observable`);
  - `actions` (`input`/`output`, флаги `safe` и `idempotent`);
  - `events` (`subscription`, `data`, `cancellation`).

  У каждого взаимодействия обязательны `forms`, у формы обязателен `href`; там же `contentType` и `op` (`readproperty`, `writeproperty`, `invokeaction`, `subscribeevent`, …). DataSchema: `type`, `unit`, `minimum`/`maximum`, `readOnly`/`writeOnly`, `enum`. Схемы безопасности: `nosec`, `basic`, `bearer`, `psk`, `oauth2`, `apikey` и др.
- **Thing Model** (`"@type": "tm:ThingModel"`) — шаблон класса устройства без коммуникационных деталей. Медиатипы: `application/td+json`, `application/tm+json`.
- **Чего в TD нет:** линейного преобразования «raw → единицы» (scale/offset). Его делает servient, то есть наш HAL. Нет и понятия «область полномочий» (capability scope) как в DCP. Его можно добавить расширением контекста TD (TD Context Extension, собственный префикс в `@context`).
- **[S1s] Официальная JSON Schema:** https://www.w3.org/2022/wot/td-schema/v1.1, `version: 1.1-12-March-2025`, draft-07. Схема в ветке `main` репозитория w3c/wot-thing-description уже ссылается на экспериментальный контекст TD 2.0, поэтому для проверки TD 1.1 брать надо опубликованную. Сохранена в `GAP2_artifacts/td-schema-v1.1_w3c_2025-03-12.json`.
- **Связь с ВКР:** формат внутренней модели «что умеет устройство», генерируемый из sysfs; `forms` с `file://` (привязка `binding-file` node-wot) для IIO/hwmon и `modbus+tcp://` для Modbus.

### [S2] W3C WoT Discovery — [V-doc]

- **Статус:** W3C Recommendation, 05.12.2023. Редакторы: A. Cimmino, M. McCool, F. Tavakolizadeh, K. Toumura. https://www.w3.org/TR/wot-discovery/
- **Две фазы:**
  - *Introduction* (открытая): прямой URL (QR, маяк), `/.well-known/wot`, DNS-SD/mDNS (`_wot._tcp`, `_directory._sub._wot._tcp`), CoRE Link Format (`wot.thing`, `wot.directory`), DID;
  - *Exploration* (после аутентификации): сервер TD или **каталог TD** (TDD) с REST API `/things` (CRUD), поиском JSONPath/XPath (синтаксически) и SPARQL (семантически), уведомлениями об изменениях через Server-Sent Events.
- **Связь с ВКР:** на одноплатнике каталогом может быть сам MCP-сервер (`list_devices` ≈ `GET /things`). Узлы ESP32 в локальной сети объявляются через mDNS `_wot._tcp`. Каталог Zion (CCNC 2024) использовали в Web-of-Drones [L1, L1z].

### [S3] WoT TD 2.0 и Binding Registry — [V-doc]

- TD 2.0 — First Public Working Draft, 04.11.2025, редактор E. Korkan. Совместимость с 1.1 не гарантируется, обещаны указания по миграции. Об LLM, агентах и MCP в документе ничего нет.
- WoT Binding Registry (черновик от 04.11.2025) в пилотной фазе: ещё не опубликован как W3C Registry, в таблице только пример-заглушка. Для ВКР опираться на **TD 1.1** (Рекомендация), 2.0 упомянуть как направление.

### [S4] IETF SenML, RFC 8428 — [V-doc]

- **Библиография:** Jennings C., Shelby Z., Arkko J., Keranen A., Bormann C. *Sensor Measurement Lists (SenML)*. RFC 8428, август 2018, Standards Track.
- **Модель:** массив записей. Базовые поля `bn`, `bt`, `bu`, `bv`, `bs`, `bver` действуют на последующие записи; обычные — `n`, `u`, `v`, `vs`, `vb`, `vd`, `s`, `t`, `ut`. «Разрешённая» запись не содержит базовых полей, имя и время абсолютные. Медиатипы: `application/senml+json`, `+cbor`, `+xml`, `senml-exi` и потоковые `sensml+…`. В CBOR метки целые (n=0, u=1, v=2, …, bn=−2, bt=−3).
- **Реестр единиц:** `Cel`, `%RH`, `Pa`, `lx`, `V`, `A`, `W`, `m/s2`, `/` (отношение, например состояние ключа), `count`, `1/min` и др.
- **Размеры из RFC (табл. 3) на одном примере:** JSON 573 байт (206 после gzip), XML 649 (235), CBOR 254 (196), EXI 161 (184).
- **[S5] RFC 8798 (июнь 2020):** дополнительные единицы и реестр *вторичных* единиц с линейным преобразованием «× scale + offset» в основную: `ms`, `h`, `kWh`, `mV`, `mA`, `hPa`, `ppm`, `/100` и др.
- **Связь с ВКР:** формат журнала событий оборудования (D) и обмена с узлами. Для промпта не лучший: по моему измерению SenML в 2,05 раза дороже компактного JSON (§6).

### [S6] OMA LwM2M и IPSO Smart Objects — [V-doc]

- LwM2M 1.2 (Core TS, 10.11.2020), 1.2.2 (13.06.2024). С версии 1.1 добавлены форматы SenML JSON (CoAP Content-Format 110) и SenML CBOR (112), с 1.2 — LwM2M CBOR.
- **IPSO-объект 3303 «Temperature»** (`urn:oma:lwm2m:ext:3303:1.1`), реестр OMNA на GitHub (62★):
  - 5700 Sensor Value — Float, R, обязательный;
  - 5601/5602 Min/Max Measured Value и 5603/5604 **Min/Max Range Value** — необязательные;
  - 5701 Sensor Units — String, необязательный;
  - 5518 Timestamp.
- **Связь с ВКР:** модель «объект/экземпляр/ресурс» с числовыми ID компактна для МК. Идея диапазонов измерения (5603/5604) полезна для TD (`minimum`/`maximum`): в IIO её нет.

### [S7] Модель данных Matter — [V-code]

- Устройство → endpoints → кластеры с атрибутами, командами и событиями. Пример: Temperature Measurement (0x0402), `MeasuredValue` типа `temperature` (0,01 °C; минимум −27315, то есть −273,15 °C), `Min/MaxMeasuredValue`, `Tolerance` (XML кластера в connectedhomeip).
- DCP критикует модель кластеров за **закрытую таксономию** устройств: самодельному железу в неё трудно вписаться [L3].
- SimuHome (C) построен на Matter: это готовый пример «стандартная модель данных → инструменты LLM».

### [S8] Онтологии SOSA/SSN и SAREF — [V-doc]

- **SOSA/SSN** — W3C Recommendation 19.10.2017 (исправления ссылок 08.12.2017). Классы `Sensor`, `Observation`, `ObservableProperty`, `FeatureOfInterest`, `Actuator`, `Actuation`, `Platform`, `Result`. Пространства имён `http://www.w3.org/ns/sosa/`, `http://www.w3.org/ns/ssn/`.
- **SAREF core v4.1.1** (31.10.2024; ETSI TS 103 264 V4.1.1, 2025-03): `Device`, `Sensor`, `Actuator`, `Function`, `Command`, `Property`, `State`, `Measurement`/`PropertyValue`, `UnitOfMeasure`, `Service`.
- **Связь с ВКР:** через `@type` в TD можно пометить «это Sensor, наблюдает Temperature у FeatureOfInterest "кухня"». Для LLM это лишние токены. Для сопоставления устройств между системами — полезно. В ВКР — упоминание и, может быть, одна аннотация `@type` в TM. Не основной путь.

### [S9] IEEE 1451.0-2024 (TEDS) — [V-doc, вторичный]

- Стандарт умных преобразователей: общие функции, протоколы и форматы TEDS (Transducer Electronic Data Sheet). Опубликован IEEE SA 26.06.2024, около 400 страниц; руководители разработки — E. Song и K. Lee (NIST).
- **Связь с ВКР:** аппаратная «самоописательность» датчика, то есть уровень A на уровне железа. В хоббийных датчиках для Pi почти не встречается. Упомянуть как альтернативу DT + профилю.

### [L1] Web-of-Drones — Iannoli et al., WoWMoM 2026 — [V-pre; venue по полю comments arXiv]

- **Библиография:** Iannoli A., Gigli L., Sciullo L., Trotta A., Di Felice M. (University of Bologna). *Say the Mission, Execute the Swarm: Agent-Enhanced LLM Reasoning in the Web-of-Drones*. IEEE WoWMoM 2026. arXiv:2605.03788 (v1, 05.05.2026).
- **Архитектура:**
  - дроны, датчики, состояние миссии и сервисы — WoT Things; на каждый БПЛА свой Servient, команды идут через MAVProxy/MAVLink в ArduPilot SITL;
  - валидация входа на границе Servient (например, `takeoff` требует строго положительный `alt`);
  - TD регистрируются в каталоге Zion [L1z] через CRUDL, поиск — по метаданным TD и JSONPath;
  - MCP-шлюз на NestJS с проверкой схем Zod — единственная точка входа агента. Действия асинхронны: вызов возвращает подтверждение, завершение проверяется чтением свойств или событием;
  - агент на LangChain: статичный core prompt, «guardrails», выведенные из наблюдаемых сбоев, и helper tools.
- **Инструменты (табл. 1):**
  - 4 core MCP tools: `list_web_things`, `read_web_thing_property`, `write_web_thing_property`, `call_web_thing_action`;
  - инструменты планирования: `plan_drone_formation`, `plan_area_coverage`;
  - helper tools: `send_drones_to_positions`, `wait_until_armed/_arrived/_landed`.
- **Эксперимент:** 10 БПЛА, 10 независимых прогонов на конфигурацию, 4 миссии. 6 LLM: GPT-5.2, DeepSeek V3.2, GLM 4.7, Grok 4.1 Fast, Claude Haiku 4.5, Qwen3 8B. Учёт токенов по usage API: T_run = Σ(T_prompt + T_completion), где T_prompt = system + user + history + toolout.
- **Результат (по аннотации):** универсальные LLM без явного grounding и поддержки исполнения ненадёжны даже на простых задачах роя. Инструменты планирования и guardrails в рантайме заметно повышают устойчивость.
- **Польза для ВКР:**
  1. Готовый образец «generic»-шлюза из 4 инструментов поверх TD — это одна из двух стратегий в §6.
  2. Формула учёта токенов по итерациям — та же декомпозиция, что нужна для метрик «во времени».
  3. Сравнение 6 моделей, включая лёгкие, — близкий аналог «GPT mini разных версий».

Ещё — свидетельство, что лёгкие облачные модели (GPT-4o mini) на доменных инструментах работают почти идеально, а локальные 3B — нет (все локальные результаты в статье получены на неквантованных весах). Это поддерживает тезис руководителя о «тупых локальных LLM».

### [L3] DCP, раздел Related Work (§5.2, §5.3, §6.3) — [V-pre]

- §5.2 «The MCP + WoT lineage»: Web-of-Drones и AgentOptics используют MCP без изменения протокола и добавляют безопасность кодом в рантайме. DCP предлагает переносить безопасность в слой схемы.
- Вывод автора: WoT остаётся полезным как формат обмена. TD описывает, *что такое* устройство, DCP — *как безопасно его вызывать*. Запланирован импорт TD → манифест DCP. В открытых вопросах (§6.3): односторонний импорт прост, обратное преобразование сложнее.
- §5.3: Matter — закрытая таксономия кластеров; Sparkplug B — промышленный MQTT без LLM-ориентированных примитивов безопасности; OpenAPI + HTTP подходит устройствам с полноценной сетью.
- **Польза для ВКР:** оправдывает решение «TD — модель, а безопасность и ограничения — отдельный слой поверх неё». Капабилити-строки DCP (`lamp.write`) можно перенести в TD расширением контекста.

### [L4] LLM-MaGe — Salama et al., ICWE 2025 — [V-peer]

- Salama F., Ennemoser F.J., Binkert R., Korkan E., Käbisch S., Steinhorst S. *LLM-MaGe: A Generative Mashup Planner for the Web of Things*. Web Engineering (ICWE 2025), LNCS, pp. 342–357, 2025. DOI 10.1007/978-3-031-97207-2_26 (Crossref). Среди авторов два редактора TD 1.1.
- LLM получает описание желаемого поведения на естественном языке и набор TD. Она строит PDDL-модель, а классический планировщик находит план мэшапа. По аннотации, простые мэшапы часто получаются верно с первой попытки.
- **Польза для ВКР:** TD как вход LLM уже используется самими авторами стандарта. Альтернатива прямому tool calling — «LLM формулирует цель, детерминированный планировщик исполняет». Это экономит токены на длинных сценариях.

### [L5] Octopus Protocol, разделы III-B/III-C — [V-pre] (дополнение к B [C5])

- **Семантическая наблюдаемость:** насколько видимые ОС свидетельства (дескрипторы, драйверы, идентификаторы, публичная документация) раскрывают, что за устройство и что оно умеет. Отсюда два слоя спецификаций:
  - Layer 1 — пять универсальных спецификаций (probe/identify/interface/serve/deploy, 365 строк markdown);
  - Layer 2 — профили устройств.
- **Три уровня по табл. I:**
  - камера и аудио — ОС раскрывает идентичность и возможности, человеку говорить ничего не надо;
  - SO-ARM101 — виден только транспорт, достаточно назвать модель;
  - самодельный рельс камеры — нужно описание.
- На macOS агент сам выбрал `system_profiler`/`ioreg` вместо `lsusb` и `/dev/cu.*` вместо `/dev/tty*`. Раздела про sysfs, udev и IIO в статье нет: обнаружение делает LLM через shell.
- **Польза для ВКР:** даёт базовую линию «LLM-обнаружение», с которой сравнивается детерминированная инвентаризация по sysfs. Метрики сравнения: минуты, токены, доля правильно описанных устройств (см. эксперимент E-HW2).

### [L6] IoT-MCP, раздел про задержки — [V-peer] (дополнение к B [C1], C [19])

- 10 повторов базового набора задач: средний ответ 205 мс. Датчики на I2C, особенно MPU6050, отвечают заметно дольше. Сервер соединений — 30–75 % времени ответа.
- Ошибки чаще у серверов с несколькими значениями за чтение («read-all»: LTR390, MPU6050).
- Формат ответа МК самодельный (`write_time`, `timestamp`, `id`, `sensor`, `data`), не SenML.
- **Польза для ВКР:** эмпирическое основание учитывать задержку шины и транспорта как отдельную составляющую времени ответа, а не только задержку LLM. Ещё — довод за инструменты на один канал вместо «прочитать всё».

### [L7] «LLM within MCP Matters» — Cho et al., SIGIR 2026 AgentSearch Workshop (non-archival) — [V-pre]

- arXiv:2608.08467. 54 000 испытаний, 24 LLM (9 Claude, 6 Gemini, 9 GPT). Справочные данные, встроенные в `instructions` MCP-сервера, модели читают надёжно (доля попаданий ≥ 98 % у 23 из 24), пока нет конкурирующего инструмента поиска. При наличии поиска 9 моделей падают ниже 15 %.
- **Польза для ВКР:** инвентарь оборудования нельзя полагать «известным модели» только потому, что он лежит в `instructions` сервера. Хост должен класть его в контекст явно (ресурс или результат `list_devices`). Это проверяемо в эксперименте.

## 6. Собственное измерение: цена представлений контекста (GAP2_artifacts)

**Метод (собств. измерение).**
1. `make_fixture.py` строит синтетическое дерево `/sys` по ABI ядра. В нём:
   - BME280 на i2c-1/0x76 (IIO с `_input`, `_raw`, `_scale`);
   - DHT22 на GPIO4 (IIO, только `_input`);
   - АЦП ADS1015 (IIO, только `raw` + `offset` + `scale`);
   - `cpu_thermal` (hwmon), DS18B20 (1-Wire, 750 мс);
   - I2C-клиент без драйвера;
   - UVC-камера (два узла V4L2), USB-UART CH340, `gpiochip0`, HAT EEPROM.
2. `declared.json` добавляет PIR и реле на GPIO и места установки.
3. `sysfs_probe.py` строит инвентарь: 14 записей, из них 7 с каналами (10 свойств, 1 записываемое).
4. `ctx_formats.py` строит 10 представлений и считает байты компактного JSON и токены **o200k_base**. Словарь восстановлен из локальной копии, его SHA-256 совпал с эталоном tiktoken 0.14.0 (446a95…1a2d), так что токенизация точная.
5. Все сгенерированные TD (7, 35, 140) проходят официальную JSON Schema TD 1.1. Валидатор проверен на 5 полных TD из текста Рекомендации и на 6 испорченных вариантах.
6. Масштабирование: k «комнат» с тем же набором (k = 1, 5, 20).
7. Цена: 480 вызовов LLM в сутки (сценарий F), входные токены RouterAI на 06.10.2026 (F).

**Наблюдения.**
1. **Полный TD в промпт класть нельзя.** `forms`, `@context` и `security` нужны машине, а не модели; они дают 75 % токенов TD (1 027 → 253). Значит, «TD как внутренняя модель» и «TD в промпте» — разные вещи. Модели отдаётся проекция.
2. **Explicit против generic.** При 10 свойствах generic (4 инструмента + `list_devices`) уже дешевле по каталогу в 1,43 раза, при 200 свойствах — в 3,42 раза. Точка безубыточности — около 6 свойств: 199 / (46,9 − 12,8) ≈ 5,8 (**расчёт** по удельным 46,9 и 12,8 токена на свойство). Цена generic — лишний шаг (`list_devices`) и параметризованные вызовы с риском ошибиться в `device_id`/`property`. Web-of-Drones именно из-за многословности шагов добавляли helper tools [L1]. **Где точка равновесия по суммарной цене задачи, а не каталога, неизвестно — это эксперимент E-HW1.**
3. **Стандартный формат состояния дороже самодельного.** SenML в 2,05 раза дороже компактного JSON из-за повторяющихся ключей `n`/`u`/`v` и URN в `bn`. SenML — для журнала и сети, где у него есть CBOR (RFC: 573 → 254 байт [S4]); в промпт — текст или компактный JSON.
4. **Правило «≈4 байта на токен» (G3) для числовых данных завышает.** На снимках состояния o200k даёт 2,6–3,0 байта на токен (SenML 636/248, JSON 350/121, текст 329/110): числа режутся на группы до 3 цифр. На JSON-схемах инструментов — 4,1–4,6. Оценивать стоимость надо токенизатором, а не делением байтов.
5. **Самодельный манифест (159) дешевле агентского вида TD (253)** на 37 %. Но текст (86) дешевле обоих, а TD стандартен и проверяем схемой. Предлагаемое решение: хранить TD, а в промпт генерировать текст или компактный манифест *из TD*. Тогда самодельный формат перестаёт быть самостоятельной схемой и становится функцией проекции.

**Ограничения.**
- Фикстура синтетическая: значения, адреса и VID:PID выдуманы, пути и единицы — по ABI.
- Считается JSON поля `tools`. Как провайдер разворачивает инструменты в промпте, не публикуется, поэтому абсолютные числа приблизительны. Сравнение представлений между собой при этом корректно.
- Качество ответов LLM на разных представлениях не измерялось — это эксперимент с реальным API.
- Кэш показан двумя крайними случаями (0 и 100 % попаданий).

**Проверка воспроизводимости:** 18 тестов `test_gap2.py` трижды подряд — OK; без tiktoken пропускается 1 тест. Повторный прогон `build_all` даёт побайтно одинаковые представления (тест `test_deterministic`).

## 7. Рекомендуемая архитектура слоя оборудования для ВКР

### 7.1. Конвейер

1. **Объявление** (человек, один раз): строки `dtoverlay=` в `config.txt` и `declared.json`/TM-профили для уровня C (GPIO-линии, UART-устройства, место установки).
2. **Инвентаризация** (детерминированная, 0 токенов): `sysfs_probe` по IIO/hwmon/w1/V4L2/USB/I2C/HAT, libgpiod (`gpioinfo`), libcamera через Picamera2 (`global_camera_info`). Шину не сканировать.
3. **Внутренняя модель**: TD 1.1 на каждое устройство (проверка официальной схемой при сборке), TM на класс (BME280, DS18B20, реле). В `forms` — `file:///sys/...` для sysfs, `gpiod://chip/line` (собственная схема, документируется) для GPIO, `modbus+tcp://...` для Modbus.
4. **Проекции для MCP** (термины спецификации 2026-07-28 по B):
   - ресурс-инвентарь: текст или агентский вид TD, URI в духе `wot://{thing}` (как у wot-mcp) вместо самодельного `hw://`, `ttlMs` большой (меняется только при hotplug);
   - ресурсы состояния: `wot://{thing}/properties/{p}`, `ttlMs` не меньше времени преобразования датчика;
   - инструменты: explicit или generic (переменная эксперимента), аннотации из TD (§7.2);
   - события: udev (`add`/`remove`) → `notifications/resources/list_changed`/`tools/list_changed`; `gpiomon`, пороги IIO → `notifications/resources/updated` (только URI, клиент сам читает ресурс).
5. **Журнал**: SenML JSON (или CBOR) с битемпоральными отметками (D: «когда было» и «когда агент узнал»).

### 7.2. Отображение TD → MCP

| TD 1.1 | MCP (2026-07-28) | Комментарий |
|---|---|---|
| `properties.X`, `readOnly: true` | getter-инструмент с `readOnlyHint: true` или ресурс | Датчик без подтверждения |
| `properties.X`, `readOnly: false` | setter с `readOnlyHint: false`, `idempotentHint: true` | Запись значения идемпотентна |
| `actions.Y`, `safe: true` | инструмент с `readOnlyHint: true` | По TD «safe» = не меняет состояние |
| `actions.Y`, `idempotent` | `idempotentHint` | По умолчанию в MCP `false` |
| актуатор без `safe` | `destructiveHint: true` (умолчание MCP) + подтверждение через elicitation (B §6.2 п. 4) | Политика подтверждения |
| `unit`, `minimum`, `maximum`, `enum` | `inputSchema` (`minimum`/`maximum`/`enum`) + единица в `description` | Некорректный вызов отсекается до привода (как bridge DCP) |
| `observable: true` | `resourceSubscriptions` в `subscriptions/listen` | Подписка вместо опроса |
| `events.Z` | ресурс-буфер событий + `notifications/resources/updated` | Как событийный буфер в wot-mcp |
| `id`, `title` | имя инструмента / URI ресурса | Детерминированный порядок `tools/list` ради префиксного кэша (G3, п. 8) |
| нет аналога: capability scope DCP | расширение `@context` TD, проверка в шлюзе | `edge:capability: "env.read"` |

### 7.3. Что поменять в заметках B и D

- **B §6.1–6.3:** уровни L0/L1/L2, `ttlMs` и подписки остаются. Схему `hw://` заменить URI, выведенными из `id` TD (`wot://…`). Манифест L0 = TD 1.1 (внутри) и проекция (в промпт). Пример `{"t":22.5,…}` оставить как проекцию L1, а не как формат хранения.
- **B/D, «манифест в стиле DCP»:** вместо отдельной схемы — TD + расширение контекста для области полномочий + шлюз-валидатор. Ссылка на DCP §5.2 как обоснование.
- **C §7, п. 1 («узкий высокоуровневый интерфейс»):** дополнить: высокоуровневые инструменты генерируются из TD, а TD — из sysfs. Сырые I2C-инструменты (PicoClaw) — только экспертный режим с подтверждением, и без `scan`.
- **A, план эмуляции:** `i2c-stub` в colima с ядром Debian stable не заработает (модуля нет); в Fedora-ВМ он есть. Основной путь — `--root`-фикстура на Mac, затем Fedora-ВМ с `gpio-sim`, `i2c-stub`, `vivid`; umockdev — для записи реальной платы.

## 9. Открытые проблемы

1. **Нет механической генерации TD из sysfs/IIO** ни в одной найденной работе или проекте. Прототип есть только в `GAP2_artifacts`, и он проверен лишь на синтетике.
2. **Единицы.** IIO хранит их неявно в ABI (по типу канала), TD — как свободную строку или IRI онтологии, SenML — как код реестра. Единого машинного словаря «тип IIO → единица SenML → IRI QUDT/OM» нет. Таблица в §2.3 — ручная.
3. **Диапазоны и точность** (IPSO 5603/5604, Matter `Tolerance`) в IIO почти отсутствуют. Их приходится брать из даташитов в профили, и это уровень C даже для «хороших» датчиков.
4. **Explicit или generic по суммарной цене задачи** не изучено. Есть только цена каталога (§6) и качественное наблюдение о многословности generic [L1].
5. **События из ядра в MCP.** udev и `gpiomon` дают события, MCP 2026-07-28 даёт `subscriptions/listen`. Но как фильтровать события, чтобы будить LLM только по значимым, не будя её на каждый фронт, никто не мерил (D: правила важности без LLM).
6. **Эмуляция IIO без своей сборки ядра** недоступна ни в Debian, ни в Fedora (`IIO_SIMPLE_DUMMY` выключен); `I2C_STUB` есть только в Fedora. Проверить Ubuntu не удалось: Launchpad вернул 403. Арх-специфичные переопределения kernel-ark для aarch64 я не просматривал — проверить `modinfo` в самой ВМ.
7. **CSI-камеры**: в libcamera нет sysfs-описания возможностей. Описание камеры как Thing (разрешения, режимы, «вопрос к кадру») остаётся ручным профилем.
8. **TD 2.0** может изменить словарь. Выбор 1.1 надёжен на срок ВКР, но требует оговорки.
