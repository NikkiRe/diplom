## 1. Зачем эта область ВКР и как она связана с legacy

**Связь с темой.** «ИИ-агент на граничном устройстве» в 2026 году — это локальная языковая модель (SLM/LLM 1–8B) + цикл «рассуждение → вызов инструмента → наблюдение» на одном устройстве (ноутбук/телефон/плата). Системные вопросы такого агента:
1. **Расписание и допуск:** на одном ускорителе конкурируют интерактивные (reactive) запросы пользователя и фоновые (proactive) задачи агента; у каждого — свой SLO (TTFT, TPOT, дедлайн). Это прямая проекция задач Orca/Sarathi/DistServe/FastServe на edge (SLICE, Agent.xpu).
2. **Контракты исполнения и runtime verification:** агентный цикл порождает трассу событий (вызовы инструментов, токены, тайминги). Корректность протокола (порядок вызовов, обязательные шаги) и временные гарантии можно формулировать как свойства (ptLTL/LTLf/LTL3) и проверять мониторами онлайн (AgentSpec, Agent-C, AgentLTL, ContrAgent, TemporalGuard).
3. Это **ИВТ / системное ПО**: планировщик, модель стоимости, управление KV-памятью, мониторы с ограниченными накладными расходами, C/C++ поверх `libllama`.

**Оценка legacy (честно).** Ветка A прошлого агента (FIFO-диспетчер + «независимый trace-checker») — по сути офлайн-RV трассы планировщика, но на нагрузке MLP 4→5→3, где время задачи — микросекунды и SLO не имеет смысла. Ветка B («агент» выбора linear/MLP/INT8 при бюджете) — игрушечная версия выбора варианта модели из INFaaS/Clipper; итог `NO_ADAPTIVE_ADVANTAGE_ESTABLISHED` структурно предопределён (накладные расходы контроллера ≥ стоимости модели). **Как методика** (независимый проверяющий трассы, честные baseline, сохранение отрицательных результатов) — забирать; **как постановку** — нет: в этой области всё имеет смысл только на нагрузке, где задержки — сотни миллисекунд–секунды (LLM на Metal), а решения планировщика меняют SLO-попадание в разы.

## 3. Разбор работ

Формат: библиографическая запись → статус проверки → проблема → метод → результаты (числа) → польза для ВКР → что заимствовать.

### A. Основы runtime verification и контрактов

#### A1. meyer1992dbc
**Meyer B.** Applying «Design by Contract» // Computer (IEEE). 1992. Vol. 25, No. 10. P. 40–51. DOI: 10.1109/2.161279.
- Проверка: Crossref (название, автор, том/выпуск/страницы) — да.
- Проблема: как систематически задавать и проверять обязательства компонентов ПО.
- Метод: предусловия, постусловия, инварианты класса; нарушение контракта — ошибка конкретной стороны (вызывающий/вызываемый); проверка во время исполнения в Eiffel.
- Результаты: концептуальная работа, численных результатов нет.
- Польза: терминологическая база для «контракта исполнения» инференс-запроса: **предусловие** = условия допуска (хватает KV-памяти, прогноз латентности ≤ дедлайна), **постусловие** = TTFT/TPOT/дедлайн выполнены и вывод соответствует схеме вызова инструмента, **инвариант** = бюджет памяти/энергии устройства.
- Заимствовать: разделение ответственности (отказ при нарушении предусловия — честный отказ системы, а не «ошибка модели»); именование в API рантайма.

#### A2. havelund2002synth
**Havelund K., Roşu G.** Synthesizing Monitors for Safety Properties // Tools and Algorithms for the Construction and Analysis of Systems (TACAS 2002), LNCS. Springer, 2002. P. 342–356. DOI: 10.1007/3-540-46002-0_24.
- Проверка: Crossref + OpenAlex — да.
- Проблема: эффективная онлайн-проверка свойств безопасности (safety) по трассе исполнения.
- Метод: свойства в прошедшем времени (past-time LTL); монитор синтезируется как программа динамического программирования: для каждого события пересчитывается массив значений подформул `now[]` по массиву `pre[]` предыдущего шага (снизу вверх по дереву формулы).
- Результаты: время на событие и память — линейны по размеру формулы, не зависят от длины трассы (свойство алгоритма; численных бенчмарков в аннотации нет).
- Польза: **основной алгоритм для C++-монитора протокола вызовов инструментов**: O(|φ|) на событие, без хранения истории — идеально для edge.
- Заимствовать: схему генерации кода монитора (формула → C++ функция `step(event)` с двумя битовыми массивами).

#### A3. havelund2004efficient
**Havelund K., Roşu G.** Efficient monitoring of safety properties // International Journal on Software Tools for Technology Transfer. 2004. Vol. 6, No. 2. P. 158–173. DOI: 10.1007/s10009-003-0117-6.
- Проверка: Crossref — да (выпуск 2004, онлайн 28.11.2003).
- Проблема/метод: журнальная расширенная версия A2 (синтез мониторов для ptLTL, применение в Java PathExplorer).
- Польза/заимствовать: цитировать как журнальный источник алгоритма; сравнение «монитор по истории» vs «монитор по состоянию».

#### A4. leucker2009brief
**Leucker M., Schallhart C.** A brief account of runtime verification // The Journal of Logic and Algebraic Programming. 2009. Vol. 78, No. 5. P. 293–303. DOI: 10.1016/j.jlap.2008.08.004.
- Проверка: Crossref + OpenAlex — да.
- Проблема: определить RV как область и отличить её от model checking и тестирования.
- Метод: обзор — мониторы, трассы, онлайн/офлайн, синхронный/асинхронный мониторинг, ограничения конечных префиксов для LTL.
- Польза: каноническое определение RV для главы 1 ВКР («монитор — устройство, читающее конечную трассу и выдающее вердикт»).
- Заимствовать: классификацию (inline vs outline мониторинг, онлайн vs офлайн) для описания архитектуры.

#### A5. bauer2011ltl3
**Bauer A., Leucker M., Schallhart C.** Runtime Verification for LTL and TLTL // ACM Transactions on Software Engineering and Methodology. 2011. Vol. 20, No. 4. Art. 14 (64 p.). DOI: 10.1145/2000799.2000800.
- Проверка: Crossref — да.
- Проблема: LTL определена на бесконечных словах, а монитор видит конечный префикс.
- Метод: трёхзначная семантика LTL3 (⊤ / ⊥ / «?»), построение минимального детерминированного автомата-монитора; расширение на временную TLTL.
- Польза: **ранний вердикт ⊥** = «нарушение уже неизбежно» — ключ к идее «прерывать/отклонять запрос, как только контракт заведомо нарушен», что экономит токены и время устройства (см. угол 3).
- Заимствовать: трёхзначный вердикт в API монитора; понятие «монитороспособности» (monitorability) для выбора поддерживаемого фрагмента спецификаций.

#### A6. bartocci2018intro
**Bartocci E., Falcone Y., Francalanza A., Reger G.** Introduction to Runtime Verification // Lectures on Runtime Verification: Introductory and Advanced Topics. LNCS, vol. 10457. Springer, 2018. P. 1–33. DOI: 10.1007/978-3-319-75632-5_1.
- Проверка: Crossref — да.
- Проблема/метод: учебное введение — спецификации, синтез мониторов, инструментирование, накладные расходы, enforcement.
- Польза: учебная ссылка для обзорной главы; таксономия (что мониторим, как реагируем: detection vs enforcement).
- Заимствовать: структуру «спецификация → монитор → инструментирование → реакция» для описания архитектуры прототипа.

#### A7. leucker2018tessla
**Leucker M., Sánchez C., Scheffel T., Schmitz M., Schramm A.** TeSSLa: Runtime Verification of Non-synchronized Real-Time Streams // Proc. 33rd ACM Symposium on Applied Computing (SAC 2018). ACM, 2018. P. 1925–1933. DOI: 10.1145/3167132.3167338.
- Проверка: Crossref/OpenAlex — авторы, SAC 2018, страницы — да; Crossref отдаёт заголовок только как «TeSSLa», подзаголовок указан по памяти (сверить при оформлении).
- Проблема: мониторинг потоков событий с метками времени (встраиваемые/реального времени системы), включая аппаратный мониторинг.
- Метод: потоковый язык спецификаций (stream RV) с явным временем; компиляция в программный или FPGA-монитор.
- Польза: SLO-контракты (TTFT/TPOT/дедлайн) — это **временные** свойства потока токенов; stream-RV даёт правильный формализм (агрегаты, задержки, окна).
- Заимствовать: идею «спецификация SLO как поток» (например, `deadline_i = D_p + i·D_d`, см. Etalon) и вычисление вердиктов инкрементально.

#### A8. liu1973scheduling
**Liu C. L., Layland J. W.** Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment // Journal of the ACM. 1973. Vol. 20, No. 1. P. 46–61. DOI: 10.1145/321738.321743.
- Проверка: Crossref — да.
- Проблема/метод: планирование периодических задач с жёсткими дедлайнами на одном процессоре; RM и EDF, границы загрузки (EDF оптимален при U ≤ 1 с вытеснением).
- Польза: теоретический baseline. Один ускоритель на edge = «однопроцессорное» планирование с вытеснением на границе итерации; EDF/LDF — естественные baseline для SLO-планировщика.
- Заимствовать: EDF как baseline; тест допустимости по загрузке как простейший admission test.

### B. Предсказуемость и допуск в обслуживании DNN (до LLM)

#### B1. crankshaw2017clipper
**Crankshaw D., Wang X., Zhou G., Franklin M. J., Gonzalez J. E., Stoica I.** Clipper: A Low-Latency Online Prediction Serving System // 14th USENIX Symposium on Networked Systems Design and Implementation (NSDI 17). Boston, 2017.
- Проверка: страница USENIX + текст PDF (arXiv 1612.03079) — да.
- Проблема: низколатентное обслуживание моделей разных фреймворков.
- Метод: слой кэширования/батчинга; **адаптивный размер батча по AIMD**: размер батча аддитивно растёт, пока латентность батча не превысит SLO, затем мультипликативный откат на 10 %; альтернатива — квантильная регрессия P99(batch); **отложенный батчинг** (аналог Nagle); выбор модели бандитами Exp3/Exp4; подавление стрэглеров.
- Результаты (из PDF): батчинг — до **26×** пропускной способности (Scikit-Learn linear SVM) при SLO **20 ms**; отложенный батчинг с задержкой 2 ms — **3.3×** для Scikit-Learn SVM; AIMD и квантильная регрессия дают близкий результат, AIMD проще и устойчивее.
- Польза: классический baseline «адаптивного батчинга под SLO»; на Apple GPU (см. §5) зависимость латентности от батча немонотонна, и AIMD может «застрять» в плохой области 2–8 — это проверяемая гипотеза.
- Заимствовать: AIMD как baseline контроллера размера батча; метод квантильной регрессии для P99-прогноза.

#### B2. gujarati2020clockwork
**Gujarati A., Karimi R., Alzayat S., Hao W., Kaufmann A., Vigfusson Y., Mace J.** Serving DNNs like Clockwork: Performance Predictability from the Bottom Up // 14th USENIX Symposium on Operating Systems Design and Implementation (OSDI 20). 2020. P. 443–462.
- Проверка: страница USENIX + текст arXiv-PDF 2006.02464 — да.
- Проблема: хвостовые задержки в обслуживании моделей возникают из-за внутренних «выборов» системы (кэши, конкурентное исполнение на GPU, аллокаторы).
- Метод: «консолидировать выбор» в центральном контроллере; воркер исполняет **один INFER за раз**; каждое действие имеет окно **[earliest, latest]**, действие, не начавшееся до `latest`, отменяется; контроллер ведёт профиль латентности по модели и размеру батча (скользящий 99-й перцентиль), **заранее отклоняет запрос, если он заведомо не уложится в SLO**; ядра компилируются под батчи 1, 2, 4, 8, 16.
- Результаты: OSDI-аннотация — 100 ms SLO для **99.997 %** запросов (arXiv — 99.9999 %); 6-часовой прогон Azure Functions trace: средняя нагрузка и goodput **9 638 r/s**, из **208 млн** запросов только **58** отказов из-за ошибок прогноза; p99 ошибки прогноза завершения INFER ≈ **1 ms**; одна задача на GPU снижает вариативность «на два порядка» при минимальной потере пропускной способности.
- Польза: **главный методологический образец** для угла 1 и 4: на одном устройстве LLM-инференс тоже почти детерминирован (llama-bench: tg 44.6 ± 0.3 ток/с), значит можно прогнозировать и делать допуск до исполнения.
- Заимствовать: action-окна earliest/latest; профиль по дискретным батчам; ранний отказ; метрику «ошибка прогноза завершения» (p99).

#### B3. romero2021infaas
**Romero F., Li Q., Yadwadkar N. J., Kozyrakis C.** INFaaS: Automated Model-less Inference Serving // 2021 USENIX Annual Technical Conference (USENIX ATC 21). 2021. (Best Paper.)
- Проверка: страница USENIX — да.
- Проблема: разработчик не должен вручную выбирать вариант модели/железо под требования к латентности/точности.
- Метод: пользователь задаёт требования (латентность, точность), система выбирает вариант модели на каждый запрос + автоскейлинг.
- Результаты: **1.3×** пропускной способности, **в 1.6 раза** реже нарушения SLO, экономия до **21.6×** (в среднем **8.5×**) стоимости на AWS EC2.
- Польза: научная «взрослая» версия legacy B (выбор варианта модели под бюджет). На edge-агенте варианты — Qwen3-1.7B/4B/8B, разные кванты; это возможная функция деградации при недопуске («не отклонить, а понизить модель»).
- Заимствовать: интерфейс «требования, а не модель»; политику выбора варианта как альтернативу отказу.

#### B4. han2022reef
**Han M., Zhang H., Chen R., Chen H.** Microsecond-scale Preemption for Concurrent GPU-accelerated DNN Inferences // 16th USENIX Symposium on Operating Systems Design and Implementation (OSDI 22). 2022. P. 539–558.
- Проверка: страница USENIX — да.
- Проблема: совместное исполнение задач реального времени и best-effort на одном GPU — либо монополизация, либо ожидание.
- Метод: вытеснение сбросом (reset-based) — ядра DNN-инференса в основном идемпотентны, их можно убить и перезапустить; динамический паддинг ядер (совмещение RT и BE).
- Результаты: накладные расходы на латентность RT-задач **< 2 %**, до **7.7×** пропускной способности против выделенного GPU, задержка вытеснения меньше до **12.3×** (NVIDIA).
- Польза: прямая аналогия «reactive vs proactive» на одном устройстве; в llama.cpp вытеснение возможно только на границе `llama_decode` (итерации/чанка) — REEF задаёт планку, что даёт мелкозернистое вытеснение.

- Метод: гетерогенный граф исполнения (NPU/iGPU), разделение prefill/decode по ускорителям, **вытеснение на границах ядер/слоёв** (< 100 ms), **slack-aware piggybacking** (reactive допускаются безусловно, свободные слоты — не более 3 — заполняются proactive). Платформа: Intel Core Ultra 5 125H (CPU+iGPU+NPU), Llama-3.1-8B / Llama-3.2-3B W8A16.
- Результаты: **1.2–4.9×** proactive-пропускной способности; снижение reactive-латентности **≥ 91 %** (91–97 % в смешанной нагрузке); энергия **−26.8 %** против iGPU-only. Baselines — llama.cpp (CPU), OpenVINO (iGPU). Код не указан.
- Польза: **ближайшая по постановке работа** для ВКР (агент на одном SoC). Apple Silicon (Metal + ANE) не исследован — ниша.
- Заимствовать: модель нагрузки reactive/proactive; метрики; llama.cpp как baseline.

#### D7. chow2025slice
**Chow W.** SLICE: SLO-Driven Scheduling for LLM Inference on Edge Computing Devices. arXiv:2510.18544, 2025 (v3 — нояб. 2025; «submitted to IEEE»), preprint.
- Проверка: arXiv abs + HTML — да.
- Проблема: на edge-устройстве (робот, автомобиль) запросы с разными SLO (TTFT, TPOT, E2E-дедлайн).
- Метод: максимизация полезности (у real-time задач в 10–100 раз больший вес) + **decode-mask matrix** — бинарная матрица «задача × такт декодирования», задающая частоту участия задачи в батче, т.е. управление скоростью генерации под её TPOT. Реализация на FastLLM (C++), RTX 4060 Ti, ChatGLM2-6B-INT4.
- Результаты: до **35×** выше SLO attainment и **3.4×** лучше время завершения против Orca и FastServe; real-time SLO ≈ **85 %** против ≈ 26 % у baseline.
- Польза: прямой аналог угла 1, но на NVIDIA и без открытого кода; одна автор-статья, не рецензирована — использовать осторожно. Идея «управлять скоростью, а не только порядком» хорошо сочетается с QoE (Andes).
- Заимствовать: decode-mask как baseline политики «rate control»; набор SLO-классов.

#### D8. yin2024llms
**Yin W., Xu M., Li Y., Liu X.** LLM as a System Service on Mobile Devices. arXiv:2403.11805, 2024 (Technical Report).
- Проверка: arXiv abs — да.
- Проблема: LLM на телефоне как системный сервис с постоянными контекстами нескольких приложений; дорогие переключения контекста.
- Метод: **LLMS** — управление KV-кэшем чанками: сжатие с учётом устойчивости точности, конвейер «чтение с диска / пересчёт», вытеснение LCTRU.
- Результаты: латентность переключения контекста меньше **до 2 порядков** против baseline.
- Польза: «переключение контекста» агента между задачами на одном устройстве — системная задача ОС-уровня; поддерживает идею сохранения/восстановления состояния `llama_state_seq_*`.
- Заимствовать: метрику латентности переключения контекста; политику вытеснения чанков KV.

### E. Runtime verification трасс LLM-агентов (2025–2026)

#### E1. wang2026agentspec
**Wang H., Poskitt C. M., Sun J.** AgentSpec: Customizable Runtime Enforcement for Safe and Reliable LLM Agents // Proc. IEEE/ACM 48th International Conference on Software Engineering (ICSE '26). ACM, 2026. P. 2938–2950. DOI: 10.1145/3744916.3764546. arXiv:2503.18666.
- Проверка: arXiv abs + Crossref — да.
- Проблема: агент может выполнять нежелательные действия; нужны настраиваемые ограничения во время исполнения.
- Метод: DSL правил «триггер — предикаты — действие enforcement»; перехват действий агента (LangChain), автогенерация правил LLM.
- Результаты: предотвращение > **90 %** небезопасных исполнений кода, **0** опасных действий в embodied-задачах, **100 %** соответствия правилам для автопилота; накладные расходы — **миллисекунды**; правила от o1: precision **95.56 %**, recall **70.96 %** (embodied).
- Польза: эталон архитектуры «перехват → проверка → реакция». В ВКР брать **не безопасность**, а корректность протокола (обязательные шаги, порядок, лимиты повторов).
- Заимствовать: структуру правила trigger/predicate/enforce; метрику накладных расходов на событие.

#### E2. kamath2025agentc
**Kamath A., Zhang S., Xu C., Ugare S., Singh G., Misailovic S.** Enforcing Temporal Constraints for LLM Agents. arXiv:2512.23738, 2025 (preprint, cs.PL).
- Проверка: arXiv abs — да.
- Проблема: guardrails не проверяют **временные** (порядковые) правила последовательности действий.
- Метод: **Agent-C** — DSL (Before/After/Forall/Exists), перевод в логику первого порядка, SMT (Z3); при попытке несоответствующего вызова — **constrained generation** альтернативы прямо во время декодирования.
- Результаты: соответствие **77.4 % → 100 %** (Claude Sonnet 4.5), **83.7 % → 100 %** (GPT-5); полезность **71.8 → 75.2 %** и **66.1 → 70.6 %** соответственно; оценка на retail/airline (τ-bench-подобные домены).
- Польза: показывает, что **превентивное** применение повышает и соответствие, и полезность. Для edge-ВКР SMT в цикле декодирования может быть дорогим — сравнение «SMT vs автомат/DP-монитор» по накладным расходам — системный вклад.
- Заимствовать: набор шаблонов свойств; метрики conformance/utility; протокол оценки.

#### E3. elkoussy2026agentltl
**Elkoussy L., Perez J.** AgentLTL: A Trace-Verification Framework for Measuring, Enforcing, and Training Procedural Compliance in Tool-Using LLM Agents. arXiv:2607.02599, 2026 (preprint, cs.SE).
- Проверка: arXiv abs + GitHub (MIT) — да.
- Проблема: оценка агентов LLM-судьёй недетерминирована; нужен детерминированный показатель соответствия процедурам.
- Метод: FO-LTL (прошлое и будущее) над трассами вызовов; режимы: post-hoc оценка и **онлайн-гейтинг** перед каждым вызовом (HARD_STOP, SOFT_BLOCK, BLOCK_AND_WARN, PERSISTENT_BLOCK, TOLERATE); соответствие как плотная награда для дообучения.
- Результаты: block-and-warn улучшает соответствие на **5 из 7** моделей; дообучение: **+38** п.п. точности и **+17.5** п.п. соответствия на отложенных шаблонах.
- Польза: готовый открытый (Python, MIT) **baseline монитора** и бенчмарк шаблонов (порядок, ветвление, итерации, grounding).
- Заимствовать: режимы эскалации; шаблоны свойств; как baseline производительности против C++-монитора.

#### E4. cohen2026temporalguard
**Cohen I., Havelund K., Omer M., Peled D.** Temporal Guardrails for LLM Conversations: A Runtime Verification Framework // AI Verification. LNCS. Springer, 2026. P. 145–166. DOI: 10.1007/978-3-032-32357-6_7.
- Проверка: Crossref (название, авторы, сборник «AI Verification» в LNCS, страницы) — да; содержание — по аннотации из поисковой выдачи и README кода LLMrv (MIT). Название конференции (вероятно, SAIV) Crossref не указывает — уточнить.
- Проблема: многоходовые нарушения политик в диалоге не ловятся «безпамятными» фильтрами.
- Метод: диалог → булева трасса атомарных пропозиций (grounding: эмбеддинги, NLI, LLM zero/few-shot), политики в **ptLTL**, онлайн-монитор (инструмент TemporalGuard/LLMrv); соавторы — авторы алгоритмов ptLTL-мониторинга (Havelund, Peled).
- Польза: мост между классическим RV (A2/A3) и LLM. Главный вывод для ВКР: **узкое место — grounding из текста**; если события — структурированные вызовы инструментов, grounding тривиален и монитор дёшев → системный фокус оправдан.
- Заимствовать: ptLTL как язык; разделение «grounding — монитор».

#### E5. xiao2026contragent
**Xiao Y., Nuzzo P.** Symbolic Temporal Supervision of LLM Agents Using Contracts. arXiv:2609.18128, 2026 (preprint).
- Проверка: arXiv abs — да.
- Проблема: детерминированный надзор за агентом по формальным контрактам.
- Метод: **ContrAgent** — assume-guarantee контракты в **LTLf** над трассой вызовов, компиляция в **DFA**, онлайн-гейтинг и офлайн-оценка, библиотека контрактов отдельно от модели.
- Результаты (по аннотации): паритет качества с существующими подходами на 4 бенчмарках при детерминированных вердиктах и «значительно меньшей латентности» онлайн (конкретных чисел в аннотации нет).
- Польза: самая близкая к «контрактам исполнения» формулировка; DFA-подход хорошо ложится на C++ и на маскирование токенов.
- Заимствовать: assume-guarantee форму контрактов; LTLf→DFA как бэкенд.

## 5. Предварительный замер на M4 Pro: немонотонная стоимость батча (важно для постановки)

Цель — проверить предположение всех работ кластеров B/C («батч дешевеет на запрос, латентность растёт плавно, ≈ α·b + β») на целевом железе. Однократные прогоны, не научный эксперимент; логи и команды: `research/literature/R8_artifacts/` (llama.cpp build 11146, Metal, Qwen3-8B Q4_K_M, flash-attn on).

**Декодирование, B параллельных последовательностей (npp=128, ntg=32):**

| B | время шага, ms | суммарно ток/с | на поток ток/с |
|---:|---:|---:|---:|
| 1 | 22.5 | 44.5 | 44.5 |
| 2 | 43.2 | 46.3 | 23.2 |
| 4 | 98.1 | 40.8 | 10.2 |
| 6 | 136.3 | 44.0 | 7.3 |
| 8 | 196.6 | 40.7 | 5.1 |
| 9 | 107.3 | 83.9 | 9.3 |
| 12 | 109.5 | 109.6 | 9.1 |
| 16 | 112.5 | 142.2 | 8.9 |
| 24 | 115.6 | 207.6 | 8.7 |
| 32 | 117.5 | 272.3 | 8.5 |

**Prefill 512 токенов в зависимости от размера микробатча (`-ub`, 3 повтора):** ub=16 — 157 ток/с; 32 — 319; 64 — 346; 128 — 360; 256 — 367; 512 — 362 ток/с.

Наблюдения:
1. **При B ≤ 8 батчинг декодирования не даёт выигрыша**: время шага растёт почти линейно (~24.6 ms на поток), суммарная скорость ≈ 41–46 ток/с. **При B ≥ 9 шаг стоит ~107–118 ms почти независимо от B**, и суммарная скорость растёт до 272 ток/с при B=32. Шаг с B=8 (197 ms) **в 1.7 раза дороже**, чем с B=32 (118 ms).
2. Вероятная причина — смена семейства Metal-ядер умножения (mat-vec `mul_mv`/`mul_mv_ext` для малого числа строк → mat-mat `mul_mm`); в `libggml-metal.so` есть оба семейства. Порог (≈ 8 строк) нужно подтвердить по исходникам ggml-metal **зафиксированного** коммита: он зависит от версии и типа квантования.
3. Prefill почти насыщается уже при чанке 64 токена (~95 % пика) → **chunked prefill (Sarathi) на Apple GPU почти бесплатен** по эффективности; чанк 16 — в 2.3 раза медленнее (та же граница ядер).
4. Следствия для постановки: (а) линейная модель α·b+β (Shepherd) и AIMD-поиск батча (Clipper) на этом железе **не подходят без модификации**; (б) llama-server с `--parallel 4` при четырёх одновременно активных слотах оказывается в «худшей» области (TPOT ~98 ms при той же суммарной скорости, что и B=1); (в) планировщик, знающий профиль «режимов ядер», может, например, держать интерактивный поток при B=1 (22 ms/токен, ~10× быстрее чтения по Andes), а фоновые задачи агента собирать в батчи ≥ 9 или добавлять к ним prefill-чанки «попутно» (piggybacking: шаг на 32 токена ≈ шаг на 9). Это конкретная, проверяемая и новая для Apple Silicon гипотеза.

## 6. Открытые проблемы (с точки зрения системной ВКР)

1. **SLO-планирование агентной нагрузки на одном edge-устройстве** изучено мало и почти без открытого кода (SLICE — препринт одного автора на RTX 4060 Ti; Agent.xpu — Intel SoC, код не заявлен). Apple Silicon (unified memory, Metal, ANE) не исследован вовсе.
2. **Модели стоимости батча на edge-GPU нелинейны** (§5), а теория планирования (Shepherd), AIMD (Clipper) и большинство LLM-планировщиков предполагают гладкую/линейную зависимость. Нет работ о «kernel-regime-aware» составлении батча.
3. **RV и планирование живут раздельно.** Работы E1–E5 мониторят протокол агента, но не измеряют накладные расходы монитора в цикле инференса на устройстве и **не используют вердикты монитора для решений планировщика** (ранний отказ/прерывание/понижение модели). Работы C/D планируют по SLO, но не формулируют SLO как проверяемую спецификацию.
4. **Ранний вердикт (LTL3 ⊥) для временных контрактов** (fluidity/дедлайн уже неизбежно нарушен) почти не используется для экономии ресурсов (Clockwork делает это только на уровне действий воркера).
5. **Политика KV на время вызова инструмента** (InferCept/LAMPS) при unified memory: стоимость swap ≈ memcpy в ОЗУ, а не PCIe — оптимальные пороги иные; не измерено.
6. **Метрики для агентов на edge**: TPOT маскирует паузы (Etalon), QoE (Andes) ориентирован на чтение человеком, а для агентных шагов важна латентность «программы» (Autellix) — единая методика не устоялась.
7. **Grounding** (E4): для свободного текста узкое место — классификация пропозиций; для структурированных вызовов инструментов — нет. Граница между ними не исследована с точки зрения стоимости.
8. Воспроизводимость: числа в препринтах и финальных версиях расходятся (FastServe 31.4× → 6.1×; Clockwork 99.9999 % → 99.997 %) — аргумент для ВКР делать собственные baseline на одном железе, а не сравниваться с чужими таблицами.

## 7. Углы ВКР (реализуемо одним студентом на M4 Pro / 24 ГБ за несколько месяцев)

Общая инфраструктура для всех углов: C++17/20-рантайм поверх `libllama` (llama.cpp **собрать из исходников с фиксированным коммитом**), локальные модели Qwen3-1.7B/4B/8B (GGUF), генератор нагрузки (Пуассон/всплески + трассы агентных шагов из BFCL multi_turn / τ-bench), независимый офлайн-чекер трасс (наследие legacy A, но на реальной нагрузке), протокол измерений (прогрев, повторы, доверительные интервалы, контроль термального режима).

### Угол 1 (основной кандидат). SLO-планировщик и управление допуском для локального LLM-агента на Apple Silicon
- **Идея.** Рантайм обслуживает несколько потоков агента (reactive: ответ пользователю; proactive: фоновые шаги/мониторинг) на одном GPU. У каждого запроса — контракт {TTFT-дедлайн, целевой TPOT/fluidity, класс}. Планировщик: (1) профиль стоимости шага по (число строк батча, длина KV, размер чанка) с учётом **режимов ядер** (§5); (2) admission test по прогнозу (Clockwork/QLM): принять / отклонить сразу / понизить модель (INFaaS); (3) итерационное вытеснение (Orca/FastServe); (4) chunked prefill с бюджетом токенов (Sarathi); (5) «попутное» добавление prefill-чанков и фоновых шагов в батчи, где это бесплатно; (6) политика KV на время вызова инструмента (preserve / discard / save-to-RAM через `llama_state_seq_get_data`) — InferCept на unified memory.
- **Гипотезы (проверяемые).** H1: kernel-regime-aware батчинг даёт ≥ 1.5× goodput против llama-server `--parallel N` при той же доле SLO; H2: ранний отказ снижает долю «потраченных впустую» токенов без потери goodput; H3: на unified memory save/restore состояния выгоднее пересчёта при паузе инструмента > X мс (найти X).
- **Baselines.** llama-server (FCFS + continuous batching, `-np` 1/4/16); FCFS без допуска; EDF/LDF (Liu & Layland; Scorpio TTFT Guard); Sarathi-подобный chunked prefill без допуска; skip-join MLFQ (FastServe); AIMD-батч (Clipper); program-level LAS (Autellix); при желании decode-mask (SLICE).
- **Метрики.** SLO attainment по TTFT/TPOT; goodput (DistServe: макс. интенсивность при ≥ 90 % в SLO); fluidity-index (Etalon) и QoE (Andes); p50/p99 латентности; доля отказов и «напрасных» токенов; латентность программы агента; ошибка прогноза завершения p99 (Clockwork); накладные расходы планировщика (мкс/итерацию); энергия — `powermetrics` запускает пользователь (sudo).
- **Выполнимость на M4 Pro.** Высокая: всё на CPU+Metal, модели помещаются (8B Q4 ≈ 4.7 ГБ, остаётся место под KV); прогон одной конфигурации — минуты. Объём кода: ~3–5 тыс. строк C++ + Python-скрипты анализа.
- **Риски.** (1) Новизна против SLICE/Agent.xpu — снимается тем, что Apple Silicon, открытый код и немонотонная модель стоимости; (2) порог ядер зависит от версии ggml и типа кванта — фиксировать коммит и проверить на 2–3 квантованиях (Q4_K_M, Q8_0, F16); (3) термальный дросселинг ноутбука искажает хвосты — фиксировать режим питания, чередовать конфигурации, повторять; (4) «справедливость» сравнения с llama-server (у него свой кэш промптов) — отключать/включать одинаково.

### Угол 2. Дешёвые мониторы протокола вызовов инструментов и их превентивное применение в декодере
- **Идея.** Спецификации протокола агента (ptLTL и LTLf-фрагмент с параметрами по имени инструмента/аргументам — подмножество Agent-C/AgentLTL) компилируются в C++: ptLTL → DP-монитор Havelund–Roşu (O(|φ|) на событие), LTLf → DFA (ContrAgent). Три режима: post-hoc, gate (проверка предложенного вызова, отказ + регенерация) и **prevent** (состояние DFA → множество разрешённых имён инструментов → динамическая GBNF-грамматика в `llama_sampler_init_grammar`, как «монитор-энфорсер» на уровне токенов).
- **Baselines.** Без монитора; AgentLTL (Python, MIT); LLMrv (Python, MIT); gate+регенерация vs prevent; (если доступен код) Agent-C с SMT.
- **Метрики.** Доля трасс, удовлетворяющих спецификации; успех задачи (BFCL multi_turn, τ-bench pass^k на локальной модели); накладные расходы монитора (нс/событие) и маскирования (мкс/токен); прирост TTFT/TPOT; число регенераций (= потраченные токены).
- **Выполнимость.** Высокая; самый «чистый» low-level компонент (кодогенерация мониторов, интеграция в сэмплер).
- **Риски.** Область 2025–2026 перегрета (AgentSpec, Agent-C, AgentLTL, ContrAgent, TemporalGuard) — вклад должен быть **системным** (стоимость и латентность на устройстве, сравнение DP/DFA/SMT), а не «ещё один DSL»; соблазн уйти в безопасность — формулировать свойства как корректность протокола (обязательные шаги, порядок, лимиты); локальная 8B-модель на τ-bench может решать мало задач — опираться на относительные метрики.

### Угол 3 (самый оригинальный, объединяющий 1 и 2). «Контракты исполнения»: временные и протокольные свойства в одном мониторе, вердикты которого управляют планировщиком
- **Идея.** Каждый запрос/шаг агента несёт контракт: временная часть (дедлайны токенов по Etalon, `D_i = D_p + i·D_d`; дедлайн шага) + протокольная часть (LTLf/ptLTL над вызовами). Монитор выдаёт трёхзначный вердикт (LTL3): «?», ⊤, ⊥. Вердикт ⊥ (нарушение уже неизбежно — по прогнозу латентности или по префиксу вызова) **немедленно** превращается в действие планировщика: прервать генерацию, освободить KV, отклонить/понизить, перепланировать. Предусловия контракта (Meyer) = admission test.
- **Гипотезы.** Ранние вердикты снижают долю напрасных токенов на X % и повышают goodput при перегрузке; ложные прерывания (запрос прерван, но успел бы) — ≤ Y % (оценивается контрфактическим воспроизведением трассы).
- **Baselines.** Проверка только по завершении (post-hoc); допуск только при поступлении (Clockwork-стиль); без допуска.
- **Метрики.** Goodput, напрасные токены/секунды GPU, SLO attainment, доля ложных прерываний, накладные расходы монитора.
- **Выполнимость.** Средняя: требует угла 1 как платформы; формальная часть умеренная (LTL3 для конечного набора шаблонов, без общего синтеза).
- **Риски.** Объём; сложность контрфактической оценки; опасность «теории без системы» — держать фокус на измеримом выигрыше.

### Угол 4 (страховочный, низкорисковый; может быть главой угла 1). Предсказуемость LLM-инференса на Apple Silicon и модель латентности для допуска
- **Идея.** Повторить методику Clockwork на M4 Pro: источники вариативности (длина KV, размер батча, режимы ядер, P/E-ядра для CPU-части, термальный режим, параллельные процессы), построить кусочную модель стоимости шага, измерить ошибку прогноза завершения (p50/p99) и её влияние на точность допуска (ложные принятия/отказы).
- **Baselines.** Линейная α·b+β (Shepherd), квантильная регрессия (Clipper), скользящий p99 (Clockwork), EWMA (наследие legacy B).
- **Метрики.** Ошибка прогноза, калибровка, false accept / false reject, стоимость прогноза.
- **Выполнимость.** Очень высокая; первые данные уже есть (§5).
- **Риски.** Сам по себе выглядит как «бенчмаркинг» — защищаем только в связке с планировщиком (угол 1/3).

**Рекомендация.** Брать угол 1 как ядро, угол 4 — как первую главу экспериментов (обоснование модели стоимости), угол 2 или 3 — как второй вклад в зависимости от темпа. Формулировка темы-кандидата: «Планирование и контроль контрактов исполнения LLM-агента на граничном устройстве (на примере Apple Silicon)».
