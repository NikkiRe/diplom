## 0. Главное

1. **Тезис R1 и R7 «prefill схем инструментов = 60–80% латентности шага» верен только для холодного шага.** Холодный шаг — это prefill без попадания в кэш. Если каталог фиксирован, `llama-server` с `cache_prompt` на втором шаге и дальше префикс уже не пересчитывает. Значит, мотивацию угла кэширования надо формулировать через ситуации, где префиксный кэш **ломается**:
   - (а) отбор инструментов под запрос: подмножество меняется, и префикс расходится;
   - (б) изменение каталога (MCP `notifications/tools/list_changed`);
   - (в) вытеснение KV при нехватке памяти или конкуренции приложений;
   - (г) холодный старт.
   
   Это не ослабляет тему, а делает её точнее. Подробности в §1.
2. **Три рычага независимы и складываются, а не конкурируют.**
   - **Отбор** уменьшает число инструментов N → k.
   - **Сжатие** уменьшает число токенов на инструмент n → n/r.
   - **Кэширование KV** убирает повторный prefill уже виденных токенов.
   
   Совместную оценку всех трёх на одном устройстве я не нашёл ни в одной работе. Ближе всех стоит препринт Nexus (2026, один автор, одна модель, M4 Max) [E1].
3. **Gisting [A5] даёт прямой количественный ответ на вопрос «зачем кэш, если можно сжать».** Против кэширования полного промпта (instruction caching) gist-сжатие ускоряет wall-clock всего на **~1%**. Зато KV на хранение нужно в **26 раз** меньше. Вывод: латентность выигрывается кэшем, а сжатие окупается **памятью**. На устройстве с 24 ГБ это главный ресурс (§1.3).
4. **Классические компрессоры промпта (LLMLingua, LongLLMLingua, LLMLingua-2, Selective Context) проверены на прозе:** GSM8K, BBH, MeetingBank, LongBench. На JSON-схемах инструментов их не проверяли. Известная проблема сжатия документации — **потеря имён функций и параметров**: при 16x на API-Bank имя ошибается в 51 случае против 21 без сжатия [B1]. Компрессор LLMLingua — это LM на 7B параметров, то есть размером с целевую модель на устройстве. LLMLingua-2 — энкодер класса XLM-R-large.
5. **Детерминированная «компиляция» схем** (TSCG [B3]) и компактные нотации (TRON/TOON [B4]) дают 18–57% экономии токенов без обучения и без модели-компрессора. Для малых локальных моделей TSCG сообщает даже **рост** точности. Оба результата — свежие препринты 2026 года от независимых авторов, их нужно воспроизводить.
6. **Отбор инструментов улучшает и точность, и стоимость.** RAG-MCP [C1]: точность выбора 13.62 → 43.13%, промпт 2133.84 → 1084 токенов. Это −49.2% по их же таблице, а в аннотации заявлено «более 50%». Less-is-More (DATE 2025, Jetson AGX Orin) [C5]: время выполнения до −70%, мощность до −40%.

   **Узкое место — качество поиска.** На ToolRet [C2] лучшие IR-модели без инструкций дают nDCG@10 ≈ 31. На LiveMCPBench [D2] около половины провалов агентов — ошибки поиска.
7. **Отбор ломает префиксный кэш.** Разные подмножества дают разные префиксы. Это прямой и пока почти не исследованный стык угла 1 (R1) и Tool RAG. В индустрии его обходят так: отложенные (deferred) определения инструментов дописываются **после** кэшируемого префикса (Anthropic Tool Search, ноябрь 2025 [D6]).
8. **Сам стандарт MCP в ревизии 2026-07-28 рекомендует** серверам отдавать `tools/list` в детерминированном порядке. Мотивация прямо указана: попадания в prompt cache LLM. Добавлены также `ttlMs` и `cacheScope` для кэширования списков [D1]. Это первоисточник, на который можно опереться в мотивации кэширования каталога.
9. **Главный риск для новизны угла 1 — препринт Nexus (arXiv:2608.20397, июль 2026)** [E1]. Он делает «пересадку» предкомпилированных KV-блоков схем в llama.cpp на Apple unified memory и отбор через INT8-индекс.
   - Результат: KV-сплайсинг даёт только **1.1–1.7x TTFT на умеренной глубине** и **~1.0x на глубине ≥1024**.
   - Основной выигрыш даёт отбор: аргументы генерируются по сжатой сигнатуре (медиана 19 токенов), первый токен аргумента приходит в 1.66 раза быстрее.
   - Слабые места: один автор, одна модель (Qwen2.5-14B), n ≤ 30, код не опубликован.
   
   ВКР должна позиционироваться как **открытое, воспроизводимое, многомодельное сравнение трёх рычагов и их композиции**, а не как «первый KV-кэш схем».

## 1. Постановка: где на самом деле тратится prefill

### 1.1. Модель стоимости шага агента

Обозначения:
- каталог из N инструментов, у i-го инструмента n_i токенов;
- системная часть N_sys, запрос N_q;
- отобранное подмножество S(q), |S| = k;
- коэффициент сжатия r;
- скорость prefill v_pp и decode v_tg в токенах в секунду. v_pp падает с глубиной контекста.

```
Холодный шаг:  T = T_sel + T_cmp + (N_sys + Σ_{i∈S} n_i / r + N_q) / v_pp + n_out / v_tg
Тёплый шаг, префиксный кэш:  T = T_sel + T_restore + (L_total − LCP) / v_pp + n_out / v_tg
Модульный KV-кэш (R1, угол 1):  T = T_sel + T_assemble(S) + Σ_{i∈S, miss} n_i / v_pp + ρ·Σ_{i∈S, hit} n_i / v_pp + …
Память кэша:  M_KV = Σ_{i∈C} (n_i / r) · b_tok,  b_tok = 2 · L · H_kv · d_head · bytes
```

Здесь:
- LCP — длина общего префикса с закэшированной последовательностью;
- ρ — доля пересчитываемых токенов на стыках (CacheBlend/EPIC, R1 [E8]);
- C — множество инструментов, чей KV хранится в кэше.

Из модели видно:
- **отбор** уменьшает сумму, но меняет префикс, поэтому LCP падает;
- **сжатие** уменьшает и prefill, и M_KV, но добавляет T_cmp, если сжатие идёт онлайн, и риск ошибок в именах;
- **кэш** обнуляет prefill попавших токенов, но стоит памяти M_KV и работает только при совпадении префикса или при позиционно-независимой сборке.

### 1.2. Уточнение тезиса «60–80%»

Расчёт R1 §5 (Qwen3-8B Q4_K_M, Metal):
- 2762 токена каталога TinyAgent при ~354 ток/с — около 7.8 с;
- план из ~100 токенов при ~44.7 ток/с — около 2.2 с;
- доля prefill 78%. После Tool RAG (1397 токенов) — около 64%.

Арифметика верна, но описывает **холодный** шаг. В многоходовом диалоге с фиксированным каталогом `cache_prompt` убирает повторный prefill каталога. Поэтому в главе «Мотивация» нужны **измеренные** значения четырёх величин:
- (1) TTFT холодного шага;
- (2) TTFT тёплого шага при фиксированном каталоге;
- (3) TTFT при отборе top-k без кэша и с префиксным кэшем;
- (4) частота «поломок» префикса на реальной трассе запросов: смена подмножества, `list_changed`, вытеснение.

GPU в момент работы занимал бенчмарк другого агента, поэтому end-to-end замеры я не запускал: они исказили бы оба результата. План замера приведён в угле G3-1.

### 1.3. Пилот (только токенизатор, без GPU): цена формата и памяти

**Формат.** Шесть инструментов из примеров спецификации MCP 2026-07-28 токенизированы токенизатором Qwen3-8B (`llama-tokenize`). Инструменты: `get_weather`, `execute_sql`, `get_weather_data`, `calculate_sum`, `list_users`, `get_current_time`. Скрипт лежит в `G3_artifacts/`.

| Представление | Токены на 6 инструментов | Относительно JSON |
|---|---:|---:|
| JSON в стиле шаблона Qwen3 (`{"type":"function","function":{…}}`, разделители `", "`/`": "`) | 381 | — |
| Тот же JSON минифицированный | 285 | −25.2% |
| Сигнатура `name(arg: type, opt?: type) - описание [описания аргументов]` | 124 | −67.5% |
| Только имена | 20 | −94.8% |

Фиксированная обвязка шаблона Qwen3 (заголовок `# Tools … <tools></tools>` и инструкция `<tool_call>`) занимает 77 токенов.

Как читать пилот. Примеры из спецификации короче реальных инструментов. В реальных каталогах на инструмент приходится:
- около 129 токенов в API-Bank и около 356 в APIBench (токенизатор LLaMA [B1]);
- около 173 токенов в TinyAgent (2762/16);
- около 89 в MCP-Zero (248.1k токенов / 2797 инструментов [C7]);
- около 255 в MCPVerse (>140k токенов / >550 инструментов [D4]).

Порядок экономии от смены формата (25–67%) совпадает с данными TSCG (46.8–57%) [B3] и TRON (до 27%) [B4].

**Память KV.** Значение взято из GGUF-метаданных локальной модели Qwen3-8B: 36 слоёв, 8 KV-голов, head_dim 128. Отсюда b_tok = 2·36·8·128·2 Б = **144 КиБ на токен** в f16.

Сколько займёт KV всего каталога (расчёт):

| Каталог | Токены (оценка) | KV f16 для Qwen3-8B | prefill при 354 ток/с (нижняя граница) |
|---|---:|---:|---:|
| TinyAgent, 16 инструментов | 2 762 | 0.38 ГиБ | 7.8 с |
| LiveMCPBench, 527 инструментов × 89–255 ток | 47–134 тыс. | 6.4–18.4 ГиБ | 132–379 с |
| MCP-Zero, весь набор (2797) | 248.1 тыс. | 34.1 ГиБ | >700 с |

Выводы:
- Каталог масштаба MCP не помещается **ни в контекст** (у Qwen3-8B в GGUF `context_length` = 40 960), **ни в память** 24 ГБ вместе с весами (4.7 ГиБ).
- Поэтому на устройстве **отбор обязателен**, а **сжатие и квантизация KV** — это способ держать в кэше больше «горячих» инструментов.
- Кэш KV при этом остаётся способом не платить prefill повторно.

Так обосновывается не «кэш вместо сжатия и отбора», а **кэш плюс отбор плюс сжатие с политикой памяти**.

## 3. Группа A. Сжатие промпта общего назначения

### [A1] LLMLingua — `jiang2023llmlingua` — [V]
- **Библ.:** Jiang H., Wu Q., Lin C.-Y., Yang Y., Qiu L. LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models // Proc. EMNLP 2023. P. 13358–13376. DOI 10.18653/v1/2023.emnlp-main.825. arXiv:2310.05736. Проверено: arXiv, Crossref.
- **Проблема.** Промпты с CoT-демонстрациями и длинным контекстом дорого обрабатывать (API-стоимость, латентность), при этом они избыточны.
- **Метод.** Компрессия от грубой к тонкой (coarse-to-fine) по перплексии **малой LM**:
  - (1) **budget controller** распределяет бюджет между инструкцией, демонстрациями и вопросом, а демонстрации отбирает целиком;
  - (2) **итеративное токен-уровневое сжатие** (ITPC): удаляются токены с низкой перплексией, с учётом зависимостей между сегментами;
  - (3) **выравнивание распределений**: малая LM дообучается на данных, сгенерированных целевой LLM.

  Малая LM — Alpaca-7B или GPT2-Alpaca. Целевые модели — GPT-3.5-Turbo-0301 и Claude-v1.3. Сжатие работает с моделью как с чёрным ящиком.
- **Результаты.**
  - До **20x** сжатия при небольшой потере качества. GSM8K: EM 78.85 у полного промпта, 77.41 при 14x, 77.33 при 20x.
  - Латентность на GSM8K (V100-32G): end-to-end 8.6 с без сжатия. При 2x/5x/10x — 4.9/2.3/1.3 с, то есть **1.7–5.7x**. Само сжатие занимает 0.8/0.3/0.2 с.
- **Критика для edge.** Компрессор (LLaMA-класса 7B) **равен по размеру** целевой модели на ноутбуке. Экономия держится на предположении «малая LM ≪ целевой LLM» (авторы оценивают c_small ≈ c_LLM/25 для 7B против 175B). Для локальной Qwen3-8B это предположение не выполняется. На прозе метод работает, на JSON-схемах его не проверяли. Удаление токенов может разрушить имена и синтаксис.
- **Польза для ВКР.** Канонический baseline «сжатие промпта» в related work. Его отсутствие в обзоре — главная претензия рецензента, которую закрывает эта заметка. Аргумент против LLMLingua-1 на устройстве — размер компрессора.
- **Заимствовать.** Идею бюджета по сегментам: системная часть, каталог, запрос. Метрику «end-to-end speedup с учётом времени сжатия». Код `microsoft/LLMLingua` (MIT).

### [A2] LongLLMLingua — `jiang2024longllmlingua` — [V]
- **Библ.:** Jiang H., Wu Q., Luo X., Li D., Lin C.-Y., Yang Y., Qiu L. LongLLMLingua: Accelerating and Enhancing LLMs in Long Context Scenarios via Prompt Compression // Proc. ACL 2024 (Vol. 1: Long Papers). P. 1658–1677. DOI 10.18653/v1/2024.acl-long.91. arXiv:2310.06839. Проверено: arXiv, Crossref.
- **Проблема.** В длинном контексте растут стоимость и латентность, падает качество, и проявляется позиционный эффект lost-in-the-middle.
- **Метод.** **Query-aware** сжатие: релевантность документов и токенов к вопросу оценивается условной перплексией. Документы переупорядочиваются, степень сжатия по документам динамическая, после сжатия восстанавливаются подпоследовательности.
- **Результаты.** NaturalQuestions: до **+21.4%** качества при ~**4x** меньшем числе токенов (GPT-3.5-Turbo). LooGLE: −94.0% стоимости. Промпт ~10k токенов при сжатии 2–6x ускоряет end-to-end в **1.4–2.6x**.
- **Критика.** Сжатие зависит от запроса, поэтому каталог **нельзя сжать офлайн один раз** — компрессор платится на каждом шаге. Сжатый промпт каждый раз разный, поэтому **префиксный кэш перестаёт работать**. Для схем инструментов это проигрышное сочетание: оно убивает KV-кэш, а точность имён не гарантирует.
- **Польза для ВКР.** Пример того, как query-aware сжатие несовместимо с кэшированием KV. Это прямой аргумент в разделе «почему не сжатие». Идея переупорядочивания по релевантности пересекается с вопросом **порядка инструментов** (§10, угол G3-2).
- **Заимствовать.** Метрики «точность против коэффициента сжатия» и «позиция ключевого элемента». Код в том же репозитории (MIT).

### [A3] LLMLingua-2 — `pan2024llmlingua2` — [V]
- **Библ.:** Pan Z., Wu Q., Jiang H., Xia M., Luo X., Zhang J., Lin Q., Rühle V., Yang Y., Lin C.-Y., Zhao H.V., Qiu L., Zhang D. LLMLingua-2: Data Distillation for Efficient and Faithful Task-Agnostic Prompt Compression // Findings of ACL 2024. P. 963–981. DOI 10.18653/v1/2024.findings-acl.57. arXiv:2403.12968. Проверено: arXiv, Crossref.
- **Проблема.** Энтропия по causal LM субоптимальна и медленна. Нужен task-agnostic компрессор, который сохраняет смысл.
- **Метод.** Дистилляция от GPT-4: на MeetingBank размечено, какие токены сохранять. Затем обучается **бинарный классификатор токенов на двунаправленном энкодере**: XLM-RoBERTa-large (в статье указано 355M) или mBERT (110M, вариант «small»).
- **Результаты.**
  - Быстрее существующих компрессоров в **3–6x**, end-to-end **1.6–2.9x** при сжатии **2–5x**.
  - На V100 сжатие длится 0.4–0.5 с. Пиковая память компрессора 2.1 ГБ против 16.6 ГБ у LLMLingua и 26.5 ГБ у Selective Context (по таблицам HTML-версии).
  - Вне домена проверено на LongBench, ZeroSCROLLS, GSM8K, BBH. Целевые модели: GPT-3.5-Turbo и Mistral-7B.
- **Критика.** Обучено на стенограммах встреч. На структурированном тексте и коде отдельной проверки нет. Препринт CORE (2026) [A10] утверждает, что на смартфоне LLMLingua-2 тратит на порядок больше энергии, чем лёгкий эвристический компрессор.
- **Польза для ВКР.** **Самый реалистичный baseline** «сжатия промпта» для ноутбука: энкодер ~0.1–0.4B запускается через ONNX/CoreML/PyTorch MPS. Для статического каталога его можно применить **офлайн** и закэшировать результат. Тогда сжатие совместимо с KV-кэшем, и эту комбинацию стоит измерить.
- **Заимствовать.** Готовые модели на HF (`microsoft/llmlingua-2-*`; лицензию проверить на карточке), протокол «латентность компрессора плюс end-to-end».

### [A4] Selective Context — `li2023selectivecontext` — [V]
- **Библ.:** Li Y., Dong B., Guerin F., Lin C. Compressing Context to Enhance Inference Efficiency of Large Language Models // Proc. EMNLP 2023. P. 6342–6353. DOI 10.18653/v1/2023.emnlp-main.391. arXiv:2310.06201. Проверено: arXiv, Crossref.
- **Метод.** Лексические единицы (токены, фразы, предложения) с низкой **self-information** по малой causal LM отсекаются по перцентилю.
- **Результаты.** −**50%** контекста, −**36%** памяти инференса, −**32%** времени инференса. Падение BERTScore 0.023 и faithfulness 0.038 на четырёх задачах: arXiv, новости, диалоги.
- **Польза для ВКР.** Простейший training-free baseline. Его легко реализовать **на C++ поверх llama.cpp**: logits той же модели дают self-information без отдельного компрессора. Это недорогой вариант «сжатия своей же моделью» для сравнения.
- **Заимствовать.** Алгоритм (десятки строк). Код `liyucheng09/Selective_Context`: лицензия в репозитории не указана, поэтому реализовать самостоятельно.

### [A5] Gisting — `mu2023gisting` — [V]
- **Библ.:** Mu J., Li X.L., Goodman N. Learning to Compress Prompts with Gist Tokens // Advances in Neural Information Processing Systems 36 (NeurIPS 2023). P. 19327–19352. DOI 10.52202/075280-0848. arXiv:2304.08467. Проверено: arXiv, Crossref.
- **Проблема.** Инструкция повторяется во многих запросах. Кэшировать её KV дорого по памяти, а дообучать модель под каждую задачу дорого по времени.
- **Метод.** При instruction tuning маска внимания меняется так, что токены после k gist-токенов не видят исходную инструкцию. Модель учится «сжимать» инструкцию в KV gist-токенов. Обучение не дороже обычного instruction tuning. По умолчанию k = 1.
- **Результаты.**
  - До **26x** сжатия промпта, до **40%** меньше FLOPs, wall-clock **+4.2%** против варианта без кэширования.
  - **Против кэширования KV полной инструкции: +1.0% wall-clock и +0.11% FLOPs**. Латентный выигрыш почти исчезает.
  - Хранение: для LLaMA-7B ~1.05 МБ KV на токен (fp32), значит при сжатии 26→1 в том же объёме помещается в **26 раз** больше промптов.
  - Слабое место — out-of-distribution инструкции: в человеческой оценке на 252 промптах win-rate gist против контроля 45.8% (LLaMA-7B) и 42.5% (FLAN-T5-XXL). Плохо сохраняются детали, которые нужно скопировать дословно.
- **Польза для ВКР.** **Ключевая ссылка для обоснования.** Это рецензируемый эксперимент с прямым сравнением «сжатие против кэша KV»:
  - по латентности кэш почти не хуже;
  - сжатие выигрывает по **памяти**;
  - для схем инструментов, где нужно дословно копировать имена и enum-значения, soft-сжатие рискованно.
  
  Следствие: на устройстве нужна **политика памяти** для KV каталога (что держать, что сжимать, что вытеснять).
- **Заимствовать.** Постановку сравнения «без кэша / кэш полного промпта / сжатый кэш» и метрики «байт KV на инструмент» и «промптов на ГБ». Код `jayelm/gisting` (Apache-2.0).

### [A6] AutoCompressors — `chevalier2023autocompressors` — [V]
- **Библ.:** Chevalier A., Wettig A., Ajith A., Chen D. Adapting Language Models to Compress Contexts // Proc. EMNLP 2023. P. 3829–3846. DOI 10.18653/v1/2023.emnlp-main.232. arXiv:2305.14788. Проверено: arXiv, Crossref.
- **Метод.** OPT и Llama-2 дообучаются рекурсивно сжимать сегменты документа в **summary vectors** (soft prompts). Обучение на последовательностях до 30 720 токенов.
- **Результаты.** Summary vectors заменяют текстовые демонстрации в ICL с ростом точности и снижением стоимости. Векторы для корпуса можно **предвычислить** (retrieval-augmented LM, переранжирование).
- **Польза для ВКР.** Пример «предвычисленного сжатого представления» — soft-аналога KV-кэша документа. Позиционирование: soft-методы (A5–A7, B1, B6) требуют **дообучения конкретной модели**, а это противоречит рамке training-free/frozen SLM в угле 1.
- **Заимствовать.** Понятие амортизируемого предвычисления. Код `princeton-nlp/AutoCompressors` (лицензия не указана).

### [A7] ICAE — `ge2024icae` — [V]
- **Библ.:** Ge T., Hu J., Wang L., Wang X., Chen S.-Q., Wei F. In-context Autoencoder for Context Compression in a Large Language Model // ICLR 2024 (poster). OpenReview uREj4ZuGJE. arXiv:2307.06945. Проверено: arXiv (camera-ready v4), iclr.cc/virtual/2024/poster/17573.
- **Метод.** LoRA-энкодер (~1% дополнительных параметров) сжимает контекст в **memory slots**, на которые условлена замороженная LLM. Предобучение — автоэнкодирование плюс LM, затем instruction fine-tuning.
- **Результаты.** **4x** сжатия контекста на базе Llama, снижение латентности и GPU-памяти.
- **Польза для ВКР.** Reconstruction loss ICAE используют в работе о сжатии документации инструментов [B1]. В обзоре ICAE — представитель soft-сжатия «LLM сама себе энкодер». Для ВКР это скорее аргумент: 4x при дообучении против 1.6–2x от формата без обучения ([B3], пилот §1.3).
- **Заимствовать.** Таксономию. Код `getao/icae` (CC0-1.0).

### [A8] Обзор Prompt Compression — `li2025pcsurvey` — [V]
- **Библ.:** Li Z., Liu Y., Su Y., Collier N. Prompt Compression for Large Language Models: A Survey // Proc. NAACL 2025 (Vol. 1: Long Papers). P. 7182–7195. DOI 10.18653/v1/2025.naacl-long.368. arXiv:2410.12388. Проверено: arXiv, Crossref.
- **Суть.** Таксономия: **hard prompt** (фильтрация, перефразирование) и **soft prompt** (энкодер-декодер, только декодер). Механизмы объяснены через оптимизацию внимания, PEFT, модальности и «синтетический язык». Будущие направления: оптимизация энкодера, гибрид hard и soft.

### [A9] Characterizing Prompt Compression Methods — `jha2024characterizing` — [V-pre, workshop]
- **Библ.:** Jha S., Erdogan L.E., Kim S., Keutzer K., Gholami A. Characterizing Prompt Compression Methods for Long Context Inference // ES-FoMo Workshop @ ICML 2024. arXiv:2407.08892. Проверено: arXiv (комментарий о воркшопе).
- **Метод.** Единое сравнение трёх семейств на LongBench (9 наборов) с GPT-3.5-Turbo, Mixtral 8x7B и DBRX:
  - **extractive** (RECOMP-extractive, реранкер mxbai-rerank-large-v1);
  - **abstractive** (RECOMP-abstractive и др.);
  - **token pruning** (LongLLMLingua, LLMLingua-2, Selective Context).
- **Результаты.** Extractive сжатие (выбор целых предложений или чанков) часто лучше всех: до **10x** при минимальной потере, а на 2WikiMQA даже +7.89 при 7.75x. Token pruning, вопреки заявлениям авторов, часто **отстаёт**. Латентность и KV в работе не обсуждаются.
- **Польза для ВКР.** Авторы — та же группа, что TinyAgent (Berkeley SqueezeAI), что сближает с R1 [B3]. Вывод «extractive > pruning» напрямую поддерживает тезис: **для каталога инструментов «сжатие» = отбор целых инструментов (extractive), а не вырезание токенов из схем**. Это методическое обоснование того, что отбор — правильная форма сжатия каталога.
- **Заимствовать.** Классификацию extractive / abstractive / pruning для главы 1.

### [A10] CORE: лёгкое сжатие промпта на edge — `xu2026core` — [V-pre] (дополнительно)

- **Суть.** Двухэтапное сжатие на уровне предложений **без вспомогательной SLM**: NER плюс семантическое сопоставление и ортогональный residual retrieval. ## 4. Группа B. Сжатие и переписывание документации инструментов

### [B1] Concise and Precise Context Compression for Tool-Using LMs — `xu2024toolcompress` — [V]
- **Библ.:** Xu Y., Feng Y., Mu H., Hou Y., Li Y., Wang X., Zhong W., Li Z., Tu D., Zhu Q., Zhang M., Che W. Concise and Precise Context Compression for Tool-Using Language Models // Findings of ACL 2024. P. 16430–16441. DOI 10.18653/v1/2024.findings-acl.974. arXiv:2407.02043. Проверено: arXiv, ACL Anthology, Crossref.
- **Проблема.** Документация инструментов длинная. Обычное soft-сжатие (а) теряет **имена инструментов и параметров**, а без них вызов не работает, и (б) имеет фиксированную длину, не подстраиваемую под объём документации.
- **Метод.** LLaMA-7B в роли компрессора и декодера, два приёма:
  - **Selective compression**: имена инструментов и параметров остаются сырыми токенами, остальной текст сжимается в soft-токены;
  - **Block compression**: документация режется на блоки, каждый сжимается в фиксированные 2 summary-токена, что даёт переменный коэффициент сжатия.
  
  Документация сжимается **один раз офлайн**: инструмент после развёртывания не меняется.
- **Результаты** (Table 2, PDF).

  API-Bank (средняя документация 129 токенов):

  | Вариант | 4x | 8x | 12x | 16x |
  |---|---:|---:|---:|---:|
  | Верхняя граница без сжатия | 71.47 | | | |
  | Selective | 70.18 | 72.75 | 69.15 | 72.49 |
  | Overall (сжатие всего текста) | 68.12 | 67.10 | 64.52 | 61.70 |

  APIBench (356 токенов): верхняя граница 88.24, selective 89.13 при 16x.

  Ошибки в именах на API-Bank: 21 без сжатия, **51 при overall-16x**, 21 при selective-16x.
- **Польза для ВКР.** **Единственная рецензируемая работа именно про сжатие документации инструментов.** Доказывает, что (1) имена и параметры — несжимаемое ядро, а (2) документация статична и сжимается офлайн. Оба тезиса совпадают с логикой KV-кэша: **статичный модуль считается один раз**. Различие: здесь «сжатое KV» получается дообучением, а угол 1 — training-free.
- **Заимствовать.** Метрику **name errors** — её стоит обязательно добавить в оценку любого сжатия схем в ВКР. Разделение «сохраняемые поля / сжимаемые поля». Средние длины документации как калибровку нагрузки.

### [B2] EASYTOOL — `yuan2025easytool` — [V]
- **Библ.:** Yuan S., Song K., Chen J., Tan X., Shen Y., Ren K., Li D., Yang D. EASYTOOL: Enhancing LLM-based Agents with Concise Tool Instruction // Proc. NAACL 2025 (Vol. 1: Long Papers). P. 951–972. DOI 10.18653/v1/2025.naacl-long.44. arXiv:2401.06201. Проверено: arXiv, ACL Anthology, Crossref.
- **Метод.** ChatGPT **один раз** переписывает разнородную и длинную документацию в единые краткие инструкции: описание, сценарии использования, примеры.
- **Результаты** (HTML-версия). Длина документации: ToolBench 2530 → 748 токенов (**−70.43%**), RestBench 3881 → 103 (**−97.35%**). Success rate на ToolBench (DFSDT):
  - ChatGPT 9.5 → 52.8%;
  - GPT-4 15.5 → 70.0%;
  - Vicuna-7B 0 → 37.3%;
  - Mistral-7B 0 → 47.0%.
- **Критика.** Переписывает внешняя LLM (облако). Числа baseline на ToolBench очень низкие, что указывает на шумную исходную документацию.
- **Польза для ВКР.** Офлайн-переписывание каталога совместимо с KV-кэшем. Это baseline «нормализации каталога» перед кэшированием. Для малых 7B-моделей эффект особенно велик: краткость помогает и точности, а не только скорости.

### [B3] TSCG: детерминированная компиляция схем инструментов — `sakizli2026tscg` — [V-pre]
- **Библ.:** Sakizli F. TSCG: Deterministic Tool-Schema Compilation for Agentic LLM Deployments. arXiv:2605.04107, 2026. Связанная работа того же автора: Tool-Schema Compression Enables Agentic RAG Under Constrained Context Budgets, arXiv:2605.26165, 2026. Код `SKZL-AI/tscg` (MIT по GitHub API).
- **Проблема.** JSON-схемы (OpenAI FC, Anthropic, MCP) рассчитаны на машинный разбор, а не на LLM. Для малых моделей (4–14B) это несоответствие, по утверждению автора, объясняет большую часть провалов tool use на реальных размерах каталога.
- **Метод.** Компилятор JSON → компактный структурированный текст **без модели и без обучения**. Восемь композиционных операторов, среди них:
  - выбор разделителей, минимизирующих число токенов **под конкретный токенизатор** (TAS);
  - вынос ограничений в начало (CFL);
  - удаление «воды» (SDM);
  - дублирование хрупких атомов (SAD-F).
  
  Доказана формальная граница сжатия ≥51% на корректных схемах. Реализация — 1200 строк TypeScript без зависимостей.
- **Результаты.**
  - TSCG-Agentic-Bench: ~19 000 вызовов, 12 моделей. Phi-4 14B при 20 инструментах поднимается с 0% до **84.4%** (90.3% при 50 инструментах).
  - BFCL: 93.2% против 85.7% у исходного формата при **46.8%** экономии токенов. Экономия 52–57% сохраняется до 100 инструментов.
  - Связанная статья: при бюджете 8K JSON-схемы 28 инструментов переполняют контекст, а сжатые возвращают RAG (+20.5 п.п. EM). При 32K эффект ≤ 1 п.п.
- **Критика.** Независимый автор, препринт, собственный бенчмарк. Улучшение точности «от формата» нужно воспроизводить. **Взаимодействие с KV- и префиксным кэшем не обсуждается.**
- **Польза для ВКР.** Сильный и дешёвый **training-free baseline сжатия схем**. Он ортогонален кэшу: компилированная схема кэшируется так же. Операторы, выравнивающие текст по токенизатору, близки к low-level теме выравнивания границ модулей KV по токенам (R1, угол 1, риск 4).
- **Заимствовать.** Операторы как набор трансформаций для эксперимента «формат × кэш». Метрику accuracy-retained ratio (ARR). Код (MIT).

### [B4] Notation Matters (TOON/TRON) — `kutschka2026notation` — [V-pre]
- **Библ.:** Kutschka L., Geiger B. Notation Matters: A Benchmark Study of Token-Optimized Formats in Agentic AI Systems. arXiv:2605.29676, 2026. Код `lkutschka/notation-matters` (лицензия NOASSERTION — проверить файл).
- **Метод.** Компактные нотации TOON и TRON против JSON на четырёх бенчмарках (BFCL, MCPToolBench++, MCP-Universe, StableToolBench). Пять open-weight моделей 17–32B на vLLM. Сжатие входа (схемы) и выхода (вызовы) разделено.
- **Результаты.**
  - TRON: до **−27%** токенов при точности в пределах **14 п.п.** от JSON.
  - TOON: до −18%, около −9 п.п., но каскадные сбои парсинга в многоходовых сценариях и поломка параллельных вызовов у большинства моделей.
  - На BFCL non-live TRON даже **увеличил** число токенов на 21%.
- **Польза для ВКР.** Трезвая проверка: «компактный формат» не всегда бесплатен, и выигрыш зависит от структуры каталога. Хорошо дополняет TSCG как контрпример.
- **Заимствовать.** Раздельный учёт сжатия входа и выхода, перечень бенчмарков.

### [B5] MCP Tool Descriptions Are Smelly — `hasan2026mcpsmells` — [V-pre]
- **Библ.:** Hasan M.M., Li H., Rajbahadur G.K., Adams B., Hassan A.E. Model Context Protocol (MCP) Tool Descriptions Are Smelly! Towards Improving AI Agent Efficiency with Augmented MCP Tool Descriptions. arXiv:2602.14878, 2026 (v3).
- **Метод.** Проанализированы 856 инструментов из 103 MCP-серверов. Рубрика из шести компонентов описания: назначение, рекомендации, ограничения, параметры, длина и полнота, примеры. Сканер «запахов» на основе FM. Затем оценено влияние дополненных описаний на MCP-Universe (GPT-4.1, Qwen3-Coder-480B, GLM-4.5).
- **Результаты.**
  - **97.1%** описаний содержат хотя бы один «запах», 56% не сообщают назначение ясно.
  - Полное дополнение описаний даёт +5.85 п.п. успеха (медиана), но **+67.46% шагов исполнения** и регрессию в 16.67% случаев.
  - Абляция: компактные комбинации компонентов сохраняют надёжность, а удаление примеров (Examples) статистически не вредит.
- **Польза для ВКР.** Показывает, что реальные MCP-каталоги «сырые»: улучшение описаний **раздувает** контекст, а значит усиливает мотивацию кэша и отбора. Даёт эмпирическую основу для выбора полей при компиляции схем.
- **Заимствовать.** Рубрику шести компонентов для анализа длины описаний в собственном каталоге.

### [B6] CAMPHOR (Apple): сжатие определений функций в один токен на устройстве — `fu2024camphor` — [V-pre]
- **Библ.:** Fu Y., Anantha R., Cheng J. CAMPHOR: Collaborative Agents for Multi-input Planning and High-Order Reasoning On Device. arXiv:2410.09407, 2024.
- **Метод.** Иерархия on-device SLM-агентов с общими параметрами. Каждое определение функции сжимается в **один токен-эмбеддинг**: выход последнего токена описания, пропущенного через ту же SLM. Эти токены ставятся в начало промпта, у всех них позиционный индекс 0. Модели — Phi-3.5 и Gemma-2, дообучаются.
- **Результаты** (HTML). Токенов промпта на 95–96% меньше (98.3% статических токенов против LLM-baseline), Plan F1 падает только на 3.61%. Tool F1 67.84% (Phi-3.5).
- **Польза для ВКР.** Индустриальное (Apple) подтверждение: **на устройстве каталог функций — главный «статический» груз промпта**, и его стоит превращать в предвычисленное представление. Это «гистинг для инструментов». Требует дообучения, поэтому служит альтернативой и верхней оценкой, а не baseline training-free угла.
- **Заимствовать.** Приём «одна позиция для всех функциональных токенов» — интересное сравнение с позиционно-независимым KV (R1 [E8]).

## 5. Группа C. Отбор (retrieval) инструментов

### [C1] RAG-MCP — `gan2025ragmcp` — [V-pre]
- **Библ.:** Gan T., Sun Q. RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation. arXiv:2505.03275, 2025. Рецензируемого venue не найдено (OpenAlex, OpenReview).
- **Проблема.** «Раздувание промпта» (prompt bloat): при сотнях и тысячах MCP-описаний в контексте падают и точность выбора, и эффективность.
- **Метод.** Внешний семантический индекс MCP-описаний. Запрос кодируется (Qwen-max), извлекаются top-k MCP, опционально проходит валидация, и в LLM передаётся только схема выбранного MCP. Baselines:
  - **Blank Conditioning** — все N описаний сразу;
  - **Actual Match** — ключевые слова.
  
  Тестовый набор — web search subset MCPBench. Это **другой** MCPBench, не MCP-Bench [D3]. По 20 прогонов на baseline.
- **Результаты** (Table 1 в HTML).

  | Метод | Точность | Токенов промпта (среднее) |
  |---|---:|---:|
  | RAG-MCP | **43.13%** | 1084 |
  | Actual Match | 18.20% | 1646 |
  | Blank Conditioning | 13.62% | 2133.84 |

  Стресс-тест: N от 1 до 11 100 MCP-схем (26 интервалов). Выше ~30 позиций успех >90%, на 31–70 нестабилен, после ~100 резко деградирует.
- **Критика.** −49.2% по таблице против «более 50%» в аннотации. Одна облачная модель, 20 прогонов, задачи только web search. Retriever (Qwen-max) — большая облачная модель, а не локальный энкодер.
- **Польза для ВКР.** Самая цитируемая формулировка проблемы «prompt bloat в MCP» и готовый протокол **стресс-теста по N**. Его стоит воспроизвести локально на Qwen3 0.6–8B: Blank против top-k против top-k+KV-кэш.
- **Заимствовать.** Протокол стресс-теста (N на логарифмической сетке), baselines Blank и Actual Match, метрики «точность / токены промпта / токены ответа».

### [C2] ToolRet — `shi2025toolret` — [V]
- **Библ.:** Shi Z., Wang Y., Yan L., Ren P., Wang S., Yin D., Ren Z. Retrieval Models Aren't Tool-Savvy: Benchmarking Tool Retrieval for Large Language Models // Findings of ACL 2025. P. 24497–24524. DOI 10.18653/v1/2025.findings-acl.1258. arXiv:2503.01763. Проверено: arXiv, Crossref. В комментарии arXiv написано «ACL 2025», по Crossref это Findings.
- **Метод.** Гетерогенный бенчмарк поиска инструментов: **7 615** задач, корпус **43 215** инструментов из 30+ наборов. Обучающий набор ToolRet-train — более 200 тыс. примеров.
- **Результаты** (HTML).
  - Без инструкций: NV-Embed-v1 nDCG@10 **31.30** (Recall@10 39.15), GTE-Qwen2-1.5B 29.17, BM25s 22.32.
  - С инструкциями: реранкеры bge-reranker-v2-gemma 47.52 и jina-reranker-v2 47.17, NV-Embed 42.71.
  - Модели, сильные на обычных IR-бенчмарках, на ToolRet слабы.
  - Плохой поиск снижает pass rate tool-use LLM (пример: −11.40 п.п. против oracle-набора). Обучение на ToolRet-train даёт заметный прирост.
- **Польза для ВКР.** Даёт **численную границу** качества отбора, то есть ответ на вопрос «почему нельзя просто отобрать»: отбор ошибается, и цена ошибки — провал задачи. Отсюда нужен **fallback**: при низкой уверенности отбора полный каталог берётся из кэша (так делает Less-is-More [C5], уровень 3).
- **Заимствовать.** Поднабор ToolRet как бенчмарк локального retriever'а, метрики nDCG@10 и Recall@10. Код `mangopy/tool-retrieval-benchmark` (Apache-2.0).

### [C3] COLT — `qu2024colt` — [V]
- **Библ.:** Qu C., Dai S., Wei X., Cai H., Wang S., Yin D., Xu J., Wen J.-R. Towards Completeness-Oriented Tool Retrieval for Large Language Models // Proc. 33rd ACM CIKM 2024. P. 1930–1940. DOI 10.1145/3627673.3679847. arXiv:2405.16089. Проверено: arXiv, Crossref.
- **Проблема.** Для многошаговых задач нужен **полный** набор инструментов, а не самые похожие. Семантический поиск возвращает избыточные и однотипные инструменты.
- **Метод.** Сначала семантическое обучение retriever'а. Затем коллаборативное обучение на двудольных графах «запрос–сцена–инструмент» (dual-view graph). Новая метрика **COMP@K**: доля запросов, у которых все нужные инструменты попали в top-K.
- **Результаты** (HTML).
  - BERT-mini (11M) с COLT лучше BERT-large (340M).
  - ToolLens (18 770 запросов, 464 инструмента): Recall@5 97.75%, COMP@5 94.08%.
  - ToolBench I2: COMP@5 70.10% против 4.37% у BM25.
- **Польза для ВКР.** Метрика **COMP@K** — правильная метрика отбора для агента. Если нужный инструмент не отобран, задача проваливается при любом кэше. Сверхмалый retriever (11M) реалистичен на ноутбуке.
- **Заимствовать.** COMP@K и идею «полноты» для многошаговых сценариев. Код `quchangle1/COLT` (лицензия не указана).

### [C4] Re-Invoke — `chen2024reinvoke` — [V]
- **Библ.:** Chen Y., Yoon J., Sachan D.S., Wang Q., Cohen-Addad V., Bateni M., Lee C.-Y., Pfister T. Re-Invoke: Tool Invocation Rewriting for Zero-Shot Tool Retrieval // Findings of EMNLP 2024. P. 4705–4726. DOI 10.18653/v1/2024.findings-emnlp.270. arXiv:2408.01875. Проверено: arXiv, Crossref.
- **Метод.** Без обучения:
  - (1) при индексации LLM генерирует синтетические запросы к каждому инструменту (document expansion);
  - (2) при выводе LLM извлекает из запроса намерения;
  - (3) инструменты ранжируются по многоракурсной близости.
- **Результаты.** ToolE: nDCG@5 +20% (один инструмент) и +39% (несколько инструментов) относительно baseline.
- **Польза для ВКР.** Индексация **офлайн** (как предвычисление KV), а выделение намерений **онлайн** стоит лишнего вызова LLM на устройстве. Хороший пример компромисса «точность отбора против латентности» для таблицы сравнения.
- **Заимствовать.** Document expansion инструментов синтетическими запросами (это делается один раз).

### [C5] Less-is-More: отбор инструментов на edge — `paramanayakam2025lessismore` — [V]
- **Библ.:** Paramanayakam V., Karatzas A., Anagnostopoulos I., Stamoulis D. Less is More: Optimizing Function Calling for LLM Execution on Edge Devices // Proc. Design, Automation & Test in Europe Conference (DATE 2025). 2025. P. 1–7. DOI 10.23919/DATE64628.2025.10992798. arXiv:2411.15399. Проверено: arXiv, Crossref.
- **Метод.** Training-free иерархический отбор:
  - LLM-«рекомендатель» описывает **идеальные** инструменты, не видя реального API;
  - описания эмбеддятся (MPNet, 768-d) и ищутся k-NN (FAISS);
  - уровни: отдельные инструменты, кластеры инструментов, полный набор как fallback при уверенности < 0.5.
  
  Пространство эмбеддингов строится офлайн.
- **Результаты** (HTML). NVIDIA **Jetson AGX Orin**, 6 моделей: Hermes2-Pro-8B, Llama3.1-8B, Mistral-8B, Phi3, Qwen2-1.5B, Qwen2-7B. Квантизации q4_0, q4_1, q4_K_M, q8_0.
  - BFCL (51 функция): время выполнения до −70…80%, мощность до −45%. Пример Llama3.1-8B: время −72%, мощность −30%, точность выбора инструмента 93.8%.
  - GeoEngine (46 функций, последовательные вызовы): время −15…40%.
  - Окно контекста уменьшено с 16K до 8K.
- **Критика.** Одна плата. «Мощность» измерена средствами Jetson. Эффект кэша не рассматривается: каждый запрос — новый промпт.
- **Польза для ВКР.** **Ближайший рецензируемый аналог по постановке «edge + стоимость каталога».** Даёт методику измерения мощности и времени и **сильный training-free baseline отбора** с fallback. ВКР может показать, как этот baseline сочетается с KV-кэшем: стоимость fallback на полный каталог при кэше почти нулевая.
- **Заимствовать.** Трёхуровневую схему с fallback, MPNet+FAISS, сетку квантизаций GGUF (совпадает с llama.cpp).

### [C6] Dynamic ReAct — `gaurav2025dynamicreact` — [V-pre]
- **Библ.:** Gaurav N., Akarsh A., Ranjan A., Bajaj M. Dynamic ReAct: Scalable Tool Selection for Large-Scale MCP Environments. arXiv:2509.20386, 2025 (cs.SE). Аффилиация — agentr.dev.
- **Метод.** Пять архитектур от простого семантического поиска до «search-and-load»:
  - мета-инструменты `search_tools` и `load_tools`: модель сама ищет и загружает инструменты;
  - вариант с иерархией «приложение → инструмент»;
  - вариант с фиксированным набором из четырёх мета-инструментов, который хорошо кэшируется, но деградирует в длинных диалогах.
- **Результаты.** Аннотация: загрузка инструментов до **−50%** при сохранении точности. По HTML: Top-5 растёт с 40% (OpenAI-эмбеддинги) до 56–60% (Voyage плюс обогащение контекста). Реестр проприетарный.
- **Критика.** Нет открытого бенчмарка и кода. Главная модель — облачная (Claude).
- **Польза для ВКР.** Архитектура «фиксированный набор мета-инструментов» явно названа кэш-дружественной. Это прямой мостик к углу 1: **неизменный префикс плюс динамически подгружаемые схемы в хвосте**.
- **Заимствовать.** Паттерн search-and-load как вариант отбора, совместимый с префиксным кэшем.

### [C7] MCP-Zero — `fei2025mcpzero` — [V-pre]
- **Библ.:** Fei X., Zheng X., Feng H. MCP-Zero: Active Tool Discovery for Autonomous LLM Agents. arXiv:2506.01056, 2025 (v4). Код `xfey/MCP-Zero` (MIT).
- **Метод.** Агент сам формулирует **запрос на инструмент** (Active Tool Request). Иерархическая маршрутизация «сервер → инструмент» на эмбеддингах text-embedding-3-large со скорингом `(s_server·s_tool)·max(s_server, s_tool)`. Набор инструментов наращивается итеративно.
- **Результаты.**
  - Датасет MCP-tools: **308** серверов и **2 797** инструментов (около **248.1k** токенов при полной вставке).

### [C8] ScaleMCP — `lumer2025scalemcp` — [V-pre]
- **Библ.:** Lumer E., Gulati A., Subbiah V.K., Basavaraju P.H., Burke J.A. ScaleMCP: Dynamic and Auto-Synchronizing Model Context Protocol Tools for LLM Agents. arXiv:2505.06416, 2025.

Эмбеддинг TDWA взвешивает поля документа инструмента. Оценка: 5000 финансовых MCP-серверов, 10 LLM, 5 эмбеддеров.

### [C10] ToolGen (и ToolkenGPT): «инструменты в весах» — `wang2025toolgen`, `hao2023toolkengpt` — [V]

## 6. Группа D. MCP: первоисточник и бенчмарки

### [D1] Спецификация Model Context Protocol, ревизия 2026-07-28 — `mcp2026spec` — [V-doc]
- **Источник:** Model Context Protocol Specification, revision 2026-07-28. Раздел Server → Tools: https://modelcontextprotocol.io/specification/2026-07-28/server/tools. Changelog: https://modelcontextprotocol.io/specification/2026-07-28/changelog. Предыдущая ревизия — 2025-11-25. Лицензия репозитория: переход с MIT на Apache-2.0, документация под CC-BY-4.0.
- **Что важно для ВКР (первоисточник формата):**
  - Тип **Tool** содержит поля: `name` (1–128 символов, `[A-Za-z0-9_.-]`, уникально в пределах сервера), `title`, `description`, `icons`, `inputSchema`, `outputSchema`, `annotations`.
    - `inputSchema` — JSON Schema, по умолчанию диалект **2020-12**.
    - `outputSchema` — опциональная JSON Schema.
    - `annotations` — подсказки о поведении, недоверенные, если сервер не доверенный.
  - Расширение `x-mcp-header` и поле `execution` — это новшество 2025-11-25.
  - `tools/list` с пагинацией (`cursor`/`nextCursor`). Уведомление `notifications/tools/list_changed` при capability `listChanged`. В 2026-07-28 оно доставляется через поток `subscriptions/listen`.
  - **Новое в 2026-07-28.**

### [E1] Nexus — `arslan2026nexus` — [V-pre] — **главный конкурент угла 1**
- **Библ.:** Arslan M. Nexus: Depth-Adaptive KV-Cache Splicing and Retrieval-Decoupled Tool Routing for Agentic LLMs on Unified Memory. arXiv:2608.20397, 2026 (v1, датировано 01.07.2026). Независимый исследователь (Стамбул).
- **Постановка.** MCP-агенты на каждом ходе заново кодируют многословные схемы. С ростом реестра prefill доминирует в TTFT.
- **Метод.**
  - (1) **Отбор отделён от prefill схем.** INT8 «semantic lookaside buffer» (SLB) с безветвевым SIMD-сканом скалярных произведений (NEON/AVX) находит инструмент за **17.6 мкс**. Пограничные случаи проверяет откалиброванный cross-encoder. Аргументы генерируются по **сжатой текстовой сигнатуре** (медиана **19 токенов**), а не по полной схеме.
  - (2) **Вторичный рычаг** — пересадка заранее скомпилированного KV-блока схемы (файлы `.atb`: заголовок с RoPE-якорем плюс выровненные F16 K/V, mmap) в живой кэш llama.cpp.
    - Вставка в позицию компиляции (anchored splice) точна по выходу.
    - Вставка в другую позицию портится из-за фазового сдвига RoPE. После порога P = 256 шов ремонтируется адаптивным суффиксным redecode, который при необходимости эскалирует до полного re-prefill.
- **Стенд.** Apple **M4 Max**, 64 ГБ, llama.cpp, **одна модель** Qwen2.5-14B-Instruct Q4_K_M, эмбеддер nomic-embed-text-v1.5.
- **Результаты.**
  - Точность маршрутизации около 89% при 250 инструментах (95% ДИ 81.4–93.7). Baseline «все схемы подряд» при таком числе переполняет контекст.
  - Первый токен аргумента приходит в **1.66 раза** быстрее, чем при полном re-prefill (443.8 против 737.3 мс), при экономии ~80% токенов основного контекста.
  - KV-сплайсинг: TTFT 1.63x при n_past = 256, 1.24x при 512 и **~1.0x при 1024–2048**.
  - Два отрицательных результата: граница точности RoPE вне якоря и неспособность drift-гейта без эталона предсказать дрейф (Spearman ρ = 0.193).
- **Ограничения** (по словам автора): одна модель, n ≤ 30 в end-to-end, «глубокий» сплайс проверен микробенчмарками, код не опубликован (выдаётся по запросу).
- **Значение для ВКР — критично.**
  1. Ниша «KV схем инструментов на Apple Silicon в llama.cpp» **частично занята**. Новизну надо формулировать через то, чего у Nexus нет:
     - (а) открытый воспроизводимый стенд;
     - (б) лестница моделей 0.6–8B и несколько семейств;
     - (в) **совместное** сравнение отбора, сжатия (TSCG, LLMLingua-2) и кэша с факторным дизайном;
     - (г) точность на стандартных бенчмарках (BFCL, LiveMCPBench), а не только agreement;
     - (д) политика памяти кэша под бюджет и инвалидация по `list_changed`;
     - (е) статистика n ≥ 30 по каждой ячейке.
  2. Их отрицательный результат по RoPE вне якоря — **гипотеза для проверки** стратегии «независимые блоки» из R1. Если подтвердится, это независимая репликация, тоже вклад.
  3. Их вывод «основной рычаг — отбор, KV-сплайсинг вторичен и ограничен» нужно **проверить на малых моделях**. У 0.6–1.7B prefill дешевле, и баланс может сместиться.

## 8. Синтез: «почему кэшировать KV, а не сжимать или отбирать» — ответ для главы 1

Свойства рычагов для **статического** каталога на устройстве:

| Свойство | Отбор (RAG-MCP, Less-is-More, COLT) | Hard-сжатие онлайн (LLMLingua-1/2, LongLLMLingua) | Сжатие офлайн (TSCG, EASYTOOL, LLMLingua-2 офлайн) | Soft-сжатие (Gist, ICAE, [B1], CAMPHOR) | KV-кэш (префиксный / модульный) |
|---|---|---|---|---|---|
| Снижает холодный prefill | да (N → k) | да (r = 2–20x) | да (r ≈ 1.5–3x) | да (r = 4–26x) | нет (холодный промах) |
| Снижает тёплый prefill | только вместе с кэшем | нет: сжатый промпт каждый раз другой | да, вместе с кэшем | да | **да, почти полностью** |
| Оверхед на пути запроса | эмбеддинг запроса (мс) плюс риск промаха | компрессор 0.2–0.8 с (V100) | 0 (офлайн) | 0 (офлайн) плюс адаптер | restore/assemble (мс) |
| Риск для точности | промах отбора (ToolRet nDCG@10 ≈ 31; LiveMCPBench ~50% провалов) | имена и параметры (name errors) | зависит от модели (TRON −14 п.п.; TSCG +) | OOD-инструкции, дословное копирование | 0 у точного префикса; RoPE-дрейф у PIC |
| Нужно обучение | нет (или retriever) | нет / компрессор | нет | **да** | нет |
| Совместимость с префиксным кэшем | **ломает**, если подмножество меняется | **ломает** | совместимо | совместимо | — |
| Память KV | ↓ в N/k раз | ↓ в r раз | ↓ в r раз | ↓ сильно | ↑ (цена кэша) |
| Динамика каталога (`list_changed`) | переиндексация | — | перекомпиляция | **переобучение** | инвалидация блоков |

**Аргументы для текста ВКР.**
1. Рецензируемые данные (Gisting [A5]) показывают: при кэшировании полного промпта сжатие почти не даёт латентности (+1% wall-clock) и выигрывает в основном **памятью**. Значит, для повторяющегося статического каталога кэш KV — основной латентный рычаг, а сжатие — рычаг памяти.
2. Каталоги MCP-масштаба (527–2797 инструментов, 47–248 тыс. токенов) не помещаются ни в контекст, ни в KV-память 8B-модели на 24 ГБ (§1.3). Поэтому **отбор обязателен**. Но отбор (а) ошибается (ToolRet, LiveMCPBench) и (б) ломает префиксный кэш. Значит, нужен механизм, который **делает отбор дешёвым при промахе и не ломает кэш**: модульный KV по инструментам, канонический порядок, отложенный хвост. Это и есть системный вклад.
3. Онлайн query-aware сжатие (LongLLMLingua) несовместимо с кэшем и дорого на устройстве (CORE [A10], размер компрессора LLMLingua [A1]). Офлайн-сжатие формата (TSCG, EASYTOOL) **совместимо** с кэшем и входит в композицию как множитель 1/r.
4. «Инструменты в весах» (ToolGen, ToolkenGPT, CAMPHOR, Octopus) снимают prefill полностью, но требуют переобучения при каждом изменении каталога. MCP же предполагает динамические каталоги (`listChanged`, `ttlMs`).

**Итоговая формулировка.** Задача ВКР — не «кэш против сжатия и отбора», а **рантайм, который компонует три рычага под бюджет памяти и латентности на устройстве**. Он должен:
- измерять, когда какой рычаг доминирует (по размеру модели, N, k, доле тёплых шагов);
- решать системные задачи их стыка: порядок, модульность KV, инвалидацию и вытеснение.

## 9. Открытые проблемы

1. **Нет совместной оценки трёх рычагов на одном устройстве.** Каждая работа меряет один рычаг, чаще на облачных API: RAG-MCP — Qwen-max, MCP-Zero — Claude/GPT, Anthropic — Claude. Исключение — Nexus [E1], но это одна модель, n ≤ 30, без кода.
2. **Сжатие промпта не проверено на JSON-схемах.** LLMLingua, LongLLMLingua, LLMLingua-2 и Selective Context оценены на прозе. Единственная рецензируемая работа о документации инструментов [B1] — soft и с дообучением. Training-free компиляторы схем (TSCG) и нотации (TOON/TRON) — препринты 2026 года с противоречивыми выводами о точности.
3. **Отбор ломает префиксный кэш.** Нет алгоритмов упорядочивания каталога, которые максимизируют ожидаемый общий префикс при top-k отборе. Нет и анализа «отбор плюс позиционно-независимый KV». MCP 2026-07-28 лишь рекомендует детерминированный порядок.
4. **Цена компрессора на edge.** LLMLingua тянет 7B-компрессор, LLMLingua-2 — энкодер ~0.1–0.4B (по CORE это дорого по энергии на смартфоне). Систематических замеров на Apple Silicon нет.
5. **Качество локального отбора.** ToolRet и LiveMCPBench оценивают крупные эмбеддеры и облачных агентов. Малые локальные эмбеддеры (Qwen3-Embedding-0.6B, MiniLM/MPNet, INT8) на этих бенчмарках системно не измерены, как и цена ошибки отбора с fallback на кэшированный полный каталог.
6. **Память KV каталога под бюджет.** Нет политики «какие инструменты держать в KV, какие сжимать, какие вытеснять» с учётом частоты, размера и стоимости пересчёта. Это аналог GreedyDual-Size для KV-блоков. Квантизация KV (`-ctk/-ctv`) взаимодействует с точностью tool calling (R1, P5).
7. **Динамика каталога.** Нет политики инвалидации KV при `list_changed` и `ttlMs`: инкрементальный пересчёт затронутых блоков против полного.
8. **Методология.** Малые выборки (RAG-MCP — 20 прогонов, Nexus — n ≤ 30), LLM-судьи (LiveMCPBench, MCP-Bench), проприетарные реестры (Dynamic ReAct), несоответствия аннотаций таблицам (RAG-MCP: «>50%» против 49.2%).

## 10. Углы ВКР в этой области (реализуемы одним студентом на M4 Pro / 24 ГБ)

Общая инфраструктура совпадает с R1 и R7:
- llama.cpp с зафиксированным коммитом, C/C++ API (`llama_state_seq_*`, `llama_memory_seq_*`);
- модели Qwen3 0.6B/1.7B/4B/8B GGUF;
- BFCL (Apache-2.0) и подмножества ToolRet (Apache-2.0), LiveMCPBench (Apache-2.0), MCP-tools из MCP-Zero (MIT);
- измерения по протоколу R7: n ≥ 5–30 повторов, медиана и p95, питание от сети, без фоновой нагрузки.

**Важно:** GPU-бенчмарки разных экспериментов нельзя запускать одновременно.

### Угол G3-1 (рекомендую как «экспериментальное ядро» вместе с R1, угол 1). Факторное сравнение и композиция рычагов «отбор × сжатие × кэш KV» для каталога инструментов на устройстве
- **Идея.** Единый C++-харнесс поверх llama.cpp. Факторы:
  - модель: 0.6/1.7/4/8B;
  - размер каталога N: 16…527 из LiveMCPBench/MCP-tools, логарифмическая сетка как в RAG-MCP;
  - отбор: нет / top-k по эмбеддингам / иерархический / с fallback;
  - формат: JSON / минифицированный / TSCG / сигнатура / LLMLingua-2 офлайн;
  - кэш: нет / префиксный (`cache_prompt`) / модульный по инструментам (R1);
  - режим: холодный / тёплый, доля «поломок» префикса на трассе.
  
  Результат — **измеренная** (а не расчётная) карта областей, где доминирует каждый рычаг, и Pareto-фронт «TTFT × точность × память KV». Заодно проверяется тезис «60–80%».
- **Системная часть.**
  - C++-инструментация фаз: tokenize, select, compile, restore/assemble, prefill, decode;
  - KV-байты на инструмент, `llama_state_seq_get_size`;
  - собственный генератор трасс запросов (распределение Zipf по инструментам).
- **Baselines.** Blank Conditioning (все N), RAG-MCP-style top-k, Less-is-More (с fallback), TSCG, LLMLingua-2, префиксный кэш llama-server, Nexus-style сигнатура для аргументов (реализовать по описанию).
- **Метрики.** TTFT p50/p95, латентность шага; точность выбора (BFCL multiple, irrelevance), **name errors** [B1], COMP@k [C3]; KV МБ и пиковый RSS; доля попаданий в кэш. Опционально энергия (R7, угол 4).
- **Осуществимость.** Высокая: обучение не требуется. Дорогая часть — время прогонов: при сетке около 4 × 6 × 4 × 5 × 3 ячеек нужен дробный факторный дизайн или отбор значимых факторов.
- **Риски.**
  - (1) Получится «бенчмарк без идеи». Лечится тем, что результат формулируется как модель стоимости из §1.1 и её валидация (предсказание против замера).
  - (2) Nexus частично пересекается. Лечится открытостью, лестницей моделей и факторным дизайном.
  - (3) Для 8B на 527 инструментах Blank Conditioning не влезает в контекст. Тогда это точка «невозможно», что тоже результат.

### Угол G3-2. Порядок и канонизация каталога для максимизации попаданий префиксного KV-кэша при отборе инструментов
- **Идея.** Отбор top-k выдаёт разные подмножества, префикс расходится на первом несовпавшем инструменте.
  - **Задача:** найти перестановку π каталога (и разбиение на «стабильное ядро» и «динамический хвост»), которая максимизирует ожидаемую длину общего префикса E[LCP] на распределении запросов при ограничении памяти.
  - Это комбинаторная оптимизация, родственная построению префиксного дерева. Эвристики: сортировка по частоте, кластеризация по совместной встречаемости (идея COLT), «ядро плюс хвост» (как `defer_loading`).
  - Плюс **канонизация** сериализации схем: стабильный JSON по RFC 8785 (JCS) или детерминированная компиляция по TSCG. Тогда одинаковые инструменты дают **байт-в-байт** одинаковые токены, а границы инструментов выравниваются по токенам.
- **Системная часть.** C++-канонизатор и компилятор схем MCP (`inputSchema`, JSON Schema 2020-12). Анализ токенизации на границах модулей (BPE-слияния через границу). Radix-дерево префиксов в рантайме (идея RadixAttention, R2) поверх `llama_memory_seq_cp/rm`.
- **Baselines.** Порядок сервера (как рекомендует MCP), алфавитный, случайный. Без канонизации. Anthropic-like «core + deferred tail».
- **Метрики.** Hit rate по токенам, средний пересчитываемый суффикс, TTFT p50/p95, накладные расходы канонизации (мкс), точность (порядок влияет на выбор: позиционные эффекты, LongLLMLingua [A2]).
- **Осуществимость.** Высокая. Хорошо подходит ИВТ: алгоритмы плюс структуры данных плюс рантайм.
- **Риски.** Если трасса запросов синтетическая, выводы зависят от её распределения. Нужна хотя бы одна реальная трасса (LiveMCPBench задачи → инструменты). Порядок может менять точность, поэтому её нужно контролировать.

### Угол G3-3. Политика памяти KV каталога под бюджет: какие инструменты держать в кэше, какие сжимать, какие пересчитывать
- **Идея.** При 144 КиБ/токен (Qwen3-8B, f16) KV каталога MCP-масштаба (6–34 ГиБ) не помещается в 24 ГБ. Варианты:
  - кэш-политика для KV-блоков инструментов: LRU, LFU, GreedyDual-Size с ценой пересчёта n_i/v_pp, оптимальная оффлайн Belady как верхняя граница;
  - ось «сжать или вытеснить»: q8_0/q4_0 KV против компактного формата против вытеснения;
  - инвалидация по `list_changed`/`ttlMs` (MCP 2026-07-28).
  
  Прямой наследник легаси «планировщика памяти тензоров по lifetimes» (D), но с реальной нагрузкой.
- **Системная часть.** Менеджер пула KV-блоков в C++ (slab-аллокатор, mmap-файлы блоков на SSD как второй уровень, аналог иерархий CachedAttention и LMCache из R2). Учёт unified memory (без PCIe: swap ≈ memcpy).
- **Baselines.** Без кэша; `--cache-ram` llama-server (LRU промптов); полный кэш при неограниченной памяти (верхняя граница); Belady (оффлайн-оптимум).
- **Метрики.** Hit rate, байты пересчёта, TTFT p95 при бюджетах 0.5/1/2/4 ГиБ, точность при квантизации KV (BFCL), накладные расходы менеджера.
- **Осуществимость.** Средне-высокая. Риск в стабильности `llama_state_seq_*` при частых restore. Задача не требует PIC: блоки можно хранить как префиксы ядра.
- **Риски.** При малых моделях (0.6–1.7B) prefill дешёв, и выигрыш кэша может быть мал. Тогда честный результат — граница применимости по размеру модели.

### Угол G3-4 (дополнительный, исследовательский). Training-free сжатие схем, сохраняющее имена: компилятор плюс проверка грамматикой
- **Идея.** Сочетание TSCG-подобной компиляции (ядро имён и типов не сжимается, [B1]) с **constrained decoding** по исходной JSON Schema (R3, R7, угол 3). Модель видит компактную схему, но генерирует вызов, валидный по полной схеме. Так компенсируется рост name errors.
- **Системная часть.** Компилятор схем на C++, генерация GBNF или llguidance-грамматики из `inputSchema`, кэш грамматик (R1, угол 2).
- **Baselines.** JSON без ограничений; JSON плюс грамматика; TSCG без грамматики; TRON.
- **Метрики.** Токены на инструмент, BFCL AST accuracy, name и type errors, TPOT-оверхед маски.
- **Риски.** Пересечение с R3/R7 (угол 3). Лучше как глава внутри G3-1, чем отдельная тема.

*Чего я **не** рекомендую как ядро:* soft-сжатие (Gist, ICAE, CAMPHOR-подобное) с дообучением 0.6–1.7B на M4 Pro. Технически это возможно (LoRA через MLX или PyTorch MPS), но это ML-, а не системная тема. Её высокий риск не окупается для ИВТ-профиля, к тому же она противоречит рамке training-free.
