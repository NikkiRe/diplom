# robot-mcp — компактный MCP-адаптер мобильного робота (R-compact v2, Go)

MCP-сервер «уровня задачи» для робота TurtleBot3 (Nav2) поверх **rosbridge**: на плате работает статический
Go-бинарник, ROS на плате не нужен. В LLM уходят пять инструментов уровня «место» и короткие сводки, а
состояние робота приходит **событиями** (`notifications/resources/updated`) только на значимые изменения.
Контракт — `research/new_topic/robot_scenario.md` §6–7 и `docs/robot_sim.md` §12.7; эталон ответов —
Python-прототип `scripts/sim/robot_mcp_compact.py`; baseline — ros-mcp-server 3.1.2.

Ключевая метрика — экономность во времени: токены каталога и ответов, число обращений к LLM, трафик плата ↔
робот, память и CPU адаптера. Все числа ниже — smoke 07.10.2026 при параллельной работе других агентов
(IMPLEMENTATION_SPEC §0 п. 4): порядок величин, а не результаты.

```
 VM sbc (плата)                                         VM sim (робот)
 edgectx ──stdio/HTTP──► robot-mcp ──── одно WebSocket ────► rosbridge :9090 ─► Nav2, AMCL, /scan, камера (lazy)
                          ├ задачи: go_to/patrol/look исполняются здесь (без LLM на участках)
                          ├ сводки: лидар по секторам, место, заряд, тревога (канонический JSON)
                          └ события: task_end, alert → resources/updated с _meta.state
```

## Инструменты

| Инструмент | Аргументы | Ответ (пример с «платы») | ток. o200k | rosbridge за вызов |
|---|---|---|---|---|
| `status()` | — | `{"alert":"none","battery_pct":100,"free_m":{"back":0.52,"front":0.9,"left":1.08,"right":0.72},"nav":"idle","place":"dock","place_m":0.05}` | 52–53 | 3,3 КБ (один `/scan` в CBOR), из кэша — 0 |
| `go_to(place)` | `place`: enum мест | `{"accepted":"door","eta_s":20,"ok":true}` — сразу; итог — уведомлением `task_end` | 14 | ≈6,2 КБ на поездку 3,7 м |
| `patrol(places, look=true)` | массив enum (1–12) | `{"accepted":2,"eta_s":34,"ok":true}`; участки исполняются на плате | 14 | ≈12–15 КБ на 2 участка |
| `look(place?, image?)` | `place`: enum; `image`: bool | `{"detector":"none","in_view":{"nearest_m":0.9,"occupied_pct":74,"side":"left"},"place":"dock"}`; `image=true` — плюс JPEG 320×240 q70 (≈4,5 КБ) | 28–30 (+130 vision у gpt-4.1-mini) | 0 (кэш) / ≈12,7 КБ с кадром |
| `stop()` | — | `{"cancelled":"window","ok":true}`; без связи — `robot offline`; Nav2 не подтвердил отмену — `stop not confirmed` | 10 | до правки 09.10 — ≈170 Б; теперь вызов сервиса отмены (≈0,35 КБ JSON, оценка) + нулевая скорость, не измерено |

- **go_to асинхронный**: в виртуальных часах (T0/T1) синхронное ожидание сим. времени внутри хода агента
  заблокировало бы реплеер (`robot_scenario.md` §10.2). `-wait-param` добавляет `wait` (только реальные часы) —
  вариант для сравнения в T2.
- Уже на месте — `{"ok":true,"place":"door","status":"here"}` без движения; повторная цель туда же, куда уже
  едет, — `"status":"already moving"` без новой цели; новая цель вытесняет текущую (Nav2 preemption).
- `look(place)` — поездка и сводка одной задачей, сводка приходит в `done.view`; кадр — только «здесь».
  `-look-place=false` убирает параметр: каталог 217 токенов вместо 274.
- Ошибки короткие: `{"error":"unknown place","known":[…],"ok":false}` — 33 токена против 88 у pydantic в
  прототипе; до rosbridge такой вызов не доходит. Прямой скорости у LLM нет (шлюз приводов — принцип 6).
- `-payload raw` (R-raw для HR1): `status`/`look` отдают сырые `/amcl_pose` и `/scan` (3 931 / 3 720 токенов).

## Ресурсы и события

| URI | Что |
|---|---|
| `robot://inventory` | устройство `robot` (схема как у устройств помещения, `robot_scenario.md` §5): свойства с `enum`, действия, места с координатами и русскими названиями, пределы, цена инструментов |
| `robot://state/robot` | состояние; подписка → `notifications/resources/updated` |
| `robot://diag` | счётчики: вызовы (байты, оценка токенов), уведомления, трафик rosbridge по видам; не для LLM |

Состояние (полное — в `_meta.state` каждого уведомления, ≈44 токена; агенту не нужно читать ресурс):

| Свойство | Значения | Когда меняется |
|---|---|---|
| `place` | id места (ближе `place_radius_m` = 0,45 м), в пути — `between`, до первой позы — `unknown` | старт задачи, прибытие (по подтверждению Nav2), сдвиг извне в простое |
| `nav` | `idle` `moving` `succeeded` `aborted` `canceled` | старт и итог задачи |
| `battery_pct` | шаг 5 % | эмуляция (`POST /control/battery`) или тема `/battery_state` (`-battery topic`) |
| `alert` | `none` `blocked` `stuck` `low_battery` `person` | тревога; снимается без уведомления |
| `done` | `{seq, task, place, status, visited?, seen?, view?}` | итог задачи, **начатой LLM**; `status: canceled` — цель отменил не адаптер |
| `seen` | `{label, place, m?}` | находка детектора на обходе (заглушка) |

Уведомления — **только значимые**: `task_end` (итог любой задачи) и `alert`. Шаг заряда и смена места на
участках обхода уходят в состояние молча (`-notify-context` включает и их). `_meta`: `device`, `state`,
`robot/event`, `robot/changed` (что изменилось), `robot/detail`. Тревоги:
- `blocked` — Nav2 прервал цель (или разорвана связь с rosbridge); с `-motion-scan-ms > 0` — ещё и
  препятствие впереди ближе `-obstacle-m` дольше `-obstacle-hold-s` до прерывания;
- `stuck` — при активной цели нет новой позы AMCL дольше `-stuck-s` (30 с) или участок дольше
  `-goal-timeout` (150 с, тогда цель отменяется); снимается, когда движение возобновилось;
- `low_battery` — заряд ≤ `-low-battery-pct` (20 %), снимается выше порога + 5 %;
- `person` — детектор на точке обхода увидел человека (детектор пока — заглушка `-detector stub`).

Пометки устаревания — в ответах инструментов, новых свойств в L1 нет (контракт гейта EdgeCtx не менялся):
`place_age_s` и `displaced` — в `status`, `lidar_age_s` и `"lidar":"no data"` — в `status` и `look` (у
`look(place)` сводка попадает в `done.view`, то есть и в L1). См. «Отмена целей Nav2 и устаревшие данные».

`_meta` вызова `tools/call` от оркестратора: `edgectx/by: rule` — задача правила (плановый обход): её итог
**не меняет `done`**, поэтому гейт EdgeCtx не будит LLM (`robot_scenario.md` §6.1). Не меняют `done` и задачи,
отменённые `stop`/вытесненные новой целью, и вызовы с `wait=true`: LLM уже знает итог. Задача, цель которой
отменил не адаптер (другой клиент rosbridge, поздно выполненная отмена), `done` меняет (`status: canceled`):
иначе LLM о ней не узнала бы.

## Отмена целей Nav2 и устаревшие данные (исправлено 09.10.2026)

Проблема из ревью 07.10 (HANDOFF §8): rosbridge 2.7.1 не отменяет цели отключившегося клиента (у
`rosbridge_library/capabilities/send_action_goal.py` нет `finish`, у базового `Capability.finish` — пустое тело;
сверено с исходниками тега 2.7.1), а адаптер отменял цель только по stop и таймауту и только в своём
соединении (`cancel_action_goal`). После обрыва связи или завершения адаптера робот доезжал до цели, о которой
агент уже не знал. Теперь все отмены — сервисом Nav2 `/navigate_to_pose/_action/cancel_goal`
(`action_msgs/srv/CancelGoal` с нулевыми `goal_id` и `stamp` — «отменить все цели»; так отменяется и цель
прежнего соединения или процесса) с ожиданием ответа не дольше `-cancel-timeout` (1 с). Подтверждение —
`result: true` и `return_code` 0; ошибка rosbridge (`result: false`) и отказ (`return_code` ≠ 0) — отмена не
состоялась:

| Когда | Что делает адаптер | Что видит агент |
|---|---|---|
| `stop()` | отмена всех целей — и при активной задаче, и без неё (цель могла остаться от обрыва или прошлого процесса); после ответа Nav2 — нулевой `TwistStamped` (раньше его перебил бы контроллер Nav2) | `{"cancelled":…,"ok":true}`; `robot offline`; `stop not confirmed` (нет ответа — соединение разорвано, нулевая скорость не ушла; ошибка или отказ — нулевая скорость отправлена) |
| таймаут участка `-goal-timeout` | отмена всех целей | `alert` stuck (`why: timeout`), `task_end` aborted |
| SIGTERM/SIGINT, конец сессии stdio | активная задача закрывается (`task_end` в журнале со статусом `shutdown`), её цель отменяется. В HTTP отмена идёт первой (идущий `go_to` с `wait=true` ждёт конца задачи), затем закрываются сессии MCP (поток уведомлений подписчика иначе держал бы остановку сервера до таймаута 3 с) и останавливается сервер. Выход — после отмены (не дольше `-cancel-timeout`) и идущих вызовов, код 0; в простое при завершении в rosbridge ничего не уходит | — (сессия закрыта) |
| обрыв rosbridge при активной цели | задача завершается сразу; при восстановлении связи клиент отменяет все цели **первым сообщением нового соединения** — раньше подписок и до того, как соединение доступно инструментам (иначе «отменить все» сняла бы и новую цель) | сразу `alert` blocked (`why: rosbridge disconnected`) и `task_end` aborted; без связи `go_to` — `robot offline` |
| первое подключение после старта | то же (цель мог оставить прошлый процесс, убитый, например, по OOM): +1 вызов сервиса на запуск, ≈0,35 КБ JSON (оценка по запросу и ответу фейка) | — |
| цель задачи LLM отменил не адаптер | задача завершается (свои stop и вытеснение закрывают задачу раньше, поэтому итог canceled приходит только извне) | `task_end`, `done` со `status: canceled` |

Порядок «отмена → новая цель». rosbridge 2.7.1 вызывает сервисы в отдельных потоках
(`call_services_in_new_thread`, в `rosbridge_websocket_launch.xml` по умолчанию `true`), поэтому отмена,
выполненная позже, сняла бы цель, отправленную после неё. Отсюда три правила клиента:
- цель, отправленная после начала отмены, уходит только после ответа на неё; если задачу за это время
  остановили, цель не уходит вовсе;
- отмена без ответа за `-cancel-timeout` **разрывает соединение**; переподключение снова начинается с отмены, и
  инструментам соединение откроется только после ответа на неё. Пока Nav2 не отвечает, адаптер offline
  (`robot offline`, `place_age_s`), а переподключения идут с паузой до 5 с. `-cancel-timeout` должен быть
  меньше `default_call_service_timeout` rosbridge (5 с): иначе его ответ-ошибка по таймауту сочтётся итогом,
  хотя отмена ещё может выполниться;
- неподтверждённая отмена (нет ответа, ошибка, отказ) повторяется первым сообщением следующего соединения.

Гарантия касается целей, отправленных после начала отмены. `task_end` от `stop` и таймаута уходит раньше
отмены: цель, отправленная в ответ на него (например, правилом), теоретически может её опередить — тогда
отмена снимет её, а агент получит `task_end` с `canceled` (не воспроизводилось: окно — микросекунды против
полного круга MCP). Итог каждой отмены — запись журнала `nav_cancel` (`why`: `connect` | `stop` | `timeout` |
`shutdown`, `goals`, `ms`, `error`) и предупреждение в stderr при сбое. Если Nav2 не ответил при завершении,
робот едет дальше — адаптер это только фиксирует в журнале.

Устаревшие данные помечаются в сводке, а не выдаются за текущие:
- **связи с rosbridge нет** — `place_age_s`: сколько секунд место не подтверждается (пока связь есть, латченная
  поза AMCL без новостей означает «не двигался»; без связи робот мог уехать — например, к неотменённой цели);
- **робота сдвинули извне в простое** — `"displaced":true` до следующей задачи, место по подтверждению Nav2
  сбрасывается и дальше считается по позе, запись журнала `displaced`. Признак: новая поза AMCL пришла позже
  окна `-pose-throttle-ms` + 1 с после остановки и отличается больше чем на 0,1 м или 0,1 рад. Окно — по
  стенным часам: прореживание rosbridge идёт по ним, а в T1 виртуальные часы прыгают вперёд за миллисекунды.
  Пороги и запас 1 с — **допущение**: пороги ниже шага публикации AMCL 0,25 м / 0,2 рад (`docs/robot_sim.md`
  §12.7 п. 6; повтор латченной позы после переподключения совпадает с прежней), на живом AMCL не проверялись,
  кандидаты в параметры предрегистрации. Скачок одометрии/перелокализация AMCL выглядят так же. Так же
  помечается любая смена места без задачи адаптера, замеченная позже окна, — в том числе доезд к цели,
  оставшейся после обрыва связи. Перенос робота без вращения колёс одометрия не видит, и AMCL не публикует новую
  позу, пока робот не поедет сам, — такой сдвиг адаптер не замечает до следующего движения;
- **скан** берётся только снятый там, где робот стоит сейчас (после конца задачи и последнего сдвига); если
  он старше `-scan-max-age`, а обновить его нельзя, — с `lidar_age_s`; скан другого места не выдаётся
  (`"lidar":"no data"`). В движении годится только свежий скан подписки движения.

Проверено только на фейковом стенде (`internal/fakebridge`, ведёт себя как rosbridge 2.7.1: цель
отключившегося клиента едет дальше; сервис `cancel_goal` отвечает как `rcl_action` — `return_code` 0 и список
отменяемых целей; режимы ответов на вызовы сервисов: с задержкой в отдельном потоке, без ответа, ошибка,
отказ), тесты — в разделе «Сборка, тесты, запуск». **С Gazebo/Nav2 на этом этапе не проверялось** (ВМ `sim` не
запускалась): время ответа настоящего `cancel_goal` (ревьюер 07.10 вручную — ≈4,9 мс), поведение
`goals_canceling` и `return_code` Nav2 Jazzy, реакция контроллера на отмену и путь торможения — не измерены.

## Как экономится (и что измерено)

- **Одно WebSocket на сессию** с переподключением; подписки и `advertise /cmd_vel` восстанавливаются сами.
- **Nav2 без feedback** (`"feedback": false`): только итог цели.
- **`/amcl_pose`** — латченная подписка с `throttle_rate` 2000 мс и `queue_length` 1 (`-pose-throttle-ms`):
  rosbridge отдаёт последнюю позу интервала; в простое трафика нет (120 с простоя — 0 байт).
- **`/scan` — только по запросу** (CBOR, типизированный массив float32: 3,1 КБ вместо 8 КБ JSON); в простое —
  из кэша, если скан снят после остановки и не старше 30 с (`-scan-max-age`). Подписка на время движения —
  флаг `-motion-scan-ms` (нужна для тревоги «препятствие впереди» до прерывания Nav2 и для T1 на паузе); вместе
  с непрореженной позой это 37–41 КБ на поездку вместо 6 КБ, поэтому по умолчанию выключена.
- **Кадр** — одна подписка на ленивую камеру в CBOR (JPEG байтами, без base64), уменьшение на плате 640→320
  усреднением 2×2 по плоскостям YCbCr и JPEG q70; ≈4 мс CPU на кадр на sbc.
- **Ответ** — один `TextContent` с каноническим JSON без `structuredContent`.
- **Мир на паузе** (T1): `/scan` и кадр по запросу не приходят (проверено: «no data» / `timeout`);
  `-sim-step-iters N` шагает мир сервисом `/world/default/control` (`multi_step`), пока ждёт сообщение —
  status 0,36 с, кадр 0,99 с.

| «Обход: коридор, база» | **3** / 1 332 / 0,065 | 2 / 810 / 0,041 (ход блокирован 41 с) | 3 / 7 545 / 0,36 |
| «Стоп» | 2 / 864 / 0,042 | 2 / 774 / 0,038 | 2 / 4 798 / 0,22 |

Что из этого следует:
1. Против ros-mcp — в 3,7–10 раз меньше входных токенов на задачу (с учётом лишнего пробуждения у поездок), в
   ≈150 раз меньше трафика на поездку и в 8 раз меньше PSS.
2. Против прототипа — в 3,6 раза меньше PSS, в 2 раза меньше трафика на поездку (прореженная поза AMCL),
   ответ `status` короче на 30–45 % (52 против 77–96 токенов). Каталог длиннее на 45 токенов из-за
   `look(place)` (он сам стоит ≈57 токенов в каждом запросе); с `-look-place=false` каталог на 12 токенов
   короче прототипа.
3. **Цена асинхронности** — +1 обращение к LLM (≈430 входных токенов), если о прибытии нужно сообщить
   пользователю. Зато ход агента не блокируется на 16–90 с, а в виртуальных часах синхронный вариант
   невозможен. Если итог `done` превращать в уведомление шаблоном гейта EdgeCtx, пробуждения не будет вовсе.
   Задачи правил (`edgectx/by: rule`) LLM не будят.
4. Участок corridor→dock на sbc дважды шёл 65–77 с: восстановление Nav2. Адаптер поднял `stuck` через 30 с
   без позы и снял его, когда робот поехал. На Mac тот же обход — 42 с. Порог `-stuck-s` — параметр
   предрегистрации.

Лимит памяти задаётся снаружи, в код не встроен: мягкий — переменной среды Go `GOMEMLIMIT` (например,
`GOMEMLIMIT=24MiB`, сборщик мусора работает чаще у предела), жёсткий — cgroup (`systemd-run --scope -p
MemoryMax=32M …` или `MemoryMax=` юнита). Подбор значений для платы — не сделан.

`notifications` (отправлено — реплеер ждёт, пока догонит `mcp.updates` агента), `active` (робот исполняет
задачу — шагать мир в T1), состояние и диагностика; `POST /control/clock {"t"}` (виртуальные часы, назад — 409);
`POST /control/battery {"pct"}`; `POST /control/detector {"place", "objects":[{"label","m","side"}]}`.

Тесты — без стенда, на фейковом rosbridge (`internal/fakebridge`: JSON и CBOR, колонны turtlebot3_world,
Nav2-подобное действие, латченная поза AMCL, ленивая камера, пауза и `multi_step`):
- CBOR (векторы RFC 8949, типизированные массивы, фаззинг);
- клиент rosbridge (разовое чтение, переподключение с восстановлением подписок, цель и вытеснение, сервис;
  отмена всех целей: запрос «отменить все»; цель во время отмены, выполняемой с задержкой в отдельном потоке,
  ждёт её ответа и не уходит, если стала не нужна; отмена при подключении первым сообщением; неподтверждённая
  (нет ответа, `result: false`, `return_code` 1) повторяется первым сообщением следующего соединения, а без
  ответа соединение закрывается и не открывается до подтверждения; без повтора после обрыва без цели и после
  завершённой цели; обработчик связи раньше ожидающих);
- сводки и паритет с Python-прототипом на одном стенде (`TestParityWithPrototype`: `free_m`, `in_view`,
  расстояние до места совпадают);
- оценщик токенов против точного o200k (`testdata/tokens_golden.json`, 146 текстов: +0,9 % в сумме, 134 из
  137 коротких ответов в пределах 15 %);
- MCP-сервер: каталог, асинхронный go_to с уведомлением, `edgectx/by: rule`, patrol, stop (порядок «отмена →
  нулевая скорость», чужая цель, Nav2 без ответа / с ошибкой / с отказом), отмена цели задачи чужим клиентом
  (`done` canceled), blocked, obstacle, low_battery (эмуляция и тема), look с кадром, look(place), person, stuck
  и таймаут с отменой цели в виртуальных часах, пауза мира с `-sim-step-iters` и без, R-raw, переподключение,
  обрыв во время цели (робот едет, пока связь не вернётся, затем отмена первым сообщением; пометки сводки,
  `displaced` после доезда без задачи), устаревание без связи, сдвиг извне (поза в окне после остановки — не
  сдвиг и при скачке виртуальных часов; поворот без переноса — сдвиг), wait, вытеснение;
- собранный бинарник по stdio и streamable HTTP с `/control/*`; завершение с активной целью (SIGTERM, конец

## Ограничения и что дальше

- **Отмена целей и пометки устаревания (09.10) проверены только на фейковом rosbridge**, не на Gazebo/Nav2 и не
  на роботе (см. раздел выше).
- **«Молчащая» связь** (потери 100 % без RST): пинга WebSocket нет (он стоил бы трафика в простое). В простое
  обрыв заметит keepalive TCP — простой 30 с (`net.Dialer.KeepAlive`) + 9 проб по 15 с (умолчания Go) ≈ 2,75 мин;
  если в полёте неподтверждённые данные, keepalive не работает, и обрыв заметят повторные передачи Linux
  (`tcp_retries2` = 15, ≈ 15 мин); зависший rosbridge при живом TCP не замечается вовсе. Быстрее — только по
  отмене без ответа (stop, таймаут участка): соединение разрывается через `-cancel-timeout`. Не проверялось
  (netem-стенд с отдельными netns не собирался).
- **Детектора нет.** `look` даёт сводку лидара в поле зрения камеры (62°), `person` — только от заглушки.
  Дальше — логическая камера Gazebo на стенде (идеальный детектор) или ONNX на плате (`robot_scenario.md` §7.3).
- **Заряд** эмулируется (`/control/battery`) или читается из `/battery_state`, которую должен публиковать драйвер
  стенда (его пока нет).
- **Тренд PSS за 8 ч (HR6)** не мерился: только 6 циклов (≈5 мин), PSS выходит на 15 МиБ.
- Числа — один-два прогона при нагруженном хосте. Время участков Nav2 сильно разбросано (15–28 с dock→door,
  42–97 с обход).
- Поза после прибытия: AMCL обновляется по сдвигу ≥ 0,25 м, поэтому после подтверждения Nav2 место берётся из
  цели, а `place_m` не сообщается, пока не придёт поза новее остановки.
- `occupied_pct` ограничен 100 % (у прототипа бывает 102 %: лучей в ±31,1° на один больше, чем в округлённой
  ширине).
- Оценка токенов в журнале — приближение. Числа для ПЗ — `tools/analyze.py` (точный o200k).
