# sysfsim — симулятор датчиков «живое sysfs»

Платы и датчиков пока нет, а hw-mcp должен читать оборудование тем же кодом, что на настоящей плате
(ABI Linux: IIO, hwmon, 1-Wire `w1_therm`, thermal, линии GPIO). `bench.sysfsim` создаёт дерево sysfs
и меняет во времени ровно те атрибуты, которые читает hw-mcp, по сценарию с физикой помещений, отказами
датчиков и «истиной» для будущих метрик. Агент тогда работает с данными в реальном времени и под
ограничениями ресурсов ВМ, а не с заранее записанным днём.

Только стандартная библиотека Python 3.12: запускается системным Python ВМ `sbc` прямо из смонтированного
только для чтения дерева проекта (`PYTHONDONTWRITEBYTECODE=1`, рядом с кодом ничего не пишется).

Что здесь своё, а что готовое. Своё — модели датчиков, физика, отказы, сценарии, часы, журнал истины.
Готовое — ядро Linux и его модуль `gpio-sim` (бэкенд gpiosim), libgpiod (только в проверке), hw-mcp
(отдельный компонент проекта). Значения фикстуры GAP2, на которой строится корень, синтетические.

## Команды

Из корня проекта; на Mac — `.venv/bin/python`, в ВМ — `python3`.

```bash
export PYTHONDONTWRITEBYTECODE=1
python -m bench.sysfsim list-scenarios                    # встроенные сценарии: dense (15 мин), day (8 ч)
python -m bench.sysfsim check --scenario dense            # проверка + прогон без записи; код 1, если ситуация не наступила
python -m bench.sysfsim init --root /tmp/board            # корень sysfs по фикстуре hw-mcp
python -m bench.sysfsim run --root /tmp/board --truth /tmp/truth.jsonl     # реальное время, линии-файлы

# hw-mcp на этом корне: те же имена устройств, что в таблице ниже
hw-mcp -root /tmp/board -declared bench/sysfsim/configs/declared.sim.json -transport http

# виртуальные часы: и симулятор, и hw-mcp двигает реплеер (сначала симулятор, затем hw-mcp)
python -m bench.sysfsim run --root /tmp/board --clock virtual --ready-file /tmp/sim.json   # адрес — в ready-file
curl -XPOST http://127.0.0.1:PORT/clock -d '{"t": 60}'

# ВМ, настоящий модуль ядра gpio-sim (root); declared с именем созданного чипа gpiochipN
sudo python3 -m bench.sysfsim run --root /tmp/board --gpio gpiosim --declared-out /tmp/declared.json
sudo hw-mcp -root /tmp/board -declared /tmp/declared.json -gpio-driver cdev   # sysfs симулятора + /dev/gpiochipN
# остановка: сначала hw-mcp (и любые другие потребители линий), затем симулятор — SIGTERM или Ctrl+C
```

`run` с бэкендом `files` завершается сам по `--duration` (по умолчанию — длительность сценария); с
`gpiosim` по концу сценария он не выходит, а держит чип с последними уровнями до сигнала: снимать чип
можно только после его потребителей (раздел «GPIO»). SIGTERM, SIGHUP (оборванная сессия ssh) и Ctrl+C
завершают прогон с уборкой и записью `run_end`, код 0. Сигнал ничего не прерывает: обработчик пуст, номер
сигнала Python пишет в канал (`signal.set_wakeup_fd`), а прогон ждёт этот канал там, где и так ждёт, — между
сроками мира, между запросами часов, после конца сценария. Поэтому запуск, шаг мира и уборка (с ожиданием
потребителей линий до 5 с) всегда доходят до конца: сигнал при запуске останавливает прогон сразу после
запуска, повторные сигналы ничего не меняют, сигнал во время уборки после ошибки не подменяет её код.
Остановка ждёт конца текущего шага, у виртуальных часов — текущего запроса (молчащий клиент — до 10 с,
«Часы»). Сигнал, игнорируемый с запуска, таким и остаётся: SIGHUP под `nohup`, SIGINT у фонового процесса
неинтерактивной оболочки. До установки обработчика (запуск интерпретатора, разбор аргументов) действует
обработчик по умолчанию — убирать тогда ещё нечего. Ошибки (сценарий, корень, права, cgroup, уже
существующий журнал, занятые при выходе линии) — сообщение `sysfsim: …` и код 1; журнал истины создаётся
после чипа и cgroup, поэтому неудачный запуск не оставляет пустого файла.

| флаг `run` | по умолчанию | смысл |
|---|---|---|
| `--root` | — | корень, созданный `init` (недостающее после прерванного прогона восстанавливается) |
| `--scenario` | `dense` | имя встроенного сценария или путь к JSON |
| `--seed` | 1 | шум, случайные отказы, стимулы PIR, дребезг |
| `--truth` | нет | журнал истины JSONL; существующий файл не перезаписывается |
| `--gpio` | `files` | `files` — `<root>/dev/<метка>/line<N>` («0»/«1»), как `gpio.Files` hw-mcp; `gpiosim` — модуль ядра |
| `--gpio-label` | `board-sim` | метка чипа; для `files` — имя каталога; для `gpiosim` — метка банка (должна быть уникальной, см. «GPIO») |
| `--declared` | `configs/declared.sim.json` | исходный declared.json для `--declared-out` |
| `--declared-out` | нет | записать declared.json, где у линий платы чип — созданный (`gpiochipN` или метка) |
| `--ready-file` | нет | JSON готовности: `pid`, `root`, `clock`, `gpio` (`backend`, `label`, `chip`), `url` (virtual) |
| `--duration` | сценария | секунды сценария до конца прогона (у `gpiosim` после него — ожидание сигнала) |
| `--clock` | `real` | `real` — монотонные часы × `--speed`; `virtual` — `POST /clock` |
| `--speed` | 1 | секунд сценария на секунду (только `real`) |
| `--control-addr` | `127.0.0.1:0` | адрес HTTP виртуальных часов (порт 0 — свободный) |
| `--load-cgroup` | нет | каталог cgroup v2 «платы»: её загрузка CPU греет SoC вместо событий `load` (только `real`); доступные CPU — меньшее из квоты `cpu.max` и числа CPU `cpuset.cpus.effective` этой cgroup (нет файла — нет этого предела) |

`init --root DIR` — каталог должен не существовать или быть пустым. `check --scenario --seed` печатает
JSON: отказы с моментами, моменты ситуаций при выключенном реле, число фронтов входов, диапазоны показаний.

## Плата: устройства и дерево

Корень — копия `hwmcp/testdata/fixture_root`, поэтому инвентарь hw-mcp тот же, что в лабораторном
сценарии. Отличия под драйверы: АЦП — `ads1115` (драйвер `ti-ads1015` не даёт атрибута смещения,
`in_voltage0_offset` фикстуры убран), у SoC добавлены `thermal_zone0/{temp,type}` и ссылка
`sys/class/thermal/thermal_zone0`, у моделей — неизменные атрибуты (масштабы, oversampling, частота АЦП).

| устройство hw-mcp | модель | где | зона |
|---|---|---|---|
| `kitchen_bme280` | BME280, драйвер `bmp280` | `sys/bus/iio/devices/iio:device0` | kitchen |
| `bathroom_dht11` | DHT11, драйвер `dht11` | `sys/bus/iio/devices/iio:device1` | bathroom |
| `bathroom_leak` | ADS1115 + датчик протечки, `ti-ads1015` | `sys/bus/iio/devices/iio:device2` | bathroom |
| `boiler_pipe_ds18b20` | DS18B20, `w1_therm` | `sys/bus/w1/devices/28-0316a2795cff` | boiler_pipe |
| `board_cpu_thermal` | SoC: hwmon + thermal | `sys/class/hwmon/hwmon0`, `thermal_zone0` | board |
| `pir_hall` | PIR HC-SR501, вход | GPIO линия 17 | — |
| `door_entry` | геркон двери, вход (1 — открыта) | GPIO линия 22 | — |
| `relay_fan` | реле вентилятора кухни, выход | GPIO линия 27 | kitchen |

Имена задаёт `configs/declared.sim.json` (места, `names` для АЦП, линии с меткой чипа `board-sim`,
пороги и шлюз — как в `hwmcp/configs/declared.lab.json`; у двери `debounce_ms: 30`). Места, линии и
пороги тестовые — это не выбранная периферия ВКР.

Атрибут меняется только целиком: временный файл рядом (`.<имя>.sysfsim`) и `rename(2)` — читатель видит
старое или новое значение, но не недописанное (проверено тестом с параллельным читателем). Пишется только
то, что изменилось после квантования, и не чаще периода обновления датчика.

## Модели датчиков

| датчик | что пишется (как драйвер) | разрешение, шум, период | источник |
|---|---|---|---|
| BME280 | ABI драйвера `bmp280` ядер ≥ 6.12: `in_temp_input` = 10·код (м°C), код 0,01 °C; `in_humidityrelative_input` = 1000·код/1024 (м%RH), код Q22.10; `in_pressure_input` = код/256000 (кПа), код Q24.8 Па; `*_raw` = код, `*_scale` 10 / 1000/1024 / 1/256000 | шум 0,004 °C, 0,02 %RH, 1,3 Па; период 1 с (допущение: чаще опроса hw-mcp не нужно); диапазоны −40…85 °C, 0…100 %RH, 300…1100 гПа | даташит Bosch BST-BME280-DS002-15 rev 1.6: табл. 4, 11, 12, 14 (oversampling ×2 / ×16 / ×16/×2 без IIR — умолчания драйвера); `bmp280-core.c` v6.12 и master (PROCESSED+RAW+SCALE, коэффициенты {10,1}, {1000,1024}, {1,256000}, IIO_VAL_FRACTIONAL); формат — `__iio_format_value` (9 знаков, отбрасывание). В v6.8 (ядро ВМ `sbc`), v6.10, v6.11 — только PROCESSED и oversampling: `in_temp_input` и `in_humidityrelative_input` целые (IIO_VAL_INT, влажность 1000·код/1024 с отбрасыванием), raw и scale нет; hw-mcp читает `*_input` в обоих случаях, разница < 0,001 %RH |
| DHT11 | `in_temp_input`, `in_humidityrelative_input` = целое × 1000 | шаг 1 °C и 1 %RH, диапазон 0…50 °C и 20…90 %RH (вне — насыщение, допущение); период 2 с; шум 0,2 °C и 0,5 %RH и `fail_rate` 0,05 — **допущение** (в даташите нет) | копии даташита Aosong/D-Robotics (диапазоны, ±2 °C, ±5 %RH, опрос не чаще 1–2 с); `dht11.c` v6.8: `DHT11_DATA_VALID_TIME` 2 с, только PROCESSED, сбой — `-EIO`/`-ETIMEDOUT` |
| DS18B20 | `temperature` = код·1000/16 м°C с отбрасыванием к нулю (как C), код 1/16 °C | 12 бит, 0,0625 °C; −55…+125 °C; обновление не чаще 0,75 с (t_CONV 750 мс); шум 0,02 °C — **допущение**; после сброса питания регистр = +85 °C | даташит DS18B20 (Dallas, табл. 2 и «Features»); `w1_therm.c` v6.8 (`w1_DS18B20_convert_temp`, 750 мс для 12 бит, при сбое `temperature` читается пустым); `w1_therm.rst` (85.00 — powerup value) |
| ADS1115 + протечка | `in_voltage0_raw` (знаковый 16 бит), `in_voltage0_scale` = 0.062500000 мВ, `in_voltage0_sampling_frequency` = 128 | PGA ±2,048 В (умолчание драйвера), насыщение кода; шум 62,5 мкВ СКО; период 1 с (допущение); датчик протечки: 0,05 В сухо, 1,6 В мокро, τ намокания 3 с, высыхания 600 с — **допущение** | TI SBAS444E (дек. 2024), табл. 6-1 (128 SPS, ±2,048 В); `ti-ads1015.c` v6.8 (`ADS1015_DEFAULT_PGA 2`, `DEFAULT_DATA_RATE 4`, масштаб FS/2¹⁵, IIO_VAL_FRACTIONAL_LOG2) |
| SoC | `thermal_zone0/temp` и `hwmon0/temp1_input`, м°C | шаг 0,5 °C, шум 0,1 °C, период 1 с; 45 °C в простое, +25 °C при полной загрузке, τ 60 с — **допущение** | — |
| PIR HC-SR501 | линия: 1 — движение | режим H (повторный запуск) — стимул продлевает импульс до стимул + `hold_s` (5 с); после спада блокировка `block_s` (2,5 с); вход в зону — стимул сразу, затем поток `rate_hz` 0,3/с; ложные `false_per_h` 0,5/ч — **допущение**; минута прогрева после питания не моделируется | описание модуля HC-SR501 (задержка 5–300 с, блокировка 2,5 с, H — по умолчанию) |
| геркон двери | линия: 1 — открыта | за фронтом `bounce_pulses` (2) возвратов в пределах `bounce_ms` (0,5 мс); число возвратов — **допущение** | даташиты Standex-Meder: ORD324 — дребезг ≤ 0,3 мс, KSK-GR501 — ≤ 0,5 мс |

hw-mcp читает `*_input`, если он есть, иначе `(raw + offset) × scale`; значение `round(·, 6)` в единицах
SenML. Показание в журнале истины считается так же (`read` модели), поэтому совпадает с hw-mcp точно.

## Физика

Тепловая модель зоны — первого порядка:
`dT/dt = (T_eq(t) + ΣΔT − T)/τ + f·(T_out(t) − T)/τ_fan`, `T_eq = base + k_out·(T_out − mean)`, где
`ΣΔT` — источники тепла сценария (`heat`, у платы — `load × load_rise_c`), `f` — вентилятор: **вход от
реле**, которое пишет hw-mcp (замкнутый контур). Влажность — парциальное давление пара `e`:
`de/dt = (e_base + Σe − e)/τ_rh + f·(e_out − e)/τ_fan`, `RH = 100·e/e_s(T)` (Магнус, коэффициенты
WMO-No. 8: 6,112; 17,62; 243,12): при нагреве без влаги RH падает. Улица: суточный ход температуры
(минимум в `coldest`), давление — медленное колебание. Интегрирование — точная экспонента на шаге 1 с при
входах на начало шага; до t = 0 — равновесие без источников.

Параметры по умолчанию — **допущения** о порядке величин (не измерены), переопределяются в сценарии:

| ключ зоны (`zones.<зона>`) | смысл | kitchen | bathroom | boiler_pipe | board |
|---|---|---|---|---|---|
| `base_c` | температура без источников, °C | 22 | 23 | 24 | 45 |
| `outdoor_k` | доля отклонения улицы от средней | 0,1 | 0,1 | 0 | 0 |
| `tau_s` | постоянная времени, с | 600 | 900 | 300 | 60 |
| `fan_tau_s` | обмен воздухом с улицей при включённом вентиляторе, с (0 — вентилятора нет) | 300 | 0 | 0 | 0 |
| `rh` | RH без источников при `base_c`, % | 45 | 50 | 40 | 40 |
| `rh_tau_s` | постоянная влажности, с | 900 | 600 | 900 | 900 |
| `load_rise_c` | прирост при полной загрузке CPU, °C | 0 | 0 | 0 | 25 |

Улица (`outdoor`): `mean_c` 8, `amplitude_c` 4, `coldest` «05:00», `rh` 80, `pressure_pa` 101325,
`pressure_amp_pa` 150, `pressure_period_s` 172800.

## Отказы

Задаются моментом `t` или частотой `rate_per_h` (пуассоновский поток по `seed`) и длительностью `duration_s`.

| вид | к чему | как эмулируется |
|---|---|---|
| `disconnect` | BME280, DHT11, DS18B20, ADS1115 | снимается ссылка шины (`sys/bus/…/devices/…`), у 1-Wire — `w1_master_slave_count` 1 → 0; при возвращении сначала пишется текущее показание, потом ссылка |
| `read_error` | датчики sysfs | атрибуты атомарно подменяются ссылкой на свой каталог: `open()` проходит, `read()` — `EISDIR` (обычный файл не умеет `EIO`); у DS18B20 — пустое чтение, как `temperature_show()` при сбое |
| `por85` | DS18B20 | показание 85,000 °C |
| `stuck` | датчики sysfs | значение, измеренное в момент начала, не меняется |
| `spike` (`amplitude`) | свойство датчика | прибавка к показанию |
| `drift` (`per_h`) | свойство датчика | прибавка `per_h × (t − t0)/3600` |
| `noise_burst` (`sigma`) | свойство датчика | шум `√(σ² + sigma²)` |
| `dht_fail_rate` (`p`) | DHT11 | доля сбоев обмена в окне (иначе — `fail_rate` устройства); сбой — как `read_error` на период |
| `bounce` (`ms` ≤ 100, `pulses` ≤ 50) | геркон | на фронтах в окне — `pulses` возвратов в пределах `ms`; возвраты, не успевшие до следующего фронта, отбрасываются парами |

Дребезг различим только потребителю фронтов: в бэкенде `files` пишется итоговый уровень, в `gpiosim`
каждый переход идёт в ядро. Ошибки чтения с 1-го чтения hw-mcp не видны: он держит прошлое значение и
сообщает `null` после 3 неудачных чтений подряд.

## Формат сценария

JSON `sysfsim/1`, проверяется при загрузке; ошибка указывает путь до поля
(`dense.json.events[3].zone: неизвестное значение 'kitchn'; допустимо: kitchen, bathroom, …`).

```json
{"format": "sysfsim/1", "name": "dense", "description": "…", "duration_s": 900, "start": "22:55",
 "outdoor": {"mean_c": 8},
 "zones": {"kitchen": {"tau_s": 600}},
 "devices": {"bathroom_dht11": {"fail_rate": 0.1}, "pir_hall": {"hold_s": 30}},
 "events": [{"t": 30, "kind": "heat", "zone": "kitchen", "rise_c": 25, "duration_s": 760, "note": "…"}],
 "faults": [{"t": 120, "kind": "por85", "device": "boiler_pipe_ds18b20", "duration_s": 30},
            {"rate_per_h": 20, "kind": "spike", "device": "kitchen_bme280", "property": "pressure",
             "amplitude": 300, "duration_s": 1}],
 "questions": [{"id": "q1", "t": 20, "text": "Какая температура на кухне?",
                "expect": {"device": "kitchen_bme280", "property": "temperature"}}],
 "situations": [{"id": "s_overheat", "kind": "overheat", "deadline_s": 120, "expect": "actuate",
                 "when": {"device": "kitchen_bme280", "property": "temperature", "ge": 35},
                 "action": {"device": "relay_fan", "property": "state", "value": true}}]}
```

- Обязательны `format`, `name`, `duration_s`, `start` (время суток в момент `t` = 0); `outdoor`, `zones`,
  `devices` переопределяют умолчания (ниже и в «Физике»), остальные разделы — списки.
- События: `heat` (`zone`, `rise_c`), `moisture` (`zone`, `rh_rise` — прирост RH при `base_c`), `load`
  (`level` 0…1, зона платы), `motion` (`device` PIR, необязательный `rate_hz`), `door` (геркон, дверь
  открыта `duration_s`), `leak` (АЦП протечки). Пересекающиеся источники складываются.
- Параметры устройств: `period_s` у датчиков (DS18B20 ≥ 0,75 с, DHT11 ≥ 1 с), `fail_rate` у DHT11,
  `hold_s`, `block_s`, `retrigger`, `rate_hz`, `false_per_h` у PIR, `bounce_ms` (0…100) и
  `bounce_pulses` (0…50) у геркона (пределы — допущение: дребезг герконов — доли миллисекунды),
  `v_dry`, `v_wet`, `tau_wet_s`, `tau_dry_s` у протечки.
- Ситуация — истина для метрик задержки реакции: `id`, `kind`, `deadline_s`, `expect` (`notify` или
  `actuate` с `action`) и момент начала: либо `t`, либо `when` — условие на **истинное** значение
  (`ge|gt|le|lt|eq`, `after`), проверяемое на каждом шаге физики; фактический момент пишется в журнал.
- Вопрос: `id`, `t`, `text`, `expect` (устройство и свойство); в журнал пишется истинный ответ на момент `t`.
- `note` — пояснение для человека, где угодно в событиях, отказах, вопросах, ситуациях.

Встроенные: **dense** — 15 минут с 22:55: духовка → перегрев кухни (≥ 35 °C в 471 с при выключенном
вентиляторе), дверь открыта 7 мин, движение после 23:00, душ, протечка, DS18B20 = 85 °C, исчезновение
DHT11, все виды отказов, 7 вопросов, 6 ситуаций. **day** — 8 ч с 08:00 с редкими событиями (душ, еда,
циклы котла, уход и возвращение, протечка, открытая дверь, перегрев к концу), случайные сбои, 8 вопросов.

Детерминизм: при одном сценарии, `seed` и входах (реле, нагрузка) содержимое атрибутов и линий в момент
`t` одинаково при любом шаге часов — датчик обновляется в моменты `k·period_s`, шум зависит от
(`seed`, устройство, свойство, `k`), промежуточные моменты при скачке часов просто пропускаются.

## Часы

- `real`: `t = speed × (монотонное время от старта)`. Цикл ждёт сигнала остановки (`select` на канале) до
  ближайшего срока (обновление датчика, фронт, событие, снимок истины), без опроса; реле читается после
  каждого пробуждения (не реже периода самого быстрого датчика) и действует с момента, когда замечено, —
  запаздывание до одного интервала ожидания.
- `virtual`: `POST /clock {"t": …}` отвечает `{"ok": true, "now": t}` после записи состояния на момент `t`;
  назад или за конец прогона — 409, плохое тело или `Content-Length` вне 0…65536 — 400, сбой шага мира
  (запись файла, линия GPIO) — 500 и выход с кодом 1; тело ошибки — `{"error": "…"}` (у 409 ещё `now`);
  `GET /healthz`. Реле, записанное hw-mcp в момент `t₀`, действует с `t₀` (читается при следующем `POST`,
  до шага). Файлы отражают момент последнего `POST`: шаг часов реплеера не должен быть больше периода
  опроса hw-mcp. Дойдя до конца, сервер завершается. Запросы обрабатываются по одному, сигнал остановки
  замечается между ними (`select` на сокете сервера и канале): клиент, оборвавший соединение, не
  останавливает прогон (строка в stderr), молчащий клиент задерживает остальных и остановку не дольше 10 с.
  Скачок часов не копит записи: у датчика — одно последнее обновление, у истины — один снимок.

## Журнал истины (JSONL)

Каждая строка: `type`, `t` (время сценария), `mono` (монотонные часы симулятора), ключи отсортированы.

| type | содержимое |
|---|---|
| `run_start` | `format` (`sysfsim-truth/1`), сценарий, его SHA-256, seed, длительность, часы, скорость, корень, GPIO (бэкенд, метка, чип), cgroup, pid |
| `value` | `device`, `property`, `value` (истина) и `reading` (что прочтёт hw-mcp; `null` — ошибка чтения) — при каждом изменении показания |
| `truth` | раз в 10 с (при скачке часов — только последний): температура и RH зон, улица, давление, напряжение протечки, нагрузка |
| `gpio` | `device`, `line`, `value`, `bounce`, `initial` — записанные переходы входов |
| `actuator` | `device`, `value` — состояние реле, прочитанное с линии; `t` — с какого момента оно действует (см. «Часы») |
| `load` | загрузка cgroup (с `--load-cgroup`) |
| `device` | `present` — исчезновение и возвращение устройства |
| `event`, `fault` | `phase` start/end, параметры, `until` |
| `question` | `id`, `text`, `expect`, `value` — истинный ответ |
| `situation` | `id`, `kind`, `deadline_s`, `expect`, `action`/`when` — с фактическим моментом начала |
| `run_end` | счётчики (`steps`, `writes`, `gpio`, `truth`), `cpu_s`, `max_rss_mib`, `wall_s` симулятора |

## GPIO: files и gpiosim

`files`: линия — файл `<root>/dev/<метка>/line<N>` (`gpio.Files` hw-mcp, `-gpio-driver files`/по
умолчанию при `-root` каталога); фронтов нет, hw-mcp опрашивает. `gpiosim` (Linux, root): устройство
configfs `sysfsim-<pid>` с банком `--gpio-label` и именованными линиями (`gpioinfo` показывает
`pir_hall`, `door_entry`, `relay_fan`); вход — запись `pull-up`/`pull-down` в
`/sys/devices/platform/gpio-sim.N/gpiochipM/sim_gpioK/pull`, ядро выдаёт настоящие события фронтов
(и подавляет дребезг по запросу потребителя); выход, выставленный потребителем, читается из
`sim_gpioK/value`. hw-mcp находит чип по метке (`"chip": "board-sim"`) или по имени из `--declared-out`.

Метку симулятор не проверяет на занятость: для этого пришлось бы читать чужие устройства configfs, а одно
зависшее устройство вешает такое чтение. Две одинаковые метки hw-mcp отвергает при поиске чипа («chip
label … is ambiguous»); параллельным прогонам нужны разные `--gpio-label`.

Порядок остановки: сначала потребители линий (hw-mcp, gpiomon, gpioset), затем симулятор. Снятие чипа
gpio-sim, линии которого заняты, на ядре 6.8 ВМ `sbc` портит ядро: «REMOVING GPIOCHIP WITH GPIOS STILL
REQUESTED», WARNING в `gpiod_free`, утечка потоков `irq/N-<потребитель>`, затем Oops и зависшие в
состоянии D процессы — их снимает только перезагрузка ВМ. Поэтому при выходе симулятор проверяет занятость
всех линий банка 0…27, а не только линий платы — запросить можно любую (`GPIO_V2_GET_LINEINFO_IOCTL`, флаг
`USED`), ждёт освобождения до 5 с и, если линии всё ещё заняты, чип не снимает: выходит с кодом 1 и
сообщением, какой потребитель их держит. Между последней проверкой и снятием чипа остаётся окно в одну
запись configfs (`live`): линию, запрошенную именно в нём, симулятор не заметит, поэтому проверка только
страхует, а порядок остановки обязателен. Если чип остался, устройство убирают вручную после остановки
потребителя (то же — после SIGKILL симулятора):

```bash
D=/sys/kernel/config/gpio-sim/sysfsim-<pid>
echo 0 | sudo tee $D/live && sudo rmdir $D/bank0/line* $D/bank0 $D
```

`vm_check.sh` (ВМ, root; запуск — в шапке скрипта) проверяет `gpiosim` независимыми инструментами uAPI
(`gpioinfo`, `gpiomon`, `gpioset` из libgpiod) и с hw-mcp (`-gpio-driver cdev`), затем журнал ядра и
`tainted`. На ядре, уже пережившем Oops (флаг D, 128, в `/proc/sys/kernel/tainted`), он не запускается и
выходит с кодом 2: упавшая задача могла оставить захваченным мьютекс ядра, и тогда любой запрос IRQ фронтов
висит в состоянии D до перезагрузки ВМ — так было после прогонов прежней версии. `gpiomon` считается
готовым, когда обе его линии заняты (`gpioinfo`) и процесс спит в ожидании событий (состояние S), не
позже 3 с. Процессы ждутся с пределом (10 с, hw-mcp — 30 с): не вышедший печатается с состоянием и стеком
ядра (`/proc/PID/stack`), скрипт пишет `FAIL`, а симулятор чип под ним не снимает.

## Ресурсы симулятора (ориентир, не результат)

ВМ `sbc` (4 vCPU, системный Python 3.12.3), `dense`, реальное время, 120 с, два экземпляра одновременно
(`files` и `gpiosim`), вне cgroup «платы»: CPU 0,34–0,35 с за 120 с (≈ 0,3 % одного vCPU вместе с
запуском интерпретатора), пиковый RSS 22,6 МиБ (`VmHWM` 23,3 МБ), ≈ 2 пробуждения в секунду,
≈ 7 записей файлов в секунду, журнал истины ≈ 4,5 строки/с (≈ 0,6 КБ/с; день 8 ч — порядка 17 МБ:
оценка по скорости `dense`, не замер).
Проигрывание `day` (8 ч) в памяти — ≈ 1,1 с CPU на Mac (≈ 40 мкс на секунду сценария). Числа сняты при
параллельной работе других агентов.

## Ограничения эмуляции (чем это не настоящий датчик)

- Чтение файла мгновенно: блокирующего чтения DS18B20 (~750 мс на `temperature`) и задержек I²C/1-Wire
  нет, шина и её занятость не моделируются. hw-mcp это не замечает, но время опроса на плате будет больше.
- Ошибка чтения — `EISDIR` вместо `EIO`/`ETIMEDOUT`; для hw-mcp это одинаково «нет значения», для
  других читателей — нет. Перечитывание атрибута не запускает новое измерение: значение обновляется по
  своему периоду, а кэш драйвера DHT11 (2 с) совпадает с периодом лишь по построению.
- Отключение — снятие ссылки шины; каталог устройства в `sys/devices` остаётся, uevent нет. На плате
  отключённый I²C-датчик обычно остаётся в sysfs и даёт ошибки чтения — это вид `read_error`.
- Нет точности и смещения калибровки (±0,5…2 °C по даташитам), гистерезиса и запаздывания влажности,
  самонагрева BME280, прогрева PIR, зависимости шума от температуры; шум гауссов и независим.
- Физика — одна ёмкость на зону, без теплообмена между зонами; параметры — допущения, не измерения.
- `gpio-sim`: фронты порождает запись в sysfs из Python — интервалы дребезга в реальном времени не
  точнее планировщика (десятки мкс), в виртуальных часах переходы между `POST` идут подряд; потребитель
  uAPI v1 (libgpiod 1.6) берёт тип фронта из уровня линии в потоке IRQ, и близкие импульсы у него
  сливаются. В бэкенде `files` фронтов нет вовсе. Электрика (уровни, подтяжки, ток реле) не моделируется.
- На ядре 6.8 чип gpio-sim нельзя снимать, пока его линии заняты (раздел «GPIO»); зависший чип вешает и
  любой поиск чипа по метке (hw-mcp, libgpiod по имени), так как тот открывает все `/dev/gpiochip*`.
- Камера и робот здесь не эмулируются.
