# Аналог PicoClaw v0.3.1 и кандидат nanobot 0.3.5

Каталог `bench/baselines/` — установка аналогов, их конфигурации, драйверы «рабочего дня» в **сжатом времени**,
сбор вызовов LLM / токенов / байт / памяти и честное описание паритета с EdgeCtx (THESIS_CONCEPT §12.7).
Ключевая метрика ВКР — экономность работы во времени (вызовы LLM, токены, ₽, трафик, память/CPU), поэтому
драйверы меряют прежде всего **что и сколько раз будит LLM** и **сколько это стоит в токенах**.

Все числа, полученные при разработке (в том числе смоук ниже), — **ориентиры, не результаты**: параллельно
работают другие процессы, LLM — оракул mock-llm, день короткий.

Текущие умолчания CLI: `k=15`, PicoClaw `--profile best`, ContextManager `legacy`; лишние файловые,
медиа-, bus- и subagent-инструменты выключены штатным конфигом. `exec` и `cron` оставлены для проверки
без LLM, `message` — для уведомлений. Старые замеры ниже при k=60 и seahorse относятся к прежнему
конфигу и не характеризуют новый best. nanobot пока кандидат, его включение в итоговое сравнение не решено.

## 0. Коротко

```bash
bench/baselines/install_picoclaw.sh --src        # PicoClaw v0.3.1: Mac + linux-arm64, SHA-256, MIT, исходники тега
bench/baselines/install_nanobot.sh               # nanobot 0.3.5 в .venv-nanobot (uv, Python 3.12, lock)
bench/baselines/install_nanobot.sh --vm sbc      # то же в Lima VM sbc: ~/.venv-nanobot
bench/baselines/smoke.sh                         # смоук: 2 ч дня при k = 60 → 2 мин на прогон, Mac и sbc

PY=.venv/bin/python
$PY -m bench.baselines.drive_picoclaw --day DAY.jsonl --k 15 --profile best            # B1-best (по умолчанию)
$PY -m bench.baselines.drive_picoclaw --day DAY.jsonl --k 15 --profile shipped         # B1-shipped
$PY -m bench.baselines.drive_nanobot  --day DAY.jsonl --k 15                           # кандидат B2
$PY -m bench.baselines.drive_edgectx  --day DAY.jsonl --k 15                           # EdgeCtx в том же режиме
#   --host sbc — аналог в Lima VM «sbc» (сервисы стенда остаются на Mac); --push signals|all|none; см. -h
$PY -m bench.baselines.report bench/baselines/smoke/20261007                           # сводная таблица
$PY -m pytest -q bench/baselines/tests                         # 53 теста (2 медленных — с BASELINES_SLOW=1)
```

Результат прогона — `<out>/<run_id>/`: `summary.md`/`summary.json` (вызовы LLM, токены, байты по источникам,
RSS, ответы на реплики, оценка sim-mcp), `manifest.json` (версии, SHA, конфиги, план сжатия и его отклонения),
сырьё (журналы llmtap, mock-llm, sim-mcp, hw-mcp, проигрывателя, памяти/CPU, логи агента).

## 3. Как до аналогов доходят реплики и события (по коду тегов)

**Реплики пользователя — штатный канал без человека:**
* PicoClaw — MQTT-канал (`pkg/channels/mqtt`): публикация `{"text": …}` в `/picoclaw/edge/user/request`, ответ —
  `/picoclaw/edge/user/response`. `client_id` в теме = сессия (своя история). Альтернативы хуже: `picoclaw
  agent -m` — новый процесс на реплику без heartbeat/cron; канал `pico` (WebSocket) требует токен и отдаёт поток.
* nanobot — WebSocket-канал (`channels/websocket`, тот же, что у WebUI): соединение `?client_id=user&token=…`,
  кадр `{"content": …}`, ответ — кадры `message` до `turn_end`. Одно соединение на весь день = одна сессия.
  `nanobot serve` (OpenAI-совместимый API) не запускает heartbeat/cron/triggers — для «работы во времени» не годится.

**События датчиков.** MCP-клиенты обоих аналогов берут у сервера только **инструменты**:
* PicoClaw: `mcp.NewClient(…, nil)` без обработчиков уведомлений; для `type: http` отключён standalone SSE —
  `notifications/resources/updated` до агента не доходят, ресурсы не читаются (`pkg/mcp/manager.go`).
* nanobot: инструменты + ресурсы и промпты **как инструменты** (`mcp_<srv>_resource_<имя>`: sim-mcp даёт
  7 инструментов + 26 ресурсов, hw-mcp 5 + 11), подписок нет (`agent/tools/mcp.py`). В каталоге запроса nanobot
  поэтому 70 инструментов против 27 у PicoClaw и 12 у EdgeCtx (sim) — это свойство системы, оно и меряется.

Поэтому события подаются двумя режимами из одного потока дня (§12.7):
* **опрос** (`--push none`) — только heartbeat с одинаковой задачей наблюдения;
* **пуш** (`--push signals`, по умолчанию для best/B2): PicoClaw — MQTT-клиент `sensors` (своя сессия);
  nanobot — **local triggers**: во втором WebSocket-соединении `/trigger sensors` создаёт триггер, события
  ставятся в очередь `LocalTriggerStore.enqueue` — ровно то, что делает CLI `nanobot trigger <id> "…"`
  (`--trigger-via cli` запускает сам CLI на каждое событие); шлюз опрашивает очередь раз в 0,5 с.
  Что пушить, решает внешний «мост» (`pushfilter.py`): те же предикаты, что у сигналов гейта EdgeCtx
  (`bench/simmcp/edgectx_simday.yaml`: change / threshold с гистерезисом / delta / конец эпизода / ignore),
  **без** debounce, cooldown, коалесценции и правил — это механизмы EdgeCtx, их вклад и сравнивается.
  `--push all` — каждое событие (граница B0-events). Текст события одинаков для обеих систем.

**Heartbeat:**
* PicoClaw (`pkg/heartbeat`): `heartbeat.interval` — целые минуты, минимум 5; первый тик через 1 с после старта;
  промпт «# Heartbeat Check … respond ONLY with: HEARTBEAT_OK» + задачи из HEARTBEAT.md; сессия `heartbeat` без
  истории; HEARTBEAT_OK подавляется, иное уходит в последний канал. Пустой HEARTBEAT.md ничего не стоит.
* nanobot (`cli/gateway_runtime.py`): системная задача cron каждые `gateway.heartbeat.intervalS` с; идёт,
  только если в HEARTBEAT.md есть «## Active Tasks» и уже есть сессия канала (не cli) — до первой реплики
  heartbeat пропускается; сессия `heartbeat` **с историей**; непустой ответ проверяет второй вызов LLM —
  оценщик «уведомлять ли» (`utils/evaluator.py`, инструмент evaluate_notification).
* Задача наблюдения одинакова у всех: «Плановая проверка помещения: оцени состояние устройств и недавние события.
  Если нужно действие или уведомление пользователя — выполни его.» (как `heartbeat_task` EdgeCtx в T0).

**Cron:** PicoClaw — `workspace/cron/jobs.json`, `every` в мс; задача-сообщение = ход агента в новой сессии,
задача `command` = команда через инструмент exec **без LLM**, вывод публикуется в канал (`pkg/tools/cron.go`).
CLI `picoclaw cron add` команд не умеет — драйвер пишет хранилище в штатном формате до старта.
nanobot — свои задачи cron создаёт LLM из чата; в прогонах не используются (кроме системных heartbeat и Dream).

## 4. Профили («как поставляется» и «лучшие штатные»)

Общее для всех профилей: конфиг = результат штатного `onboard` (умолчания версии) + модель (OpenAI-совместимый
`base_url` → llmtap → mock-llm, ключ-заглушка), канал, MCP-серверы; выключено лишнее (веб-поиск/веб-загрузка,
у PicoClaw ещё реестры навыков). Навыки рабочей области, файлы памяти, системные промпты — штатные.

| Профиль | Что включено | Зачем |
|---|---|---|
| **B1-shipped** (`drive_picoclaw --profile shipped`) | heartbeat 30 мин с задачей; пуша нет | проверка «как поставляется» |
| **B1-best** (`--profile best`, по умолчанию) | shipped + пуш событий в MQTT + cron `command` (проверка помещения `check_room.sh` каждые 5 мин суток, без LLM, вывод — MQTT-клиент `alerts`; требует штатного `tools.exec.allow_remote`) + legacy как ContextManager, лишние инструменты выключены | экономная штатная настройка для сценария датчиков |
| **кандидат B2** (`drive_nanobot`) | штатно: heartbeat 30 мин, Dream каждые 2 ч, idle-компакция 15 мин, пуш через local triggers; `ssrfWhitelist` 127/8 (и 192.168.5/24 в ВМ) — иначе SSRF-фильтр nanobot блокирует MCP по локальному адресу | требует отдельного решения о включении |
| EdgeCtx (`drive_edgectx`) | конфиг T0 `bench/simmcp/edgectx_simday.yaml`, все периоды /k, clock: real | паритет режима времени |

**Tool Discovery PicoClaw-best в T0 выключен** (`--discovery` включает): скрытые инструменты MCP вызываемы
только после поиска (TTL > 0, `pkg/tools/registry.go`), а оракул mock-llm вызывает лишь инструменты из
списка запроса — с Discovery все действия оракула отклонялись бы. Эффект Discovery (короче каталог + поисковый
вызов на «разблокировку») оценивается отдельно или на живой модели (E0-Q/T2).

## 5. Сжатие времени дня в k раз (`timecomp.py`)

У аналогов нет виртуальных часов, все таймеры — стенные. День проигрывается в реальном времени, сжатом в k раз:
событие дня с моментом t подаётся в `wall0 + (t − t0)/k` (16 ч при k = 60 → 16 мин; смоук 2 ч → 2 мин).
Все периоды, выраженные в стенном времени, делятся на k в пределах того, что допускает конфиг:

| Параметр | Сутки | k = 60 (конфиг) | Точно при | Если не делится |
|---|---|---|---|---|
| PicoClaw heartbeat | 30 мин | эмуляция: задача cron every = 30 с с промптом heartbeat | k ∈ {1, 2, 3, 5, 6} штатно (целые мин ≥ 5) | `--hb-mode cron`: новая сессия на тик, нет строки «Current time», HEARTBEAT_OK уходит в канал `hb` |
| PicoClaw cron command | 5 мин | every = 5 с | любое (целые с) | — |
| nanobot heartbeat | 30 мин | intervalS = 30 | любое (целые с) | — |
| nanobot Dream | 2 ч | `dream.cron = "*/2 * * * *"` | k ∈ {1, 2} (intervalH) или «*/m», где m делит 60 | ближайшая частота, отклонение в manifest |
| nanobot idle-компакция | 15 мин | 1 мин (= 60 мин суток) | k ∈ {1, 3, 5, 15} | **отклонение**: целые минуты, 0 выключил бы компакцию |
| nanobot idle-проверка | 60 с | 1 с | любое | — |
| nanobot лимит сообщений/мин | 6 | 360 (×k) | — | лимит на стенную минуту иначе ужесточился бы в k раз |
| nanobot опрос local triggers | — | 0,5 с стенных = 30 с суток задержки | не настраивается | отклонение |
| mock-llm TTL кэша | 300 с | `--cache-ttl 5 --clock wall` | любое | — |
| mock-llm задержка | `--latency` суток | делится на k (медиана lognormal) | — | по умолчанию 0 |
| sim-mcp | часы дня | двигает проигрыватель (`/control/clock`) | — | таймеры устройств — в шкале дня |
| hw-mcp | опрос 1 с | не сжимается (реальное железо) | — | фикстура статична |

Точно для всех периодов одновременно: PicoClaw — k ∈ {1, 2, 3, 5, 6}; nanobot — только k = 1 (Dream и
idle-компакция); при k = 60 неточности nanobot — idle-компакция (реже в 4 раза) и задержка опроса триггеров.
Каждая неточность пишется в `manifest.deviations` и в `summary.md`.

**Какие метрики при сжатии корректны** (`timecomp.METRIC_VALIDITY`):

| Метрика | Годится | Почему |
|---|---|---|
| вызовы LLM за день, по источникам | да | счётная; периоды /k, события — в те же моменты дня |
| входные/выходные токены | да | зависят от содержимого, оракул детерминирован |
| кэш-токены | да, при TTL/k | погрешность — время обработки, растянутое в k раз в шкале дня |
| байты LLM / MCP / канала | да | keep-alive MQTT/WebSocket по стенным часам даёт в k раз меньше служебного трафика |
| число heartbeat/Dream/cron | да, если период точный | иначе — фактический период из manifest |
| RSS/PSS: уровень и пик | ориентир | рост от числа событий сохраняется, рост/сборка по стенным часам — сжаты |
| наклон памяти, CPU-с/сутки, пробуждения/с, энергия | **нет** | фоновые затраты сжаты в k раз, затраты на событие — нет |
| задержки «реплика → ответ», «событие → действие» | **нет** (в шкале дня) | 50 мс обработки = 3 с суток при k = 60; стенные RTT пишутся как справка |
| качество живой модели | **нет** | в промптах аналогов стенное время, а не время дня — только T2 |

Ещё одно следствие: пользователь ждёт ответа, поэтому реплики идут строго по одной; если ход длиннее паузы
между репликами (в смоуке паузы бывают 4 с суток = 67 мс стенных), следующая подаётся с опозданием (`lag_day_s`
в журнале), а часы sim-mcp удерживаются перед неотправленной репликой (иначе sim-mcp открыл бы её окно по часам
и приписал бы ей вызовы текущего хода).

**Паритет с EdgeCtx.** Основной режим EdgeCtx — виртуальные часы T0 (`bench/replay`): точнее и в сотни раз быстрее.
Сравнивать T0-EdgeCtx с аналогами в сжатом времени можно только по счётным метрикам (таблица выше). Для сравнения
«один в один» тот же проигрыватель гоняет EdgeCtx в сжатом реальном времени: `drive_edgectx.py` —
`timecomp.edgectx_compressed_config()` ставит `clock: real` и делит на k `heartbeat_min`, `snapshot_period_s`,
`profile_consolidate_s`, гейт (`debounce_s`, `cooldown_s`, `coalesce_s`, `self_echo_s`) и `gap_s`/`debounce_s`/
`cooldown_s` сигналов (все — float, деление точное); события идут уведомлениями sim-mcp по подписке, реплики —
`POST /v1/user`, класс вызова llmtap берёт из `X-Edgectx-Wake-Reason`/`Purpose`. Не масштабируются `for_s` правил,
созданных LLM, и TTL решений шлюза hw-mcp; время в промпте — стенное. **Рекомендация для agent/**: режим часов
`clock: scaled` (реальные часы с темпом k: `Now = epoch + start_t + k·(wall − wall0)`, таймеры `AfterFunc(d/k)`)
сделал бы паритет точным, включая время в промпте и `ts_clock`, без правки конфигов.

## 6. Оракул и честность сравнения

LLM — `bench/mockllm` в режиме oracle (свой экземпляр на каждый прогон): «идеальная модель» по разметке дня;
токены — o200k по Cookbook, кэш — эмуляция префикса. Чтобы оракул был одинаково идеален для разных систем:

* **«Ничего не делать» — по протоколу системы** (`--noop-text`): PicoClaw — `HEARTBEAT_OK` (так heartbeat
  подавляется штатно), nanobot — `All clear.` (преамбула heartbeat nanobot), EdgeCtx — пустой ответ (как в T0).
* **Подсказки X-Bench-Wake/Purpose** от llmtap (классы — по маркерам из исходников тегов, проверяются тестами
  «дрейфа маркеров»): `user` → wake=user (сопоставление реплики по тексту), `heartbeat`/`event` → фон
  (ситуация или ничего), внутренние вызовы (сводки seahorse, компакция и Dream nanobot) → purpose=summary
  (оракул отвечает сводкой фиксированной длины и **не трогает ожидания** — иначе компакция могла бы «съесть»
  реакцию на ситуацию), оценщик heartbeat nanobot → фон (короткий ответ без вызова — nanobot не уведомляет).
* **Длина сводки «как просили»**: seahorse PicoClaw задаёт цель («Target length: about N tokens») и при превышении
  повторяет запрос «агрессивно»; фиксированные 400 токенов оракула давали лишний вызов на каждую сводку (смоук:
  18 внутренних вызовов вместо 9). llmtap укорачивает ответ до цели (o200k и 2,25·N символов под оценщик PicoClaw
  2,5 символа/токен) и правит `usage` — `usage_adjusted` в журнале, `--no-fit-summary` выключает.
* **SSE**: nanobot всегда зовёт провайдера потоком; llmtap отдаёт ответ mock-llm как chat.completion.chunk + usage.
* **Артефакт оракула, не исправляемый на стенде**: после действия по ситуации оракул завершает ход пустым текстом;
  nanobot на пустой финал делает ещё один вызов без инструментов («Please provide your response…», класс того же
  хода), PicoClaw пишет «The model returned an empty response». Живая модель обычно что-то говорит — в T0 у nanobot
  это +1 вызов на ситуацию.
* Число вызовов на вход добирается оракулом до `k` разметки daygen (VisionClaw), одинаково для всех систем.

## 9. Ограничения паритета (что сравнение НЕ показывает)

1. LLM — оракул: качество, длина ответов, решения «уведомлять ли», использование навыков и памяти живой модели не
   моделируются; Dream nanobot получает сводку без правок файлов памяти; Tool Discovery PicoClaw не проверяется.
2. Сжатие времени портит временные метрики (CPU-с/сутки, задержки, наклон памяти) — они только из T2 (реальное время).
3. Неточные периоды при k = 60: эмуляция heartbeat PicoClaw задачей cron; idle-компакция nanobot 60 мин вместо 15;
   опрос триггеров nanobot до 30 с суток. Точнее — k ∈ {1, 2, 3, 5, 6} для PicoClaw (штатный heartbeat).
4. Пуш через внешний мост: что считать значимым, решает фильтр с предикатами гейта EdgeCtx (без его debounce,
   cooldown, коалесценции, правил) — это выбор протокола, а не свойство аналогов; `--push all|none` — границы.
5. Память на Mac — RSS по psutil (macOS, другой аллокатор и страницы 16 КиБ), в ВМ — RSS/PSS по smaps_rollup
   (страницы 4 КиБ). В дерево агента входит hw-mcp (stdio-потомок); sim-mcp и сервисы стенда — нет.
6. MQTT-брокер и сервисы стенда — на Mac (как брокер в LAN), их ресурсы не считаются; трафик агента до них —
   в журнале llmtap (LLM) и счётчиках клиента MQTT, сетевые счётчики netns (§12.3) — дело T2.
7. Время в промптах аналогов — стенное; на ответы оракула не влияет, на токены — на единицы.
8. nanobot в ВМ: Python 3.12.3 (системный, база venv), на Mac 3.12.15 (uv); версии пакетов одинаковые.
