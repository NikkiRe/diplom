# Робот NeuroChip «жест → движение»: анализ текущего состояния

Срез: 14.10.2026. Объект — код лаборатории NeuroChip (ИТМО) из присланных архивов:
- `third_party/neurochip/demo/demo-ros2_feature/` — «демо». Главный файл `src/camera/predict_live.py`, 708 строк; ссылки вида `:615` — номера его строк.
- `third_party/neurochip/ros_mcp_server/ros_mcp_server-master/ros_mcp_server.py` — «MCP лаборатории», 704 строки; ссылки вида `mcp:442`.
- PicoClaw v0.3.1 — `bench/baselines/vendor/`; ссылки вида `pc:pkg/…`.

Подробности, замеры и все источники — в `docs/neurobot/research/R1…R6`; здесь сводка. Решения — в `PLAN.md`.

Пометки:
- [код] — проверено по исходнику;
- [опыт] — воспроизведено настоящим PicoClaw v0.3.1 на заглушке LLM, 3 повтора с одинаковым итогом (R3);
- [замер] — наш замер на Mac на синтетике или реплике логики; ориентир, а не результат;

- [гипотеза] — проверить на роботе.

Код лаборатории не запускали и не меняли. Веса разобраны только статически.

## 0. Главное

1. **Рефлекс «жест → движение» в демо уже работает без LLM.** `predict_live.py` сам публикует `/cmd_vel`, PicoClaw в этот контур не входит [код]. Значит, задача не «ускорить LLM», а сделать быстрым и надёжным локальный контур и правильно подключить агента сверху.
2. **«После пары использований надо перезагружать» — несколько независимых механизмов, все подтверждены кодом:**
   - в демо поток камеры молча умирает от первого исключения (например, таймаута кадра RealSense), а процесс остаётся живым и «глухим»;
   - в агентской части PicoClaw не поднимает упавший stdio MCP-сервер, одна строка в stdout рвёт соединение навсегда, `/reload` убивает stdio-серверы, у вызова инструмента нет таймаута;
   - инструменты камеры и лидара в MCP лаборатории не работают никогда.

   Слово «говорит, надо перезагружать» указывает скорее на агентскую часть: так отвечает LLM, получив `connection closed`. Без журналов это **гипотеза** (§3).
3. **Задержку задаёт конструкция.** Жест считается законченным только через 1,5 с без руки в кадре, поэтому от конца жеста до команды проходит ≈1,6–1,8 с [оценка]. Сама SNN с предобработкой стоит ≈0,6–0,8 мс [замер, numpy]. После команды робот 3–11 с «глух» к жестам.
4. **Распознавание часто ошибается из-за предобработки.** Холст 28×28 в 3–25 раз бледнее MNIST. SNN не выдаёт спайков, а argmax от нулей даёт класс 0, то есть разворот на 7 с. «Немых» ответов 7–88 % [замер на синтетике, ориентир].
5. **Безопасность держится на неизвестной прошивке STM32.** При препятствии и при выходе демо не посылает ноль, а просто замолкает. Gazebo DiffDrive в таком случае держит последнюю скорость [код + замер стенда]. Вопрос №1 к лаборатории.
6. **Через PicoClaw реального времени не будет по построению.** MCP-событий он не принимает. Каждое событие — это ход LLM: 2 вызова, ≈3,1–3,6 тыс. входных токенов на вызов, ≈3–6 с до движения [оценка]. MCP лаборатории двигает робота толчками ≤ 0,044 м: «0,5 м» — это 13–17 вызовов LLM [оракул, ориентир].

## 1. Как устроено сейчас

```
           Jetson Nano, Ubuntu 20.04, ROS 2 Foxy, Python 3.8 (по README; на роботе не проверено)
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ python3 predict_live.py — ОДИН процесс, узел "velocity_publisher"                           │
│  главный поток: rclpy.spin (:699)                                                           │
│     ├ таймер 0,1 с → /cmd_vel Twist (:370–372, :473–486): в покое нули; при препятствии —     │
│     │   НИЧЕГО                                                                               │
│     └ /scan → лучи 166–515, порог 0,25 м (:459–467)                                          │
│  поток-демон «зрение» (:595–597, :602–668), без try/except:                                  │
│     D435i 640×480@30 (pyrealsense2) → wait_for_frames (:615) → YOLOv5s «hand» (torch.hub,    │
│     size 320, max_det 1) → боксы копятся, пока робот стоит → 1,5 с без руки и ≥6 боксов       │
│     (:610, :636) → квадраты 10 % бокса (:640) → 28×28 → Бернулли 25 шагов (:212)             │
│     → SNN 784-128-4 → argmax (:276) → класс 0..3 → Queue(3) (:647–656)                       │
│     → полноэкранное окно OpenCV на каждом кадре (:662–666)                                   │
│  поток-демон «контроллер» (:494–512): манёвр = x/th + time.sleep 3–11 с                      │
│     0→turn180 7 с, 1→come 3 с, 2→go_left/right 8 с, 3→think 11 с                             │
│        │ /cmd_vel                                                                            │
│        ▼                                                                                     │
│ мост /cmd_vel→UART (не в архиве) → STM32F103 + L298N;  URG-04LX → /scan                       │
│ rosbridge :9090 ◄── НОВОЕ WS-соединение на каждое сообщение (mcp:161–193) ── ros_mcp_server  │
│   (FastMCP, только stdio mcp:700, Python ≥3.10) ◄─stdio─ PicoClaw (версия, машина, канал —    │
│   неизвестны) ⇄ LLM                                                                          │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

Следствия:
- в `/cmd_vel` пишут два контура (жесты демо и толчки агента), арбитража нет;
- камерой владеет демо;
- неизвестно, где и каким Python запущен MCP-сервер: под Python 3.8 он не импортируется (M13).

Что сделано хорошо и стоит сохранить:
- рефлекс локальный;
- у MCP лаборатории белый список тем, пределы скорости и длительности на стороне сервера, обязательный автостоп;
- каталог инструментов маленький — 127 токенов [замер].

## 3. «Надо перезагружать»: как отличить причину по журналам

Порядок строк — наша оценка, то есть [гипотеза].

| Симптом | Что посмотреть | Вероятная причина |
|---|---|---|
| Агент отвечает «ошибка / недоступен / перезапустите» | журнал PicoClaw: `connection closed`, `EOF`, `invalid trailing data`, `Config reload triggered`; `ps` — жив ли ros_mcp_server.py; `dmesg \| grep -i oom` | PC1–PC3; при «посмотри / что впереди» — M1 |
| Агент молчит во всех чатах | `Tool execution started` без `completed`; `All MCP servers failed` | PC4, PC5, PC10 |
| Окно застыло, процесс жив, на жесты не реагирует | консоль демо: `Exception in thread`, `Frame didn't arrive within 5000` | R1, затем G4 |
| После перезапуска камера не находится или старт висит | dmesg (USB), 100 % CPU на старте | R2, R3 |
| Разворот вместо команды | `Predicted label: 0` на непохожих жестах | G1, G2 |
| «Сначала работало, потом хуже» | tegrastats, FPS | R9 → G1 |
| Дёргается при командах агента | демо и толчки запущены вместе | S4 |

## 4. Что подтверждено, что нет

- **Кодом:** R1, R3–R8, L1–L6, G1–G5, S1–S4, M1–M3, M5–M10, M13, M14, PC1–PC9.
- **Опытом** с PicoClaw v0.3.1: PC1–PC5 и PC7. Самовосстановление по HTTP тоже подтверждено: перезапуск сервера, вызов при лежащем сервере, зависание + сторож.
- **Замер-ориентир:** G1–G3 (синтетика, numpy-порт), M3 (реплика логики), M7–M8 (токены, оракул).
- **Гипотезы:** R2, R9, M4, M11, PC8, S5; какая причина из §3 действует у лаборатории; все задержки на Jetson (цикл YOLO 60–110 мс, итог 1,6–1,8 с); поведение STM32 при тишине `/cmd_vel`.
- **Поправка к R5 и R2.** Там сказано, что twist_mux по таймауту выдаёт ноль; это взято из комментария в yaml. По коду foxy-devel `VelocityTopicHandle::callback` только пересылает пришедшее сообщение через `publishTwist`, `LockTopicHandle::callback` только запоминает состояние, единственный таймер — диагностический. twist_mux допустим только вместе с отдельным deadman-узлом после него.

## 5. Что спросить у лаборатории (по приоритету; первые три блокируют выпуск в непрерывный режим)

1. **STM32 и мост `/cmd_vel`→UART:** какой узел и тип; останавливается ли робот сам при тишине `/cmd_vel` и через сколько мс; единицы `linear.x`/`angular.z`; реальные скорость и тормозной путь при 0,5 и 1,0.
2. **Как выглядит «надо перезагружать»:** кто это говорит (PicoClaw/LLM или демо), дословный текст, через сколько жестов или минут, что перезапускают. Журналы PicoClaw, консоль демо, dmesg, tegrastats.
3. **Версии и размещение:**
   - модель Nano (4 или 2 ГБ), образ, JetPack/L4T, `python -V`, `pip freeze`, `dpkg -l | grep ros-foxy`, версия rosbridge;
   - версия PicoClaw и config.json без ключей (транспорт MCP, канал, Telegram через прокси?, hot_reload);
   - где и каким Python запущены PicoClaw и ros_mcp_server;
   - **актуальная версия ros_mcp_server.**
4. **Жесты:** какие 4 класса и как их рисовать; скрипт и данные обучения, точность; нужен ли жест «стоп»; 5–10 записей каждого класса (rosbag или видео) и дампы `spikes_out`.
5. **Датчики:** есть ли `/odom` и `/imu`; параметры `/scan` без массивов и QoS; порог 0,25 или 0,35 м.
6. **Условия:** фактический FPS, дистанция, освещение, вентилятор, nvpmodel, питание; нужно ли окно с видео.
7. **Требования:** допустимая задержка «жест → движение» и жестов в минуту; нужна ли LLM на каждый жест; можно ли менять демо (публиковать класс жеста, не писать `/cmd_vel`).
8. **Железо:** есть ли Orin Nano или Raspberry Pi 5 («железка не важна»)? Уход с EOL-стека Foxy/JetPack 4 снимает Python 3.8, rosbridge 1.3.1 и сборку TensorRT на старом JetPack.

## 5.1. Первые ответы (14.10.2026, со слов студента)

- Остановится ли робот при тишине `/cmd_vel` и какой узел пишет в STM32 — неизвестно. Работаем от худшего случая: робот держит последнюю команду.
- «Надо перезагружать»: перезагружают вручную, примерно после 3–4 жестов. Кто сообщает и что именно перезапускают — неизвестно.
- Актуальная версия ros_mcp_server и порядок запуска — ответа пока нет.
- Классы жестов: «вроде понимает нарисованные цифры, и помахать тоже». Это согласуется с гипотезой, что 4 выхода SNN — цифры 0–3 из EMNIST balanced (метаданные весов: emnist balanced). Зондирование весов (R1 §7) даёт: 0 — круг, 1 — угловатое, 2 — горизонтальный штрих, 3 — вертикаль. Окончательное соответствие «форма → класс» снимаем на стенде самой сетью: прогоняем траектории цифр 0–3 и махания через настоящие веса.

Что даёт «3–4 жеста» для приоритета гипотез. Это [гипотеза], проверяем на стенде и простыми опытами у лаборатории:
1. **Камера отваливается под нагрузкой моторов.** После каждого жеста едут моторы. Просадка питания или помеха по USB роняет D435i: «Frame didn't arrive within 5000» → R1, поток зрения умирает. Часто помогает только переподключение или перезагрузка — отсюда «вручную». Это согласуется с R9: питание Nano 5 В/4 А, общая батарея с моторами. Проверка у лаборатории: запустить демо из терминала, держать `dmesg -w` и сделать 5 жестов; при остановке сфотографировать терминал и dmesg.
2. **Агентский путь.** Каждая команда агента через ros_mcp_server даёт ≈10 новых WS-соединений к rosbridge и advertise/unadvertise `/cmd_vel` (M3). rosbridge 1.3.1 на Foxy деградирует при такой частой пересборке соединений (R5 §2, #774). 3–4 команды — это 30–40 циклов. Проверка на стенде — rosbridge Foxy 1.3.1 в контейнере.
3. PicoClaw: stdio-сервер, stdout, `/reload` (PC1–PC3) — если сбой сообщает агент.

Наш пакет 1 закрывает все три механизма, не дожидаясь ответов:
- лесенка восстановления камеры внутри процесса, вплоть до сброса USB-порта;
- MCP по HTTP с одним постоянным соединением;
- супервизия.

Ответы лаборатории нужны для порядка проверки на роботе и для таймаута STM32.

## 5.2. Новые материалы лаборатории (14.10, вечер): что изменилось

Подробности — `research/R7_robotic_platform.md` (стек MCP, конфиг и журналы PicoClaw с робота) и `research/R7_robot_slides.md` (презентация «Робот-сканер»). Здесь главное.

1. **Цепочка движения на роботе другая** [журнал PicoClaw с выводом `ros2 node/topic list`, 02.06; слайд 5]: `/cmd_vel` → `twist_mux` (входы `/cmd_vel`, `/cmd_vel_joy`, `/cmd_vel_tracker`) → `/diff_cont/cmd_vel_unstamped` → `diff_drive_controller` (ros2_control) → STM32.
   - У `diff_drive_controller` в Foxy `cmd_vel_timeout` по умолчанию 0,5 с. Значит, при тишине `/cmd_vel` робот, **вероятно**, тормозит примерно через 0,5 с, если параметр не меняли. Это частичный ответ на вопрос №1 (N13). Снять параметры с робота всё равно нужно.
   - На стенде основной режим `stm32_sim` — таймаут 500 мс («вероятный реальный»), hold — худший случай.
   - Любой издатель `/cmd_vel_tracker` или `/cmd_vel_joy` перекрывает наш явный ноль по приоритету. Предстартовая проверка: таких издателей нет. Источники скорости — геймпад и RViz на ПК (RS11).
2. **Лидар, вероятно, не видит прямо по курсу и справа спереди** (RS3; крит.; гипотеза сильная). D435i стоит перед URG почти в плоскости скана. В скане с робота сплошной блок NaN из 186 лучей от −60,8° до +4,2°, и его ширина совпадает с корпусом камеры. Демо отбрасывает NaN молча, поэтому около 53 % сектора остановки не видно. Проверка у лаборатории — минута с листом картона. Наш страж обязан считать NaN/«нет данных» в секторе остановки запретом движения вперёд.
3. **Лидар на высоте около 0,67 м не видит низких препятствий** (RS1). Порог 0,25 м отсчитывается от оси лидара, а край базы — на 0,21 м: запас около 4 см при выбеге 0,16–0,23 м на 0,5 м/с (RS2). Наезд вероятен. Порог считать от края корпуса, скорость ограничить.
4. **Агентский стек сейчас другой** (R7a):
   - PicoClaw 0.2.8, а не 0.3.1;
   - LLM — gpt-4o-mini через cloud.ru, каналы VK и pico;
   - единственный MCP — `robot_vision_demo_mcp` (stdio-прокси к воркеру :8766). Кода воркера в архиве нет, и ничего его не запускает: 29.09 все вызовы получали «Connection refused».
5. **Дубли инструментов движения** (N1, подтверждено опытом с mcp 1.30 и по исходникам 1.2–1.27.2). FastMCP оставляет ПЕРВУЮ регистрацию, поэтому миллисекунды уходят в воркер как `duration_s` (2000 или 300). Опасно; исправление — в пакете 1.

   - Между перезапусками ros_mcp_server выдерживал медиану 2 вызова; в 85 % жизней — не больше 4. Это совпадает с «после 3–4».
