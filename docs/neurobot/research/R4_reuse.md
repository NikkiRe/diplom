# R4 — что из нашего проекта переиспользовать для робота NeuroChip

Сценарий: робот с камерой распознаёт жест, робот едет, агент работает поверх этого.
Срез на 14.10.2026. Код лаборатории (`third_party/neurochip/…`) только читали. Веса `*.pt`/`*.pth` не загружали:
посмотрели только список содержимого zip. ВМ не запускали. Внешние факты даны со ссылками, они собраны в §9.
Свои оценки помечены словом «оценка».

## 0. Коротко

1. **Транспорт и каркас у нас уже есть**, и их можно взять почти без изменений:
   - rosbridge-клиент на Go (`robotmcp/internal/rosbridge`): одно постоянное WebSocket-соединение, переподключение, CBOR, учёт трафика;
   - каркас MCP-сервера с событиями (`robotmcp/internal/server`, `cammcp/internal/server`);
   - хост MCP, гейт и локальные правила агента EdgeCtx. Правило умеет вызвать инструмент без LLM, то есть даёт рефлекс «жест → движение» без задержки модели;
   - ВМ `sim` (Jazzy, Gazebo Harmonic, rosbridge 2.7.1) и инструменты замеров.
2. **Логика robot-mcp для их робота не подходит.** Она построена вокруг Nav2: цели по местам, AMCL, `send_action_goal`, отмена целей сервисом. У их робота Nav2 нет. Кроме того, в rosbridge для Foxy (1.3.1) нет поддержки действий: она появилась только в 2.0.0. Нужен режим «скорость»: примитивы `move` / `turn` / `stop`, повтор публикации и сторожевой таймер.
3. **Блокер совместимости.** Тип `/cmd_vel` в robot-mcp зашит константой `geometry_msgs/msg/TwistStamped` (`robot.go:79, 240, 866`). Их робот (Foxy) использует `Twist`. rosbridge 1.3.1 при несовпадении типа бросает `TypeConflictException`, поэтому `stop()` на их роботе не сработает.
4. **Симуляция.** Достаточно взять TurtleBot3 waffle_pi и поменять параметры сенсоров в нашем launch-файле: он уже переписывает SDF и мост. Оценка — 0,5–1 день. Своя SDF нужна, только если важны габариты и места крепления сенсоров. Оценка — 1,5–3 дня плюс калибровка по замерам на роботе. Руку YOLO в Gazebo не увидит. Поэтому жесты в симуляции подаются двумя способами:
   - инжектором класса, чтобы мерить цепочку «агент → робот»;
   - записью RealSense `.bag`, которую pyrealsense2 воспроизводит штатно, чтобы проверять YOLO+SNN без камеры.
5. **PicoClaw не может пользоваться событиями.** Проверено по коду v0.3.1, это же последний релиз и текущий main. MCP-клиент создаётся без обработчиков уведомлений, ресурсы не читаются. Обходные пути:
   - MQTT-канал и внешний мост: в `bench/baselines` уже есть `pushfilter.py` и `mqttlite.py`;
   - синхронные инструменты (`-wait-param`);
   - рефлекс вне агента.
6. **Цепочку задержек сейчас не измеряет ни один инструмент.** Есть части: `robot-probe` (задержка вызова, стоп, проезд по истинной позе), `rosbridge_probe.py drive`, `topic_rates.py`, трассы JSONL с `ts_wall`. Не хватает:
   - наблюдателя `/cmd_vel` и `/odom` в ВМ `sim`;
   - инжектора жестов;
   - сведения часов разных ВМ.

   Часы можно свести через `/rosapi/get_time`: этот сервис есть и в 1.3.1, и в 2.7.1.

## 2. Карта переиспользования

Условные обозначения: **как есть** — брать без правок кода; **доработать** — правки с оценкой объёма; **нет** — у нас этого нет или не подходит.

### 2.1. robot-mcp (`robotmcp/`, Go, 5,5 тыс. строк кода, 1,6 тыс. строк тестов)

| Часть | Статус | Что и почему |
|---|---|---|
| `internal/rosbridge` — клиент v2 | **как есть** (с одной оговоркой) | Одно соединение на сессию. После обрыва переподключается и сам восстанавливает подписки и `advertise`. `Once` (subscribe → первое сообщение → unsubscribe). Учёт трафика по видам сообщений. CBOR с типизированными массивами. Оговорка: `Options.Actions` в `main.go:203` всегда равен `{/navigate_to_pose}`, поэтому при подключении клиент вызывает `cancel_goal`. Без Nav2 такого сервиса нет: rosbridge 1.3.1 ответит ошибкой `InvalidServiceException` (`services.py:108–111`), и отмена будет повторяться на каждом подключении. В режиме «скорость» передавать пустой список |
| `internal/cbor`, `canon`, `clock`, `trace`, `tokens`, `imgutil` | **как есть** | `canon` — канонический JSON, `clock` — часы real/virtual, `trace` — журнал JSONL с `ts_wall`. `tokens` — оценка o200k для журнала. `imgutil` уменьшает JPEG, если агенту понадобится кадр |
| `internal/server` + `dispatch.go` | **как есть** как каркас | MCP на go-sdk 1.8.0. Подписка, `resources/updated` с `_meta.state`. Рассыльщик с очередью на 64 события не блокирует ядро. Состав инструментов — новый (см. ниже) |
| `cmd/robot-probe` | **как есть** + доработать | Уже меряет: задержку вызова (`ms`), `stop_ms`, проезд после стопа `coast_m` по `/ground_truth/pose`, задержку уведомления `event_ms`, трафик через счётный TCP-прокси, PSS/CPU. Добавить сценарий «жест → движение» |
| `-wait-param`, `-transport http`, `/control/*` | **как есть** | `-wait-param` даёт синхронный режим: итог задачи приходит в ответе инструмента. Это вариант для PicoClaw, у которого нет событий (§5) |
| Ядро `internal/robot`: места, Nav2, AMCL, `go_to`/`patrol`/`look(place)`, `displaced` | **нет** (для их робота) | Нет карты, Nav2 и AMCL, нет действий в rosbridge 1.3.1 (§4). В этом режиме выключить |
| Тип `/cmd_vel` | **доработать** (обязательно) | Константа `twistType = geometry_msgs/msg/TwistStamped` (`robot.go:79`) используется в `Advertise` (`:240`) и в `Stop` (`:866`). Нужен параметр конфигурации `cmd_vel_type: Twist \| TwistStamped`. Оценка: ≈0,5 дня с тестами |
| `Stop()` | **доработать** | Сейчас порядок такой: `CancelAllGoals` → нулевая скорость (`robot.go:854–876`). Без Nav2 нулевую скорость надо слать сразу, несколько раз. Сервисы на «моторном» соединении не вызывать: в 1.3.1 вызов сервиса выполняется синхронно в очереди этого клиента (`call_service.py:100` — `ServiceCaller(...).run()`, `websocket_handler.py` `IncomingQueue`). Зависший сервис задержит и стоп |
| Примитивы движения | **нет** → сделать | `move(dir: forward\|back, m \| s)`, `turn(deg)`, `stop()`. Исполняются на плате: повтор публикации 10 Гц, как у демо и как ждёт база. Сторожевой таймер (deadman): без обновления — ноль. Ограничения скорости и длительности — по образцу шлюза hw-mcp (clamp, pulse, interlock). Если есть `/odom` — замкнутый контур, иначе по времени. Оценка: 2–3 дня с тестами |
| Охрана по лидару | **доработать** | `ParseScan` и сектора (`summary.go:23–81`) работают по углам и поэтому годятся для 240°. Но сектор `back` (≥150°) у URG-04LX пуст и отдаётся как `">rmax"`, то есть «свободно». Нужно `"no data"`. Тревогу «препятствие впереди» (`-obstacle-m`, `-motion-scan-ms`) можно переиспользовать как interlock примитивов. Оценка: 0,5 дня |
| `internal/fakebridge` | **доработать** | Сейчас эмулирует Nav2, AMCL, `/scan`, камеру. Для `/cmd_vel` только считает нулевые команды, кинематики и `/odom` нет. Добавить кинематику дифференциального привода по `Twist` и тему `/odom`. Оценка: 1 день |

Итого по robot-mcp в режиме «скорость» — около 4–5 дней (оценка).

### 2.4. hw-mcp, bench, sysmon

- **hw-mcp, шлюз приводов**: clamp, `rate_limit`, interlock, аренда со сторожевым таймером, `pulse` с автоостановкой точно в срок, `safe_state` при завершении. Это **образец политики** для примитивов `/cmd_vel`: `pulse` — тот же `nudge`, только с точным сроком. Код GPIO/sysfs не нужен.
- **bench/mockllm** — заглушка LLM для агента сверху (ключ не тратим). **bench/baselines**: драйвер PicoClaw, MQTT-канал, `pushfilter.py`, `mqttlite.py` — готовый обходной путь подачи событий в PicoClaw (§5). **sysmon** — PSS/RSS/CPU процессов на «плате».

- **Вариант A — waffle_pi с правками сенсоров.** Оценка — 0,5–1 день. Наш launch уже переписывает `model.sdf` регулярными выражениями. Что добавить:

Нужен, если важны габариты (проезды, расстояние срабатывания охраны) или правдоподобие поворотов в ВКР. Начинать с A, B делать после ответов лаборатории.

- **Жесты в симуляции.** YOLO обучен на руках, а в мире Gazebo руки нет: «человек» в `world_events.py` — цилиндр. Варианты по возрастанию сложности:
  1. **инжектор жестов** — публикует класс (или траекторию рамок) в тему или событие gesture-mcp. Мерит всё после распознавания и годится для рабочего дня T0/T1;
  2. **запись RealSense `.bag` + pyrealsense2 `enable_device_from_file`**. Повтор включён по умолчанию [S8]. Это сквозная проверка YOLO+SNN без камеры, а в коде демо меняется одна строка конфигурации. YOLO можно запускать на Mac или в ВМ на CPU (в ВМ нет GPU) — это даст только логику и порядок величин, а не задержки Jetson;
  3. каталог кадров (`dir`, как в cam-mcp) — то же без librealsense.
- **Цена камеры Gazebo.** Постоянный рендер 640×480 при 30 Гц в ВМ снижает RTF до 0,68 (`robot_sim.md` §7, конфигурация A). Если Gazebo-камеру никто не потребляет, держать её ленивой (по умолчанию) или выключить.
- **Их Python-код в симуляции.** `rclpy`-часть демо (Twist, LaserScan) переносится в Jazzy без правок по API. Связь Foxy ↔ Jazzy напрямую через DDS не гарантируется [S11, S12]. Поэтому либо их узлы запускаются в Jazzy, либо в контейнере Foxy, а граница проходит по rosbridge JSON.

## 5. События: как устроены у нас и может ли PicoClaw ими пользоваться

**Как устроено у нас.**
- **robot-mcp.** Ядро ставит событие в очередь (`Notify`). Рассыльщик отправляет `notifications/resources/updated` по `robot://state/robot`. В `_meta`: `device`, `state` (полное состояние, ≈44 токена), `robot/event`, `robot/changed`, `robot/detail` (`server.go:368–378`). Уведомления шлются только по значимым событиям: `task_end` и `alert`. Очередь на 64 события; при переполнении событие сливается с последним (`dispatch.go`).
- **cam-mcp** устроен так же: `motion_start`, `motion_end`, `camera_lost`, `camera_back`.
- **EdgeCtx.** Обработчик `ResourceUpdatedHandler` в mcphost кладёт событие в ограниченную очередь (1024). `onUpdate` берёт `_meta.state` или читает ресурс, затем `ingest`. Дальше гейт: дебаунс → `no_change` → правила (`tool` / `notify` без LLM) → эхо собственных команд → значимость → cooldown → коалесценция → пробуждение LLM по приоритету.

**PicoClaw.** v0.3.1 — последний релиз (GitHub API на 14.10.2026), коммит `2cf030d` лежит в `bench/baselines/vendor/src/picoclaw`. В `pkg/mcp/manager.go:337–340` клиент создаётся как `mcp.NewClient(&mcp.Implementation{…}, nil)`: без `ClientOptions`, то есть без обработчиков уведомлений. Для `type: http` отключён отдельный поток SSE (`:356–375`). Вызовов `ListResources`, `ReadResource` и `ResourceUpdated` в `pkg/` нет. В текущем `main` то же самое. Вывод: **PicoClaw видит только инструменты**, наши события до него не доходят.

**Обходные пути для PicoClaw.**
1. **MQTT-канал PicoClaw и внешний мост**, который превращает события в реплики. Уже есть в `bench/baselines` (`pushfilter.py`, `mqttlite.py`, драйвер `drive_picoclaw.py`). Цена: каждое событие — это ход LLM (задержка и токены).
2. **Канал `maixcam`** (TCP, JSON). Принимает только `person_detected` (`maixcam.go:145–212`) и превращает его в текст для LLM. Для жестов подходит плохо.
3. **Синхронные инструменты**: `-wait-param` в robot-mcp. Итог движения приходит в ответе инструмента, событие не нужно. Движение длится секунды, поэтому для PicoClaw это приемлемо.
4. **Cron `command`** (exec без LLM) — опрос по расписанию.
5. **Рефлекс вне агента.** Узел жестов сам вызывает примитив движения. PicoClaw получает только команды на естественном языке и состояние по запросу. **Рекомендуется** вместе с п. 1 для уведомлений.

Для EdgeCtx рефлекс делается правилом гейта `action: tool` — без LLM и с трассой каждого шага. Поэтому сравнение «PicoClaw + мост» против «EdgeCtx + правило» по задержке и числу обращений к LLM — честная часть ВКР.

## 6. Как измерять задержки в симуляции

**Цепочка меток** (все в `ts_wall`; в скобках — источник):

| Метка | Событие | Источник |
|---|---|---|
| t0 | конец жеста — последний кадр с рукой | узел жестов (новое поле журнала) |
| t1 | класс выдан (SNN) | узел жестов |
| t2 | событие отправлено: `resources/updated` или прямой вызов | трасса gesture-mcp, запись `notify` |
| t3 | вход в агент → `rule_fired` → `tool_call` | трасса EdgeCtx |
| t4 | `tool_call` принят robot-mcp → `publish /cmd_vel` | трасса robot-mcp (добавить запись `publish` с меткой) |
| t5 | первое ненулевое `/cmd_vel` видно в графе ROS | **новый** наблюдатель в ВМ `sim` (rclpy, как `topic_rates.py`) |
| t6 | начало движения: \|v\| в `/odom` > ε или сдвиг `/ground_truth/pose` > ε | тот же наблюдатель |

Отрезки: распознавание (t1−t0), доставка (t2…t4), rosbridge → ROS (t5−t4), физика и контроллер (t6−t5), итог (t6−t0). Для стопа — отдельно `stop_ms` и `coast_m`: `robot-probe` их уже меряет.

**Что уже есть.**
- `robot-probe`: время вызова и уведомления, `stop_ms`, `coast_m`, трафик, PSS/CPU.
- `rosbridge_probe.py drive`: сдвиг по `/odom` без времени; `snapshot`: задержка кадра p50/p95.
- `topic_rates.py`: частоты, RTF по `/clock`.
- `measure_load.sh` и `load_matrix.sh`: нагрузка.
- `lockstep_probe.py`: сим. время и стенное время.
- Трассы всех наших компонентов с `ts_wall`.
- Истинная поза `/ground_truth/pose` (ленивая, 10 Гц).

**Чего нет и что сделать** (оценки объёма):
1. **Наблюдатель в ВМ `sim`.** Подписки на `/cmd_vel` (тип из конфигурации), `/odom`, `/ground_truth/pose`. Пишет время приёма (CLOCK_REALTIME ВМ) и `header.stamp` (сим. время) в JSONL. Оценка: 0,5 дня.
2. **Инжектор жестов с меткой t0** и сценарий повторов (N ≥ 30 на класс, оценка), сводка p50/p95/max по отрезкам. Оценка: 1 день.
3. **Сведение часов.** ВМ `sbc`, `sim` и Mac — разные часы. Синхронность Lima-ВМ не проверялась. Смещение считать по `/rosapi/get_time`: сервис есть в 1.3.1 (`rosapi_msgs/srv/GetTime.srv`) и в 2.7.1. Схема Кристиана: смещение = t_srv − (t_send + t_recv)/2, погрешность ≤ RTT/2. Наш rosapi запущен без `use_sim_time`, поэтому отдаёт стенное время ВМ `sim`. Альтернатива — все метки ставить в ВМ `sim`.
4. **Частоты.** `/odom` — 50 Гц, квант 20 мс. `/ground_truth/pose` — 10 Гц, квант 100 мс: для замера поднять `ground_truth_hz` до 50–100. DiffDrive TurtleBot3 ограничивает ускорение 1 м/с² [S4]. Порог ε выбирать с учётом шума.
5. **Режим.** Только реальное время (T2, RTF ≈ 1, ленивая камера: RTF 0,994 в `robot_sim.md` §7). Ускоренные и пошаговые прогоны для задержек непригодны (`timecomp.METRIC_VALIDITY`). Все числа на ноутбуке — ориентир, а не задержки Jetson.
