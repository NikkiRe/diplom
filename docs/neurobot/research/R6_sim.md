# R6-sim. Как моделировать и тестировать «жест → робот + агент» без настоящего робота

Срез: 14.10.2026. Автор: Claude (часть R6 исследования NeuroChip). Только чтение кода лаборатории
(`third_party/neurochip/…`), веса не загружались: `*.pt/*.pth` разобраны `zipfile` + `pickletools.dis`,
тензоры SNN прочитаны как сырые байты. Скрипты пробы лежат вне проекта (scratchpad сессии), их
вывод приведён ниже. Пометки: **[код]** — проверено по исходнику (файл:строка), **[замер-проба]** — мой
прогон на Mac, ориентир, **[ист. N]** — внешний источник (§12), **[оценка]** — моя оценка без замера.
MCP-сервер лаборатории подробно разобран в `R2_ros_mcp_server.md`. Здесь от него взято только то, что нужно
для стенда и инъекции отказов.

## 0. Главное (на один экран)

1. **Тестировать надо два конвейера на одних сценариях.** Первый — демо лаборатории **как есть**
   (`predict_live.py` без правок, через подставные модули). Второй — наша система. Иначе в ВКР не будет
   честного «до/после». Демо как есть в нашем симуляторе сразу не заработает. Ему мешают **четыре** вещи
   (§2: P1–P4), и одна из них молча подменяет веса SNN случайными.
2. **Главный источник для долгих прогонов — (a) синтетические траектории bbox руки на входе распознавателя.**
   Подавать их можно в демо (подставной YOLO) и в наш узел (интерфейс источника bbox). Источник
   детерминирован, работает без камеры и человека, годится для 8-часовых прогонов и инъекции отказов.
   Генератор датасета из `snn_prod` для этого **не подходит**: он готовил данные для другой сети, прогноза
   траектории (§1.3). Генератор жестов придётся писать самим, а соответствие «форма → класс» — узнать у
   лаборатории.
3. **(c) Видеофайлы с жестами** нужны как источник честной точности и реальной нагрузки детектора.
   (b) **живая веб-камера** нужна для демонстрации и проверки руками. Камеру Mac в ВМ не пробросить:
   встроенная камера не висит на USB, а Lima 2.1.1 USB не пробрасывает. Кадры передаются по сети
   (§4.2). (d) **актёр в Gazebo** для распознавания жестов не годится. Он полезен только для геометрии
   «человек ↔ робот» (§4.4), приоритет низкий.
4. **Задержку «жест → движение» в демо задаёт конструкция, а не вычисления.** Жест считается законченным
   только после **1,5 с без руки в кадре** [код :610–613]. SNN с предобработкой стоит ≈0,8 мс
   [замер-проба, numpy]. Поэтому замер надо раскладывать на ожидание конца жеста, вычисление, отправку
   (таймер 10 Гц) и разгон.
5. **Результат распознавания сильно зависит от частоты детектора и размера жеста** [замер-проба, §3]. Кроме
   того, при «молчащей» SNN всегда выбирается класс 0, то есть «разворот на 180°» [код :273–276]. Отсюда
   правило стенда: частоту детекции держать **как на Jetson** (её надо измерить у лаборатории). Если YOLO
   на Mac работает быстрее, точность получится не та, что на роботе.
6. **Проверка «процесс жив» ничего не говорит.** У демо ошибка в потоке камеры (например, тайм-аут
   `wait_for_frames` у RealSense) молча убивает рабочий поток, а узел ROS продолжает жить и публиковать
   нули [код :595–615]. Это лучший кандидат на «после пары использований надо перезагружать» со стороны
   демо. Живость системы надо мерить по прогрессу (кадры/с, свежесть bbox), а инъекция отказов должна
   ловить «глухой, но живой» узел.
7. Что считается результатом. В симуляции **результат** — структурные счётчики: вызовы и токены LLM на
   жест (ожидается 0), число перезапусков, видимых пользователю, наклон памяти наших процессов, логика
   восстановления. **Ориентиром** остаются задержки, CPU и точность на синтетике. Окончательные цифры
   задержки и времени восстановления — только на роботе (§8).

## 1. Что именно тестируем: как устроено демо (то, что важно для стенда)

### 1.1. Временная линия одного жеста в `predict_live.py`
| Этап | Что происходит | Доказательство |
|---|---|---|
| Кадр | `pipe.wait_for_frames()` (RealSense 640×480@30, BGR), затем зеркалирование `cv2.flip(…,1)` | [код :546–549, :615–619] |
| Детекция | `yolo_model(color_image, size=320)`: YOLOv5 через `torch.hub` AutoShape, conf 0,35, iou 0,45, max_det 1 | [код :519–557, :625] |
| Накопление | Пока робот стоит, рамки копятся в `black_white_map`, а каждая рамка сбрасывает таймер конца жеста | [код :630–635] |
| Конец жеста | Через **1,5 с без единой рамки** при числе рамок **≥ 6** (`MIN_FRAMES_TO_DETECT`) | [код :41, :610–613, :636–637] |
| Распознавание | Центры рамок рисуются квадратами 10 % размера (PIL 256×256), затем картинка 28×28 «как MNIST», кодирование Бернулли на 25 шагов, SNN 784→128→4 (LIF, β = 0,5), argmax | [код :312–348, :135–190, :208–212, :233–284] |
| Команда | Метка → `Queue(3)`, поток контроллера выполняет сценарий через `sleep` (`come` — 3 с вперёд; `turn180` — 7 с поворота; `go_left/right` — 8 с; `think` — 11 с) | [код :356, :398–454, :494–512] |
| Публикация | Таймер **10 Гц** публикует `Twist` (0,5·x м/с, 1,0·th рад/с) в `/cmd_vel`, если лидар не видит препятствия | [код :362–363, :370–372, :473–486] |
| Лидар | Препятствие — при дальности ≤ **0,25 м** в лучах с **166 по 515** (в README сказано 0,35 м) | [код :459–467]; README |

Нижняя граница задержки «рука ушла из кадра → первая ненулевая команда» ≈ 1,5 с + кадр + YOLO + SNN + ≤ 100 мс
таймера **[оценка по коду]**. Начало движения на роботе зависит ещё от STM32 и разгона. Направление `go_left`
или `go_right` выбирается по `x1` первой и последней рамки [код :322–328]. Поэтому при махании рукой
сторона получается почти случайной: она зависит от того, где кончилось махание [замер-проба: wave → 80/120].

### 1.2. Модели (без загрузки, `pickletools`)
- `yolo_hand.pt` (SHA-256 `dafddc97…66e2b2`, 14,3 МБ): чекпойнт YOLOv5 на 1 класс `hand`. Множители глубины
  и ширины 0,33/0,5 — это **YOLOv5s**. Веса в fp16 (`HalfStorage`), обучение `imgsz=256`, 100 эпох, `weights=yolov5s.pt`.
  Код ultralytics/yolov5 — master, коммит `725b922e…`, дата 2025-10-03, пути Windows. Pickle ссылается
  только на `models.common.*`, `models.yolo.*` (код yolov5), `torch.*`, `torch.nn.*`, `collections.OrderedDict`,
  `__builtin__.set` и **`pathlib._local.WindowsPath`**. Последнее значит, что файл сохранён на Python ≥ 3.13
  под Windows, поэтому демо и подменяет `pathlib._local` [код :687–692]. Явно опасных ссылок (`os.system`,
  `builtins.eval` и т. п.) нет. Но загрузить файл можно только исполнением кода yolov5.
- `snn_emnist_small.pth` (SHA-256 `bda97d30…7d2406`): `model_state_dict` (`fc1` 128×784 + bias, `fc2` 4×128 без
  bias, LIF: порог 1,0, β 0,5, сброс вычитанием) плюс `model_topology` и `dataset: {name: emnist, split:
  balanced, fix_orientation}`. Pickle содержит **только** `OrderedDict` и тензоры, так что
  `torch.load(…, weights_only=True)` его откроет [ист. 14]. Разброс весов `fc1` (σ 0,043, диапазон −0,25…0,33)
  выходит за границы инициализации по умолчанию: веса обучены, это не случайная инициализация **[замер-проба]**.
- В EMNIST balanced 47 классов, а у сети 4 выхода. **Какие 4 класса взяты и как их рисовать — в репозитории
  не сказано.** Кода обучения этой SNN в архиве нет. Это главный вопрос к лаборатории для варианта (a).

### 1.3. Что на самом деле генерирует `snn_prod` / `drawing_tools`
- `nettools/snn_prod/generate_dataset.py` вклеивает `file/ball.png` (файла в архиве нет) в фоны Kaggle
  «scene-classification» и двигает его по прямой (35 кадров). Это данные для **SNN прогноза траектории**
  (`nets/SnnNet.py`: `SnnSingleNet`/`PredNet`, `snn_checkpoint.pth`). Эта сеть используется только в
  `live_stream_yolo.py` [код]. `drawing_tools.py` рисует рамки формата YOLO v1 (7×7×30) и анимации matplotlib.
- **К 4-классовому распознавателю жестов из `predict_live.py` эти генераторы отношения не имеют.** Полезна
  только идея «вклеить объект в фон по траектории». Её можно взять для кадровой синтетики (a′, §4.1).
- `live_stream_yolo.py` импортирует `from camera import RsCamera, WebCamera`, а модуля `camera` в архиве нет
  [код :9]. Скрипт не запустится. Значит, у лаборатории был и путь через веб-камеру (вопрос §11).

## 3. Проба: синтетические траектории → предобработка демо → SNN (numpy) [замер-проба]

Что сделано. На numpy заново реализованы `write_map_number` (тем же PIL), `to_mnist_canvas` (усреднение по
площади, как `F.interpolate(mode="area")`; билинейная ветка приближена) и `rate_encoding`, а также прямой
проход SNN по формулам snnTorch Leaky (сброс по предыдущему потенциалу и вычитание порога). Веса прочитаны
как сырые байты. Генератор — параметрические штрихи: «0» эллипс, «1» вертикаль, «2», «3», горизонтальный
мазок, махание, «рука стоит» и ещё 25 форм. Рука — рамка ≈90×110 px в кадре 640×480, шум σ 4 px,
10 % пропусков детекции. **Это приближение демо, а не оно само: torch-эталоном не проверено.**

| Форма (область 300 px, 30–60 рамок) | Классы 0/1/2/3 из 200 | Наблюдение |
|---|---|---|
| махание, горизонтальные мазки | 0/0/200/0 | Класс 2 (`go_left/right`) устойчив. Сторона при махании — 80 влево / 120 вправо |
| «рука стоит» | 178/5/0/17 | Класс 0, то есть `turn180` |
| «0» (эллипс) | 182/18/0/0 | Класс 0 |
| «1», «2», «3» | 0 и смесь | «1»: 138 из 150 прогонов SNN **молчит**, отсюда 0 |
| «V», диагональ ↘ | 1-й класс ≈ 90–98 % | Класс 1 (`come`) даёт «V», а не цифра |
| «beckon» (вверх-вниз на месте) | 3-й класс 95 % | Класс 3 (`think`) |

Зависимость от плотности и размера (по 120 прогонов на ячейку; классы 0/1/2/3 и число «немых» SNN):
- Область 150 px при 30 к/с: «0» → 0 (95 %), «1» → 3 (96 %), «2» → 1 (98 %). **Тот же набор при ≈8 к/с
  (8–15 точек траектории, после 10 % пропусков ≈7–14 рамок)**: 71–75 % ответов «немые», то есть всё уходит
  в класс 0.
- Область 450 px: «немые» почти все формы, кроме махания при 30 к/с.
- Одна и та же траектория «2» при 50 разных кодированиях Бернулли: 12 раз класс 0, 38 раз класс 1. Распознавание
  **недетерминировано**, для повторяемости нужен seed.
- SNN с предобработкой — ≈0,84 мс на жест, сам проход SNN — 0,37 мс (Mac, numpy, один поток).

Выводы для стенда (сами числа — ориентир):
1. Смысл классов на «цифры 0–3» явно не ложится. Генератор (a) нельзя писать «на глаз»: нужен список
   4 классов EMNIST и правила рисования от лаборатории.
2. Плотность траектории — фактор первого порядка. Частоту детекции на стенде надо задавать как на Jetson.
3. «Немая» SNN → `turn180` даёт ложные развороты. На стенде нужны отрицательные сценарии и метрика ложных
   действий.
4. Распознаватель дешёвый, так что для нашего узла его можно перенести на numpy или ONNX. Сначала —
   тест эквивалентности с torch-эталоном на одних и тех же картинках 28×28 и одном seed (при разрешении
   ставить torch CPU, §9).

### 4.1. (a) Синтетические траектории bbox
- **Генератор `gesturegen`** (seed): класс из списка лаборатории, форма как ломаная или кривая. Варьируются
  масштаб (100–450 px), поворот ±15°, длительность 0,7–2,5 с, шум, пропуски детекций, размер руки (дистанция
  0,5–3 м), паузы. Выход — JSONL `{t, bbox|null, truth: {gesture_id, class, phase}}` при 30 к/с камеры с
  прореживанием до частоты детекции Jetson. Отрицательные сегменты: рука стоит, проход человека (длинный
  мазок), ложные рамки с частотой r.
- **Лучше параметрики — записанные треки.** Прогнать YOLO один раз по видео из (c) или по журналам рамок с
  робота и проигрывать треки тысячи раз («записать один раз — проигрывать много»). Так (a) получает
  реальную форму жестов.
- **Куда подавать:**
  1. **Демо как есть.** Запускатель (`runpy`) подменяет `torch.hub.load` на `FakeYolo`: объект с
     `.max_det/.conf/.iou/.to()/.eval()/.half()`, на вызов отдаёт `results.xyxy[0]` из сценария, синхронно с
     кадром. Подставной пакет `pyrealsense2` (`pipeline/config/start/get_active_profile().get_device().sensors`,
     `wait_for_frames()` → кадр 640×480 BGR с темпом 30 к/с, режимы отказа). Настоящий YOLO не нужен,
     а **исходный код демо исполняется без правок**, включая таймер 1,5 с, Queue, DriveController и лидар.
  2. **Наш узел.** Интерфейс `BBoxSource {yolo | replay | synthetic}`.
- **Время:** демо работает по стенным часам (`time.time`, `sleep`), ускорить нельзя, долгие прогоны идут в
  реальном времени. Наш агент с виртуальными часами в T0 годится только для счётных метрик.

### 4.2. (b) Живая веб-камера Mac → YOLO → тот же конвейер → робот в Gazebo
- **Проброс камеры в ВМ невозможен.** `system_profiler`: встроенная «Камера (MacBook Pro)» есть в
  `SPCameraDataType`, но **в дереве USB её нет** (проверено на этом Mac, macOS 27.0.1). У Lima 2.1.1 нет
  настроек USB. В Virtualization.framework общий USB-проброс появился только как `VZUSBPassthroughDevice`
  (macOS 27.0+) [ист. 2]. Поддержки в Lima не нашёл (в проверенных источниках не найдено), и встроенную
  камеру он не покрывает. Внешнюю USB-камеру теоретически можно пробросить через новый API, но Lima этого
  не умеет.
- **Как передать кадры** (ВМ видит сервисы Mac на `host.lima.internal`, путь проверен — `docs/robot_sim.md` §1):
  1. **Захват на Mac** — либо страница в браузере (`getUserMedia` → JPEG → WebSocket на локальный сервер:
     разрешение на камеру даёт сам браузер), либо OpenCV/ffmpeg `-f avfoundation` [ист. 9]. Во втором случае
     терминалу нужен доступ к камере в «Конфиденциальность и безопасность → Камера» [ист. 8]. Включает
     **сам студент**, мне менять системные настройки нельзя.
  2. **Транспорт — ROS-тема**: публикация `sensor_msgs/CompressedImage` через rosbridge в тему как у
     RealSense-обёртки (`/camera/camera/color/image_raw/compressed`). Топология будет как на роботе
     (камера — один издатель, см. P11). JPEG q80 640×480 ≈ 13 КБ, в JSON rosbridge ≈ 17–18 КБ [`robot_sim.md` §5],
     30 к/с ≈ 0,5 МБ/с, для loopback это немного **[оценка]**. Альтернатива — MJPEG по HTTP
     (`cv2.VideoCapture("http://host.lima.internal:…")`): проще, но камера при этом не ROS-тема.
  3. В кадре передаются метка захвата (монотонные часы Mac) и номер кадра, чтобы считать задержку (§6).
- **Где и на чём запускать YOLO без CUDA:**
  | Вариант | Плюсы | Минусы |
  |---|---|---|
  | onnxruntime CPU в ВМ `sbc` («плата») | Ближе к плате по ресурсам, без torch во время работы, колесо 14,5 МБ (aarch64) [ист. 11] | Нет GPU: время ≠ Jetson |
  | OpenCV DNN (`readNetFromONNX`) | Один пакет (opencv 33–46 МБ) [ист. 11] | Медленнее и капризнее к операторам **[оценка]** |
  | torch CPU (как у лаборатории, через hub) | Ровно код демо | torch 62 МБ (macOS) / 90 МБ (aarch64) [ист. 11], исполнение pickle, P4/P5 |
  | на Mac нативно (CoreML/MPS) | Быстро | Это уже не плата |

  Рекомендация: **onnxruntime в `sbc` с темпом детекции как на Jetson**, плюс один прогон «без ограничения
  темпа» для сравнения. YOLOv5s — 16,5 GFLOPs на 640×640 [ист. 7], при 256×320 ≈ 3,3 GFLOPs
  **[оценка пропорцией]**. На Jetson Nano для yolov5s 640 на форуме NVIDIA приводят ≈120 мс/кадр [ист. 12];
  при 320 будет быстрее, но **замера при 320 нет**. Его надо снять у лаборатории.
- **Конвертация `yolo_hand.pt` → ONNX** (один раз, в изолированной ВМ, офлайн, с разрешения студента):
  код yolov5 на коммите `725b922e`, `export.py --weights yolo_hand.pt --include onnx --imgsz 256 320 --opset 12`
  (fp32: `--half` только на GPU) [ист. 6]. Нужны `onnx>=1.12` и, для `--simplify`, `onnxslim` и onnxruntime [ист. 6].
  Размер входа 256×320 выбран так. AutoShape при `size=320` для кадра 480×640 масштабирует до 240×320 и
  округляет до кратного шагу 32 [ист. 6]. Округление вверх до 256 — **[оценка по коду `make_divisible`]**,
  проверить при экспорте. Ещё нужен обход `pathlib._local`, как в демо.
  - **Особенность, которую надо сохранить или явно исправить:** демо передаёт в AutoShape кадр OpenCV в BGR, а
    AutoShape массивы numpy не переставляет и считает их RGB [ист. 5]. Чтобы ONNX-путь был эквивалентен демо,
    надо подавать те же байты. Если исправить, это будет отклонение с записью.
  - **Тест эквивалентности:** не меньше 200 кадров из (c); torch (AutoShape) против ONNX-конвейера (letterbox,
    NMS conf 0,35, iou 0,45, max_det 1). Порог: IoU ≥ 0,95 и |Δconf| ≤ 0,01 на ≥ 99 % кадров — задать до прогона.
- **Ограничение:** веб-камера Mac — не RealSense D435i (другие оптика, экспозиция, демо выключает
  автоэкспозицию [код :108–129]), и расстояние до пользователя другое. Это ориентир.

### 4.3. (c) Видеофайл (или rosbag) → тема камеры
- **Свой набор:** записать на Mac ≥ 30 клипов на класс от ≥ 3 человек при 2 вариантах освещения, плюс
  отрицательные клипы (жеста нет, рука стоит, проходят люди). Разметка в JSON рядом с клипом: класс,
  `t_start`, `t_end`. Хранить только локально: в кадре лица, нужно согласие, в git и в публикации не класть.
- **Проигрывание:** для демо — подставной `pyrealsense2` читает видео с родной частотой (семантика «последний
  кадр»: медленный потребитель теряет кадры). Для нашего конвейера — издатель ROS-темы с метками времени
  проигрывания. Плейлист в петле со случайными паузами — это долгий прогон с реальной нагрузкой детектора.
- **Записи лаборатории:** попросить rosbag2 с `/camera/camera/color/image_raw` (сжатым), `/scan` и `/cmd_vel` с
  реальных сеансов, вместе с журналами. Это реальные кадры RealSense и реальные следы отказов. Читаются ли
  мешки Foxy (sqlite3) в Jazzy, **не проверено** — проверить на первом файле.
- Готовые наборы видео жестов (Jester, EgoGesture и т. п.) — другие классы и не «рисование в воздухе», а
  большие загрузки (> 1 ГБ — только с разрешения). Брать не советую. Лицензии и размеры конкретных наборов
  в этой работе не проверял.

### 4.4. (d) Рука или человек в Gazebo (actor)
- Gazebo Sim: актёры движутся по сценарию (скелетная анимация из COLLADA или BVH, траектория по путевым
  точкам в `<script>`). На физику и контакты не реагируют, **их видят RGB-камеры и GPU-сенсоры**, в том числе
  `gpu_lidar` [ист. 15].
- **Для жестов не годится.** Стандартный актёр (`walk.dae`) не рисует рукой в воздухе. Анимацию кисти
  пришлось бы делать самим. YOLO, обученный на настоящих руках, отрендеренную руку (llvmpipe) скорее всего
  не найдёт **[оценка]**, поэтому детектор пришлось бы заменить заглушкой с истинной рамкой из проекции.
- **Цена:** рендер камеры 30 Гц на llvmpipe опускает RTF стенда до 0,68 и съедает 2,3 ядра против 0,85 в
  ленивом режиме [`docs/robot_sim.md` §7, конфигурации A и C]. Для замеров задержки при 30 к/с это непригодно.
- **Зачем всё-таки нужен:** сценарии, которых нет в (a)–(c). После `turn180` пользователь оказывается за
  спиной робота: следующий жест невозможен, пока робот не развернётся обратно. Это проблема
  «непрерывного режима». Человек перед роботом при `come` — лидарная остановка в 0,25 м (P2). Вместо
  актёра хватит «заместителя руки»: тела с текстурой, которое двигается через `/world/default/set_pose`
  (уже есть, `--world-control`, `robot_sim.md` §13), плюс заглушка детектора. Приоритет низкий.

## 6. Методика замеров для ВКР

### 6.1. Задержка «жест → движение»
- **Точки на одной линии времени** (метки в JSONL: монотонные нс + стенное время):
  `t_hand_last` (последний кадр с рукой: истина из (a) или разметки (c), в (b) — последняя рамка детектора),
  `t_rec` (решение распознавателя), `t_cmd` (первая ненулевая `/cmd_vel` у наблюдателя), `t_motion` (|v| > 0,05 м/с
  или |ω| > 0,1 рад/с по `/odom`, или смещение истинной позы > 1 см).
- **Разложение:** `Δ_end` (ожидание конца жеста, у демо ≥ 1,5 с по конструкции) + `Δ_compute` (YOLO
  последнего кадра + SNN) + `Δ_dispatch` (очередь + таймер 10 Гц) + `Δ_act` (разгон; на роботе ещё STM32).
  Так видно, где выигрыш: в конструкции или в вычислениях.
- **Статистика:** p50, p95, p99 по ≥ 200 жестам на условие. ДИ — блочный бутстреп по времени
  (`harness/stats.py`). Отдельно первый жест после старта: у `torch.compile` на первом вызове компиляция
  **[оценка]**.
- **Условия:** демо как есть и наша система × источник (a) и (c) × темп детекции (Jetson / без ограничения) ×
  свободная плата / квоты из лестницы ограничений. В отчёт идут RTF стенда и проверка, что RTF ≥ 0,95
  (`robot_sim.md` §13: при нагрузке хоста бывает 0,47–0,82).

### 6.2. Непрерывная работа N часов
- **Сценарий дня:** жесты пуассоновским потоком (1/мин, 4/мин, всплески), смесь классов, отрицательные
  сегменты, запросы к агенту через mockllm (например, «что впереди?» раз в 10 мин), расписание отказов (§7).
  Стандарт — **8 ч** реального времени (T2, как в плане ВКР), гонять ночью. Источник (a) — для
  повторяемости, (c) в петле — для реальной нагрузки детектора.
- **Метрики за каждый час:** PSS/RSS и CPU каждого процесса (sysmon), число потоков и дескрипторов, кадры/с
  детектора, длины очередей, p50/p95 задержки, доля пропущенных жестов, ложные действия в час, число
  соединений и RSS rosbridge, рост `/tmp` и журналов, байты в сети, перезапуски компонентов (журнал
  супервизора).
- **Критерии (предложение для предрегистрации):** наклон памяти ≤ 1 МиБ/ч на процесс (ДИ наклона Сена, как
  H4); дрейф p95 за час ≈ 0 (ДИ наклона накрывает 0 или < 5 %/ч); **0 перезапусков, видимых пользователю**.
- **Определение «видимого перезапуска».** Валидный сценарный жест не получил верной реакции за SLA (например,
  ≤ 3 с после `t_hand_last`), ИЛИ движение прервалось на середине команды, ИЛИ система была недоступна дольше
  интервала между жестами, ИЛИ понадобился человек. Доступность = доля сценарных жестов с верной реакцией
  за SLA. Перезапуск процесса, после которого всё это выполнено, считается **невидимым**.

### 6.3. Вызовы и токены LLM
- Счётчики mockllm/llmtap по классам вызова. Ожидается **0 вызовов на жест** (рефлекс локальный). LLM вызывается
  только на запросы пользователя и, возможно, на агрегированные события («за час 37 жестов, 2 ложных»).
  Отчёт: вызовы, входные и выходные токены в час и на запрос, трафик. Это структурный счётчик: на заглушке
  он **результат**, а не ориентир (число вызовов от модели не зависит, если нет ветвления по её ответу).
- Для сравнения — та же нагрузка через PicoClaw + MCP лаборатории (базовая линия): сколько вызовов и токенов
  стоит одна команда движения.

### 6.4. Инструменты
sysmon (уже есть), журналы JSONL узлов, наблюдатель, `harness/stats.py`. ros2_tracing (LTTng) — по желанию,
для задержек внутри ROS в ВМ `sim`: накладные ≈0,0033 мс на сообщение [ист. 16], работает только на Linux.
Перед прогонами — протокол HANDOFF §12: Mac от сети, без фоновой нагрузки, повторы, запись окружения.

## 7. Инъекция отказов

| Отказ | Как вызвать | Чего ждать от демо как есть [код] | Что мерить у нашей системы |
|---|---|---|---|
| Камера: нет кадров больше 5 с / исключение | подставной `pyrealsense2` (задержка, `RuntimeError`); остановить источник на Mac | Поток умирает, узел «глухой, но живой» (P6) | Время обнаружения (TTD), время восстановления (TTR), потерянные жесты, видимость |
| Камера: замороженный или чёрный кадр, падение частоты | источник отдаёт один кадр, нули, 5 к/с | Нет реакции или ложные классы | Обнаружение «замёрзшего» потока, деградация вместо ложных действий |
| YOLO: исключение, медленный кадр, OOM | `FakeYolo` бросает исключение или спит; cgroup `MemoryMax` | Смерть потока; при OOM — процесс | Рестарт супервизором (systemd `Restart=on-failure`, `WatchdogSec` + `sd_notify` от прогресса [ист. 17]), TTR, без ложного движения |
| Лидар: другой формат или NaN, пропал | профиль лидара, стоп моста `/scan` | IndexError → падение узла (P1) | Остановка движения при отсутствии лидара |
| rosbridge: падение, рестарт, задержка, сброс | `kill`/рестарт в `sim`; toxiproxy (`latency`, `timeout`, `reset_peer`) [ист. 18]; `tc netem` | MCP: ошибки на каждом вызове (R2 D10) | Переподключение, остановка робота сторожем ≤ 0,5 с, TTR |
| MCP-сервер: `kill -9`, зависание (`SIGSTOP`) | сигнал процессу | — | Агент перезапускает stdio-сервер, рефлекс жестов не страдает |
| Агент: `kill -9` | сигнал + systemd | — | **Жесты работают без агента** (ключевое свойство). Агент возвращается и подхватывает состояние |
| Сеть к LLM: обрыв, задержка 2 с, 429/500 | `tc netem loss 100%`, mockllm в режиме ошибок | — | Рефлекс не страдает; повторы, лишние токены и ответ пользователю в норме |
| База робота: `/cmd_vel` никто не слушает, мост упал | стоп моста cmd_vel в `sim` | Робот едет или стоит (P2) | Обнаружение по `/odom` «команда есть, движения нет» |
| Нехватка ресурсов | `CPUQuota`, `MemoryMax` (лестница ограничений) | — | Как деградируют кадры/с, задержка и точность (P9) |

Для каждой инъекции фиксируются момент отказа, TTD, TTR, потерянные жесты, небезопасное движение (робот едет
без свежей команды дольше 0,5 с) и итог «видим / невидим» по §6.2. Расписание отказов одинаково для демо
и для нашей системы (seed). Тема ВКР — работа во времени, а не надёжность. Поэтому отказы входят как часть
непрерывного дня, отдельного «рейтинга надёжности» нет.

## 8. Что в симуляции не проверить → минимум проверок на роботе (HIL)
Не проверяются: USB и драйвер RealSense (обрывы кадров, экспозиция, ИК-засветка), GPU Jetson (CUDA, fp16,
TensorRT, OOM при 4 ГБ общей памяти), тепловое и энергорежимы (5/10 Вт), UART и прошивка STM32
(сторож, отображение Twist в ШИМ), реальная динамика и пробуксовка, реальные пользователи и фоны.
Минимум на роботе: (1) задержка по стадиям на Jetson (кадр, YOLO@320, SNN, публикация) — 200 жестов;
(2) реакция STM32 на тишину `/cmd_vel`; (3) 1–2 ч непрерывной работы с журналами и sysmon;
(4) 5–10 жестов каждого класса с записью rosbag — для (c) и калибровки темпа (a).
По этим данным подбираются квоты ВМ `sbc` и темп детекции на стенде. Цифры стенда при этом остаются
ориентиром, а цифры робота — результатом.

## 9. Загрузки, безопасность, разрешения
- Размеры колёс (PyPI JSON, только метаданные) [ист. 11]: torch 2.4.1 — 62,1 МБ (macOS arm64) / 89,6 МБ
  (Linux aarch64); torchvision 0.19.1 — 1,7 / 14,1; onnxruntime 1.22.1 — 34,3 / 14,5; onnx 1.18 — 18,3 / 17,4;
  opencv-python(-headless) 4.12 — 37,9 / 45,9 (33,1 headless aarch64); ultralytics 8.3.190 — 1,1; snntorch 0.9.1 —
  0,1. Набор для конвертации в ВМ с зависимостями (pandas, scipy, matplotlib) — ≈0,3–0,4 ГБ **[оценка]**.
  Это **меньше 1 ГБ**, но всё равно спросить, раз ставится в ВМ. Записать версии, размеры, SHA-256 и лицензии
  (PROVENANCE).
- Всё, что больше 1 ГБ (наборы видео жестов, образы, CUDA), — только с разрешения студента.
- `yolo_hand.pt` — pickle из стороннего источника. Исполнять его можно только в изолированной ВМ, офлайн,
  с кодом yolov5 на закреплённом коммите. Пока что `pickletools` показал только ожидаемые ссылки (§1.2).
  SNN — `weights_only=True`. Для (a) с `FakeYolo` YOLO-pickle не нужен совсем.
- Доступ терминала к камере на Mac включает только студент (Системные настройки → Конфиденциальность и
  безопасность → Камера) [ист. 8]. Вариант через браузер обходится без этого.
- rosbridge не выставлять дальше 127.0.0.1 (HANDOFF §12). Видео с лицами не публиковать.

## 10. План работ (порядок; оценки в днях — [оценка])
1. **Профиль «neurobot» стенда** (URG-лидар, мост Twist, камера выкл., сторож `/cmd_vel`, мир со стеной) — 1 дн.
2. **Обвязка «демо как есть»** (подставной `pyrealsense2`, `FakeYolo`, сокрытие `torch.compile`, Xvfb, симлинки,
   манифест отклонений) и воспроизведение P1/P2/P6/P7/P8 — 2 дн. Это базовая линия ВКР.
3. **`gesturegen` + наблюдатель + метрики §6** (после ответа лаборатории о классах) — 2 дн.
4. **Наш gesture-node** (тот же распознаватель с тестом эквивалентности, явный конец жеста, порог
   уверенности / «не знаю», супервизор) на тех же сценариях — объём в других частях исследования.
5. **Инъекция отказов** (подставные модули, toxiproxy/netem, сигналы, расписание) — 2 дн.
6. **(c) запись и проигрывание видео** + конвертация YOLO в ONNX (с разрешения) + тест эквивалентности — 2–3 дн.
7. **(b) живая камера** для демонстрации — 1–2 дн. поверх (6).
8. Прогоны: дымовые 30 мин → 8 ч (демо и наше) × источники; HIL у лаборатории (§8).
9. (d) — только если останется время.
