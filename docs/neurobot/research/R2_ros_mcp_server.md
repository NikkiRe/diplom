# R2. ros_mcp_server лаборатории NeuroChip: разбор, дефекты, оценка, решение

Дата: 14.10.2026. Объект: `third_party/neurochip/ros_mcp_server/ros_mcp_server-master/`
(`ros_mcp_server.py` 704 строки, `readme.md` 1 735, `config_parameters.md` 159). Всё читалось как есть, ничего
не менялось. Код лаборатории не импортировался и не запускался. Числа получены так:
(а) реплика **интерфейса** (те же имена, подписи, docstring) на FastMCP из mcp 1.30.0 — для каталога и ответов;
(б) своя реализация **логики** `publish`/`robot_nudge`/`robot_stop` (тот же порядок операций и паузы) против
локального счётчика WebSocket-кадров на 127.0.0.1 — для хронометража;
(в) оракул `simulate()` из `scripts/sim/rosmcp_analyze.py` — тот же, что в таблице `robotmcp/README.md`.
Все цифры сняты на Mac под нагрузкой (load ≈ 4), без rosbridge и робота. Это **ориентиры, а не результаты.**
Скрипты лежат в scratchpad сессии (§10).

## 0. Главное

1. Сервер задуман как **безопасный шлюз**: шесть фиксированных инструментов, белый список тем в JSON,
   ограничение скорости и длительности, автостоп. Каталог маленький: **127 токенов** на 3 инструмента по
   умолчанию и 221 на все 6 [замер]. Это меньше, чем у нашего robot-mcp (274) и у ros-mcp-server 3.1.2 (2 221).
2. **Камера и лидар не работают никогда.** Оба инструмента вызывают `ros.read_one_message`, а такого метода
   в `ROSBridgeClient` нет. Кроме того, без секции `frame_capture` в конфиге камера падает с `KeyError` [код].
3. **Движение — только «толчок»: не дольше 0,5 с и не быстрее 0,08 м/с.** Каждая публикация открывает новое
   WebSocket-соединение, делает `advertise` и ждёт 50 мс. В замере `robot_nudge(500 мс)` длился **≈1,10 с**:
   10 соединений, 5 «едущих» Twist с шагом ≈111 мс (≈9 Гц, а не 20 Гц) и 0,5 с на автостоп. Путь за вызов —
   **не больше 0,044 м** [замер + оценка].
4. **«Проехать 0,5 м» = 12–16 последовательных вызовов LLM.** Это 13–17 обращений к модели, 15,9–26,2 тыс.
   входных токенов (оракул без накладных PicoClaw) и **≈25–40 с**. Робот едет рывками и проходит в среднем
   1,3–2 см/с [оценка]. Инструмент уровня задачи `drive(0.5)` обошёлся бы в 2 обращения и 415 токенов
   (в 33–38 раз дешевле).
5. **Событий нет.** Ни у сервера (нет подписок и уведомлений), ни у PicoClaw (его MCP-клиент создаётся без
   обработчиков уведомлений; heartbeat не чаще раза в 5 мин) [код]. Поэтому «помахали рукой — поехало» через
   LLM в реальном времени **невозможно в принципе**. Рефлекс «жест → движение» должен работать на плате без
   LLM, а LLM нужна для команд уровня задачи и для отчёта о событиях.
6. **Конфликт с демо:** узел демо сам публикует `/cmd_vel` 10 раз в секунду, в покое — нулевой Twist. Он
   перебивает толчки сервера. Камеру демо открывает напрямую через pyrealsense2, а инструмент камеры ждёт
   темы ROS-обёртки. Одну D435i обычно не могут держать два процесса сразу [код + ист.].
7. **Причины «надо перезагружать» на стороне MCP (гипотезы):** (а) PicoClaw не переподключает упавший
   stdio-сервер: повторное подключение он делает только при `session not found`, а это ошибка HTTP-транспорта
   [код]; (б) история хода быстро разрастается (десятки толчков с ответами по 127 токенов), а
   `max_tool_iterations` по умолчанию 50, то есть «2 м вперёд» в него уже не помещается [код + оценка];
   (в) инструменты камеры и лидара всегда возвращают ошибку; (г) публикация сразу перед `close` может
   теряться в rosbridge [код rosbridge].
8. **Решение: заменять, а не чинить.** Агенту остаётся интерфейс уровня задачи (наш robot-mcp с новым
   профилем «база без Nav2»). Рефлекс «жест → движение» работает на плате, у `/cmd_vel` один писатель (или
   twist_mux), соединение с rosbridge одно и постоянное, события — уведомлениями (EdgeCtx) или пушем в канал
   PicoClaw. У лаборатории стоит взять идеи белого списка в JSON, ограничений на стороне сервера, автостопа,
   «тяжёлое — не в LLM» и имена инструментов (как совместимые псевдонимы).

## 1. Что сервер умеет

**Транспорт и запуск.** FastMCP (`mcp` Python SDK), только stdio (`ros_mcp_server.py:700`). Запуск:
`python3 ros_mcp_server.py --config cfg.json` (`:684–700`). Без `--config` берётся `DEFAULT_CONFIG` (`:22–55`)
без проверки. С файлом конфиг сливается с умолчаниями (`deep_update`) и проверяется `validate_config`
(`:87–114`: есть секции, есть `cmd_vel` и `rosapi_topics`, пределы ≥ 0).

**Инструменты.** Регистрируются по `enabled_tools` (`:662–680`). По умолчанию включены только первые три.

| Инструмент | Аргументы | Что делает (по коду) | Состояние |
|---|---|---|---|
| `robot_get_status` | — | вызов `/rosapi/topics`; ответ: connected, motion_allowed, has_cmd_vel, **весь список тем** (`:242–273`) | работает |
| `robot_stop` | `reason="requested"` | 5 раз нулевой Twist, каждый — отдельным соединением, пауза 50 мс (`:326–340`) | работает, ≈0,5 с |
| `robot_nudge` | `direction` ∈ {forward, backward, turn_left, turn_right}, `duration_ms=300`, `speed=0.05` | ограничение: 50 ≤ ms ≤ 500, линейная ≤ 0,08, угловая ≤ 0,4; цикл публикаций, затем `robot_stop` (`:342–400`) | работает (см. дефекты) |
| `sensor_get_status` | — | есть ли в графе темы с `access == "read"` (`:275–324`) | работает |
| `camera_capture_frame_to_file` | `stream` ∈ {color, depth} | один `sensor_msgs/Image` → `.raw` + `.json` в `/tmp/ros_mcp_frames` (`:419–500`) | **не работает** (D1, D2) |
| `lidar_capture_scan_to_file` | — | один `LaserScan` → JSON + метаданные в `/tmp/ros_mcp_lidar` (`:526–660`) | **не работает** (D1) |

**Предполагаемые ROS-интерфейсы** (readme §5, `config_parameters.md`): `/cmd_vel`
`geometry_msgs/msg/Twist` (write); `/scan` `sensor_msgs/msg/LaserScan` (read, `urg_node`);
`/camera/camera/color/image_raw` и `/camera/camera/depth/image_rect_raw` `sensor_msgs/msg/Image`;
`.../camera_info` (зарезервировано); сервис `/rosapi/topics` (нода rosapi из `rosbridge_websocket_launch.xml`).
Подключение — rosbridge v2, `ws://127.0.0.1:9090`, таймаут 3 с.

**Безопасность** (readme §29): фиксированный набор инструментов, белый список тем с режимом доступа,
ограничения скорости и длительности на стороне сервера, обязательный автостоп, нет «сырых» publish и
call_service (`deny_raw_*` зарезервированы и не используются, readme §17.1). Ограничение длительности на
сервере — правильная идея: агент может попросить 10 с и 1 м/с, но не получит.

**Подключение к PicoClaw** (readme §7.3): `picoclaw mcp add ros_mcp --command python3 --args "…"` с оговоркой
«синтаксис может зависеть от версии». В PicoClaw v0.3.1 синтаксис другой:
`add [flags] <name> <command-or-url> [args...]` или `add <name> -- <command> [args...]`
(`bench/baselines/vendor/src/picoclaw/cmd/picoclaw/internal/mcp/add.go:24`). Флагов `--command`/`--args`
там нет. Разбор аргументов (`parseAddArgs`) сохранит в качестве команды строку `--command` [код]. Рабочий
вариант для v0.3.1: `picoclaw mcp add ros_mcp -- python3 /path/ros_mcp_server.py --config /path/cfg.json`.
Версию PicoClaw в лаборатории мы не знаем (вопрос §8).

**Задуманный поток данных** (readme §26–36): кадр или скан → файл → агент получает `frame_ref`/`scan_ref` →
передаёт его «NeuroChip MCP/SDK» (его в архиве нет) → результат возвращается агенту. Идея «тяжёлое не в LLM»
верная. Но для реального времени цепочка «агент просит кадр → агент передаёт путь второму серверу» — это два
и больше обращений к LLM на кадр.

## 2. Дефекты (с доказательствами)

Серьёзность: critical — функция не работает или робот может уехать; major — ломает работу во времени или
реальное время; minor — неточность.

| id | Дефект | Доказательство | Проявление |
|---|---|---|---|
| D1 | **Несуществующий метод `read_one_message`** | В `ROSBridgeClient` (`:117–193`) есть только `call_service` и `publish`; вызовы — `:442` (камера) и `:539` (лидар) | Камера: `AttributeError` → FastMCP возвращает isError. Лидар: исключение ловится, ответ `{"ok":false,"error":"'ROSBridgeClient' object has no attribute 'read_one_message'"}`. Оба инструмента не работают **никогда** — critical |
| D2 | **`KeyError: 'frame_capture'`** | В `DEFAULT_CONFIG` (`:22–55`) нет секции `frame_capture`, `validate_config` (`:87–114`) её не требует, `:423` читает `cfg["frame_capture"]["enabled"]` без `.get`. Лидар (`:528`) читает через `.get` — несогласованно. `frame_capture.overwrite_existing` описан, но не реализован | Инструмент включили, а секцию забыли → исключение вместо понятного отказа — major (маскируется D1) |
| D3 | **Новое WebSocket-соединение + `advertise` + `sleep(0.05)` на КАЖДУЮ публикацию** | `publish()` `:161–193` (`create_connection`, `advertise`, `time.sleep(0.05)`, `publish`, `close`); цикл nudge `:382–384` с ещё одной паузой 50 мс; `robot_stop` `:331–333` | [замер, 10 повторов] `robot_nudge(forward,500,0.08)` идёт 1 089–1 112 мс (медиана 1 101); **10 соединений** (5 движения + 5 стопа); 5 «едущих» Twist с шагом 108–111 мс (≈9 Гц), окно команды движения ≈0,55 с, фаза стопа ≈0,5 с; первая публикация через ≈56 мс. По сети (Wi-Fi) каждое соединение — ещё +2 RTT на TCP и рукопожатие WS [оценка] — major |
| D4 | **Потеря публикаций в rosbridge** | rosbridge кладёт входящие сообщения в очередь отдельного потока `IncomingQueue`, а `on_close` вызывает `incoming_queue.finish()`: «Clear the queue and do not accept further messages» — так в теге 1.1.2 (эпоха Foxy) и в ветке ros2 [ист. 1, 2]. Клиент закрывает соединение сразу после `publish` (`:181–193`). Кроме того, издатель в rosbridge живёт после ухода последнего клиента `unregister_timeout` = 10 с [ист. 3]: после паузы > 10 с создаётся новый DDS-издатель, и `sleep(0.05)` — ничем не гарантированный подбор под время обнаружения подписчиков | [гипотеза; механизм подтверждён исходниками rosbridge, потерю не воспроизводили] Если поток очереди не успел (Jetson загружен YOLO), `publish` выбрасывается: толчок короче или пропадает; может пропасть и нулевой Twist стопа (спасают 5 повторов) — major |
| D5 | **Синхронные блокирующие инструменты в FastMCP** | Все инструменты — `def`, не `async def`. В mcp 1.30.0 синхронная функция вызывается прямо в цикле событий: `func_metadata.py:112–115` (`return fn(**arguments_parsed_dict)`); `time.sleep` и блокирующий `websocket` | Пока идёт `robot_nudge` (≈1,1 с) или ожидание `call_service` (до 3 с), сервер не принимает **ничего**, в том числе `robot_stop`. PicoClaw и так исполняет вызовы по очереди (`pkg/agent/pipeline_execute.go:126`). Прервать толчок нельзя — major |
| D6 | **Автостоп не в `finally`** | `:380–390`: если `ros.publish` бросит исключение (rosbridge упал, таймаут соединения 3 с), цикл прервётся, а `robot_stop` не вызовется. Стопа нет и при убийстве процесса (PicoClaw закрыл stdio, OOM) | Последней остаётся ненулевая команда. Поедет ли робот дальше, зависит от сторожевого таймера в прошивке STM32/мосте UART — неизвестно (вопрос §8) — critical для безопасности |
| D7 | **Ответы раздуты** | FastMCP сериализует `dict` в `TextContent` с отступом 2 (`_convert_to_content`, mcp 1.30); `robot_nudge` повторяет весь `applied_twist`; `robot_get_status` отдаёт **весь** список тем (`:264`) | [замер] nudge — 305 Б / **127 токенов** (компактный JSON того же содержания — 79, минимальный `{"ok":true,"dir":"forward","ms":500}` — 13); status — 85 токенов (6 тем) / 163 (14 тем, оценка графа демо) / **833** (100 тем — граф нашего стенда с Nav2). В цикле ReAct каждый ответ остаётся в истории до конца хода, поэтому рост квадратичный — major |
| D8 | **Мелкие шаги движения** | `max_duration_ms=500`, `max_linear_speed=0.08`, `max_angular_speed=0.4` (`:45–51`); `speed` по умолчанию 0,05 — один параметр и для м/с, и для рад/с (`:342–378`) | За вызов ≤ 0,08 × 0,55 ≈ **0,044 м**; поворот ≤ 0,4 × 0,55 ≈ 0,22 рад ≈ 12,6°, а со скоростью по умолчанию — 0,05 рад/с ≈ 1,6° за вызов. 0,5 м — 12+ вызовов, 90° — 7+, 180° — 15+ (каждый с кругом LLM). «2 м вперёд» ≈ 46+ толчков — на пределе `max_tool_iterations` = 50 у PicoClaw (`pkg/config/defaults.go:33`, ответ при исчерпании — `agent.go:123`). | D17 | Логи rosbridge на каждое соединение | rosbridge пишет «Client connected/disconnected» на каждое подключение и обновляет `/connected_clients` (`websocket_handler.py`, `on_close` [ист. 2]); у сервера 10 подключений на толчок | Шум в `/rosout`, лишняя нагрузка на CPU Jetson [оценка] — minor |

Что в сервере сделано хорошо (взять): белый список тем с режимом доступа в JSON; ограничения скорости и
длительности на сервере, а не в промпте; автостоп как обязательная политика; маленький каталог (127 токенов);
идея «тяжёлые данные — ссылкой, не в LLM»; понятные короткие ошибки (`motion is disabled by config`).

## 3. «После пары использований надо перезагружать» — что может давать MCP-сторона

Гипотезы, по убыванию правдоподобия. Проверять на роботе, по журналам PicoClaw и `ps`/`dmesg`.

1. **Упавший stdio-сервер не поднимается.** PicoClaw v0.3.1 переподключает MCP-сервер, только если ошибка —
   `session not found` (`shouldReconnectCallError`, `pkg/mcp/manager.go:541–557, 598–606`). Эту ошибку
   выдаёт только streamable HTTP (go-sdk: `mcp/transport.go:45`, `streamable.go:2605`; смотрели v1.8.0, у
   PicoClaw — v1.6.1, `go.mod:32`). Если Python-сервер умер (OOM рядом с PyTorch/CUDA на 4 ГБ, падение
   интерпретатора, Ctrl+C в чужом терминале), все инструменты робота до перезапуска PicoClaw отвечают
   «MCP tool execution failed: … connection closed». **Пользователь видит: «надо перезагрузить».**
   [код, уверенность средняя]
2. **Разрастание истории.** Один «0,5 м вперёд» — 13–17 обращений и 16–26 тыс. входных токенов только на
   оракуле (§4), у PicoClaw плюс системный промпт на каждое обращение. Несколько команд — и сессия уходит в

## 4. Оценка: «поехать вперёд на 0,5 м» через PicoClaw + этот сервер

**Модель шага.** Окно команды движения за `robot_nudge(500 мс, 0,08)` — 0,55 с [замер], путь не больше
0,08 × 0,55 = 0,044 м (без учёта разгона L298N, поэтому реально меньше). Значит, нужно N = ⌈0,5/0,044⌉ =
**12** толчков; с потерями на разгон и торможение — около **16** [оценка]. Без одометрии модель не знает,
сколько проехала: N — её догадка.

**Токены и ₽ (оракул `simulate()`: обращение к LLM на каждый вызов + финальный ответ, без кэша; системный
промпт стенда ≈100 токенов, БЕЗ накладных расходов PicoClaw)** [замер токенов o200k, оценка задачи]:

| Вариант | Обращений к LLM | Входных токенов | Выходных | ₽ gpt-4.1-mini | ₽ gpt-4o-mini | Время инструментов |
|---|---|---|---|---|---|---|
| ReAct, 12 толчков, каталог 3 | 13 | 15 938 | 278 | 0,75 | 0,28 | 13,2 с |
| ReAct, 12, каталог 6 | 13 | 17 160 | 278 | 0,81 | — | 13,2 с |
| `robot_get_status` + 12 | 14 | 18 563 | 286 | 0,87 | — | 13,3 с |
| ReAct, 16 толчков | 17 | 26 248 | 366 | 1,22 | 0,46 | 17,6 с |
| Все 12 вызовов в одном ответе модели | 2 | 2 408 | 278 | 0,16 | — | 13,2 с (PicoClaw исполняет по очереди) |
| **Предлагаемый `drive(distance_m=0.5)`** (синхронный) | **2** | **415** | 26 | **0,023** | 0,009 | ≈6,3 с движения при 0,08 м/с |
| robot-mcp `go_to(place)` (для сравнения, README) | 3 | 1 325 | — | 0,064 | — | асинхронно |

₽ — по замороженному прайсу стенда (`bench/costmodel`, RouterAI 06.10: gpt-4.1-mini 44,16 / 176,66 ₽ за 1 млн
входных/выходных, gpt-4o-mini 16,56 / 66,25).

**Накладные PicoClaw** [оценка]: в нашем смоуке (сенсорный день) PicoClaw тратил 4,5–6,9 тыс. входных токенов
на обращение (shipped 381 331/84, best-simonly 623 721/91; `bench/baselines/smoke/20261007/table.md`). На 13
обращений это ещё +59–89 тыс. токенов: **+2,6–3,9 ₽ (4.1-mini) или +1,0–1,5 ₽ (4o-mini) на 0,5 м** без кэша,
0,65–1,0 ₽ при кэше префикса по цене 4.1-mini. 100 таких команд за демо-день — сотни рублей.

**Задержка** [оценка]: шаг LLM ≈ TTFT + генерация ≈30 токенов вызова. TTFT по Artificial Analysis (медиана за
72 ч, вход 10 тыс. токенов): gpt-4.1-mini 0,68 с (OpenAI), gpt-4o-mini 0,82 с; скорость 120–154 ток/с
[ист. 7, 8]. Итого ≈0,9–1,0 с напрямую. Через RouterAI из России задержки не опубликованы (в проверенных
источниках не найдено), закладываем 1–2 с. У рассуждающих моделей шаг дольше: GPT-5 mini (high) ≈49 с до
первого токена ответа [ист. 9]. Отсюда:
- ReAct, 12 толчков: 13 × (0,9…2) + 12 × 1,10 ≈ **25–39 с**; из них робот едет ≈6,6 с короткими рывками по
  0,55 с. Средняя скорость 1,3–2 см/с. Аварийный «стоп» придёт только после текущего толчка (D5), и сам он —
  ещё один круг LLM;
- пакетный вариант: 2 × (0,9…2) + 13,2 ≈ 15–17 с, тоже рывками; число толчков модель угадывает;
- `drive(0.5)`: 2 × (0,9…2) + 6,3 ≈ 8–10 с, непрерывно (при пределе 0,2 м/с — ≈5–6 с);
- реакция на жест без LLM (как в демо): распознавание + ≤0,1 с до первой команды (таймер 10 Гц).

**Жест через PicoClaw.** PicoClaw о жесте сам не узнает: уведомлений MCP его клиент не принимает
(`mcp.NewClient(..., nil)`, `pkg/mcp/manager.go:337–340`), heartbeat — не чаще раза в 5 мин. Нужен пуш в канал
(MQTT, как в нашем стенде аналогов) → 1 обращение (≈1–2 с) → вызовы инструментов. При нынешних толчках это
снова 12+ кругов. Реальное время по-прежнему недостижимо.

## 6. Решение: заменять, а не чинить

**Почему не чинить.** D1–D10 исправимы (§7), но главная беда — в архитектуре: LLM стоит внутри цикла
управления движением, шаг — 0,044 м. Даже идеальный транспорт оставит 12+ кругов LLM на 0,5 м. А событий
PicoClaw не принимает, так что «реакция на жест» через него медленная при любом сервере.

**Чем заменять (предложение):**
1. **Рефлекс на плате, без LLM:** распознанный жест → задача движения (как `DriveController` демо, но через
   исполнителя задач). Задержка — распознавание + ≤0,1 с. LLM узнаёт о произошедшем постфактум.
2. **Один писатель `/cmd_vel`.** Его держит исполнитель задач в robot-mcp: публикация 10–20 Гц по одному
   постоянному соединению, остановка по лидару в секторе (порог из конфига; у демо в коде 0,25 м, в README
   0,35 м), стоп в `finally`, при обрыве и при SIGTERM. Если демо остаётся писателем — **twist_mux**
   (есть для Foxy 4.0.1, Humble, Jazzy) с приоритетами: безопасность > рефлекс > агент [ист. 10].
3. **robot-mcp, профиль «база без Nav2».** Инструменты уровня задачи `drive`, `turn`, `stop`, `status` и
   совместимые псевдонимы `robot_stop`, `robot_nudge`, `robot_get_status` для промптов PicoClaw, которые уже
   есть в лаборатории. Задачи асинхронные, итог — `task_end`. Ответы — короткий канонический JSON (13–50
   токенов). `status` без списка тем. Белый список и пределы — в YAML/JSON (идея лаборатории).
4. **Жест — событием.** Демо (или наш конвейер) публикует класс жеста в ROS-тему (например
   `/gesture` std_msgs/String). robot-mcp подписан и шлёт `alert/gesture` в `resources/updated` (EdgeCtx). Для
   PicoClaw — пуш в MQTT-канал, как в `bench/baselines` (уведомлений MCP PicoClaw не принимает).
5. **Камера: кадры не в LLM.** Детектор работает на плате (YOLO + SNN демо или cam-mcp), агенту уходит сводка;
   кадр — только по запросу, JPEG ≈4,5 КБ через CBOR. Камеру держит один процесс, остальные берут кадры из
   него (тема ROS или cam-mcp).
6. **Для ВКР:** это прямо гипотезы H1/H5/H6 (событийный фильтр против опроса, сводки вместо кадров и тем). На
   стенде `sim` можно поставить базу без Nav2 (TurtleBot3, публикация `/cmd_vel` Twist, `/scan`) и класс жеста
   по сценарию. Тогда честное сравнение: «PicoClaw + сервер лаборатории» против «EdgeCtx + robot-mcp
   (профиль база)» против «PicoClaw + robot-mcp (база) + MQTT-пуш». Метрики: обращения к LLM, токены, ₽,
   задержка жест→движение и команда→движение, трафик, RAM/CPU за 8 ч.

## 7. Если лаборатории нужно срочно и на своём коде (минимальный список правок)

1. Выключить `camera_capture_frame_to_file` и `lidar_capture_scan_to_file` в `enabled_tools`, пока нет
   `read_one_message`. Добавить `frame_capture` в `DEFAULT_CONFIG` и в `validate_config`.
2. Одно постоянное соединение с rosbridge в фоновом потоке: `advertise` один раз, переподключение с паузой,
   повторный `advertise` после переподключения, флаг `online`. `publish` — без `close` после каждого
   сообщения (снимается D4, кроме первого издателя).
3. Движение — в фоновом потоке-исполнителе с частотой 10–20 Гц. Инструменты — `async def` (или
   `anyio.to_thread.run_sync`), чтобы `robot_stop` проходил во время движения. Автостоп — в `try/finally` и
   на выходе процесса (`atexit`, SIGTERM).
4. Добавить `robot_drive(distance_m)` и `robot_turn(angle_deg)`: цикл внутри сервера (по времени или по
   `/odom`), проверка `/scan` в секторе движения. Пределы скорости и пути — в конфиг. `speed` для линейного и
   углового движения — разные параметры.
5. Ответы — компактная строка JSON: если вернуть `str`, FastMCP не добавит отступы. `robot_get_status` —
   без списка тем, только `topic_count`, `has_cmd_vel` и `missing`.
6. Отключить публикацию `/cmd_vel` демо, пока работает агент, или поставить twist_mux.
7. Запускать на Python 3.10+ (uv venv рядом с системным 3.8) и закрепить версии `mcp` и `websocket-client`.
8. В PicoClaw подключать через `-- python3 …` (§1), а лучше — по streamable HTTP: тогда при потере сессии
   PicoClaw переподключится сам (`session not found` → `reconnectServer`). Сервер — под systemd с
   `Restart=always`.

Это уберёт перезапуски и рывки, но не задержку цикла через LLM (§4).
